Workshop rundown · Mastra evals

Evals, demonstrated in the browser

A cue-by-cue run of Mastra Studio that walks the whole eval loop — write a scorer, catch a regression, and turn real traffic back into a test — without leaving the UI.

One URL localhost:4111 Runtime ~24 min, 8 cues Needs OPENAI_API_KEY for cue 6

Before the room fillsPre-flight

Four commands. Run them once the night before and once again an hour before, so a cold pnpm install is never the thing standing between you and cue 1.

cd examples/evals-workshop
pnpm install
pnpm reset      # wipes the DBs and re-seeds — safe to repeat
pnpm dev        # API + Studio, both on :4111
Rehearse with reset pnpm seed is not idempotent — running it twice gives you two datasets named nimbus-support-qa and a confusing demo. pnpm reset deletes both databases first, so you can rehearse as many times as you like and always land on the same three experiments. Stop the dev server before resetting.

Confirm you're green

Open localhost:4111/evaluation. You want 4 scorers · 1 dataset · 3 experiments. If experiments show as hex IDs instead of baseline / regression / fix, you're on a stale database — reset.

Set the window up The evaluation tables are wide. Collapse the Studio sidebar with the toggle at the top-left before you start, and go as wide as the projector allows — the Compare button in cue 5 sits at the far right of the toolbar and is the one thing that hides on a narrow window.

Part one · the runEight cues

Each cue is one click path, one thing on screen, and one line worth saying out loud. The order builds: nothing in a later cue depends on you having explained something you skipped.

CUE 1

The dashboard, cold

Evaluation → Overview

≈ 2 min

Four tiles — 4 scorers, 1 dataset, 3 experiments, an average score — then a scores-over-time chart with three series.

This is what it looks like when a team has evals. Not a number in a spreadsheet — a dataset, a history of runs against it, and a trend.

Don't linger. This is the establishing shot; everything after it explains one tile.

CUE 2

What a scorer is

Evaluation → Scorers

≈ 2 min

Four rows, each tagged CODE: Answer Relevancy, Toxicity, Answer Accuracy, Support Rubric.

A scorer takes an input and an output and returns a number between 0 and 1. Two of these are deterministic code. Two ask a language model to grade. That split decides your whole strategy.

The number to have ready: in the terminal exercises, four items through three code scorers takes 124 ms; the same four through two LLM judges takes 82 seconds. Roughly 660×. Code scorers gate merges; judges watch quality.

CUE 3

What it grades against

Evaluation → Datasets →
nimbus-support-qa → Items

≈ 2 min

Four items: a question and the fact a good answer must contain — 15 GB, 30 days, 14 days, not SMS. Header reads Latest version v1.

A dataset is questions with known-good answers. It is versioned, and that matters more than it sounds — hold that thought.

Point at the fourth row, "Can I use my phone number for login codes?". That one is designed to fail. A dataset where everything passes teaches nothing.

CUE 4

A run is an experiment

… → Experiments tab
click baseline
then Summary / Results

≈ 3 min

Three named runs — baseline, regression, fix. Inside baseline: Summary shows answer-accuracy 0.875 over 4 items; Results shows each row — 1.00 · 1.00 · 0.50 · 1.00.

Every time you run the dataset you get an experiment: a permanent, comparable record. The 0.5 is the agent honestly saying it doesn't know — half credit, because a refusal is much better than a confident wrong answer.

That 0.5 is worth dwelling on. It's a design decision in the scorer, not a technicality, and it's the moment people realise scorers encode judgement.

CUE 5

The regression

Experiments tab → Compare
tick baseline first
tick regression second
→ Compare Experiments

≈ 4 min · the centrepiece

Side-by-side headers, both stamped v1. One scorer row: 0.875 → 0.375, delta −0.50 ↓. Below it, per-item: two rows unchanged, two rows 1.00 → 0.00.

Nobody set out to break this agent. Somebody made it hedge more — it sounded more careful — and the hedging swallowed the exact numbers the scorer was looking for. Without this view you ship that.

Order matters when you tick. First selected becomes the baseline, second becomes the contender. Tick them the other way round and the delta shows as an improvement.

Two things to draw out. First, both sides say v1 — the comparison is only meaningful because the data didn't move. Second, the average slipping 0.5 could have been every row sagging a little; the per-item rows show it was two rows falling off a cliff. Those call for completely different responses.

CUE 6

Scoring live traffic

Agents → Nimbus Support Agent
ask: How long do I have
to request a refund?
wait ~10s
→ Evaluation → Overview

≈ 4 min

The agent answers correctly. Ten seconds later the Overview chart has a new point — answer-relevancy and toxicity scored that reply as it arrived.

These evals aren't only for a fixed test set. Every real reply gets graded on the way out, at whatever sampling rate you can afford.

Then ask the obvious question before they do: why only those two scorers? Because a live request has no ground truth — nobody labelled the answer a user just received. answer-accuracy compares against a known fact, so on live traffic it would score zero on every single request and paint a perfectly healthy agent as totally broken. Only reference-free scorers belong here.

If nothing appears Live scores hang off trace spans. No Observability config means no spans, means no scores — and nothing errors. If the chart stays flat, that's the cause, not the scorer.

CUE 7

Where datasets come from

Observability → Traces
click any agent run row
→ Save as Dataset Item
(read it, then Cancel)

≈ 6 min · the payoff

A trace panel with three buttons — Evaluate Trace, Save as Dataset Item, Add tool mocks to item — over the full span tree.

Every eval talk skips the hardest question: where do the test cases come from? Here's the answer. This is a real request somebody made, and it becomes a test case in one click.

Open Save as Dataset Item and read the pre-filled fields out loud — this is the moment that lands:

  • Input — the real question the user asked
  • Ground Truth — the agent's actual answer, for you to correct into what it should have said
  • Expected Trajectory — the recorded sequence of steps
  • Tool Mocks — the real tool calls with their real responses

Cancel out — saving bumps the dataset to v2 and disturbs cue 5 if you loop back.

Then the other two buttons, briefly. Add tool mocks to item turns this trace into a deterministic fixture: the agent replays against recorded tool responses, so a database row changing tomorrow can't break the test. Evaluate Trace opens a Scoring tab where you pick a scorer and hit Start Scoring — grading traffic that already happened.

You can write a scorer today and find out how the agent has been doing on it since March. Nothing gets re-run. The trace already holds the input and the output.

CUE 8

Humans in the loop

in the span panel:
Feedback tab

≈ 1 min

Tabs reading Details · Scoring · Feedback.

Machine scores and human judgement live side by side on the same span. A thumbs-down from a real user is an eval signal too.

Close on the loop: traffic became a dataset, the dataset caught a regression, and the fix went back out to traffic. That's the whole argument.

Part threeThe functionality map

Everything the workshop covers, in the order it makes sense to teach it — each layer only needs the one above. Use this to plan; use the cues to perform.

01

A scorer is a four-step pipeline

preprocess → analyze → generateScore → generateReason. Each step is either a plain function or an LLM prompt, and you can mix them in one scorer. The reason string is what makes a score arguable instead of oracular.

cue 2 · pnpm ex:1

02

Two families, one strategic split

8 code scorers (deterministic, free, milliseconds) and 15 LLM judges (non-deterministic, costs money, seconds) ship built in. Code gates merges; judges track quality on sampled traffic. Measured here at ~660× apart.

cue 2 · pnpm ex:2

03

Failing a build: gates vs thresholds

Only gates produce verdict: 'failed'. A missed threshold yields 'scored' — so CI written as if (verdict === 'failed') merges straight through a quality regression. The most expensive gotcha in the set.

pnpm ex:3

04

Datasets and experiments

A dataset is a versioned, named set of items. Running it produces an experiment — a durable record you can compare against later. This is the hinge between "I scored something once" and "we have evals".

cues 3–4 · pnpm ex:6

05

Comparison, and the real CI gate

compareExperiments returns per-scorer deltas, per-item diffs, and one hasRegression boolean. Thresholds carry a direction, because plenty of things you score are costs — latency, tokens, tool calls — where up is bad.

cue 5 · pnpm ex:8

06

Versioning, and the score that lies

Items are stored SCD-2, so any past version reads back exactly. This matters because a dataset edit and a model improvement look identical in a score — both make the number go up. Pinning a run to an old version is how you tell them apart.

cue 3 · pnpm ex:9

07

Determinism: tool mocks and record/replay

Per-item mocks pin what a tool returns; unmockedToolPolicy: 'deny' makes "our evals are hermetic" checkable rather than hoped-for. collectToolMocks reads a real trace and writes the mocks for you — incident to regression test in one step.

cue 7 · pnpm ex:10

08

Production: live scoring and scoring history

Scorers attach to an agent with a sampling rate and grade real replies as they happen. Separately, scoreTraces grades traffic that already happened. Both require reference-free scorers — no ground truth exists out there.

cues 6–7 · pnpm ex:11

09

Closing the loop

Promote a trace to a dataset item and the cycle completes: production traffic becomes the test set, the test set catches the regression, the fix ships. Everything above is machinery in service of this one circuit.

cue 7

Also in the repo but not on the critical path: multi-turn evaluation (inputs vs turns), workflow targets (overall / per-step / trajectory), and evaluating an agent that has memory — exercises 4, 5 and 7.

AppendixQuestions you will get

"Why is the dashboard empty?"

Almost always one of three silent failures, in order of likelihood: no Observability config (so no spans, so no live scores); scorers not registered on the Mastra instance (scores print in the terminal but never persist); or LibSQL serving the observability domain, which accepts writes and stores no spans. The workshop splits storage — LibSQL for everything, DuckDB for observability alone — precisely because of the third.

"Can I write the judge in the UI?"

Not in this version, and it's worth being straight about it. The backend is complete — you can create a stored LLM judge over HTTP and it gets versioned — but new definitions land as draft, the list only returns published, and nothing in the shipped API or UI moves one to the other. So a judge you create is invisible. Judge-prompt design is better demoed with support-rubric in the repo, which carries a deliberate bug: it scores 0.667 on a completely correct answer because it marks true extra detail as invented. A design bug, not a model failure.

"What about A/B testing two prompts?"

The grouping fields — variantId, trialIndex, experimentSetId — exist in the Mastra source but aren't in the published @mastra/core@1.57.0 this workshop pins. Same for experiment lifecycle hooks. Fair to mention as coming; don't promise a demo.

"Does this work in CI?"

Yes, and that's the point of the headless half. Ten of the eleven exercises run without an API key on a deterministic mock model, so the numbers are byte-identical on every machine. mastra experiment build bundles a standalone experiment worker if you want it as its own CI job.

"Why is the seeded history on a fake model?"

Deliberate. pnpm seed skips .env so the baseline→regression→fix story is 0.875 / 0.375 / 0.875 on every machine in the room, while the dev server does load it so live chat in cue 6 uses a real model. Reproducible history, real traffic, one dashboard.
