# Chat behavior baseline

Before replacing a Studio or Factory renderer, reproduce the affected scenario below. A person reopening a conversation must still see the saved answer, understand work in progress, and be able to answer a pending prompt.

This is step 1 of the chat UI unification: examples and preservation criteria. It changes no application rendering, session ownership, persistence, subscriptions, or message reconstruction. The stories use the existing Playground UI renderers; they do not represent Factory's local components or a complete production conversation.

## Review the states

Run `pnpm --filter ./packages/playground-ui storybook` from the repository root. Open the following groups in Storybook:

| Group                         | States to inspect                                                                                          |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Chat / Message Text**       | Reloaded Markdown, incomplete streaming Markdown, error, warning, blocked response with expandable details |
| **Chat / Reasoning**          | Reloaded, collapsed, waiting for text, partial streaming text, provider-redacted, empty completed          |
| **Chat / Attachments**        | Image, text preview, Unicode and literal tags, long filename, remote PDF, provider-only URI, inline binary |
| **Chat / Tool Approvals**     | Pending, stream/generate/network callback dispatch, running, approved, declined, already executed          |
| **Chat / Signals**            | State, reactive, notification                                                                              |
| **Chat / System Reminders**   | Collapsed and expanded reminder contents                                                                   |
| **AI / Tool Call** (existing) | Running, completed, failed, controlled disclosure                                                          |

`Collapsed`, `Text Preview Open`, `Blocked With Details`, approval dispatch/disabled states, and system reminder `Expanded` include executable Storybook interactions. These cover presentation and callback selection. They do not exercise an API or prove that a mutation retries correctly. Streaming stories are fixed snapshots; the consumer suites below cover reveal timing and ordering.

## Differences that need a decision before replacement

These are observed differences, not evidence that the divergence was intentional. Keep each application's current result until the corresponding migration explicitly chooses its replacement.

| Surface         | Studio today                                                    | Factory today                                                                     | Decision for the migration                                                                              |
| --------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Reasoning       | Collapsible plain text, streaming placeholder, redaction notice | Inline italic Markdown in `MessageBubble`                                         | Choose disclosure and Markdown behavior before adopting one renderer.                                   |
| Attachments     | Dialogs for images/text, PDF links, unsupported-file chips      | Inline images; other file parts rendered as serialized data                       | Choose preview behavior and normalize Factory image data at its adapter. Test raw base64 and data URLs. |
| Approvals       | Context-owned controls for stream, generate, and network modes  | `ApprovalCard` shows tool arguments, focuses Approve, submits tool and prompt IDs | Keep mutation ownership local; choose argument layout and focus behavior before extracting the view.    |
| Signals         | Shared badges, reminders, notification notices                  | Local signal rows and notification cards with app-specific suppression            | Preserve filtering and visible content before selecting common presentation.                            |
| Message actions | Studio copy, speech, and model controls                         | Factory sender identity and whole-turn copy metadata                              | Keep these app-owned slots until the message envelope migration.                                        |

The [Studio message row](../../../../playground/src/lib/ai-ui/messages/message-row.tsx) and [Factory message bubble](../../../../../mastracode/factory-ui/src/ui/domains/chat/components/MessageBubble.tsx) own these integrations. Agent Builder's [chat primitives](../../../../playground/src/domains/agent-builder/components/chat-primitives) are a third consumer to include when the composer/envelope work begins.

## Gates for each later migration

- Add a failing consumer test for the behavior being changed, then adopt the shared component and remove the replaced renderer in the same change.
- For approvals and suspensions, use the real client and React Query against MSW to verify the payload, one request for a rapid double click, and retry after a failed request. The callback-only stories here do not cover those guarantees.
- For Factory attachments, add consumer coverage before replacement; the shared renderer tests do not cover Factory's current raw-base64 conversion.
- Inspect the affected story at mobile, tablet, and desktop widths. Check long text, disclosure, dialog dismissal, and keyboard focus return.
- Verify the consuming application for scroll anchoring, focus, and streaming transitions. Isolated stories do not establish those behaviors.

Complete conversations, Factory-local presentation stories, and Agent Builder integration remain later steps. The existing `ChatShell` stories use sample content and cannot substitute for that validation.
