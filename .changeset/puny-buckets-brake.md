Fixed durable thread streams replaying a queued or steered user message as still "sending" after a reconnect. On retaining transports such as Redis Streams and Valkey Streams, the pending announcement now leaves the thread stream when the run it waited on ends: right away for a successful run of an agent with memory, and 30 seconds later for a run without memory or one that fails, is canceled, or aborts. Later `subscribeToThread()` calls no longer show it. A message whose run died before delivering it can still replay as pending. Refs #30792.

Also fixed a forwarded user message running twice on multi-process deployments. When the run it was forwarded to finished and released its thread lease while the forwarding process was still behind on the thread stream, lease recovery could queue the message again even though it had already run. The forwarding process now reads the thread back to its own marker before it requeues, so on brokers that deliver a topic's messages in order, such as Redis Streams, a message whose admission the owner published before that marker runs once. Narrow windows remain where the message can still run twice: a run that regains the lease, admits the message, and releases the lease again between two of the forwarder's lease checks; and an admission publish that is still being retried when its run releases the lease and then fails. A forwarder on an older version keeps the previous behavior until it upgrades.
