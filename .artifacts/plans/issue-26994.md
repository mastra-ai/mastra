# Plan: issue #26994 — durable agents drop a declined subagent tool approval

## Goal

When a durable (`EventedAgent` / `createDurableAgent`) supervisor declines a tool approval raised by a subagent (delegated through an `agent-<name>` or `workflow-<name>` tool), the decline is passed down to the suspended inner run, the same way approval already is and the same way the non-durable `Agent` handles it. The inner tool never runs, the subagent gets `{ approved: false, reason }` and finishes its own run, and the supervisor's delegation tool call ends with the subagent's real result. It must not end as a local `output-denied` on the supervisor's `agent-*` call. A decline at the supervisor's **own** pre-execution gate (before the subagent starts) still short-circuits locally as `output-denied` with the reason. Done = new regression tests for those cases pass (and fail on current `main`), and existing durable approval tests still pass.

## Root cause (checked against origin/main 0ee20403)

`packages/core/src/agent/durable/workflows/steps/tool-call.ts`:
- `approvalGated` (~L952) is true for both a pre-execution gate and a delegated approval, because both suspend with `type: 'approval'`.
- In the `if (approvalGated && approvalDecision)` block (~L1058), `if (!approvalDecision.approved)` (~L1072) returns `output-denied` right away.
- Delegated identity (`resolveFrameworkSuspendedToolIdentity`, ~L1160–1175) and `isDelegatedApprovalResume` (~L1188, currently `!!approvalGrant && !!suspendedToolRunId`) are computed **after** that return, and only for approve (`approvalGrant`). So a decline never reaches the wrapper tool's `resumeData`.
- Non-durable parity: `packages/core/src/loop/workflows/agentic-execution/tool-call-step.ts` computes `isDelegatedApproval` from the suspend payload's `requireToolApproval` marker **before** gating and excludes it from `approvalGated` (~L520–541). Both decisions therefore reach the agent tool.

## Scope

In:
- Move delegated-identity resolution ahead of the decline short-circuit in the durable tool-call step, and widen `isDelegatedApprovalResume` to both decisions.
- Pass the raw workflow decision (`{ approved, reason }`) to the wrapper tool for delegated resumes.
- Regression tests and a `@mastra/core` patch changeset.

Out:
- Changes to the non-durable loop, the agent-tool wrapper (it already forwards `resumeData` to `resumeStream`), docs (they already describe this behavior), and PR #26686's requestContext work in the same file.

1. Move the block that computes `isResumableTool`, `needsRunIdLookup`, `hasModelResumeData`, `resolvedSuspensionIdentity` and `suspendedToolRunId` (currently ~L1151–1175) to **just before** `if (approvalGated && approvalDecision)` (~L1058).    const isDelegatedApprovalResume =
     approvalGated && !!approvalDecision &&
     !!(delegatedMarker?.requireToolApproval || delegatedMarker?.suspendedToolRunId) &&
     resolvedSuspensionIdentity?.type === 'approval' &&
     resolvedSuspensionIdentity.toolCallId === toolCallId;

The executor must confirm that a local pre-execution gate makes this **false**: no historical delegation may bypass it.

5. Check that `approvalGrant` is not attached to a delegated **decline** (it already requires `approved === true`). Also check that a delegated decline does not emit a local `tool-output-denied` chunk for the outer call.

## Risks

- **A local gate wrongly treated as delegated**: the resolver's message-history fallback may find an older delegation for the same tool. Mitigation: require the per-call suspend payload marker and a `toolCallId` match. Phase 2's pre-execution-gate test catches this.
- **Model-supplied ids overriding the framework decision**: covered by `hasModelResumeData` excluding approval decisions. Existing PR #24121 tests (malformed `suspendedToolRunId`) must still pass.
- **Merge conflict with PR #26686** (same file, requestContext on approved resume): keep the edit small, and rebase if #26686 lands first.
- **Parallel delegations**: `parallel-delegation-approval-durable.test.ts` must stay green. Each tool call has its own resumeLabel/suspend payload.

## Assumptions

- The approach mirrors the non-durable step (forward delegated decisions, deny only local gates) and reuses the existing durable approve-path machinery. I rejected adding decline handling inside the agent-tool wrapper: the decision never reaches the wrapper today, so the step is the right layer.
- The delegated-approval marker is the per-call suspend payload (`requireToolApproval` / `suspendedToolRunId`), plus a framework-resolved identity of type `approval` for the same `toolCallId`. This is stricter than the current approve-path check (`suspendedToolRunId` present) and is a deliberate hardening.
- The wrapper receives the raw `workflowResumeData` for delegated resumes, so the decline reason reaches the subagent unchanged.
- Cherry-picking ff34380 with attribution is acceptable if it applies cleanly and passes review. Its test claims are self-reported and must be re-run. Implementing it by hand is equally acceptable.
