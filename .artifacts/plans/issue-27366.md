# Plan: recover a crashed plain-Agent resume claim (#27366)

## Goal
Today, if a plain `Agent` resume (`resumeGenerate`, `resumeStream`, `approveToolCall*` or `declineToolCall*`) dies after `claim.start()`, the agentic-loop row stays `running` forever. Every later resume then throws `AGENT_RESUME_ALREADY_CLAIMED`.

After this fix, a later resume takes the run over once nobody holds a **live, renewed lease** on the claim. A live claimant keeps renewing its lease, so it is never taken over. The #26133 guarantee is unchanged: while the claimant is alive, concurrent resumes still execute the tool at most once. After a crash the guarantee is at-least-once, meaning the in-flight tool may run again. The maintainer accepted this, and it is documented.

Rows left `running` by older versions have no lease record. They are treated as having an expired lease and can be taken over in the same way (maintainer decision).

The fix is done when:
- new regression tests in `packages/core/src/agent/__tests__/concurrent-resume-claim.test.ts` show that a crash after `start()` with an expired lease is resumed exactly once;
- a pre-fix `running` row with no lease is resumed exactly once;
- a `running` claim with a live lease is still rejected;
- two concurrent takeovers produce exactly one winner;
- all existing tests in that file pass;
- `npx tsc --noEmit -p packages/core` is clean.

## Maintainer decisions (Oct 17, 2026)
1. The lease TTL comes from the environment through the shared run-ownership module planned by #27364, `packages/core/src/agent/run-ownership.ts`. The TTL is `MASTRA_AGENT_THREAD_LEASE_TTL_MS` and the owner token is `<sourceId>/<runId>`. Do **not** use the `ExecutionFence` constants. Do not add a new constant or env var.
2. Re-running the tool at least once after a crash is acceptable. Document it in the docs and the changeset.
3. Rows left `running` by pre-fix versions get a recovery path. A `running` claim with no live lease is treated as expired and taken over through the generation-pinned force claim.

## Scope
**In scope:**
- A lease for `running` claims in `#claimSuspendedAgenticLoopRun` (`packages/core/src/agent/agent.ts`, about lines 7980-8110). The lease is stored through the storage run-ownership API (`claimRunOwnership`, `renewRunOwnership`, `releaseRunOwnership`, `getRunOwnership`). The TTL, renewal interval and owner token come from `agent/run-ownership.ts`.
- Renewing the lease on a timer while the resumed loop runs, and releasing it when the loop ends.
- Taking over a `running` row whose lease has expired or does not exist, including rows left by pre-fix versions.
- Tests, a docs note and a changeset.

**Out of scope:**
- A public "release claim" API.
- Taking over a row only because its `resumeClaimedAt` is old. Takeover always goes through the lease record.
- Claimant identity keyed on workflow run + step.
- DurableAgent and #27365.
- Storage adapter changes. Run ownership already exists in inmemory, pg, libsql, d1, cloudflare DO, convex, dsql and dynamodb.
- `ExecutionFence` itself, which keeps its own constants.

## Background (verified on main 0ee20403)
- **Claim flow.** The claim moves the row `suspended -> pending` and stamps `resumeClaimedAt`. `start()` moves it `pending -> running` (agent.ts ~8093). The existing stale takeover (agent.ts ~8039-8043) only accepts a `pending` row at least `AGENT_RESUME_CLAIM_STALE_MS` (60s) old.
- **Release.** `release()` (agent.ts ~8065) returns early once `onExecutionStarted` has set `started`. The loop calls `claim.release()` in its `finally` (`loop/workflows/stream.ts` ~554), so release runs on every loop exit. The resume methods also call it when they fail (agent.ts ~10684, ~10886). `start()` is called at `stream.ts` ~442, before `run.resumeClaimed(...)`.
- **`run-ownership.ts` is not on main yet.** It is a deliverable of the #27364 plan. Today `MASTRA_AGENT_THREAD_LEASE_TTL_MS` (default 15s) and `MASTRA_AGENT_THREAD_LEASE_RENEW_INTERVAL_MS` (default TTL/3) are read privately in `agent/thread-stream-runtime.ts` ~150-159 through `readPositiveIntEnv` (`../utils`). `leases.md` documents both variables.
- **InMemory `claimRunOwnership`** (`storage/domains/workflows/inmemory.ts` ~228):
  - `expectedGeneration` is compared against `current?.generation ?? 0`, so `expectedGeneration: 0` means "only if no record exists".
  - A live record blocks the claim unless `force` is set.
  - An expired or released record can be claimed without `force`.
  - Each claim bumps `generation`; the first claim is seeded from the clock.
  - Use `force + expectedGeneration` everywhere so behavior does not depend on per-store expiry semantics.
- **`supportsRunFencing(store)`** lives in `agent/durable/execution-fence.ts`. `RunOwnershipRecord` (`storage/run-fencing.ts`) has `generation`, `ownerId`, `leaseExpiresAt` and `live`, with `live` judged on the store clock.

## Phase 1: Lease the running claim
Changes go in `packages/core/src/agent/agent.ts` (`#claimSuspendedAgenticLoopRun` and its doc comment).

1. **Lease key.** Add `export const agentResumeLeaseRunId = (runId: string) => \`agent-resume:${runId}\``. The namespace keeps this lease from colliding with DurableAgent/workflow ownership, the thread lease and memory-fence generations on the same `runId`. Export it for tests only; it does not go in the package index.
   - Owner id: `<owner token from run-ownership.ts for this runId>`, so `<sourceId>/<runId>`.
   - TTL and renewal interval: from `run-ownership.ts`.
2. **Fencing capability.** After the `supportsConcurrentUpdates()` branch, compute `const leased = await supportsRunFencing(workflowsStore)`. If importing it from `./durable/execution-fence` creates a cycle, re-export it from `run-ownership.ts`.
3. **Takeover of a dead `running` claim.** In the `!claimed` branch, keep the existing pending-abandoned logic and add a case for `current?.status === 'running' && current.timestamp === snapshot.timestamp && leased`:
   1. Read `record = await workflowsStore.getRunOwnership({ runId: leaseKey })`.
   2. If `record?.live`, call `throwAlreadyClaimed()`.
   3. Otherwise (the lease expired, was released, or there is no record, as with pre-fix rows), win the takeover atomically:
      ```ts
      claimRunOwnership({
        runId: leaseKey,
        ownerId,
        leaseMs: LEASE_TTL,
        force: true,
        expectedGeneration: record?.generation ?? 0,
      })
      ```
      `expectedGeneration` pins the takeover to the record that was read, so exactly one competitor wins. If the claim is not acquired, call `throwAlreadyClaimed()`.
   4. The winner moves the row with `updateWorkflowState({ status: 'pending', expectedStatus: 'running', resumeClaimedAt: Date.now() })`. If that returns undefined, release the lease and call `throwAlreadyClaimed()`.
   5. Log a `warn`: `Taking over resume claim for run X with no live lease; the suspended tool may run again`. Say whether a lease record existed, since a missing record usually means a pre-fix claimant.
   6. Keep `{ownerId, generation}` in a local `lease` so `start()` reuses it.
4. **`start()`.** If `leased` is true and no lease is held yet, acquire one before the `pending -> running` CAS:
   - Read the record, then claim with `force: true, expectedGeneration: record?.generation ?? 0`. If `record?.live`, do not claim; set `released = true` and call `throwAlreadyClaimed()`. A live lease on a `pending` row means another process's `start()` is in progress.
   - If the claim is not acquired, set `released = true` and call `throwAlreadyClaimed()`.
   - Then do the CAS. If it fails, call `releaseRunOwnership` and throw as today.
   - On success, start the renewal timer: `setInterval(LEASE_RENEW_INTERVAL)` calling `renewRunOwnership({ runId: leaseKey, generation, ownerId, leaseMs: LEASE_TTL })`, with `.unref?.()`.
   - If a renewal returns `renewed: false`, stop the timer and log a warn that the claim was superseded. Do not abort the run.
   - If a renewal throws, log a warn and keep the timer running.
5. **`release()`.** It must stay idempotent. Always stop the renewal timer first. Then, if a lease is held, call `releaseRunOwnership({ runId: leaseKey, generation, ownerId })`, catching failures and logging a warn. Only after that run the existing hand-back (`if (started || released) return` ...), so the lease is released even after the run started.

   A crash between acquiring the lease and the CAS leaves the row `pending`. The existing 60s pending takeover still recovers it, and by then the 15s lease has expired, so the normal `start()` path can claim it.
6. **Stores with `supportsConcurrentUpdates()` but not `supportsRunFencing()`.** Keep today's behavior: a `running` claim is never taken over. Log one `warn` per run when a resume hits a `running` row on such a store.

**Verify:** `npx tsc --noEmit -p packages/core`. If core needs a build first, rebuild `packages/_internal-core` first.

## Phase 2: Tests
All tests go in `packages/core/src/agent/__tests__/concurrent-resume-claim.test.ts`, which uses InMemoryStore (it supports concurrent updates and run fencing).

1. **Helper.** Add `strandRunningClaim(workflowsStore, runId, { leaseMs?: number })`. It CASes `suspended -> pending` with `resumeClaimedAt`, then claims ownership of `agentResumeLeaseRunId(runId)` with owner `dead-source/<runId>`, but only if `leaseMs` is given. It then CASes `pending -> running`.
2. **"lets a later approval take over a run whose resume died after it started".** Strand with `leaseMs: 1`, wait ~20ms, then `drain(await agent.approveToolCall(...))`. Expect `execute` once and a final snapshot status that is not `running`. Add the `approveToolCallGenerate`/`resumeGenerate` variant, which is the reporter's path.
3. **"recovers a running claim left by an older version without a lease".** Strand with no lease record. Expect `execute` once.
4. **"rejects an approval while a started resume still holds its lease".** Strand with a lease of `60_000` ms. Expect `AGENT_RESUME_ALREADY_CLAIMED` and `execute` not called.
5. **"lets only one of two concurrent takeovers win".** Run it twice, once with an expired lease and once with no lease. Use `Promise.allSettled` on two approvals. Expect one fulfilled, one `AGENT_RESUME_ALREADY_CLAIMED`, and `execute` once.
6. **"renews the lease while the resumed tool runs and releases it when done".**
   - Gate the tool's `execute` and spy on `renewRunOwnership`.
   - Use `vi.useFakeTimers({ toFake: ['setInterval', 'clearInterval'] })` and advance by the renewal interval read from `run-ownership.ts`. Expect the spy to have been called.
   - Open the gate and drain. Expect `getRunOwnership(agentResumeLeaseRunId(runId)).live === false`.
   - Restore real timers.
7. **"uses the run-ownership owner token".** After a resume starts, the lease `ownerId` matches `<sourceId>/<runId>`.
8. **"keeps running claims on stores without run fencing".** Mock `supportsRunFencing` to return false, strand a `running` row, and expect a rejection.

Existing tests must stay green, especially the pending-takeover and non-atomic ones.

## Phase 3: Docs and changeset
- **Docs note.** In `docs/src/content/en/reference/agents/generate.mdx` and `docs/src/content/en/reference/streaming/agents/stream.mdx`, add a short note where `AGENT_RESUME_ALREADY_CLAIMED` is described. It should say:
  - On a store with run fencing, if the process running a resume dies, another resume can take over once the claim's lease expires. That is 15s by default, set with `MASTRA_AGENT_THREAD_LEASE_TTL_MS`.
  - A takeover re-runs the suspended tool (at-least-once on crash), so tools should be idempotent.
  - A tool that blocks the event loop longer than the TTL can be taken over while it is still running.
  - Runs left `running` by earlier versions are also recovered.
- **Lint the docs:** `npx remark --no-stdout --frail --quiet --ext mdx <files>` and `npx oxfmt-mdx --check <files>`.
- **Changeset.** Add `.changeset/<name>.md` with `'@mastra/core': patch`. It should say:
  - A resume whose process died after starting no longer blocks the run forever. Another resume takes over once the lease expires (`MASTRA_AGENT_THREAD_LEASE_TTL_MS`, 15s default).
  - This includes runs stuck by earlier versions.
  - The in-flight tool may run again.

## Risks
- **Conflict with #27364 over `run-ownership.ts`.** Phase 0 mirrors #27364's module shape and only moves existing env reads. If both PRs create the module, the PR that lands second rebases onto the first one's file.
- **Shorter TTL.** The default is 15s instead of `ExecutionFence`'s 30s. A GC pause or blocked event loop longer than ~15s, which also means missing two renewals at TTL/3, can trigger a takeover of a live resume. That is the same trade-off the thread lease already accepts, and it is documented.
- **Mixed-version rollout.** Under decision 3, a resume still running on a pre-fix process has no lease, so a post-fix process can take it over and the tool runs twice. This is accepted as at-least-once. The `warn` log names the case.
- **A partitioned, not dead, claimant** can finish while its successor runs, which also runs the tool twice. This is accepted and logged at warn.
- **Import cycle** between `agent.ts` and `durable/execution-fence.ts` for `supportsRunFencing`. Mitigation: re-export it through `run-ownership.ts`.
- **Fake timers with the agent stream** can be flaky. Fake only `setInterval`/`clearInterval`.

## Assumptions
- The recovery mechanism is a renewed lease stored through the storage run-ownership API. A `running` claim is taken over only when no live lease exists, never because of `resumeClaimedAt` age alone. This avoids changing `updateWorkflowState` in every adapter.
- The lease key is `agent-resume:<runId>`. The owner token is the `<sourceId>/<runId>` format from `run-ownership.ts`.
- The TTL and renewal interval are `MASTRA_AGENT_THREAD_LEASE_TTL_MS` and `MASTRA_AGENT_THREAD_LEASE_RENEW_INTERVAL_MS`, both already existing variables, read through `run-ownership.ts`. The renewal variable is used because "shared TTL" implies the matching existing renewal setting, and adding a new one is forbidden.
- If #27364 has not landed, this PR creates `run-ownership.ts` in #27364's planned shape.
- A failed lease renewal does not abort the running resume. It only stops renewing and logs a warning.
- Stores without run fencing keep today's behavior.
- `AGENT_RESUME_CLAIM_STALE_MS` and the pending takeover are unchanged.
