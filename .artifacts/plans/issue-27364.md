# Plan: #27364 — thread stream runtime must decide run ownership/state from storage, not process-local events

Base: `main` @ `0ee20403`, branch `factory/issue-27364`. Package: `@mastra/core` (`packages/core`).
Coordinated with #27365 (DurableAgent execution claim) and #27366 (plain Agent running resume claim): see "Shared ownership model".

## Goal

`AgentThreadStreamRuntime` (`packages/core/src/agent/thread-stream-runtime.ts`) stops judging a run's ownership and state from the last streamed part or a replayed pubsub event. Done means all of these are covered by new unit tests that pass and fail on `main`:

1. When a follower sees the run lease lost, it reads the stored run status before it reports anything. `suspended` gives `run-suspended`. `running` keeps waiting up to one lease TTL for recovery. A terminal status gives completed and frees the thread. No row, no storage, or a read error falls back to today's heuristic.
2. A replayed `run-suspended` only blocks the thread when storage agrees, or when storage cannot answer.
3. The thread lease owner is `<sourceId>/<runId>`, not a bare `runId`. Every place that reads `lease.owner` as a runId parses it first.
4. An owner whose renewal finds the key empty re-acquires it while the run is still executing. It stops only when another owner holds the key.
5. `Mastra.shutdown()` releases this process's thread leases and publishes `run-suspended` for approval-parked runs. A follower then sees the suspension at once, without waiting a TTL.

## Shared ownership model (applies to #27364, #27365 and #27366)

The three issues are one model seen from three sides. This plan lands the shared pieces first (Phase 0) so the other two plans build on them and do not invent their own:

- **Who owns a run is decided by storage plus a renewed lease. Process memory is only a cache.** The authoritative run status is the workflows-store row (`getWorkflowRunById({ runId, workflowName: DurableStepIds.AGENTIC_LOOP })`, the same read `DurableAgent.#isRunningSnapshot` already does at `durable-agent.ts:~944`). A lease only says "a live process is still driving it".
- **One owner-token format:** `<holderId>/<runId>`. `holderId` is the runtime's per-process `#getSourceId()` for thread leases. For execution claims it is the existing per-execution `executionId`, so no format change there. #27366's new renewed resume lease uses the same `<sourceId>/<runId>`.
- **One TTL source:** `MASTRA_AGENT_THREAD_LEASE_TTL_MS` (default 15 s) plus its renew interval (TTL/3). #27365 case 4 makes `EXECUTION_LEASE_TTL_MS` default to this value. #27366 uses it for the plain-agent resume-claim lease instead of a new constant.
- **One shutdown rule:** `Mastra.shutdown()` releases every lease this process holds (execution claims via `abandonDurableAgentExecutions`, thread leases via this plan, and plain-agent resume leases via #27366) while storage and pubsub are still open.

Phase 0 creates `packages/core/src/agent/run-ownership.ts`, which exports:
- `AGENT_LEASE_TTL_MS` and `AGENT_LEASE_RENEW_INTERVAL_MS`, moved out of `thread-stream-runtime.ts` (L150–159) together with `readPositiveIntEnv`. Keep the env var names.
- `formatLeaseOwner(holderId: string, runId: string): string` returns `${holderId}/${runId}`.
- `leaseOwnerRunId(owner: string | undefined): string | undefined` returns the text after the first `/`, or the whole string when there is no `/` (a legacy bare-runId owner).
- `readStoredRunStatus(mastra, runId): Promise<'running' | 'suspended' | 'terminal' | 'missing' | 'unknown'>`. It reads the AGENTIC_LOOP row and parses a string snapshot like `#isRunningSnapshot`. `pending`/`waiting` count as `running`. `success`/`failed`/`canceled`/`tripwire`/`bailed` count as `terminal`. No row is `missing`. No storage or a thrown read is `unknown`. Callers act only on `running`, `suspended` and `terminal`.

#27365 and #27366 import these helpers. If either lands first, it creates the same module with the same names, and this plan reuses it.

## Scope

In scope: `thread-stream-runtime.ts`, the new `run-ownership.ts`, the shutdown hook in `mastra/index.ts`, the single `owner === runId` consumer in `durable/durable-agent.ts` (`isRunHoldingThreadLease`), tests and a changeset.

Out of scope:
- `LeaseProvider` interface changes. Owners are opaque strings, so Redis and in-memory providers need nothing.
- `ExecutionFence` wait/TTL behavior (#27365).
- Plain-agent `#claimSuspendedAgenticLoopRun` (#27366).
- Queued signal preservation across takeover (#23891).
- Message-during-lease-window (#26474).

## Phases

### Phase 0 — shared helpers (`run-ownership.ts`)
- Create the module above. Re-import the constants in `thread-stream-runtime.ts` and delete the local definitions. `threadLeaseTtlMs` keeps returning the same value.
- Test: `packages/core/src/agent/__tests__/run-ownership.test.ts`. Cover the format/parse round trip, the legacy bare id, and a runId that itself contains `/` (parse splits on the first `/` only, and sourceId is a UUID). Cover every status mapping in `readStoredRunStatus`, using an in-memory store (`InMemoryStore`), a string snapshot, a missing row, and a store whose `getWorkflowRunById` throws.
- Verify: `cd packages/core && npx vitest run src/agent/__tests__/run-ownership.test.ts`.

### Phase 1 — per-process lease owner token (case 3)
- In `thread-stream-runtime.ts`, wrap every runId passed as a lease owner in `formatLeaseOwner(this.#getSourceId(), runId)`: acquire, renew, release, transfer and `getLeaseOwner` comparisons. Today these are at L777, L794, L819, L838, L888, L928, L3282, L3330, L4394, L4702 and L5977–5993. Re-grep `acquireLease\|renewLease\|releaseLease\|transferLease\|getLeaseOwner` to catch every site. The claim lease at L1345/1352/1532 already uses `sourceId`; leave it alone.
- Anywhere `lease.owner` / `owns.owner` / `winnerRunId` is used as a runId (L1945–1956, L3739–3747, L4085–4088, L5993), use `leaseOwnerRunId(owner)`.
- Remote-ownership checks (`owner === runId` at L4394 and L4702, plus `isRunHoldingThreadLease`) compare `leaseOwnerRunId(owner) === runId`. A run moved to another process still counts as "held by that run".
- Cross-process resume in `#registerRunStrict` (L3330): when `acquireLease` fails and `leaseOwnerRunId(lease.owner) === output.runId` (same run, a dead or stale process), call `transferLease(key, lease.owner, newToken, TTL)` after `registrationOptions.validate()` has confirmed this execution's claim. The execution fence is the authority on who runs the run. Throw `AgentThreadLeaseConflictError` only when the transfer fails or the owner is a different run. This keeps today's idempotent same-runId takeover without sharing a token.
- `#sweepStaleSuspendedRecords` stays local (no release), as it is today.
- Tests (`agent/__tests__/agent-thread-lease.test.ts`): (a) the lease value is `<sourceId>/<runId>`; (b) two runtimes (two `new AgentThreadStreamRuntime()` on one in-memory pubsub) for the same runId: the second takes over by transfer, and the first one's later `releaseLease` does not clear it; (c) a legacy bare-runId owner is still recognized by `isRunHoldingThreadLease` and the remote watch. The existing test "does not release a lease taken over by a cross-instance resume…" (L167) must still pass.
- Verify: `npx vitest run src/agent/__tests__/agent-thread-lease.test.ts src/agent/__tests__/thread-stream-liveness.test.ts src/agent/durable`.

### Phase 2 — re-acquire a freed lease while running (case 4)
- `#startLeaseRenewal` (L832): when `renewLease` returns false, call `getLeaseOwner`. If the key is empty and the run's record is still actively running (`state.threadRunsById.get(runId)` exists and `#isActivelyRunning`), call `acquireLease` with the same token and keep the timer. Stop the timer only when another token holds the key or the record is gone. Mirror the claim-lease re-acquire at L1345–1352.
- Test (liveness or lease suite): run in progress, `provider.releaseLease(key, token)` from outside (simulating `DEL`), advance fake timers one renew interval, assert the owner is restored. Also: another owner present means no re-acquire and the timer stops.

### Phase 3 — storage-checked lease loss and replayed run-suspended (cases 1a, 1b, 2)
- Inject storage: `subscribeToThread` already receives `agent`. Use `agent.getMastraInstance?.()` for `readStoredRunStatus`.
- `startRemoteRunLeaseWatch.checkLease` (L4674–4740): on `leaseOwnerRunId(owner) !== runId`, call `readStoredRunStatus` before the existing branch. Re-check the existing "still current" guards (`done`, `watchToken`, `remoteRun.done`) after the await, as the code already does around `getLeaseOwner`.
  - `suspended`: take the existing parked branch (park the run, `lifecycle='suspended'`, enqueue the deferred record) even if no suspension prompt was seen. This is case 1b.
  - `running`: if it is the first miss for this streamId, keep watching (`scheduleCheck()`, one more TTL for a recovering process to acquire). On the second consecutive miss with `running`, fall through to the lease-lost error. This bounds the wait to 2×TTL. Case 1a.
  - `terminal`: end the remote run as completed (no error part), `clearActiveIfCurrent`, `#clearSuspendedRun`, drain idle signals. Thread free.
  - `missing`/`unknown`: unchanged behavior (prompt heuristic). This keeps plain non-durable runs, which have no row while running, and storage-less setups exactly as today.
- Replayed `run-suspended` handler (L5047–5052): after marking suspended, if the event is a replay (published before this subscription's `historyReadAt`, the same publish-time test used at L5018–5021) and the agent has storage, read the status asynchronously. On `terminal` or `missing`, clear `suspendedRunIds`/lifecycle for that runId and `#clearSuspendedRun`, so `#isThreadBlockingRun` (L1201) no longer blocks and a queued `sendMessage` proceeds. On `running`, mark it as a remote running run and start the lease watch. `suspended`/`unknown` changes nothing.
- Tests in `agent/__tests__/thread-stream-liveness.test.ts` with a `Mastra` + `InMemoryStore` whose AGENTIC_LOOP row is seeded per case:
  - lease lost + row `running`: no `AgentThreadLeaseLostError` after one TTL. After a recovering owner acquires, the stream continues. After 2×TTL with no owner, the error appears.
  - lease lost + row `suspended`, no approval part seen: the subscriber gets a suspended run, no error.
  - lease lost + row terminal: the stream finishes cleanly and the thread is free.
  - replayed `run-suspended` + row terminal or missing: `sendMessage` is not queued behind the run.
  - Existing assertion "lease-lost terminates live remote stream with `AgentThreadLeaseLostError`" keeps passing (no storage means `unknown`, the old path).

### Phase 4 — shutdown releases thread leases and publishes suspension (case 5)
- Add a public `releaseHeldThreadLeases(): Promise<void>` on `AgentThreadStreamRuntime`. For each pubsub state, and each `leaseRenewalTimers` entry or each record whose key this process holds: stop renewal and `await releaseLease(key, token)`. For records in `lifecycle==='suspended'` (approval-parked), `await #publishRunSuspended(...)` first, if it was not already published. Use `Promise.allSettled` and swallow errors (best effort, TTL is the backstop).
- `mastra/index.ts` shutdown, right after `abandonDurableAgentExecutions(this)` (L7740), while pubsub and storage are still open: `await agentThreadStreamRuntime.releaseHeldThreadLeases()`. Only release leases for runs that belong to this Mastra: filter by `record.agent.getMastraInstance?.() === this` if the record keeps the agent, otherwise release all. The runtime is a process singleton, so record which was used as an assumption.
- Test: `packages/core/src/mastra/__tests__/` (or the lease suite) parks a run with `requireApproval`, calls `mastra.shutdown()`, and asserts the lease key is empty and a second runtime's subscriber received `run-suspended`.

## Risks
- **Rolling deploys:** an old process compares `owner === runId` and sees a new `<sourceId>/<runId>` token as "not held". It may treat a live run as lost (old follower error path) or try a fresh acquire, which fails, so there is no double ownership. Mitigation: parsing accepts both formats in new code. Note it in the changeset. Check with test (c) in Phase 1.
- **Plain agents have no stored row while running.** `missing` must never mean "ended" on the lease-loss path, or live non-durable runs get cut short. Covered by the `missing` → heuristic rule and a test.
- **Async storage read inside the event handler races with later events.** Always re-check `remoteRun.done`/watch-token/record identity after the await. Run the existing liveness suite (15 tests) after every phase.
- **Transfer takeover in strict registration** could steal a lease from a legitimately live same-runId execution if `validate()` were skipped. Only transfer after `validate()` resolves. The test asserts that a conflict is still thrown for a different runId.
- **Shutdown publish** could fail when pubsub is already closing. Keep it before `stopWorkers`, and use best effort.

## Assumptions
- The triage findings were re-verified at `0ee20403`. The runtime has no storage reads. Renewal stops on a false renew (L840–844). The owner is the bare runId at every site listed. Shutdown only abandons fences (L7740).
- Storage access is through `agent.getMastraInstance()`. No new constructor dependency on the singleton runtime.
- The status source is the AGENTIC_LOOP workflow row, the same one `DurableAgent.#isRunningSnapshot` reads. `missing`/`unknown` keep the current behavior, so the change is strictly additive for setups without a row.
- The recovery window for `running` without a lease is one extra lease TTL (2×TTL total). That is long enough for durable recovery to re-acquire, and avoids a new config knob.
- Case 1a counts as a bug despite the existing liveness test: that test has no storage, so it stays valid under the `unknown` fallback.
- The owner-token format, TTL source, storage helper and shutdown rule are shared with #27365 and #27366 through `run-ownership.ts`. `ExecutionFence`'s `executionId` already gives a unique holder, so it is not reformatted.
- Same-run takeover uses atomic `transferLease` after the fence validation, rather than waiting for TTL. This keeps the current resume latency.
- The phases are one PR in order 0→5. Each phase leaves the suite green.

## Open questions
