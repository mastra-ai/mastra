# Plan: issue #27365: DurableAgent resume-claim losers

## Goal
When two `DurableAgent.resume()` calls (for example two `approveToolCall`s) race for one suspended run, or a resume arrives for a run that already finished:
- the losing call fails quickly with a clear error id (`AGENT_RESUME_ALREADY_CLAIMED` or `AGENT_RESUME_NO_SNAPSHOT_FOUND`);
- it never publishes an error to the run's shared topic, never ends the run's spans with an error, and never raises the memory fence;
- it never writes a workflow row for a run whose snapshot is gone.

Separately, the execution lease TTL follows `MASTRA_AGENT_THREAD_LEASE_TTL_MS`, the single agent lease TTL shared with #27364 and #27366.

"Done" means the new tests below pass, the existing durable test suites still pass, and core typechecks.

## Scope
**In scope:** `packages/core/src/agent/durable/durable-agent.ts` (`resume()`, `#claimExecution`), `execution-fence.ts` (constants, settled getter), `stream-adapter.ts` (scoped error events), `leases.md`, new tests, and a changeset (`@mastra/core` patch).

**Out of scope:**
- Making the cross-process acquire grace wait fail fast while a remote holder is mid-segment (see Assumptions A3).
- Changes to the non-durable `Agent` resume claim (`agent.ts`).
- Storage schema changes.

## Verified root causes (main 0ee20403)
1. **Missing snapshot is treated as resumable.** The post-claim check in `resume()` (around `durable-agent.ts:3352-3370`) only rejects when `current` exists and has a terminal status. If the winner finished, `deleteRunSnapshots` has already removed the row, so `current` is undefined and the check passes. `workflow.createRun` then persists a new `pending` row, and `run.resume()` throws `WORKFLOW_RUN_NOT_SUSPENDED`. This was reproduced: the deleted row came back as `pending`, and the stream emitted an `error` chunk with `AGENT_RESUME_ALREADY_CLAIMED`.
2. **The lost race is reported on the shared run.** The `WORKFLOW_RUN_NOT_SUSPENDED` → `AGENT_RESUME_ALREADY_CLAIMED` mapping (around 3622-3636) is rethrown into `.catch(error => this.settleExecution(...))`, which calls `emitError`. `emitError` calls `endRunSpansWithError(runId)` and publishes on `AGENT_STREAM_TOPIC(runId)` with the loser's generation. That generation is newer than the winner's, and `createRunGenerationFilter` (`stream-adapter.ts:60`) ratchets `newestGeneration` upward. So with storage fencing, the winner's followers can then drop the winner's later events. This was reproduced: `emitError(runId, AGENT_RESUME_ALREADY_CLAIMED)` was called.
3. **The memory fence is raised before the claim is confirmed.** `#claimExecution(runId, 'acquire', resumeRequestContext)` calls `#coverMemory` immediately after the fence claim (around 2401-2418), before the snapshot check.
4. **The in-process loser waits for the whole winning segment.** `resume()` awaits `priorExecution` (the registry's `workflowExecution`, around line 3301). Once a winning resume has installed its own `workflowExecution`, a second resume waits for that entire segment. This was reproduced: the loser waited about 8 s, the length of the winner's tool call. Cross-process, the acquire loop in `ExecutionFence.claim` (`execution-fence.ts:548-560`) waits `EXECUTION_CLAIM_WAIT_MS` (5 s) and then throws `DURABLE_AGENT_EXECUTION_CONFLICT`.
5. **The lease TTL is hard-coded.** `EXECUTION_LEASE_TTL_MS = 30_000` and `EXECUTION_LEASE_RENEW_INTERVAL_MS = 10_000` at `execution-fence.ts:36-37`. No environment override exists.

## Phases

### Phase 1: Never resume a run whose snapshot is gone (fixes case 3; most of case 2)
**Changes in `durable-agent.ts` `resume()`, post-claim `try` block:**
- If the workflows store exists and `current` is null or undefined, throw a `MastraError` with:
  - `id: 'AGENT_RESUME_NO_SNAPSHOT_FOUND'`
  - `domain: AGENT`, `category: USER`
  - text: "…cannot resume the run because it has no persisted snapshot (it may have already finished)"
  - details: `{ agentName, runId }`
- Keep the existing terminal-status branch (`AGENT_RESUME_ALREADY_CLAIMED`).
- The existing `catch` already releases the fence with `executionFence.settle(async () => {})` and rethrows. `resume()` therefore rejects before any stream, `createRun`, or registry mutation happens.
- Keep the behaviour when no workflows store is configured (`current` undefined with no store); don't reject that case.
- Optional fast path in the same spirit: the cold path already loads `persisted`. For the warm path, do the same `loadWorkflowSnapshot` read **before** `await priorExecution`/claim, and fail immediately when the snapshot is missing or terminal. This removes the 5 s cross-process wait whenever the winner has already finished. The post-claim check stays as the authoritative one.

**Tests:** add a new file `packages/core/src/agent/durable/__tests__/resume-claim-loser.test.ts`. Model it on `durable-agent-execution-fence.test.ts` helpers (InMemoryStore, EventEmitterPubSub, `requireApproval` tool, `createDurableAgent`, Mastra with storage and pubsub).
- **Warm resume after the run finished:** suspend, then delete the row with `workflows.deleteWorkflowRunById({ runId, workflowName: DurableStepIds.AGENTIC_LOOP })` while the `globalRunRegistry` entry stays. Then assert all of:
  - `resume()` rejects with `AGENT_RESUME_NO_SNAPSHOT_FOUND`;
  - `getWorkflowRunById` still returns null;
  - `workflow.createRun` was not called (spy);
  - no ERROR event was published on `AGENT_STREAM_TOPIC(runId)` (subscribe a spy).
- **Sequential double approval in one process:** the first resume completes and the second is called afterwards. Assert it rejects with `AGENT_RESUME_NO_SNAPSHOT_FOUND`, with no new row.

**Verify:** `cd packages/core && npx vitest run src/agent/durable/__tests__/resume-claim-loser.test.ts src/agent/durable/__tests__/resume-api.test.ts src/agent/__tests__/concurrent-resume-claim.test.ts src/agent/__tests__/resume-stream-no-snapshot.test.ts`

### Phase 2: Lost claim stays private to the loser (case 2 residual, memory fence)
**Memory fence:**
- In `resume()`, call `#claimExecution(runId, 'acquire')` without the request context.
- After the post-claim snapshot check passes (just before `setExecutionClaim`), call `await this.#coverMemory(executionFence, resumeRequestContext)`.
- Keep `#claimExecution`'s signature for other callers (`stream`, recovery).
- If `#coverMemory` throws, release the fence the same way the `catch` already does: move the call inside the `try`.

**Scoped error delivery:**
- `stream-adapter.ts`:
  - Add an optional `executionId?: string` to `AgentErrorEventData` and a matching parameter to `emitErrorEvent`, put into `data`.
  - Add `executionId?: string` to `DurableAgentStreamOptions`.
  - In the ERROR handling path, ignore events whose `data.executionId` is set and differs from the reader's `executionId`. Apply this check **before** `keepGeneration`, so a foreign scoped event never ratchets the generation filter.
- `durable-agent.ts` `resume()`:
  - Pass `executionId: executionFence.executionId` to `createDurableAgentStream`. Check that the fence exposes `executionId`; if it doesn't, expose it as a readonly field.
  - In the `run.resume()` catch, when the error is `WORKFLOW_RUN_NOT_SUSPENDED`, don't rethrow into `settleExecution`. Instead:
    - release with `await executionFence.settle(async () => {})`;
    - publish `emitErrorEvent(this.pubsub, runId, alreadyClaimedError, executionFence.generation, 'reject', executionFence.executionId)` wrapped in `runOutsideRunFenceScope`;
    - end only the resume spans this call opened (`resumeAgentSpan`/`resumeModelSpan` it created; capture them in locals) rather than calling `endRunSpansWithError(runId)`;
    - return.
  - Don't call `emitError`/`settleExecution` with an error on this path.

**Tests (same new file):**
- **Forced lost race:** spy `workflow.createRun` so the run's `resume` rejects with `WORKFLOW_RUN_NOT_SUSPENDED` (pattern from `resume-api.test.ts:448`). Then assert:
  - the loser's `fullStream` yields an `error` chunk with `AGENT_RESUME_ALREADY_CLAIMED` (the existing contract);
  - a second reader on the same run (`agent.observe(runId)`, or `createDurableAgentStream` without `executionId`) receives **no** error chunk;
  - `emitError` was not called (spy).
- **Memory fence:** a resume that fails the post-claim check doesn't call `#coverMemory`. Spy on the memory store fence method used by `#coverMemory`, or assert there's no memory fence record in the InMemoryStore; read `#coverMemory` to pick the observable.
- **Stream adapter unit test:** an ERROR event with a foreign `executionId` and a higher generation is dropped, and a later event from the lower generation is still kept.

**Verify:** the Phase 1 command plus `npx vitest run src/agent/durable/__tests__/durable-agent-execution-fence.test.ts src/agent/durable/__tests__/stream-adapter*.test.ts`. Use `find_files` for the exact adapter test file names.

### Phase 3: In-process loser fails fast instead of waiting for the winner's segment (case 1, in-process)
**Changes:**
- In `execution-fence.ts`, add a `get settled(): boolean` to `ExecutionFence`, set where `whenSettled` resolves.
- In `durable-agent.ts`, when a resume wins its claim and installs `reg.executionFence = executionFence`, also mark the registry entry. For example, `reg.resumeExecutionFence = executionFence`; add the optional field to the run-registry entry type in `run-registry.ts`/types.
- At the start of `resume()`'s claim section, before `await priorExecution`: if `getRunRegistryEntry(runId)?.resumeExecutionFence` exists and is not `settled`, throw `AGENT_RESUME_ALREADY_CLAIMED` immediately. Use the same error shape as the existing ones; consider a shared local helper, since the same error is now built three times.
- The suspending segment of `stream()` doesn't set that field, so the existing grace wait for a just-suspended run is unchanged.

**Tests (new file):** a tool with a gated `execute` (use `gate()`-style promise from the fence tests).
- Resume A starts and the tool is blocked.
- Resume B is called and must reject with `AGENT_RESUME_ALREADY_CLAIMED` within 1 s; measure with `Date.now()`, or use fake timers as `withFakeClock` does.
- Release the gate. A completes, and the tool executed exactly once.

**Verify:** the Phase 1 and 2 commands.

## Risks
- **Runs without a persisted snapshot that are still legitimately resumable.** Examples: the workflow persists lazily, or a store returns a `null` snapshot briefly. Check that `withSuspensionAfterPersist` and the awaited `priorExecution` guarantee the suspended row is written before any resume can claim. Run the full `src/agent/durable` suite; `durable-agent-version-resume`, `recover-run` and `recover-active-runs` exercise deleted and missing rows.
- **Existing tests that assert `AGENT_RESUME_ALREADY_CLAIMED` on a finished run** may now get `AGENT_RESUME_NO_SNAPSHOT_FOUND`. Update them only where the snapshot really is gone; the `resume-api.test.ts:448` stream contract must keep passing.
- **Scoped error filtering hides real errors.** Only events that carry an `executionId` are filtered; all existing publishers omit it. Test both directions.
- **Shorter default execution lease (30 s to 15 s).** A holder stalled for more than 15 s without renewing (for example a blocked event loop) can now be taken over. Renewal every 5 s keeps healthy holders safe. If #27364 lands first, rebase onto its `run-ownership.ts` instead of creating it.
- **Moving `#coverMemory` later** opens a window where the claim is held without a memory fence. Nothing writes memory in that window (snapshot read, tool-call load, offset read only); confirm by reading `#loadRecalledMessages`.
- **A loser that finds the run re-suspended** (the winner hit a second approval and suspended again) would resume the *new* suspension with stale approval data. This is pre-existing and not changed here. Note it in the PR body if the executor confirms it.

## Assumptions
- A1: A warm resume whose snapshot is gone reports `AGENT_RESUME_NO_SNAPSHOT_FOUND`. This matches the issue's expectation and the non-durable `Agent` semantics in `concurrent-resume-claim.test.ts:159`, and it is rejected from `resume()` rather than streamed, as the cold path already does.
- A2: The stream-delivered `AGENT_RESUME_ALREADY_CLAIMED` contract for a lost race at `run.resume()` (`resume-api.test.ts:448`) is kept. Only its audience changes, through `executionId`-scoped error events. Rejected alternatives:
  - removing the error entirely: it would break the caller's contract;
  - an in-memory side channel: the reader may sit behind a remote pubsub.
- A3: The cross-process acquire grace wait (`EXECUTION_CLAIM_WAIT_MS`) is kept. With no persisted marker, a settling suspender can't be told apart from a live remote resumer: both appear as "held + row suspended/running". Telling them apart would need a schema change. Phase 1's pre-claim snapshot read already removes the wait when the winner has finished.
- A4 (maintainer decision): `EXECUTION_LEASE_TTL_MS` defaults to `MASTRA_AGENT_THREAD_LEASE_TTL_MS` (15 s) through the shared `run-ownership.ts` module from the #27364 plan. There is no separate env var and no Mastra config option. The default drops from 30 s to 15 s, and renewal stays at TTL/3.
- A5: Case 2 is fixed in two ways. Phase 1 removes its main trigger (the winner finished and the snapshot was deleted). Phase 2 makes the remaining `WORKFLOW_RUN_NOT_SUSPENDED` path private to the loser. The real Redis Streams plus PG interleaving wasn't run; there is no Redis or PG in the sandbox.
- A6: Fence and memory-claim changes stay inside `resume()`. `stream({ runId })` and recovery keep `#claimExecution` with memory coverage as they are now.
