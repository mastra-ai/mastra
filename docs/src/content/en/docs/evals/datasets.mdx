# Datasets

**Added in:** `@mastra/core@1.4.0`

Datasets are collections of test cases that you run experiments against to measure how well your agents and workflows perform. Each mutation creates a new version, so you can reproduce past experiments exactly. Pair datasets with [scorers](/docs/evals/overview) to track quality across prompts, models, or code changes.

<Inject>
  **For AI agents:** Run `npx mastra api dataset create '{"name":"translation-pairs"}'` to create a dataset directly instead of opening Studio or writing a temporary script. The command requires a running Mastra server with a storage adapter that supports datasets; start the local server with `npx mastra dev`, or pass the reachable server's base URL with `--url`. Run `npx mastra api dataset create --schema` before adding different dataset fields. Install Mastra's skill with `npx skills add mastra-ai/skills --skill mastra` for complete API CLI discovery, targeting, schema, authentication, and error-handling guidance.
</Inject>

## Usage

### Configure storage

Configure storage in your Mastra instance. Datasets require a storage adapter that provides the `datasets` domain:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'my-store',
    url: 'file:./mastra.db',
  }),
})
```

### Accessing the datasets API

All dataset operations are available through `mastra.datasets`:

```typescript
const datasets = mastra.datasets

// Create a dataset
const dataset = await datasets.create({ name: 'my-dataset' })

// Retrieve an existing dataset
const existing = await datasets.get({ id: 'dataset-id' })

// List all datasets
const { datasets: all } = await datasets.list()
```

Visit the [`DatasetsManager` reference](/reference/datasets/datasets-manager) for the full list of methods.

## Studio

You can also manage datasets in [Studio](/docs/studio/overview). After opening Studio, select **Datasets** from the sidebar to see all your available datasets or create a new one.

To get started, select **Create Dataset** and set a name, description, and optional schemas. After confirming, you'll see the dataset details page with two tabs: **Items** and [**Experiments**](/docs/evals/experiments#run-experiments-in-studio).

In the **Items** view you can add, update, and delete items, and view version history. Select **Add Item** to insert a new item with JSON editors for input and ground truth. From this view you can also import items in bulk from a CSV or JSON file. When importing, map each column to the corresponding dataset field.

Select **Versions** to see the full history of changes to the dataset. After selecting **Compare Versions**, choose any two versions and select **Compare** to see a side-by-side diff of all items that were added, changed, or removed between those versions.

## Creating a dataset

Call [`create()`](/reference/datasets/create) with a name and optional description:

```typescript title="src/mastra/datasets/create-dataset.ts"
import { mastra } from '../index'

const dataset = await mastra.datasets.create({
  name: 'translation-pairs',
  description: 'English to Spanish translation test cases',
})

console.log(dataset.id) // auto-generated UUID
```

### Defining schemas

You can enforce the shape of `input` and `groundTruth` by passing a [Standard JSON Schema](https://standardschema.dev/json-schema) ([Zod](https://zod.dev/), [Valibot](https://valibot.dev/), [ArkType](https://arktype.io/), etc.) when creating the dataset:

```typescript title="src/mastra/datasets/create-with-schema.ts"
import { z } from 'zod'
import { mastra } from '../index'

const dataset = await mastra.datasets.create({
  name: 'translation-pairs',
  inputSchema: z.object({
    text: z.string(),
    sourceLang: z.string(),
    targetLang: z.string(),
  }),
  groundTruthSchema: z.object({
    translation: z.string(),
  }),
})
```

Items that don't match the schema are rejected at insert time.

## Adding items

Use [`addItem()`](/reference/datasets/addItem) for a single item or [`addItems()`](/reference/datasets/addItems) to insert in bulk:

```typescript title="src/mastra/datasets/add-items.ts"
// Single item
await dataset.addItem({
  input: { text: 'Hello', sourceLang: 'en', targetLang: 'es' },
  groundTruth: { translation: 'Hola' },
})

// Bulk insert
await dataset.addItems({
  items: [
    {
      input: { text: 'Goodbye', sourceLang: 'en', targetLang: 'es' },
      groundTruth: { translation: 'Adiós' },
    },
    {
      input: { text: 'Thank you', sourceLang: 'en', targetLang: 'es' },
      groundTruth: { translation: 'Gracias' },
    },
  ],
})
```

### Stored field values

In-memory, LibSQL, PostgreSQL, MySQL, MongoDB, and Spanner dataset storage preserve JSON `null` in `input`, `groundTruth`, and `expectedTrajectory`, along with empty strings, arrays, and objects. Omitted optional JSON fields remain absent when serialized. Dataset schemas still determine which values an item accepts.

Snapshot validation doesn't override database restrictions. MongoDB rejects object property names containing NUL (`\u0000`), even in valid JSON. A batch insert containing such keys fails without storing any items or advancing the dataset version.

For configuration updates, `null` clears schemas, tags, target type, target IDs, or scorer IDs. These adapters return cleared settings as `undefined`, while preserving empty arrays and objects. An item update with `scorerIds: null` removes its scorer override, whereas `scorerIds: []` disables scoring for that item. Omitted update fields leave existing values unchanged.

Retries with the same `externalId` retain the original item's representation. For backward compatibility, insert operations treat omitted and `null` payload fields as equivalent when comparing a retry with an existing item. For example, inserting an item without `groundTruth` and retrying with `groundTruth: null` returns the original item with no ground truth. Use an item update to store an explicit `null` instead.

Unset configuration now reads as `undefined` where some adapters previously returned `null`, so serialized responses omit those properties. Use nullish checks such as `value ?? fallback` rather than relying on an explicit `null` property. LibSQL also returns an omitted dataset description as `undefined`, matching its declared type.

Older LibSQL, PostgreSQL, MySQL, and Spanner writes stored optional JSON `null` values as SQL `NULL`, so those values remain indistinguishable from omitted fields. Older MongoDB writes stored omitted optional payload fields as BSON `null`. The storage fixes preserve new writes but don't reconstruct previously lost distinctions.

## Transfer a dataset

Export a snapshot and import it into a **new dataset** to move evaluation cases between environments. The transfer preserves stored configuration, authored item fields, item timestamps, and portable identities without synchronizing an existing destination dataset. Scorer code, workflow definitions, models, and external dependencies aren't included.

This example uses two in-memory instances. Configure persistent storage in each instance when transferring between deployed environments:

```typescript title="src/mastra/datasets/transfer.ts"
import { Mastra } from '@mastra/core/mastra'
import { InMemoryStore } from '@mastra/core/storage'

const source = new Mastra({ storage: new InMemoryStore() })
const destination = new Mastra({ storage: new InMemoryStore() })
const dataset = await source.datasets.create({ name: 'translation-pairs' })
await dataset.addItem({ input: 'Hello', groundTruth: 'Hola' })

const snapshot = await dataset.exportSnapshot({
  acknowledgeSensitiveData: true,
})
const request = {
  snapshot: JSON.stringify(snapshot),
  idempotencyKey: 'translation-release-2026-09-18',
}

const report = await destination.datasets.preflightSnapshot(request)
if (!report.canImport) {
  throw new Error('Register the missing references listed in report.errors')
}

const result = await destination.datasets.importSnapshot(request)
if (!result.datasetExists) {
  throw new Error('This request already completed, but its dataset was deleted')
}

const copy = await destination.datasets.get({ id: result.receipt.datasetId })
console.log((await copy.listItems()).items.length) // 1
```

### Choose the captured version

`exportSnapshot()` captures the current item version by default. Pass `version` to select an earlier item version, but configuration is always captured at export time because configuration history isn't stored. The artifact records this distinction as `configurationBasis: 'export-time'`. Export fails if the selected content has been purged or doesn't satisfy the captured schemas.

Export requires `acknowledgeSensitiveData: true` because inputs, request context, metadata, and tool mock outputs can contain secrets. Review the dataset before exporting, and protect the resulting JSON as sensitive data. Automatic redaction isn't performed.

Portable identities are stored separately from authored metadata and remain stable across re-exports. Exported items are sorted by portable identity, so repeated exports of unchanged content produce identical files. A dataset without a description exports with the field omitted, even when an artifact imported it as `null`. Imported items retain their source `createdAt` and `updatedAt`, while the receipt records completion time. A later destination edit advances `updatedAt` normally. The destination starts at item version `1`, or `0` for an empty dataset, rather than copying the source's version history.

### Check destination references

`preflightSnapshot()` validates the artifact, captured schemas, and adapter capabilities without writing a dataset or receipt. Its report includes `targetIds`, `scorerIds`, `targetMappings`, `scorerMappings`, and an `errors` array of unresolved references. A valid report has `canImport: true`, but database restrictions can still cause the subsequent transaction to fail.

Register referenced agents, workflows, and scorers in the destination before importing. If their identifiers differ, pass explicit `targetMappings` and `scorerMappings` arrays containing `{ from, to }` entries to both preflight and import. Scorer mappings apply to both dataset configuration and item overrides without changing the source artifact, but matching references doesn't establish equivalent behavior in the destination code.

Artifacts arrive from outside the destination, so preflight also vets regular expressions in the captured `inputSchema`, `groundTruthSchema`, and `requestContextSchema` before compiling them. A schema `pattern` or `patternProperties` key is rejected with `DATASET_SNAPSHOT_UNSAFE_SCHEMA` when it uses a backreference, exceeds 512 characters, or can backtrack catastrophically, such as repetition nested inside repetition without a separating literal (`(\w+\s?)+`) or a repeated alternation whose branches overlap (`(a|ab)*`). Fenced shapes like `^(\d{1,3}\.){3}\d{1,3}$` and `^\w+(,\w+)*$` pass. Simplify the source schema and export again to import such a dataset.

Import repeats the reference checks before creating a dataset, though recovering an already completed request doesn't require those references to remain registered. Use `destination: { name, organizationId, projectId }` to override the destination name or tenancy. Source ownership and candidate bindings aren't copied. In server code, derive tenancy from the authenticated caller and apply authorization before calling these APIs.

### Retry an import

Reuse the same artifact, options, and `idempotencyKey` after a lost response. An atomic import commits the dataset, items, portable identity mappings, and receipt together after reading back the stored values. A failed transaction publishes none of them.

Keys are scoped by destination organization and project. Reusing a key with a different artifact, name, or reference mapping fails instead of creating another copy. Completed receipts survive dataset deletion, so retrying a deleted import returns its original receipt with `datasetExists: false`. Use a new key when you intend to create another dataset.

Look up an outcome without resubmitting the artifact:

```typescript
const outcome = await destination.datasets.getSnapshotImport({
  idempotencyKey: request.idempotencyKey,
})
console.log(outcome?.receipt.datasetId, outcome?.datasetExists)
```

Include `organizationId` and `projectId` in this lookup when the import used those fields. In-memory receipts last only as long as the storage instance.

### Storage requirements and limits

Snapshot transfer is implemented for in-memory, LibSQL, PostgreSQL, MySQL, MongoDB, and Spanner storage, with these restrictions:

- MongoDB requires a replica set or sharded deployment with transaction support. Snapshots can't be exported while a dataset's nontransactional deletion is in progress, including after a partial deletion failure. Retry deletion to finish removing that dataset.
- MySQL rejects nonempty item `toolMocks` during preflight rather than dropping them.
- Processor target references fail destination preflight because the experiment runner doesn't currently resolve processor targets.
- Local LibSQL file databases rely on the `LibSQLStore` busy timeout so that concurrent processes wait for the SQLite write lock. Pass `connectionTimeoutMs` to `LibSQLStore` rather than a raw `@libsql/client` without a timeout, because a client whose `BEGIN` fails can't commit later transactions.
- Adapters without snapshot support reject the operation rather than falling back to a non-atomic import.

Export locks the dataset row for the duration of the capture on PostgreSQL, MySQL, and MongoDB so that identities and items are read consistently. Concurrent writers to that dataset wait until the export commits.

Receipts are retained indefinitely so that retries stay safe. There's no API for removing them, so delete rows from the `mastra_dataset_snapshot_imports` table directly if you need to reclaim space.

Captured schemas from an artifact are compiled into validators before import, including any `pattern` regular expressions. Only import artifacts from sources you trust.

Pass `maxBytes` to export, preflight, or import to change the default 4 MiB UTF-8 budget. The same format limits described below still apply. A successful preflight doesn't reserve database capacity, and storage limits or transaction timeouts can reject an import without creating a partial dataset.

These are core APIs. They don't add HTTP endpoints or change Studio's item-array JSON importer.

## Validate snapshot artifacts

Use `createDatasetSnapshot()` and `parseDatasetSnapshot()` from `@mastra/core/datasets` to create and validate a versioned JSON artifact. These are pure format utilities: they don't export from storage, import a dataset, allocate portable identities, or change Studio's JSON importer.

```typescript title="src/mastra/datasets/snapshot.ts"
import { createDatasetSnapshot, parseDatasetSnapshot } from '@mastra/core/datasets'

const snapshot = createDatasetSnapshot({
  formatVersion: 1,
  datasetIdentity: '00000000-0000-4000-8000-000000000001',
  configuration: { name: 'translation-pairs' },
  items: [
    {
      itemIdentity: '00000000-0000-4000-8000-000000000002',
      createdAt: '2026-09-01T09:00:00.123Z',
      updatedAt: '2026-09-10T10:00:00.456Z',
      payload: { input: 'Hello', groundTruth: 'Hola', scorerIds: [] },
    },
  ],
  provenance: {
    exportedAt: '2026-09-11T12:00:00Z',
    sourceDatasetId: 'dev-translations',
    itemVersion: 1,
    configurationBasis: 'export-time',
  },
})

const parsed = parseDatasetSnapshot(JSON.stringify(snapshot))
console.log(parsed.digest === snapshot.digest) // true
```

The artifact includes configuration, complete authored item payloads, portable UUIDs, and provenance. Supply stable lowercase UUIDs rather than generating new identities on every serialization. Authored `externalId` values are separate from portable identity and remain unchanged. Absent, `null`, and empty overrides remain distinct. Omit optional properties rather than assigning `undefined`. Dataset descriptions also preserve absent, `null`, and string values.

Each item requires `createdAt` and `updatedAt` as UTC ISO 8601 strings with millisecond precision, matching `Date.toISOString()` for four-digit years. Both timestamps are included in the integrity digest. They represent the item's actual dates, not transfer provenance: an importer must preserve them as the destination item's `createdAt` and `updatedAt`, rather than replacing them with import time. An importer records transfer time in a separate receipt, while later edits in the destination update `updatedAt` normally. Implementing storage import remains outside the scope of these format helpers.

This preservation applies to the supplied artifact content. Storage adapters may already have normalized values before capture. Format validation neither recovers those distinctions nor guarantees that ordinary dataset CRUD operations can restore them. PostgreSQL JSONB, for example, rejects strings containing the NUL character (`\u0000`) even though they're valid in an artifact. Validate destination storage restrictions before writing artifact contents.

Both helpers throw a Zod validation error for invalid content or size options. `datasetSnapshotContentSchema.safeParse()` validates unsigned content and identity uniqueness, while `datasetSnapshotSchema.safeParse()` additionally checks the digest. These schemas don't enforce a byte limit. Use `parseDatasetSnapshot()` for untrusted text to enforce a size budget before parsing and reject duplicate JSON property names.

The helpers default to a 4 MiB UTF-8 budget (`DATASET_SNAPSHOT_DEFAULT_MAX_BYTES`). Pass `{ maxBytes }` as the second argument to either helper to raise or lower it. The value must be a positive safe integer. This is an operational limit, not part of the v1 format or digest. For example, parse the snapshot above with an 8 MiB budget:

```typescript
const parsedWithLargerBudget = parseDatasetSnapshot(JSON.stringify(snapshot), {
  maxBytes: 8 * 1024 * 1024,
})
```

`createDatasetSnapshot()` measures the complete artifact's compact `JSON.stringify()` output, including the digest. `parseDatasetSnapshot()` measures the supplied text, including whitespace. Pretty-printing can exceed a budget that accepts the compact artifact. Neither helper truncates data. During creation, validation, cloning, and hashing happen before the byte-size check. Because shared references can expand during JSON serialization, the budget limits output size without bounding CPU time or peak memory. When adding a transport, configure HTTP request-body limits separately from this budget.

Artifacts have a maximum nesting depth of 100, measured from the envelope root. They reject unknown structural fields, duplicate item identities or non-null `externalId` values, non-JSON values, and invalid Unicode. Programmatic content must use plain objects and standard arrays, not class instances or array subclasses. Arbitrary JSON inside authored payloads remains intact, including trajectory expectations. Dataset schemas are preserved as JSON objects, but these utilities don't compile them or validate items against them. Destination authorization, reference resolution, and storage support also require separate preflight checks.

The digest is a lowercase hexadecimal SHA-256 hash of the RFC 8785 canonical JSON representation of the envelope without `digest`. Items are sorted by portable identity for hashing, while authored array order is preserved. Provenance is covered, so a new capture time changes the digest. A matching digest verifies integrity but doesn't establish authorship or approval. Review sensitive data before creating an artifact, as the utilities don't redact it.

## Updating, deleting, and purging items

[`updateItem()`](/reference/datasets/updateItem), [`deleteItem()`](/reference/datasets/deleteItem), and [`deleteItems()`](/reference/datasets/deleteItems) create new dataset versions as they modify or remove items:

```typescript title="src/mastra/datasets/update-delete.ts"
await dataset.updateItem({
  itemId: 'item-abc-123',
  groundTruth: { translation: '¡Hola!' },
})

await dataset.deleteItem({ itemId: 'item-abc-123' })

await dataset.deleteItems({ itemIds: ['item-1', 'item-2'] })
```

Deleting an item hides it from the current dataset version but retains its content in historical rows and the deletion tombstone. Use [`purgeItem()`](/reference/datasets/purgeItem) to redact the item's stored content across its existing history:

```typescript title="src/mastra/datasets/purge-item.ts"
await dataset.purgeItem({ itemId: 'item-abc-123' })
```

Purging replaces content in every historical row and deletion tombstone with redacted values, and scrubs linked experiment-result payloads, tags, and comments. Later experiment-result submissions for the item are also stored with redacted content.

Purge serializes or conflicts with concurrent dataset item writers without guaranteeing which operation completes first. If a mutating `updateItem()` call loses the race, it re-reads the purge marker and rejects with `DATASET_ITEM_PURGED`. `deleteItem()` remains idempotent, and any deletion tombstone created during the race stays redacted.

Normal item mutations use Slowly Changing Dimension Type 2 (SCD-2) versioning. Permanent purge intentionally overrides historical immutability for erasure while preserving item identity and the dataset version timeline. It doesn't create a dataset version and can't be undone. Experiment counters and review status are also preserved. Avoid storing sensitive data in `externalId`, which remains unchanged as the item's identity key.

MongoDB storage requires a replica set or sharded deployment with transaction support for this operation. Purging fails before changing data when MongoDB transactions aren't available.

## Listing and searching items

[`listItems()`](/reference/datasets/listItems) supports pagination and full-text search:

```typescript title="src/mastra/datasets/list-items.ts"
// Paginated list
const { items, pagination } = await dataset.listItems({
  page: 0,
  perPage: 50,
})

// Full-text search
const { items: matches } = await dataset.listItems({
  search: 'Hello',
})

// Search and pagination can be combined with a specific version
const { items: v2Matches } = await dataset.listItems({
  version: 2,
  search: 'Hello',
  page: 0,
  perPage: 50,
})

// Version-only snapshot returns a bare DatasetItem[]
const v2Items = await dataset.listItems({ version: 2 })
```

## Versioning

Adding, updating, or deleting dataset items bumps the dataset version. Purging an item's stored content with [`purgeItem()`](/reference/datasets/purgeItem) doesn't create a new version. This lets you pin experiments to a specific snapshot of the data while erasing sensitive content without changing the version history.

### Listing versions

Use [`listVersions()`](/reference/datasets/listVersions) to see the paginated history of versions:

```typescript title="src/mastra/datasets/list-versions.ts"
const { versions, pagination } = await dataset.listVersions()

for (const v of versions) {
  console.log(`Version ${v.version} — created ${v.createdAt}`)
}
```

### Viewing item history

See how a specific item changed across versions by calling [`getItemHistory()`](/reference/datasets/getItemHistory) with the `itemId`:

```typescript title="src/mastra/datasets/item-history.ts"
const history = await dataset.getItemHistory({ itemId: 'item-abc-123' })

for (const row of history) {
  console.log(`Version ${row.datasetVersion}`, row.input, row.groundTruth)
}
```

### Pinning to a version

Fetch the exact items that existed at a past version:

```typescript title="src/mastra/datasets/pin-version.ts"
const items = await dataset.listItems({ version: 2 })
```

You can also pin experiments to a version, see [running experiments](/docs/evals/experiments). Visit the [`Dataset` reference](/reference/datasets/dataset) for the full list of methods and parameters.
