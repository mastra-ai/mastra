# MCP events

MCP events let an MCP client react when something happens on a server, such as a ticket being opened or a build finishing, instead of calling a tool on a schedule to check. A server describes the event types it offers, a client subscribes with arguments, and the server delivers each matching occurrence.

This guide shows both sides in Mastra: an [`MCPServer`](/reference/tools/mcp-server#events-experimental) that publishes events and an [`MCPClient`](/reference/tools/mcp-client#events-property-experimental) that subscribes and starts agent runs.

:::warning

MCP events implement [SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415), a draft MCP extension. The wire format and the Mastra API are experimental and may change in any release.

:::

## How events work

- **Event type:** A named kind of occurrence, such as `ticket.created`. Each type has an optional `inputSchema` for subscription arguments and a `payloadSchema` for occurrence data. Clients discover types with `events/list`.
- **Subscription:** One client request for one event type with arguments, such as `{ project: 'web' }`. The server only delivers occurrences that match those arguments.
- **Occurrence:** One delivered event with an `eventId`, `name`, `timestamp`, and `data`.
- **Delivery mode:** How occurrences reach the client. In `push` mode the client holds one long-lived `events/stream` request open per subscription. In `poll` mode it repeats `events/poll` requests. In `webhook` mode the server POSTs each occurrence to a URL the client registered.
- **Cursor:** An opaque position in the event sequence. The client saves it and passes it back to resume after a restart without missing occurrences.

Delivery is at least once. After a reconnect or a resume, the server can send an occurrence the client has already seen. `MCPClient` drops duplicates by `eventId` within a window of recent ids, and your handler should still tolerate a repeat.

Clients only send `events/*` requests to servers that advertise the `io.modelcontextprotocol/events` extension, and servers without event types never advertise it.

## Publish events from a server

Declare each event type with `defineEvent()` in the `events` option of `MCPServer`, then publish occurrences with `server.events.emit()`. This server emits `ticket.created` whenever its `openTicket` tool runs:

```typescript title="src/mcp/server.ts"
import { createTool } from '@mastra/core/tools'
import { MCPServer, defineEvent } from '@mastra/mcp'
import { z } from 'zod'

const ticket = z.object({ id: z.string(), project: z.string(), title: z.string() })

const openTicket = createTool({
  id: 'openTicket',
  description: 'Opens a support ticket',
  inputSchema: ticket,
  execute: async input => {
    const occurrence = await server.events.emit('ticket.created', input)
    return { eventId: occurrence.eventId }
  },
})

export const server: MCPServer = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: { openTicket },
  events: {
    'ticket.created': defineEvent({
      description: 'A support ticket was opened',
      inputSchema: z.object({ project: z.string() }),
      payloadSchema: ticket,
      match: (args, data) => data.project === args.project,
    }),
  },
})
```

`match` decides which subscriptions receive an emitted occurrence. A client subscribed with `{ project: 'web' }` receives the ticket above only when its `project` is `web`. The server rejects subscription arguments that fail `inputSchema` and occurrence data that fails `payloadSchema`.

`match` filters on the arguments the client chooses, so it doesn't control who can subscribe. To restrict callers, add `authorize`. It receives the validated arguments and the caller's `requestContext`, which includes `user` when you set `mapAuthInfoToUser`:

```typescript title="src/mcp/server.ts"
const ticketCreated = defineEvent({
  description: 'A support ticket was opened',
  inputSchema: z.object({ project: z.string() }),
  payloadSchema: ticket,
  match: (args, data) => data.project === args.project,
  authorize: ({ arguments: args, requestContext }) => {
    const user = requestContext.get('user') as { projects: string[] } | undefined
    return user?.projects.includes(args.project) ?? false
  },
})
```

Returning `false` rejects the poll or subscription with `-32024`. `authorize` runs on every poll and every subscription open. An open subscription isn't checked again until it reconnects. Visit the [`authorize` reference](/reference/tools/mcp-server#events-experimental) for details.

The server serves events over stdio and Streamable HTTP, the same transports as its tools.

### Choose an event source

An event type gets its occurrences from one of two sources, and the source decides which delivery modes the server advertises:

| Source | Advertised delivery | Use it when |
| - | - | - |
| `server.events.emit()` | `push` and `poll`, plus `webhook` when enabled | Your server process learns about the event directly, for example from a tool call or an incoming webhook. Polls read an in-memory buffer of recent occurrences. |
| A `poll` function | `poll` only | The events live in another system you can query, such as a database table or an upstream API. The server calls your function for each `events/poll` request. |

A `poll` source receives the subscription arguments and the client's cursor, and returns the occurrences after that cursor with the new cursor:

```typescript title="src/mcp/server.ts"
import { defineEvent } from '@mastra/mcp'
import { z } from 'zod'

const buildFinished = defineEvent({
  description: 'A build finished',
  inputSchema: z.object({ branch: z.string() }),
  payloadSchema: z.object({ id: z.string(), branch: z.string(), status: z.string() }),
  poll: async ({ arguments: args, cursor }) => {
    // A null cursor means "start from now".
    const builds = await db.buildsAfter(cursor ?? (await db.latestBuildId()), args.branch)
    return {
      events: builds.map(build => ({ eventId: build.id, data: build })),
      cursor: builds.at(-1)?.id ?? cursor,
      nextPollMs: 5000,
    }
  },
})
```

Return the same `eventId` every time the same occurrence is polled, for example the upstream record id. Clients use it to drop duplicates. `db` stands in for your own data access.

## Subscribe from a client

List the event types a server offers, then subscribe with `mcp.events.subscribe()`. The returned subscription is an async iterable of occurrences:

```typescript title="src/mcp/client.ts"
import { MCPClient } from '@mastra/mcp'

const mcp = new MCPClient({
  servers: {
    tickets: { url: new URL('http://localhost:4111/mcp') },
  },
})

const eventTypes = await mcp.events.list('tickets')

const subscription = await mcp.events.subscribe('tickets', 'ticket.created', { project: 'web' })

for await (const event of subscription) {
  console.log(event.eventId, event.data)
}
```

`subscribe()` resolves once the server has accepted the subscription, so invalid arguments reject there instead of inside the loop. The client picks the first mode the event type offers in this order: `webhook` (only when the client has [`webhook` settings](#webhook-delivery)), `push`, then `poll`. Pass `delivery` in the options, such as `{ delivery: 'poll' }`, to force a mode.

A new subscription starts from now. Occurrences emitted before `subscribe()` resolves aren't delivered unless you resume from a cursor.

### Resume from a cursor

`subscription.cursor` is the latest position that's safe to persist. It never moves past an occurrence your loop hasn't received yet. Save it after you finish handling each occurrence, and pass it back as `cursor` when you subscribe again:

```typescript title="src/mcp/client.ts"
const subscription = await mcp.events.subscribe(
  'tickets',
  'ticket.created',
  { project: 'web' },
  { cursor: await loadCursor('tickets:web') },
)

for await (const event of subscription) {
  await handleTicket(event.data)
  if (subscription.cursor) await saveCursor('tickets:web', subscription.cursor)
}
```

The resumed subscription delivers the occurrences that happened while you were away, then live ones. If the saved cursor is older than what the server retains, `subscription.truncated` is `true` and some occurrences were skipped. A `null` cursor means the event type doesn't support replay, so don't persist it.

Within one process, the client also reopens dropped push streams and keeps polling after a reconnect, including after `mcp.reconnectServer()`, without any work from you.

### Handle errors

Errors before delivery starts reject `subscribe()` with a `MastraError` whose id is `MCP_CLIENT_SUBSCRIBE_EVENT_FAILED`. Its `cause` identifies the problem:

| `cause.id` | Meaning |
| - | - |
| `MCP_EVENTS_NOT_SUPPORTED` | The server doesn't advertise the events extension. The client sends it no `events/*` requests. |
| `MCP_EVENTS_UNKNOWN_EVENT` | The server doesn't offer an event type with that name. |
| `MCP_EVENTS_NO_COMPATIBLE_DELIVERY_MODE` | You forced a delivery mode the event type doesn't offer. |
| `MCP_EVENTS_WEBHOOK_NOT_CONFIGURED` | You forced `webhook` on a client without `webhook` settings. |
| `MCP_EVENTS_SUBSCRIPTION_FAILED` | The server rejected the subscription, for example because the arguments failed `inputSchema` or a webhook subscription came from an unauthenticated caller. |

`mcp.events.list()` rejects with `MCP_CLIENT_LIST_EVENTS_FAILED` and the same kind of `cause`.

After delivery starts, the client retries transient failures with backoff and reports them to `subscription.onError()`. The loop throws when the subscription can't continue, for example with `MCP_EVENTS_SUBSCRIPTION_TERMINATED` when the server ends a push or webhook subscription. Breaking out of the loop or calling `subscription.cancel()` stops the subscription.

## Webhook delivery

With webhook delivery, the server POSTs each occurrence to an HTTP endpoint on the client side, so the client doesn't hold a connection open. Use it when the server is remote and your application already serves HTTP.

Enable it on the server with `eventsOptions.webhook`. Event types fed by `emit()` then also advertise `webhook`. Types with a `poll` source stay poll only:

```typescript title="src/mcp/server.ts"
export const server: MCPServer = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: { openTicket },
  events: {
    'ticket.created': defineEvent({
      inputSchema: z.object({ project: z.string() }),
      payloadSchema: ticket,
      match: (args, data) => data.project === args.project,
    }),
  },
  eventsOptions: {
    webhook: { ttl: { defaultMs: 30 * 60_000 } },
  },
})
```

The server only accepts webhook subscriptions from authenticated callers over HTTP, because it identifies each subscription by the caller, the URL, the event name, and the arguments. `authorize` runs on each webhook subscribe and each refresh, and a denied refresh removes the subscription. Serve it with [authentication](/docs/guides/mcp-authentication-authorization). By default, callback URLs must use `https` and resolve to public addresses.

On the client, set `webhook.url` and mount `mcp.events.handleWebhook()` on that route. The handler verifies each request's signature, answers the server's verification challenge, and routes occurrences to the matching subscription:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { registerApiRoute } from '@mastra/core/server'
import { MCPClient } from '@mastra/mcp'

export const mcp = new MCPClient({
  servers: {
    tickets: {
      url: new URL('https://tickets.example.com/mcp'),
      requestInit: { headers: { Authorization: `Bearer ${process.env.TICKETS_MCP_TOKEN}` } },
    },
  },
  webhook: { url: 'https://agent.example.com/mcp/webhook' },
})

export const mastra = new Mastra({
  server: {
    apiRoutes: [
      registerApiRoute('/mcp/webhook', {
        method: 'POST',
        // Deliveries are authenticated by their signature, not by Mastra auth
        requiresAuth: false,
        handler: c => mcp.events.handleWebhook(c.req.raw),
      }),
    ],
  },
})
```

Subscribe and iterate the same way as with the other modes. `subscription.mode` is `'webhook'`. Subscriptions with the same event name and arguments share one server-side subscription, and each still receives every occurrence. The client refreshes the subscription before it expires and updates `subscription.deliveryStatus` with the server's report. When the server reports failing deliveries, for example because your endpoint timed out, `onError` receives `MCP_EVENTS_WEBHOOK_DELIVERY_FAILING`. Cancelling sends `events/unsubscribe`.

The `cursor` in each webhook delivery only covers occurrences your endpoint has already acknowledged. Resuming from a saved cursor can deliver the last handled occurrence again, so drop repeats by `eventId`.

Visit the [`MCPServer` webhook reference](/reference/tools/mcp-server#webhook-delivery) and the [`MCPClient` webhook reference](/reference/tools/mcp-client#webhook-delivery) for every option.

## Start an agent run per occurrence

To let an agent react to events, start one run for each occurrence. The occurrence data comes from the server, so pass it to the agent as data rather than as instructions:

```typescript title="src/mcp/triage.ts"
import { Agent } from '@mastra/core/agent'

const triage = new Agent({
  id: 'triage',
  name: 'Triage',
  instructions: 'You triage support tickets. Reply with a priority and one sentence of reasoning.',
  model: 'openai/gpt-5-mini',
})

const subscription = await mcp.events.subscribe('tickets', 'ticket.created', { project: 'web' })

for await (const event of subscription) {
  const result = await triage.generate(`Triage this ticket:\n${JSON.stringify(event.data)}`)
  console.log(event.eventId, result.text)
  if (subscription.cursor) await saveCursor('tickets:web', subscription.cursor)
}
```

The loop handles one occurrence at a time. A slow run delays the next one. When occurrences are independent and order doesn't matter, you can start runs without awaiting them. Then save the cursor only once every earlier run has finished. Otherwise a crash loses the occurrences whose runs were still going.

With push or webhook delivery, the client buffers occurrences your loop hasn't read yet. A loop that falls more than `maxBufferedEvents` (1000 by default) behind loses the oldest unread occurrences. The client reports `MCP_EVENTS_BUFFER_OVERFLOW` to `onError` and marks the next occurrence `truncated`. Visit the [`events` reference](/reference/tools/mcp-client#events-property-experimental) to change the limit.

The [MCP events example](https://github.com/mastra-ai/mastra/tree/main/examples/mcp-events) runs this flow end to end against a local stdio server.

To deliver occurrences to an agent's threads as notifications instead of writing your own loop, use [`MCPEventsSignalProvider`](/reference/tools/mcp-client#events-in-agents-and-workflows-experimental).

## Start a workflow run per occurrence

A subscription can start a workflow the same way. Pass the occurrence data as the workflow's `inputData`:

```typescript title="src/mcp/builds.ts"
const workflow = mastra.getWorkflow('deployWorkflow')

const subscription = await mcp.events.subscribe('ci', 'build.finished', { branch: 'main' })

for await (const event of subscription) {
  const run = await workflow.createRun()
  await run.start({ inputData: event.data })
  if (subscription.cursor) await saveCursor('ci:main', subscription.cursor)
}
```

Use the occurrence's `eventId` to detect a run you already started, because delivery is at least once.

## Limits

- **In-process emits:** Occurrences from `server.events.emit()` stay in the process that emitted them. Push streams and buffered polls only see events emitted by the same `MCPServer` instance. On serverless or multi-instance deployments, use a `poll` source backed by shared storage.
- **In-memory buffer:** The emit buffer holds the most recent occurrences per type (1000 by default, set with `bufferSize`). A restarted server treats earlier cursors as a gap and reports `truncated`.
- **No list change notifications:** The server doesn't announce changes to its event types yet, because the MCP TypeScript SDK 2.2.0 doesn't carry the events filter on `subscriptions/listen`. Call `mcp.events.list()` again to see new types.
- **Webhook subscription store:** The server keeps webhook subscriptions in memory by default. After a restart they're lost until clients refresh them. Pass a durable `store` to keep them across restarts or share them between instances. Subscriptions that never expire (`allowNoExpiry`) need a durable store.
- **Webhooks need authenticated HTTP:** The server refuses webhook subscriptions over stdio and from unauthenticated callers. A subscription that doesn't force a mode falls back to `push` or `poll`, and `onError` receives `MCP_EVENTS_WEBHOOK_UNAVAILABLE` once. Forcing `delivery: 'webhook'` rejects instead.
