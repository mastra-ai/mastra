# End-user connections

By default, connections belong to your project: every agent request uses the same Linear workspace or Slack account. End-user connections add a second kind of connection, owned by one user of your application. Each connection carries a resource ID, an opaque key you choose for that user, and the platform only serves it to requests asserting the same key.

With end-user connections, an agent resolves your project's shared connections plus the calling user's own, so "create an issue" lands in that user's Linear workspace rather than yours.

Before you start, follow the [Connect setup](/docs/mastra-platform/connect/overview#get-started) to configure your project.

## Identify your users

End-user connections require authenticated users. Configure [server auth](/docs/server/middleware#authentication) and map each authenticated user to a stable resource ID:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  server: {
    auth: {
      authenticateToken: async token => verifyToken(token),
      // The resource ID is the key end-user connections are stored under.
      // Use a stable, non-reusable identifier for the user.
      mapUserToResourceId: user => user.id,
    },
  },
})
```

The server derives the resource ID after authentication, so a client can't claim another user's key.

## Scope agent tools to the calling user

Pass `resourceId` to [`tools()`](/reference/connect/tools) inside a dynamic `tools` function. The agent then resolves global connections plus that user's connections on every call:

```typescript title="src/mastra/agents/assistant.ts"
import { Agent } from '@mastra/core/agent'
import { MASTRA_RESOURCE_ID_KEY } from '@mastra/core/request-context'
import { tools } from '@mastra/connect'

export const assistant = new Agent({
  id: 'assistant',
  name: 'assistant',
  instructions: 'You help the user manage their own tasks.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  tools: ctx =>
    tools({
      providers: ['linear'],
      resourceId: () => ctx.requestContext?.get(MASTRA_RESOURCE_ID_KEY) as string | undefined,
    }),
})
```

Calling `tools()` per request is cheap: identical options share one internal state, with snapshots cached per resource ID. When the resource ID resolves to `undefined`, the agent gets global connections only, the same behavior as before.

If both a global and a user connection exist for one provider, the agent sees both through the usual [multi-connection handling](/docs/mastra-platform/connect/tools#choose-between-connections).

## How user isolation is enforced

Scoping by an identifier is only as strong as the binding between the signed-in user and that identifier. In systems where application code passes a user ID as an ordinary parameter, isolation depends on every call site labeling every request correctly. Mastra removes that burden: the resource ID is never a value a request gets to choose, and the binding is verified again on every call.

- The server derives the resource ID. `mapUserToResourceId` runs after authentication and writes the result to a reserved request-context key that clients can't set. No route or tool accepts a resource ID from request input.
- The platform verifies it at execution time. Every call made under a resource ID carries an assertion, and the platform compares it to the connection's stored resource ID before serving tool calls, credentials, or proxy traffic. A mismatch is rejected as if the connection didn't exist, so one user's connection can never serve another user's request.
- Ownership is checked before OAuth begins. Creating a connection returns a launch URL that re-verifies the caller owns the pending session before redirecting into the provider's flow. See [the authorization link never leaves the server](#the-authorization-link-never-leaves-the-server).

The inverse is deliberate: a connection without a resource ID is global. It belongs to the project, ignores the assertion, and serves every user's requests. Only create a global connection for an account meant to be shared by everyone, such as a team Slack workspace. Anything a single user should own belongs in an end-user connection.

## Let users connect their accounts

[`userConnectRoutes()`](/reference/connect/user-connect-routes) mounts the API your frontend needs: a provider catalog, the caller's connections, connect-session creation, status polling, disconnect, and a hosted connect page. Register it on the server:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { userConnectRoutes } from '@mastra/connect'

export const mastra = new Mastra({
  server: {
    auth: {
      authenticateToken: async token => verifyToken(token),
      mapUserToResourceId: user => user.id,
    },
    apiRoutes: [
      ...userConnectRoutes({
        // Optional: override the project's provider configuration.
        // Omit to use endUserProviders from Mastra Platform.
        providers: ['linear', 'slack'],
      }),
    ],
  },
})
```

The routes do no authentication of their own. Your server's auth pipeline authenticates each request, and the routes are gated on the resource ID it derives, so a request without one gets a 401. All platform calls happen server-side with your platform token. The browser never sees it.

To start a connection, send the user to the hosted page:

```text
GET /connect/linear?returnTo=/settings/integrations
```

The page shows a Connect button, opens the provider's authorization flow in a popup, polls until the connection is active, and then redirects back to `returnTo` with `connectionId` and `status` query parameters. `returnTo` accepts relative paths only, unless you allowlist origins with `returnTo.allowedOrigins`.

The hosted page is a plain browser navigation: it carries no `Authorization` header, and the page's own status calls send only same-origin cookies. It therefore requires auth that can authenticate the request itself, such as a session cookie. `authenticateToken` receives the raw request as its second argument:

```typescript title="src/mastra/index.ts"
const auth = {
  authenticateToken: async (token: string, request: Request) => {
    // JSON routes send a bearer token.
    if (token) return verifyToken(token)
    // The hosted page sends no token: authenticate the session cookie.
    return verifySessionCookie(request.headers.get('cookie'))
  },
  mapUserToResourceId: (user: { id: string }) => user.id,
}
```

With token-only auth, the hosted page returns a 401. The JSON routes still work: call them with the bearer token and build your own UI instead.

Prefer your own UI? Call the JSON routes directly. See the [route reference](/reference/connect/user-connect-routes#routes).

### The authorization link never leaves the server

The provider's authorization link is a bearer capability: anyone who opens it can bind their third-party account to the pending connection. For end-user sessions, that link stays on the platform. Session creation returns a `launchUrl` instead: an authenticated route that re-verifies the caller owns the session before redirecting into the provider's flow. A forwarded or leaked launch URL returns 404 for anyone else, so another user can't attach their account to a session they don't own.

## Let agents prompt for a connection

Resource-scoped tool resolutions include a built-in `request_connection` tool. When a task needs a provider the user hasn't connected (or the user asks to connect one), the agent calls it and gets back a structured list of connectable providers with their current connection state. Chat UIs that understand the payload (Studio does) render it as a connect card: the user clicks Connect, authorizes in a popup through the mounted routes, and the agent can retry the task against fresh tools.

The connectable set follows your `tools()` configuration. A `providers` allowlist overrides the project's provider configuration in Mastra Platform. When you omit it, an unset project configuration exposes the full catalog, a configured list restricts providers, and an empty list disables new connections. The tool never creates sessions or handles authorization links. It only reports what can be connected. It's also never added to global-only resolutions, since there is no user to scope a new connection to. To turn it off, pass `connectPrompt: false` to [`tools()`](/reference/connect/tools).

## Inspect connections in Studio

With `userConnectRoutes()` mounted, Studio's **Connections** page shows the project's global connections alongside the connections belonging to the resource ID your studio session resolves to, and lets you run the connect flow against the providers your routes expose. Because the routes are gated on an end-user identity, the page needs `server.auth` with `mapUserToResourceId` configured. Without it, Studio shows a setup prompt instead.

## Clean up after deleted users

When you delete a user from your application, delete their connections too. Each mounted `DELETE /connect/connections/:id` call disconnects one of the caller's own connections; for offboarding, use the platform API's bulk cleanup for the user's resource ID from your backend.
