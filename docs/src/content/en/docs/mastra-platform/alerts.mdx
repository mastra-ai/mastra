# Alerts

Alerts notify your team when something in your Mastra projects needs attention. When an alert's condition is met, Mastra sends a notification to the destinations you chose, such as a Slack channel, an email group, or PagerDuty.

By the end of this page, you'll have a tested destination and an enabled alert that sends to it.

Mastra platform has two kinds of alerts. Both are managed on the same **Alerts** page and send to the same destinations.

| Kind | Watches | Examples |
| - | - | - |
| Observability alert | Traces, spans, and scores that your application sends to [Mastra Platform Observability](/docs/mastra-platform/observability/overview). Opens when a value crosses a threshold you set. | An agent fails more than 5% of its runs, a model's p95 latency goes above 8 seconds, today's spend passes a budget |
| Platform alert | Events from projects you deploy on Mastra platform, and organization usage. Opens when the event happens. | A production deploy fails, a service stops responding, usage nears a plan limit |

## Before you begin

- Use an organization admin account. Members and viewers can see alerts and destinations, but only admins can create, change, or delete them.
- Check that your plan includes alerts. On a plan without alerts, **New alert** offers **Upgrade plan**. Your plan also sets how many observability alerts can be enabled at once.
- For observability alerts, send traces to [Mastra Platform Observability](/docs/mastra-platform/observability/overview). A backtest needs recent data to show anything useful.

Open the [Mastra platform dashboard](https://projects.mastra.ai), then select **Observability** > **Alerts**. The page has three tabs:

- **Alerts**: Every alert with its state, type, and destinations.
- **Activity**: Which alerts opened and closed, and where each notification went.
- **Destinations**: Where alerts send notifications.

If **Alerts** isn't under **Observability**, your organization still uses the earlier alerts page. Open your organization settings and select **Alerts** to manage platform alerts and destinations there.

## Add a destination

A destination is a place where Mastra sends notifications. One destination can serve many alerts of either kind.

1. On the **Alerts** page, open the **Destinations** tab and select **New destination**.
1. Choose a **Type** and fill in its fields. Expand a type below to see what it needs.
1. Enter a **Name** that tells your team where the notifications go, for example `On-call team`, then select **Create destination**. Each name must be unique among destinations of the same type. For a webhook, copy the signing secret before you close the dialog. Mastra can't show it again.
1. Open the new destination and select **Send test**. Check that the message arrives.

You can also add a destination while you create an alert. Open the **Send to** list and select **New destination**.

### Create an alert from a dashboard card

On the **Metrics** page of the organization or a project, admins see a **Create alert** action, shown as a bell icon, on dashboard cards. It opens a new observability alert with the card's measure, filters, and grouping filled in. From a project, the alert applies to that project. Review the threshold and window, then continue from the backtest step.

Some cards can't become alerts, so their action is disabled. For example, the card shows every scorer instead of one, filters by labels or tags, uses a metric that alerts can't watch yet, or has filters that exclude every run. Hover over or focus the action to see the reason.

## How notifications work

When an alert's condition is met, the alert opens and Mastra sends a notification to each of its destinations. The alert stays open while the condition lasts. Once the condition clears, the alert closes and Mastra sends a **Closed** notification.

- **Observability alerts** send when they open and when they close, at most once every 15 minutes per group. Mastra doesn't send reminders while an alert stays open.
- **Platform alerts** resend according to **Repeat**. The first notification, recovery notifications, and increases in severity always send immediately. Incidents for **Usage threshold crossed** stay open, because they don't resolve on their own.

Slack messages update in place, for example when another group of the same observability alert opens. Discord and Microsoft Teams post a separate **Closed** message.

Notifications for an open observability alert let you close it by hand. Slack messages have a **Close alert** button, and emails and webhooks include a link that opens the alert's **Close alert** dialog. See [Close an open alert](#close-an-open-alert).

## Observability alert checks

Mastra checks every enabled observability alert every five minutes. Each check measures the window you chose: with **the last 1h**, each check measures the past hour. **today (since midnight)** measures from the start of the day in the timezone shown in the window's label.

Open **Advanced** in the alert form for these settings:

- **Recovers below** or **Recovers above**: A level further from the threshold, so a value that hovers near it doesn't keep opening and closing the alert. For example, an alert that opens above a 5% error rate and recovers below 2% stays open until the error rate drops to 2%.
- **Skip agents with fewer than**, or the same setting for another group such as models: For spans and traces with a separate alert for each group, a minimum number of runs per check, so an agent with one failure out of two runs doesn't open the alert.
- **Wait for late data**: A minute or two of the newest data to skip, if an alert on a short window opens and closes on its own within minutes. Keep **None** unless that happens.

Some alerts can measure each group on its own. Under **Alert for**, choose **One alert for all traffic** for one check over everything, or a separate alert for each group, such as **A separate alert for each agent**, so one failing agent isn't hidden by healthy ones. If the backtest finds a group that crossed the threshold while all traffic combined didn't, the form shows a warning with a button to switch. Mastra checks up to 50 groups, prioritizing those closest to the threshold. All groups of one alert share one incident.

An observability alert shows one of these states:

| State | Meaning |
| - | - |
| Not checked yet | The alert hasn't run its first check. |
| OK | The latest check was on the safe side of the threshold. |
| Alert open | The latest check crossed the threshold. |
| Closed | The alert was open and has since recovered, or someone closed it by hand. |
| No data | The window contained no matching data. |
| Error | The query failed, for example because it timed out. |
| Disabled | The alert is turned off and isn't checked. |

**No data** and **Error** don't send notifications. If an alert stays in either state, check its filters and whether your application sent matching data during the window.

## Platform alert events

Each platform alert watches one or more events:

| Event | Sends when |
| - | - |
| Deploy failed | A build or deploy fails to reach a running state. |
| Service crashed | A running service exhausts its restart policy and stops. |
| Service out of memory | A service is stopped after running out of memory. |
| Service unreachable | Health checks get no response from a deployed service for several minutes in a row. |
| Elevated error rate | More than 10% of requests to a deployed service return `5xx` errors over a 5-minute window. |
| Resource usage threshold crossed | An environment uses more CPU, memory, or egress over a window than the thresholds you set. |
| Usage threshold crossed | Organization usage nears or reaches a plan limit. |
| Alert rule | An observability alert in the covered projects opens or closes. Use it to route every observability alert to one place, such as an on-call PagerDuty service. |

**Resource usage threshold crossed** adds a **Usage window**, from **Last 15 minutes** to **Last 24 hours**, and thresholds for **CPU above**, **Memory above**, and **Egress above**. Enter an amount, or switch the unit to **% of monthly allowance**. Leave a metric empty to skip it. Mastra adds up each environment's usage every five minutes, about 10 minutes behind real time.

**Usage threshold crossed** covers the whole organization, so it can't be combined with other events or limited to projects. Choose a **Meter**, such as **Usage credits**, or **Any meter**. Under **Sends when**, choose **Near or at the limit** or **At the limit**.

## Close an open alert

Close an observability alert by hand when you know about the problem and don't want it to stay open, for example while a fix rolls out. Only organization admins can close an alert.

1. Open the alert from the **Alerts** tab. The page shows **Close alert** when at least one group of the alert is open.
1. Select **Close alert**, then confirm.

The alert closes on the next check, and the **Closed** notification shows who closed it. It stays closed until a check finds the value back on the safe side of the threshold, or past the recovery level if you set one. After that, it can open again.

You can also close the alert from its notifications. In Slack, select **Close alert** on the message. Slack matches your account to a Mastra user by email, so this works only for admins in your Mastra organization. In an email or a webhook, follow the close link to the alert's page.

## Manage alerts and destinations

Open an alert from the **Alerts** tab to see its state, settings, and notification history. On the alert's page:

- Use the switch next to the alert's name to turn it off or on.
- Select **Edit** to change the alert, then select **Save changes**.
- Select **Edit** > **Delete alert** to delete it. Its past incidents stay on the **Activity** tab.

Inside a project, the **Alerts** page shows that project's alerts plus the organization's alerts that apply to all projects. Edit an alert that applies to all projects from the organization's **Alerts** page.

Open a destination from the **Destinations** tab to see its deliveries and the alerts it serves. On the destination's page:

- Turn off the switch next to its name to pause it. Alerts skip a paused destination until you turn it back on.
- Select **Send test**, or select **Edit** to change its name or settings.
- Select **More actions** > **Rotate secret** to replace a webhook's signing secret. The new secret takes effect immediately, so update your endpoint first.
- Select **More actions** > **Remove** to delete the destination.

On the organization's **Destinations** tab, **Slack workspaces** lists each connected workspace and how many destinations use it. To disconnect a workspace, select **Disconnect**. Remove the destinations that use it first.

When the last two deliveries to a destination fail, its page shows a **Failing** badge and the error. Select **Fix it** to edit the destination.

## Review alert activity

The **Activity** tab shows each time an alert opened or closed, from the last 24 hours to the last 30 days. Use **Filter activity** to narrow the list by alert, event, destination, or delivery status.

| Delivery status | Meaning |
| - | - |
| Scheduled | Queued to send. |
| Sent | The destination accepted the notification. |
| Suppressed | Not sent, because a matching notification went out recently. |
| Retrying | The last attempt failed, and Mastra is trying again. |
| Exhausted | Every retry failed. The notification wasn't delivered. |
| Config error | The destination rejected the notification because its settings are wrong. Edit the destination to fix it. |
| Replayed | A failed delivery that was sent again. |

## Receive webhook notifications

A webhook [alert destination](#add-a-destination) receives an HTTP `POST` request with a JSON body each time an alert sends a notification. Mastra shows the destination's signing secret once, after you create it.

### Webhook payload

The following example shows a failed deploy:

```json
{
  "id": "deploy.failed:dep_8c2f1a:triggered",
  "version": "2026-09-01",
  "type": "deploy.failed",
  "createdAt": "2026-09-24T14:03:11.000Z",
  "fingerprint": "deploy.failed|prj_41d9e2|server|production",
  "severity": "error",
  "status": "triggered",
  "summary": "Deploy failed on support-agent (production): Build failed",
  "source": "mastra",
  "data": {
    "deployId": "dep_8c2f1a",
    "projectName": "support-agent",
    "gitBranch": "main",
    "error": "Build failed",
    "errorCode": "BUILD_FAILED",
    "errorCategory": "build",
    "deployUrl": "https://projects.mastra.ai/..."
  },
  "links": []
}
```

| Field | Description |
| - | - |
| `id` | Notification ID. Stays the same when Mastra retries the same notification |
| `version` | Payload version. The current version is `2026-09-01` |
| `type` | Event type. See [Event types](#alert-event-types) |
| `createdAt` | ISO 8601 time when the event occurred |
| `fingerprint` | Identifies the incident the notification belongs to. Notifications for the same failing deploy target or service share a fingerprint |
| `severity` | `critical`, `error`, `warning`, or `info`. These values match PagerDuty severities |
| `status` | `triggered` for a new or repeated notification, `resolved` when the incident recovers |
| `summary` | One-line description of the event |
| `source` | Always `mastra` |
| `data` | Event-specific details. Fields vary by event type |
| `links` | Related links, each with `href` and `text`. Can be empty. For an open observability alert, includes a link to close it in Mastra platform |

### Alert event types

The `type` field has one of these values:

| Type | Trigger | Common `data` fields |
| - | - | - |
| `deploy.failed` | **Deploy failed** | `deployId`, `projectName`, `gitBranch`, `error`, `errorCode`, `errorCategory`, `deployUrl` |
| `service.crashed` | **Service crashed** | Same as `deploy.failed` |
| `service.oom` | **Service out of memory** | Same as `deploy.failed` |
| `service.unreachable` | **Service unreachable** | `projectName`, `probeUrl`, `error`, `consecutiveFailures` |
| `service.error_rate` | **Elevated error rate** | `requests`, `errors5xx`, `ratePct`, `windowMinutes`, `environmentSlug`, `error` |
| `service.resource_usage` | **Resource usage threshold crossed** | `projectName`, `policyName`, `metric`, `unit`, `usage`, `limit`, `thresholdKind`, `thresholdValue`, `windowMinutes`, `error` |
| `billing.usage_threshold` | **Usage threshold crossed** | `featureId`, `featureLabel`, `thresholdDisplay`, `error` |
| `observability.rule` | An [observability alert](#create-an-alert) opens or closes | `ruleId`, `ruleName`, `ruleUrl`, `value`, `threshold`, `summary`, `groups`, `firingCount`, and `closedBy` when someone closed the alert by hand |

Crash, out-of-memory, and unreachable events for the same service share a fingerprint, so one outage produces one incident. Usage threshold incidents don't send a `resolved` notification.

Test notifications use `type: "deploy.failed"`, `severity: "info"`, and include `"test": true` in `data`.

### Request headers

| Header | Value |
| - | - |
| `content-type` | `application/json` |
| `user-agent` | `Mastra-Alerts/1.0` |
| `x-mastra-signature` | Signature of the request body. See [Verify webhook signatures](#verify-webhook-signatures) |
| `x-mastra-idempotency-key` | Same value as the payload `id` |

### Verify webhook signatures

Verify the signature before you trust a request. The `x-mastra-signature` header has this format:

```text
t=1790258591,v1=5f0c9d3e...
```

`t` is the Unix time in seconds when Mastra signed the request. `v1` is a hex-encoded HMAC-SHA256 of the string `<t>.<raw request body>`, using the destination's signing secret as the key.

To verify a request:

1. Read the raw request body before parsing it as JSON. Parsing and serializing the body again can change it.
1. Compute the HMAC of `<t>.<raw body>` and compare it with `v1` using a constant-time comparison.
1. Reject requests where `t` is more than a few minutes old to prevent replayed requests.

<Tabs>
  <TabItem value="node" label="Node.js">
    ```typescript title="verify-mastra-signature.ts"
    import { createHmac, timingSafeEqual } from 'node:crypto'

    const TOLERANCE_SECONDS = 300

    export function verifyMastraSignature(
      rawBody: string,
      signatureHeader: string,
      signingSecret: string,
    ): boolean {
      const parts = new Map(signatureHeader.split(',').map(part => part.split('=') as [string, string]))
      const timestamp = Number(parts.get('t'))
      const signature = parts.get('v1')
      if (!Number.isInteger(timestamp) || !signature || !/^[0-9a-f]{64}$/.test(signature)) return false
      if (Math.abs(Date.now() / 1000 - timestamp) > TOLERANCE_SECONDS) return false

      const expected = createHmac('sha256', signingSecret)
        .update(`${timestamp}.${rawBody}`)
        .digest('hex')
      const expectedBytes = Buffer.from(expected, 'hex')
      const signatureBytes = Buffer.from(signature, 'hex')
      return (
        expectedBytes.length === signatureBytes.length && timingSafeEqual(expectedBytes, signatureBytes)
      )
    }
    ```
  </TabItem>

  <TabItem value="python" label="Python">
    ```python title="verify_mastra_signature.py"
    import hashlib
    import hmac
    import time

    TOLERANCE_SECONDS = 300


    def verify_mastra_signature(raw_body: bytes, signature_header: str, signing_secret: str) -> bool:
        parts = dict(part.partition("=")[::2] for part in signature_header.split(","))
        try:
            timestamp = int(parts["t"])
            signature = parts["v1"]
        except (KeyError, ValueError):
            return False
        if abs(time.time() - timestamp) > TOLERANCE_SECONDS:
            return False

        expected = hmac.new(
            signing_secret.encode(),
            f"{timestamp}.".encode() + raw_body,
            hashlib.sha256,
        ).hexdigest()
        return hmac.compare_digest(expected, signature)
    ```
  </TabItem>
</Tabs>

Return a `401` status for a request that fails verification. After you rotate a destination's secret, requests are signed with the new secret immediately.

### Retries and duplicates

Mastra treats any `2xx` response as delivered and doesn't retry it. Persist or durably enqueue the notification before responding, and return a `5xx` response if that step fails so Mastra retries the delivery. Respond within 10 seconds and process the notification after responding if the work takes longer. Mastra doesn't follow redirects.

When a request fails, Mastra retries based on the response:

- **`4xx` response:** Mastra stops and marks the delivery **Config error**. Fix the endpoint, then open the destination and select **Send test** to confirm it works.
- **`5xx` response, timeout, or network error:** Mastra retries twice within a few seconds. If those requests also fail, the delivery shows **Retrying** and Mastra tries again after about 30 seconds, doubling the wait each time up to 15 minutes. After 6 failed attempts, the delivery shows **Exhausted**.

Discord, Microsoft Teams, PagerDuty, and incident.io destinations follow the same schedule. For those destinations, Mastra also retries `408` and `429` responses.

Retries can deliver the same notification more than once. Store the `x-mastra-idempotency-key` value of each processed request and skip requests with a key you've already seen. Use `fingerprint` to group notifications that belong to the same incident.

### PagerDuty and incident.io fields

PagerDuty and incident.io destinations receive the same event, mapped to each service's format. Changes made in those services, such as acknowledging an incident, don't update the Mastra incident.

| PagerDuty field | Value |
| - | - |
| `event_action` | `trigger` for a new or repeated notification, `resolve` for a recovery |
| `dedup_key` | The Mastra incident ID |
| `payload.summary` | The `summary` field |
| `payload.severity` | The `severity` field |
| `payload.source` | `mastra:<project>/<environment>` |
| `payload.custom_details` | The `data` field |

| incident.io field | Value |
| - | - |
| `status` | `firing` for a new or repeated notification, `resolved` for a recovery |
| `deduplication_key` | The Mastra incident ID |
| `title` | The `summary` field |
| `description` | The error message, when the event has one |
| `metadata` | The `data` field plus `source`, `event_type`, `severity`, `project_id`, and `environment` |
