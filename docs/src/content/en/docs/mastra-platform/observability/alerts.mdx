# Observability Alerts

An observability alert checks the data your Mastra application sends to [Mastra Platform Observability](/docs/mastra-platform/observability/overview) and notifies your team when a value crosses a threshold. For example, an alert can fire when an agent fails more than 5% of its runs, a model's p95 latency goes above 8 seconds, or today's spend passes a budget.

By the end of this page, you'll have an enabled alert, a preview of how often it would have fired, and a page that shows its current state.

Observability alerts are different from [platform alerts](/docs/mastra-platform/alerts), which react to deploy, service, and usage events. Both kinds are listed on the same **Alerts** page and send notifications to the same destinations.

## Before you begin

- Send traces to Mastra Platform Observability. Follow [Observability on Mastra platform](/docs/mastra-platform/observability/overview) if your project doesn't send data yet. A backtest needs recent data to show anything useful.
- Use an organization admin account. Members and viewers can see alerts, but only admins can create, edit, enable, or delete them.
- Check that your plan includes alerts. On a plan without alerts, **New alert** offers **Upgrade plan** instead of observability alerts.
- Add a [destination](/docs/mastra-platform/alerts#add-a-destination), such as a Slack channel or email group, to receive notifications. You can add one on the **Destinations** tab of the **Alerts** page, or while you create the alert.

If **Alerts** doesn't appear under **Observability** in the sidebar, observability alerts aren't available for your organization yet.

## Create an alert

<Steps>
  <StepItem>
    Open the [Mastra platform dashboard](https://projects.mastra.ai) without selecting a project, then select **Observability** > **Alerts**. The **Alerts** tab lists every alert in the organization.
  </StepItem>

  <StepItem>
    Select **New alert** > **Observability alert**, then choose a template such as **Agent error rate** or **Daily cost budget**. Select **Blank** to write your own query and condition instead.
  </StepItem>

  <StepItem>
    Enter a **Name**. Use **Description** to explain what the alert means and how to respond, for example with a link to a runbook.
  </StepItem>

  <StepItem>
    Under **What to watch**, choose what the alert covers under **Applies to**: **All projects** or one project. An alert that applies to all projects reads the projects in one region, which you choose under **Region** if the field is shown. You can't change **Applies to** after you create the alert.
  </StepItem>

  <StepItem>
    Under **Watch**, choose **Spans**, **Traces**, or **Scores**, then choose a **Metric** and, when offered, a **Statistic**, such as an error rate or a p95 duration. Add filters to narrow the data, for example to one agent.
  </StepItem>

  <StepItem>
    Under **When it fires**, choose a comparison (**above**, **at or above**, **below**, or **at or below**) and enter a threshold. Under **Over**, choose a window, such as **the last 15m** or **today (since midnight)**.
  </StepItem>

  <StepItem>
    Review the **Backtest** chart. It replays the alert against past data, over the last 6 hours, 1 day, or 2 days where the rule allows it, and draws the value against the threshold. Adjust the threshold or window until the alert would fire only when you'd want someone to act.

    The backtest uses past data only. It doesn't send notifications or prove that a destination works.
  </StepItem>

  <StepItem>
    Under **Notify**, choose one or more destinations in **Send to**. Leave **Enabled** on.
  </StepItem>

  <StepItem>
    Select **Create alert**. Mastra opens the alert's page.
  </StepItem>

  <StepItem>
    Check the result. The alert's state starts as **Not checked yet**. Within about five minutes, it changes to **OK**, **Firing**, **No data**, or **Error**. The alert's page also shows the backtest chart over recent data.
  </StepItem>
</Steps>

To confirm that notifications reach your team, open the **Destinations** tab on the **Alerts** page, select a destination, then select **Send test**.

## How alerts work

These sections explain how Mastra checks alerts, decides when they fire and recover, and sends notifications.

### Understand checks and windows

Mastra checks every enabled alert every five minutes. Each check measures the window you chose. An alert with the window **the last 1h** checks every five minutes and each check measures the past hour of data. The window **today (since midnight)** measures from the start of the current day. The window's label shows which timezone the day starts in.

If an alert fires on a short window and the value settles once late data arrives, open **Advanced** and set **Ingest delay** to a minute or two so each check skips that much of the newest data. Most alerts work without a delay.

### Set a recovery level

By default, an alert recovers as soon as the value is back on the safe side of the threshold. A value that hovers near the threshold can then keep switching between firing and recovered.

Open **Advanced** and enter a number in **Recovers below** to set a level further from the threshold. For an alert that fires when a value drops too low, the field is **Recovers above**. For example, an alert that fires above a 5% error rate and recovers below 2% stays firing until the error rate drops to 2%.

### Alert for each group

Some alerts can measure all matching data together or each group on its own. Choose under **Alert for**:

- **All traffic combined**: One check covers everything that matches. The alert fires once.
- **Each \<group>**: For example, **Each agent**, **Each model**, or **Each user**. Each group is checked on its own, so one failing agent isn't hidden by healthy ones, and the alert names the group that fired.

Mastra checks up to 50 groups, prioritizing the groups closest to firing. If more groups match, the alert's page says that only the top 50 groups were checked. For spans and traces, open **Advanced** and set **Skip groups with fewer than** so a group with only a few runs, such as one failure out of two runs, doesn't fire the alert.

All groups of one alert share one incident. When another group starts firing, Slack destinations update the existing message to list it. Other destinations aren't notified again until the incident recovers.

### Understand notifications

Each destination gets a message when the alert fires and when it recovers, at most once every 15 minutes per group. Mastra doesn't send reminders while an alert keeps firing.

The **Activity** tab on the **Alerts** page shows incidents and their delivery attempts.

### Understand alert states

The **Alerts** page and each alert's page show one of these states:

| State | Meaning |
| - | - |
| **Not checked yet** | The alert hasn't run its first check. |
| **OK** | The latest check was on the safe side of the threshold. |
| **Firing** | The latest check crossed the threshold. |
| **Resolved** | The alert fired and has since recovered. |
| **No data** | The window contained no matching data. |
| **Error** | The query failed, for example because it timed out. |
| **Disabled** | The alert is turned off and isn't checked. |

Only firing and recovery send notifications. **No data** and **Error** are shown on the alert's page. Alerts created through the API can instead treat missing data as firing and notify. Their page then shows a **When there is no data** setting. If an alert stays in either state, check its filters and whether your application sent matching data during the window.

## Manage alerts

Open an alert from the **Alerts** tab. Use the **Enabled** switch on the alert's page to pause or resume it. Select **Edit** to change the alert, then select **Save changes**. To remove an alert, select **Edit** > **Delete alert**, then confirm.

When you open **Alerts** inside a project, the page shows that project's alerts plus the organization's alerts that apply to all projects. Edit an alert that applies to all projects from the organization's **Alerts** page.

## Create an alert from a dashboard card

On the **Metrics** page of the organization or a project, admins see a **Create alert** action, shown as a bell icon, on dashboard cards. Selecting it opens a new alert with the card's measure, filters, and grouping already filled in. From a project, the alert applies to that project. Review the threshold and window, then continue from the backtest step.

Some cards can't become alerts, so their action is disabled. For example, the card shows every scorer instead of one, filters by labels or tags, uses a metric that alerts can't watch yet, or has filters that exclude every run. Hover over or focus the action to see the reason. See [Build custom dashboards](/docs/mastra-platform/observability/dashboards) for dashboard setup.
