# LSP inspection

LSP inspection gives workspace-backed agents semantic code intelligence. When you enable LSP on a workspace, agents can inspect symbols in supported files to retrieve hover information and jump to definitions. They can also find implementations.

## When to use LSP inspection

Use LSP inspection when your agent needs semantic code understanding instead of plain-text search alone:

- Inspect symbols and their inferred types in any supported language
- Find where a symbol is declared before editing related code
- Explore implementations across a codebase without manually tracing every file
- Combine semantic inspection with `read_file` and `grep` for faster navigation
- Add LSP support for additional languages by [registering custom language servers](#custom-language-servers)

## Quickstart

Install the protocol packages and a language server. This example uses the TypeScript language server:

```bash npm2yarn
npm install vscode-jsonrpc vscode-languageserver-protocol typescript typescript-language-server
```

Enable LSP on a workspace by setting `lsp: true`:

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

const workspace = new Workspace({
  filesystem: new LocalFilesystem({ basePath: './workspace' }),
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  lsp: true,
})
```

LSP requires a static sandbox whose process manager provides streamed output and writable input because each language server is a long-lived, bidirectional process. `LocalFilesystem` and `LocalSandbox` use the same physical directory in this example, so the language server and file tools inspect the same files.

## Agent tool

When LSP is enabled, the workspace exposes `mastra_workspace_lsp_inspect` by default.

```json
{
  "path": "/absolute/path/to/file.ts",
  "line": 10,
  "match": "const foo = <<<bar()"
}
```

The `match` field must include exactly one `<<<` cursor marker. The marker identifies the symbol position on the specified line.

The tool returns up to four result groups:

| Result | Description |
| - | - |
| `hover` | Type information or documentation for the symbol at the cursor |
| `diagnostics` | Line-scoped LSP diagnostics for the inspected line, when present |
| `definition` | Declaration locations with a one-line preview |
| `implementation` | Implementation locations returned by the language server |

## Tool name remapping

Use `WORKSPACE_TOOLS.LSP.LSP_INSPECT` to configure the inspection tool. Set `enabled: false` to remove it from the agent's toolset, or set `name` if the agent expects a different name:

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalFilesystem, LocalSandbox, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  filesystem: new LocalFilesystem({ basePath: './workspace' }),
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  lsp: true,
  tools: {
    [WORKSPACE_TOOLS.LSP.LSP_INSPECT]: {
      name: 'lsp_inspect',
    },
  },
})
```

This changes the exposed tool name only. The configuration key stays `WORKSPACE_TOOLS.LSP.LSP_INSPECT`.

See [`WorkspaceToolsConfig`](/reference/workspace/workspace-class#tool-configuration) for approval settings, dynamic policies, output limits, and hooks shared by workspace tools.

## LSP configuration

Set `lsp` to `true` for default behavior, or provide an object to customize server startup and diagnostics:

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

const projectPath = process.env.PROJECT_PATH!

const workspace = new Workspace({
  filesystem: new LocalFilesystem({ basePath: projectPath }),
  sandbox: new LocalSandbox({ workingDirectory: projectPath }),
  lsp: {
    root: projectPath,
    diagnosticTimeout: 4000,
    initTimeout: 8000,
    maxOpenClients: 4,
    disableServers: ['eslint'],
    binaryOverrides: {
      typescript: '/custom/path/to/typescript-language-server --stdio',
    },
    searchPaths: ['/opt/mastra-tools'],
  },
})
```

Use custom configuration when you need to:

- Increase timeouts for large repositories
- Limit retained language server processes
- Disable specific language servers
- Point Mastra at custom language server binaries
- Add package roots whose `node_modules` contain language-server binaries or modules

### Limit retained clients

Set `maxOpenClients` to a positive integer to limit the language server clients retained by a workspace. When the limit is reached, the workspace closes the least recently used client that has no active query lease. If every retained client is active, the next acquisition waits up to five seconds for a lease to be released. If no lease becomes available, `prepareQuery()` and `getDiagnostics()` return `null`, while `getDiagnosticsMulti()` omits the unavailable server.

Workspaces retain an unlimited number of clients when `maxOpenClients` is omitted. Mastra Code sets `maxOpenClients` to `4` by default.

### Release prepared queries

When you call `prepareQuery()` directly, close the file before releasing the client lease. Use a `finally` block so the client can be evicted even if the query fails:

```typescript
const query = await workspace.lsp?.prepareQuery(filePath)

if (query) {
  try {
    const hover = await query.client.queryHover(query.uri, position)
  } finally {
    query.client.notifyClose(filePath)
    query.release()
  }
}
```

During workspace teardown, Mastra waits up to five seconds for active leases to be released before it forces language server shutdown.

## Custom language servers

By default, Mastra includes built-in support for TypeScript, JavaScript, Python, Go, and Rust. To use LSP inspection with other languages (e.g. PHP, Ruby, Java, Kotlin, Swift, Elixir), register a custom language server via the `servers` field:

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

const workspace = new Workspace({
  filesystem: new LocalFilesystem({ basePath: './workspace' }),
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  lsp: {
    servers: {
      phpactor: {
        id: 'phpactor',
        name: 'Phpactor Language Server',
        languageIds: ['php'],
        extensions: ['.php'],
        markers: ['composer.json'],
        command: 'phpactor language-server',
      },
    },
  },
})
```

Each custom server definition requires these fields:

| Field | Description |
| - | - |
| `id` | Unique identifier for the server |
| `name` | Human-readable name shown in logs |
| `languageIds` | Language Server Protocol (LSP) language identifiers this server handles |
| `extensions` | File extensions, including the dot |
| `markers` | Files or directories that identify the project root (e.g. `composer.json`, `Gemfile`) |
| `command` | Full command string to start the server |

When a server has multiple language IDs, Mastra maps each extension to the first entry in `languageIds`.

You can also pass optional `initializationOptions` to send custom settings during the LSP handshake.

Custom servers are merged with built-in servers. To replace a built-in server, use the same `id` (e.g. `id: 'go'` replaces the built-in Go server). Register multiple servers to support several languages at once:

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

const workspace = new Workspace({
  filesystem: new LocalFilesystem({ basePath: './workspace' }),
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  lsp: {
    servers: {
      phpactor: {
        id: 'phpactor',
        name: 'Phpactor Language Server',
        languageIds: ['php'],
        extensions: ['.php'],
        markers: ['composer.json'],
        command: 'phpactor language-server',
      },
      solargraph: {
        id: 'solargraph',
        name: 'Solargraph',
        languageIds: ['ruby'],
        extensions: ['.rb', '.erb'],
        markers: ['Gemfile'],
        command: 'solargraph stdio',
      },
    },
  },
})
```

## Requirements and limitations

- Configure a static sandbox whose process handles expose readable output and writable input streams. A filesystem alone can't run a language server, resolver-backed sandboxes aren't supported with LSP, and some remote process managers don't provide the required bidirectional streams.
- Install `vscode-jsonrpc` and `vscode-languageserver-protocol` in the Mastra application. Mastra disables LSP during workspace construction when these host-side protocol packages aren't available.
- Ensure the project files and language-server process use the same paths. `lsp.root` must be an absolute path available to the process manager.
- Install the required language-server binary and runtime in the environment where the sandbox process runs. Built-in discovery checks the project, configured `searchPaths`, and the Mastra host environment before using `packageRunner`.
- LSP inspection only works for file types with a matching built-in or custom language server.
- `LocalFilesystem` containment and `allowedPaths` don't constrain LSP inspection. Restrict `lsp.root` to a trusted project and don't expose LSP tools where users can supply untrusted host paths.
- External package inspection may resolve to declaration files such as `.d.ts` instead of runtime source files.
- `lsp_inspect` complements `read_file` and `grep`, but doesn't replace reading implementation code when you need full context.

### Remote sandboxes

Remote LSP isn't backend-transparent in the current Workspace implementation. The language-server command runs through the remote sandbox process manager, but binary discovery and some source previews still use the Mastra host. A language-server binary installed only on the host can't run in the remote sandbox, while files available only in the remote sandbox can't provide every host-side preview.

Use remote LSP only when the process manager supplies readable and writable streams, the project has matching absolute paths on both the Mastra host and remote sandbox, and `binaryOverrides` names a command installed in the remote image. A local filesystem and remote sandbox don't synchronize automatically. For remote-only projects, use `grep`, indexed search, and sandbox commands until backend-transparent LSP file access is supported.
