# PubSub

Mastra uses a publish/subscribe (pub/sub) system as its internal event bus. Components publish events to topics, and other components subscribe to those topics to react. The backend determines whether events are delivered within a single process, between processes on one host, or across separate instances.

Set the backend once on the `Mastra` instance for use throughout the system. The default is an in-process backend that requires no setup.

## How Mastra uses PubSub

Several built-in systems publish and subscribe to events through the same pub/sub bus:

- **Workflow execution**: The scheduler publishes a `workflow.start` event, and a long-lived worker consumes it to run the workflow. Step and lifecycle events flow over pub/sub during execution.
- **Scheduled workflows**: The scheduler dispatches due runs by publishing to the workflow topic. See [Scheduled workflows](/docs/workflows/scheduled-workflows).
- **Background tasks**: A task manager dispatches work to a worker group and fans task lifecycle updates out to subscribers, which is how background task streams stay live. See [Background task streaming](/docs/harness/background-tasks#subscribe-to-all-task-events).
- **Agent signals**: Sending a signal to an active agent run publishes an event on a thread topic, so a run executing in another process receives the signal.
- **Resumable streams**: Stream chunks are published per run, so a client that reconnects can replay what it missed.

Because these systems run on one bus, the backend you choose applies to all of them at once.

## Delivery modes

Backends deliver events in one of two modes, defined by the [`PubSub`](/reference/pubsub/base) contract:

- **Pull**: Consumers read from the backend on their own, which Mastra does with a long-lived worker loop. Distributed backends such as [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) use this mode.
- **Push**: Events arrive without the consumer asking, either in process or over HTTP. The default [`EventEmitterPubSub`](/reference/pubsub/event-emitter) delivers this way in process.

Subscribers can also distribute work through consumer groups. Members of the same group split the events so each event is handled once. A subscriber without a group receives every event, which fans the stream out to all ungrouped subscribers.

## Default backend

When you don't set the `pubsub` option, Mastra uses [`EventEmitterPubSub`](/reference/pubsub/event-emitter). It delivers events in process using a Node.js [`EventEmitter`](https://nodejs.org/api/events.html#class-eventemitter), so it works without any external service.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

// No pubsub option: Mastra uses EventEmitterPubSub
export const mastra = new Mastra({})
```

Because it runs in process, events aren't persisted and don't reach other processes. The default suits a single instance, which covers most applications.

## Choosing a backend

Set the `pubsub` option on the `Mastra` instance to choose a backend. Each backend implements the same [`PubSub`](/reference/pubsub/base) contract, so the rest of your application doesn't change.

The deciding questions are where the subscriber runs and whether [evented workflows and agents](#evented-workflows-and-agents) run on more than one process.

| Backend | Scope | Evented runs on several processes | Mode | Package |
| - | - | - | - | - |
| [`EventEmitterPubSub`](/reference/pubsub/event-emitter) | Single process | No | Pull and push | `@mastra/core` |
| [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) | Multiple processes, one host | No | Push | `@mastra/core` |
| [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) | Distributed, multiple hosts | Yes | Pull | `@mastra/redis-streams` |
| [`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams) | Distributed, multiple hosts | Yes | Pull | `@mastra/valkey-streams` |
| [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub) | Distributed, multiple hosts | Yes | Pull | `@mastra/google-cloud-pubsub` |

### Multiple processes on one host

Use [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) when several processes on the same machine need to share streams and signals. It delivers events over a Unix domain socket and elects one process as a broker. If the broker exits, the remaining processes elect a new one. It doesn't redeliver the events a stopped process held, so it isn't a backend for evented workflows or agents that run on several processes.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { UnixSocketPubSub } from '@mastra/core/events'

export const mastra = new Mastra({
  pubsub: new UnixSocketPubSub('/tmp/mastra/events.sock'),
})
```

### Distributed deployments

Use a distributed backend when you run more than one instance or host, and every instance receives the same events. This matters whenever a request handled by one instance must reach work running on another.

For example, sending a signal to an agent run requires the signal event to cross the process boundary to the instance that owns the run. With the in-process default, that instance never receives the event.

[Durable agent](/docs/harness/durable-agents#run-ownership) crash recovery also depends on the backend when the storage adapter doesn't support run fencing. Recovery then uses the backend's leases to tell whether another instance still drives a run. `RedisStreamsPubSub` provides leases across hosts. `GoogleCloudPubSub` doesn't.

Both backends below deliver across processes and hosts and persist events for redelivery.

The following example uses [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/):

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    url: 'redis://localhost:6379',
  }),
})
```

The following example uses [Google Cloud Pub/Sub](https://cloud.google.com/pubsub/docs):

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { GoogleCloudPubSub } from '@mastra/google-cloud-pubsub'

export const mastra = new Mastra({
  pubsub: new GoogleCloudPubSub({
    projectId: 'my-project',
  }),
})
```

## Evented workflows and agents

Workflows on the [evented execution engine](/docs/workflows/scheduled-workflows#execution-engine) and agents using [evented durable execution](/docs/harness/durable-agents#execution-variants) advance a run one event at a time. Any worker can take the next event, which lets several processes share one run. That only holds when the deployment has both of the following:

- **A PubSub backend that redelivers unacknowledged events**: When a worker stops in the middle of a step, the backend gives the step's event to another worker.
- **A storage adapter with workflow step guards**: The backend can deliver the same event more than once, and the step guard keeps a later delivery from saving the step's result a second time. A step can still run more than once, so [make steps with side effects idempotent](/docs/workflows/overview#restarting-active-workflow-runs).

The backends that redeliver are marked **Yes** in the [Choosing a backend](#choosing-a-backend) table. A backend's reference page says whether redelivery can be turned off. The storage adapters with workflow step guards are `@mastra/pg` and `@mastra/libsql`. With `@mastra/libsql`, see [evented agent worker takeover](/reference/pubsub/redis-streams#evented-agent-worker-takeover) for the database setups that work across machines.

[`EventEmitterPubSub`](/reference/pubsub/event-emitter) and [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) don't redeliver an event that a stopped process received and never acknowledged. On the default `EventEmitterPubSub`, evented workflows and agents run in one process, which is how you try the evented engine locally and run it in tests. Don't use either backend to run evented workflows or agents on several processes:

- `EventEmitterPubSub` delivers inside one process. An event never reaches another instance, and each instance that boots restarts the active evented workflow runs of the others.
- `UnixSocketPubSub` reaches the other processes on the host, but no other process picks up the step of a process that stopped, and each process that boots restarts the active evented workflow runs of the others.

### Warning for unsupported setups

Mastra logs a warning the first time an evented run is created in a setup that can't support several processes:

- The PubSub backend delivers to other processes and doesn't redeliver unacknowledged events.
- The PubSub backend redelivers unacknowledged events and the storage adapter has no workflow step guards.

The default `EventEmitterPubSub` doesn't trigger the warning, because its events never leave the process. `UnixSocketPubSub` triggers it even when one process uses the socket, because Mastra can't tell how many processes share it.

If you see the warning with your own [`PubSub`](/reference/pubsub/base) implementation, override the properties that describe its transport. Mastra reads them instead of checking which class the backend is:

```typescript title="src/mastra/pubsub.ts"
import { PubSub } from '@mastra/core/events'

export class MyBrokerPubSub extends PubSub {
  // The broker hands an unacknowledged event to another consumer in the group.
  override get redeliversUnacked(): boolean {
    return true
  }

  // publish(), subscribe(), unsubscribe(), flush()
}
```

Return `true` from `redeliversUnacked` only when the broker redelivers an abandoned event to another consumer of the same group, and only after 30 seconds or more. If your implementation delivers only inside the publishing process, return `false` from `deliversAcrossProcesses` instead. See the [`PubSub` properties](/reference/pubsub/base#properties).

To disable the warning for a setup that one process uses, set the `MASTRA_DISABLE_EVENTED_SETUP_WARNING` environment variable to `true`.

## Resumable streams

Resumable streams let a client reconnect and replay events it missed, which requires the backend to keep recent history. Distributed backends such as [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) persist events, so they support replay on their own.

In-process delivery doesn't keep history. To add replay on top of [`EventEmitterPubSub`](/reference/pubsub/event-emitter), wrap it in [`CachingPubSub`](/reference/pubsub/caching-pubsub), which records published events per topic so a late or reconnecting subscriber can catch up before continuing with live events.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { CachingPubSub, EventEmitterPubSub } from '@mastra/core/events'
import { InMemoryServerCache } from '@mastra/core/cache'

const cache = new InMemoryServerCache()

export const mastra = new Mastra({
  pubsub: new CachingPubSub(new EventEmitterPubSub(), cache),
})
```

Visit the [PubSub reference](/reference/pubsub/base) for the full delivery contract and the configuration options for each backend.
