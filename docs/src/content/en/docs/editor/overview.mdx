# Editor

Editor enables collaborators to update your agent without needing access to your codebase or the ability to write code. They can change its instructions and tools in Studio, then test a draft before publishing it.

Developers still define the agent in code. Editor saves changes separately, so collaborators can improve the agent while developers retain control over its model, identity, and runtime.

## What collaborators can do

Editor doesn't rewrite your agent's source code. It adds an editable layer to the agents registered in your Mastra instance and applies those changes when an agent runs.

From Studio, collaborators can:

- **Change instructions**: Rewrite the agent's prompt or reuse instructions shared across several agents.
- **Choose tools**: Add or remove available tools and explain when the agent should use them.
- **Test before publishing**: Work on a draft without affecting the live version. Compare versions or restore an earlier one when needed.

## Quickstart

Install `@mastra/editor`. This quickstart uses LibSQL to store Editor changes:

```bash npm2yarn
npm install @mastra/editor @mastra/libsql
```

Add `MastraEditor` and storage to your Mastra instance. If your project already has storage, keep using it instead of adding the LibSQL store shown here.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraEditor } from '@mastra/editor'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  agents: {/* your existing agents */},
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db',
  }),
  editor: new MastraEditor(),
})
```

In [Studio](/docs/studio/overview), open an agent from **Agents** and select **Editor**. Change its instructions, then save your work as a draft. Publish the draft when you're ready for the agent to use it.

## Decide what collaborators can edit

By default, collaborators can change an agent's instructions and manage its tools, including their descriptions. The agent's `id`, `name`, and `model` always come from code.

Use the agent's `editor` field to limit what can be changed:

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support agent',
  instructions: 'Help customers with Acme products.',
  model: '__GATEWAY_OPENAI_MODEL__',
  editor: { instructions: true, tools: { description: true } },
})
```

This agent lets collaborators change its instructions and improve the descriptions of tools already attached to it. They can't add or remove tools.

| `editor` value | What collaborators can change |
| - | - |
| Omitted | Instructions, tools, and tool descriptions |
| `false` | Nothing |
| `{ instructions: true }` | Instructions |
| `{ tools: true }` | Tools and tool descriptions |
| `{ tools: { description: true } }` | Descriptions of tools already added in code |

Studio shows everything else as read-only. See [editor overrides](/reference/agents/agent#editor-overrides) for the complete configuration.

## Edit instructions

Instructions tell an agent how to behave. Collaborators can write them directly in the agent or add prompt blocks saved elsewhere in Studio.

A prompt block is a reusable piece of instruction text. Create one under **Prompts**, publish it, then open an agent's **Instructions** section and select **Add block**. When several agents use the same block, you can update that instruction in one place.

For example, a support agent, returns agent, and order-status agent may all need the same refund policy. Save the policy as a prompt block and add it to each agent. When the policy changes, update and publish the block once instead of editing three agents.

Prompt blocks can include values from the current request. For example, <code>{'{{userName}}'}</code> inserts a name supplied through request context. A display condition can include a block only for a customer, role, or feature flag.

See the [prompt blocks reference](/reference/editor/prompt-blocks) for template syntax, conditions, versions, and APIs.

## Choose tools

Tools let an agent take actions. Collaborators can choose from tools already in your project, tools from providers such as Composio or Arcade, and tools exposed by Model Context Protocol (MCP) servers.

In the agent's **Tools** section, add the tools it needs. You can also rewrite a tool's description for that agent. A more specific description helps the agent understand when to use the tool without changing the tool itself.

Tools are saved as part of the agent's draft. You can test a different set of tools before publishing, then return to the previous version if the change doesn't work as expected.

See the [Editor tools reference](/reference/editor/tools) to configure providers, MCP clients, conditions, and tool filtering.

## Choose where changes are stored

Editor can save changes in your database or as files in your repository.

### Your configured database

The database option is the default. Editor uses the storage configured on your `Mastra` instance for agent changes and prompt blocks. It keeps their version history there too. If your app already uses a supported store such as LibSQL, PostgreSQL, or MongoDB, Editor can use that same store.

You can also give Editor its own database. The following example keeps the app and Editor in separate LibSQL files:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraCompositeStore } from '@mastra/core/storage'
import { MastraEditor } from '@mastra/editor'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  agents: {/* your existing agents */},
  storage: new MastraCompositeStore({
    id: 'mastra-storage',
    default: new LibSQLStore({
      id: 'app-storage',
      url: 'file:./mastra.db',
    }),
    editor: new LibSQLStore({
      id: 'editor-storage',
      url: 'file:./editor.db',
    }),
  }),
  editor: new MastraEditor(),
})
```

Collaborators can save drafts and publish from Studio. Their changes go to `editor.db` in this example, not to the agent's source file.

### Files in your repository

Set `source: 'code'` when Editor changes should go through the same pull-request and deployment process as the rest of your code:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraEditor } from '@mastra/editor'

export const mastra = new Mastra({
  agents: {/* your existing agents */},
  editor: new MastraEditor({
    source: 'code',
    codePath: './mastra/editor',
  }),
})
```

In this mode, Studio writes one JSON override file for each agent. It doesn't generate TypeScript or change the file where you created the agent. By default, an agent with the ID `support-agent` gets this file:

```text
mastra/editor/agents/support-agent.json
```

The file contains only the parts managed by Editor. For example:

```json title="mastra/editor/agents/support-agent.json"
{
  "instructions": "Help customers with Acme products and answer in their language.",
  "tools": {
    "searchOrders": {
      "description": "Look up an order by its number"
    }
  }
}
```

The agent's model, name, and other code-owned fields stay in its TypeScript file. Mastra reads the JSON and applies these values when the agent runs.

When a collaborator saves in Studio, they can write the file to the local filesystem or download it. With a source-control integration, Studio can open a pull request instead. Git then provides the review and version history.

See [`MastraEditor`](/reference/editor/mastra-editor#source) for file locations and source options.

## Work with drafts and versions

With the database option, saving a change creates a draft version. The live agent keeps using the published version until you publish the draft.

Publishing makes that version live. Restoring an older version creates another draft first, so you can test it before it replaces the current version.

You can also choose a version for an individual request. This lets you:

- Compare two versions in an A/B test.
- Give a draft to a small group before publishing it for everyone.
- Keep production on the published version while staging uses the latest draft.
- Pin a customer to a particular version.

The same version controls work when a supervisor calls sub-agents. You can test a draft sub-agent without changing the rest of the system.

See the [Editor versioning reference](/reference/editor/versioning) for version selection, sub-agent behavior, REST endpoints, and SDK methods.

## Use Editor from code

You don't have to make changes through Studio. Editor is also available through [`mastra.getEditor()`](/reference/core/getEditor), the Mastra server API, and the Client SDK.

These APIs are useful for bulk updates and automated experiments. For example, run a [dataset experiment](/docs/evals/datasets/running-experiments), then save a proposed instruction change as a draft. Compare its scores with the published agent before deciding whether to publish it.

Use the stored-agent REST or Client SDK draft flow when an experiment must leave the live agent unchanged. The direct `editor.agent.update()` method activates its new version immediately.
