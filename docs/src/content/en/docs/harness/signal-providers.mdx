# Signal providers

**Added in:** `@mastra/core@1.42.0`

A signal provider watches an external system, such as CI, GitHub, or your own API, and sends its events to the agent threads that asked for them. The provider keeps track of which thread watches which external resource, and turns each matching event into a [notification](/docs/harness/notifications).

Use a provider when many threads watch many resources and events arrive by polling or webhook. If you already know which thread an event belongs to, call [`agent.sendNotificationSignal()`](/docs/harness/notifications#send-a-notification) directly instead.

## How a provider works

A provider extends `SignalProvider` and is passed to an agent in `signals`. It has three parts:

- **Subscriptions:** `subscribe(target, externalResourceId)` records that a thread wants events for a resource such as a pipeline name or pull request URL. The registry is in memory.
- **Ingestion:** `poll(subscriptions)` runs on `pollInterval` for systems you have to ask, and `handleWebhook(request)` handles systems that call you.
- **Delivery:** `notify(notification, target)` sends a notification to a subscribed thread through the agent the provider is registered on.

The agent also adds any tools the provider returns from `getTools()` and any processors from `getInputProcessors()` and `getOutputProcessors()`. Tools let the agent subscribe its own thread.

## Build a provider

This provider watches CI pipelines. The agent subscribes its thread with a tool, the provider polls each subscribed pipeline every 30 seconds, and it also accepts a webhook from the CI system.

```typescript title="src/mastra/signals/ci-signals.ts"
import { createTool } from '@mastra/core/tools'
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderWebhookRequest, SignalSubscription } from '@mastra/core/signals'
import { z } from 'zod'

type Build = { id: string; status: 'running' | 'passed' | 'failed' }

// Replace with a call to your CI system's API.
async function fetchLatestBuild(pipeline: string): Promise<Build> {
  return { id: 'build_123', status: 'failed' }
}

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const
  readonly pollInterval = 30_000

  getTools() {
    return {
      watchPipeline: createTool({
        id: 'watch-pipeline',
        description: 'Get notified in this thread when a CI pipeline fails.',
        inputSchema: z.object({ pipeline: z.string() }),
        execute: async ({ pipeline }, context) => {
          const threadId = context.agent?.threadId
          const resourceId = context.agent?.resourceId
          if (!threadId || !resourceId) throw new Error('watch-pipeline needs a memory thread')
          this.subscribe({ threadId, resourceId }, pipeline)
          return { watching: pipeline }
        },
      }),
    }
  }

  async poll(subscriptions: SignalSubscription[]) {
    for (const sub of subscriptions) {
      const build = await fetchLatestBuild(sub.externalResourceId)
      if (build.status === 'failed') await this.notifyFailure(sub, build)
    }
  }

  async handleWebhook({ body }: SignalProviderWebhookRequest) {
    const { pipeline, build } = body as { pipeline: string; build: Build }
    const subscriptions = this.getSubscriptionsForResource(pipeline)
    if (build.status === 'failed') {
      for (const sub of subscriptions) await this.notifyFailure(sub, build)
    }
    return { status: 200, body: { matched: subscriptions.length } }
  }

  private notifyFailure(sub: SignalSubscription, build: Build) {
    return this.notify(
      {
        source: this.id,
        kind: 'build-failed',
        priority: 'high',
        summary: `Build ${build.id} failed on ${sub.externalResourceId}`,
        payload: build,
        dedupeKey: `${this.id}:${sub.externalResourceId}:${build.id}`,
      },
      { resourceId: sub.resourceId, threadId: sub.threadId },
    )
  }
}
```

The `dedupeKey` includes the build ID, so polling the same failed build again updates the pending notification instead of creating a new one. See [Merge repeated events](/docs/harness/notifications#merge-repeated-events).

Mastra skips a poll when there are no subscriptions, and doesn't start a new poll while the previous one is still running. Errors thrown from `poll()` are logged, and polling continues.

## Register the provider

Pass the provider to an agent with memory, and register the agent on a `Mastra` instance with notification storage. `notify()` calls `sendNotificationSignal()`, which [needs the `notifications` storage domain](/docs/harness/notifications#set-up-notification-storage).

`handleWebhook()` isn't mounted as an HTTP route. Add your own route, verify the request, and pass the body and headers to the provider:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { registerApiRoute } from '@mastra/core/server'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'
import { CiSignals } from './signals/ci-signals'

export const ciSignals = new CiSignals()

const opsAgent = new Agent({
  id: 'ops-agent',
  name: 'Ops Agent',
  instructions: 'Watch pipelines when asked. When a build fails, explain the failure.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory(),
  signals: [ciSignals],
})

export const mastra = new Mastra({
  agents: { opsAgent },
  storage: new LibSQLStore({ id: 'mastra-storage', url: 'file:./mastra.db' }),
  server: {
    apiRoutes: [
      registerApiRoute('/webhooks/ci', {
        method: 'POST',
        handler: async c => {
          if (c.req.header('x-ci-token') !== process.env.CI_WEBHOOK_TOKEN) {
            return c.json({ error: 'unauthorized' }, 401)
          }
          const { body } = await ciSignals.handleWebhook({
            body: await c.req.json(),
            headers: c.req.header(),
          })
          return c.json(body)
        },
      }),
    ],
  },
})
```

Use the signature check your CI system documents in place of the shared token.

When the user asks the agent to "watch acme-app-main", the agent calls `watchPipeline`, which subscribes the thread. The next failed build reaches the thread as a `high` priority notification: delivered immediately when the agent is idle, or summarized and delivered after the current run otherwise.

## Lifecycle

When an agent is created with a provider, it calls `connect()`, starts polling if `pollInterval` is set, and then calls `start()` if you defined it. Keep in mind:

- **Subscriptions don't survive a restart.** Store them yourself if they must, and restore them in an overridden [`__registerMastra()`](/reference/signals/signal-provider#__registermastramastra) that calls `super`. `start()` runs when the agent is created, usually before the provider can reach `this.mastra` and its storage.
- **`start()` isn't awaited.** The agent can receive input before it finishes, and a rejected promise isn't caught by Mastra. Handle errors inside `start()`.
- **Mastra doesn't call `stop()`.** Call `provider.stop()` during your app's shutdown to stop polling and clear subscriptions. If you override `stop()`, call `super.stop()`.
- **Use one provider instance per agent.** A provider connects to the first agent that registers it. Another agent that registers the same instance gets its tools and processors, but notifications still go through the first agent.
- **Agent tools win name conflicts.** If an agent tool and a provider tool share a name, the agent's tool is used.

## Built-in providers

Mastra includes these providers:

| Provider | Package | What it does |
| - | - | - |
| [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider) | `@mastra/core/signals` | Routes webhook payloads to subscribed threads without writing a subclass |
| [`TaskSignalProvider`](/reference/signals/task-signal-provider) | `@mastra/core/signals` | Adds the built-in task tools and keeps the task list current with a [state signal](/docs/harness/custom-signals#state-signals) |
| [`GoalSignalProvider`](/reference/signals/goal-signal-provider) | `@mastra/core/signals` | Keeps the agent's current objective in context. Added automatically when the agent has `goal` config |
| `GithubSignals` | `@mastra/github-signals` | Subscribes threads to GitHub pull requests and sends commits, reviews, and merge or close events. See [GitHub](/integrations/channels/github) |

### Generic webhooks

`WebhookSignalProvider` handles the common webhook case with two functions: one that reads the resource ID from the payload, and one that builds the notification.

```typescript title="src/mastra/index.ts"
import { Agent } from '@mastra/core/agent'
import { WebhookSignalProvider } from '@mastra/core/signals'
import { Memory } from '@mastra/memory'

type BuildEvent = { repository: string; status: string }

export const webhooks = new WebhookSignalProvider({
  extractResourceId: payload => (payload as BuildEvent).repository,
  buildNotification: (payload, sub) => ({
    source: 'ci',
    kind: 'build-status',
    priority: 'medium',
    summary: `Build ${(payload as BuildEvent).status} for ${sub.externalResourceId}`,
  }),
})

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory(),
  signals: [webhooks],
})

webhooks.subscribeThread({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme/app')
```

Call `webhooks.handleWebhook({ body, headers })` from your route, as in [Register the provider](#register-the-provider). It returns `{ status: 200, body: { matched } }`, where `matched` counts the notifications sent. A notification that fails is logged and left out of the count instead of failing the request.
