# Notifications

A notification is an external event addressed to an agent thread: a CI failure, a review comment, a Slack mention, an incident. Mastra stores each notification in an inbox, then decides from its priority and the thread's state whether to show it to the agent now, show a short summary, or wait until the agent is free.

Use notifications for events that arrive on their own schedule and shouldn't derail the agent every time, and [`sendSignal()`](/docs/harness/custom-signals) for one-off context that doesn't need an inbox. To watch an external system and route its events to many threads, build a [signal provider](/docs/harness/signal-providers) on top of notifications.

## Set up notification storage

`sendNotificationSignal()` stores records in the `notifications` storage domain, so the agent must be registered on a `Mastra` instance whose storage supports it: [libSQL](/integrations/databases/libsql), [PostgreSQL](/integrations/databases/postgresql), or [MongoDB](/integrations/databases/mongodb). Without it, the call throws `sendNotificationSignal requires a notifications storage domain`.

Give the agent the inbox tool too, so it can read the notifications behind a summary:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({ id: 'mastra-storage', url: 'file:./mastra.db' })
const notifications = await storage.getStore('notifications')

const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions:
    'When you see a <notification-summary>, call notification-inbox with action "read" to get the full notifications.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory(),
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notifications! }),
  },
})

export const mastra = new Mastra({
  agents: { supportAgent },
  storage,
})
```

## Send a notification

Call `sendNotificationSignal()` with the event and the thread it belongs to:

```typescript title="src/ci-webhook.ts"
const agent = mastra.getAgent('supportAgent')

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed.',
    payload: { repository: 'acme/app', branch: 'main' },
    dedupeKey: 'github:acme/app:main:ci',
  },
  { resourceId: 'user_123', threadId: 'thread_456' },
)

console.log(decision.action) // 'deliver' when the thread is idle
```

`source` and `kind` describe where the event came from and what it is. `summary` is the text the model reads. `payload` is stored with the record for tools and the inbox, but the model doesn't see it. `priority` defaults to `medium`.

When Mastra delivers a notification, the model receives it as a `notification` tag:

```xml
<notification id="0a49706f-…" kind="ci-status" priority="high" source="github" status="delivered" type="ci-status">CI failed on main: 3 tests failed.</notification>
```

Pass an array to send several notifications in one call. Mastra resolves the thread's state once and returns one result per notification, in order.

## When the agent sees a notification

By default, the delivery decision depends on the notification's priority and whether the thread is running:

| Priority | Thread idle | Thread active |
| - | - | - |
| `urgent` | Delivered, wakes the agent | Delivered into the run |
| `high` | Delivered, wakes the agent | Summary now, full notification when the thread is idle again |
| `medium` | Delivered, wakes the agent | Summary now; full notification only when the agent reads it |
| `low` | Summary at the next dispatch, without waking the agent | Summary at the next dispatch |

A summary tells the agent that records are waiting without showing their contents:

```xml
<notification-summary pending="3">github: 1, slack: 1, email: 1</notification-summary>
```

Summarized notifications stay `pending` in the inbox until the agent reads them with the inbox tool, or, for `high` priority, until Mastra delivers them in full once the run ends. Delivered records move to `delivered`. Records the agent reads move to `seen`.

### Dispatch

Deferred deliveries and `low` priority summaries are sent by a dispatcher that runs every minute. Dispatch is on by default, with two requirements:

- A storage adapter with the `schedules` domain, which libSQL, PostgreSQL, and MongoDB provide. Without one, nothing is dispatched and no error is raised.
- Running Mastra workers. The Mastra server and worker builds start them. A standalone script that only creates a `Mastra` instance never dispatches.

Change the schedule with `notifications.dispatch` on [`Mastra`](/reference/core/mastra-class#constructor-parameters), or set `dispatch: { enabled: false }` to turn it off:

```typescript title="src/mastra/index.ts"
export const mastra = new Mastra({
  agents: { supportAgent },
  storage,
  notifications: {
    dispatch: { cron: '*/5 * * * *' },
  },
})
```

If a delivery fails five times, Mastra marks the record `failed` and stops retrying it.

## Change the delivery policy

Set `notifications.deliveryPolicy` on the agent to override the defaults. Each entry is an action or a full decision:

```typescript title="src/mastra/agents/support-agent.ts"
const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory(),
  notifications: {
    deliveryPolicy: {
      sources: { pagerduty: 'deliver' },
      priorities: { low: 'persist' },
      decide: ({ record }) => {
        if (record.kind === 'marketing') return 'discard'
        return undefined
      },
    },
  },
})
```

Mastra checks `decide` first, then `sources` by the record's `source`, then `priorities`, then `default`, and finally the built-in table. `decide` returns `undefined` to fall through.

The actions are:

- `deliver`: Show the full notification now. Wakes an idle thread.
- `summarize`: Send a summary at `summaryAt`. Return a decision object such as `{ action: 'summarize', summaryAt, deliverAt }`. Add `deliverAt` to also schedule full delivery. A bare `'summarize'` string has no `summaryAt`. The record stays `pending` and is never summarized or delivered.
- `defer`: Keep the record pending until `deliverAt`, then deliver it through the dispatcher. Return `{ action: 'defer', deliverAt }`. Without `deliverAt` the record stays `pending` and is never delivered.
- `persist`: Store the record without notifying the agent. It's available through the inbox tool.
- `discard`: Store the record as `discarded` and never deliver it.
- `queue`: Handled the same as `deliver`.

Mastra runs `decide` again when the dispatcher delivers a deferred or summarized record. At that point only the returned `streamOptions` and `hold` are used, so keep `decide` free of side effects. Use `streamOptions` to pass the request context an idle thread needs to start a run, such as model selection.

## Read the inbox

The tool from [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool) gives the agent one tool for its inbox. Its `action` input is `list`, `read`, `search`, `markSeen`, `dismiss`, or `archive`.

After a summary, the agent calls `read`. Mastra delivers the unread notifications as `notification` signals in the thread, rather than as tool output, and marks them `seen`, so they aren't delivered again. `list` and `search` return records as tool output and also mark the returned unread records `seen`.

## Merge repeated events

Set `dedupeKey` or `coalesceKey` when the same event can be sent more than once. If a `pending` record has the same thread, resource, agent, `source`, and `kind`, and either its `dedupeKey` matches the `dedupeKey` you send or its `coalesceKey` matches the `coalesceKey` you send, Mastra updates that record with the new summary and payload and increments its `coalescedCount` instead of creating another. Once a record has been delivered or read, the next send with the same key creates a new record.
