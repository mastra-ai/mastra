# Custom signals

Messages carry what a user wrote, and notifications carry external events with an inbox. Everything else the model should know about mid-thread is a signal: a policy reminder, the current time, a file's instructions after the agent opens it, the state of a browser tab. This page covers sending signals yourself, emitting them from processors, and state signals for values that change over time.

## Send a signal

`sendSignal()` takes the contents, a `type`, and optional attributes, and addresses them to a thread like any other input:

```typescript title="src/mastra/reminders.ts"
agent.sendSignal(
  {
    type: 'notification',
    contents: 'PR #123 has a new review comment.',
    attributes: { source: 'github', pr: '123' },
  },
  { resourceId: 'user_123', threadId: 'thread_456' },
)
```

The model receives the contents wrapped in a tag named after the type, with attributes as XML attributes:

```xml
<notification pr="123" source="github">PR #123 has a new review comment.</notification>
```

The `type` is the signal's category:

| Type | Default tag | Use it for |
| - | - | - |
| `user` | `user` | Input a person wrote. Prefer [`sendMessage()`](/docs/harness/signals-messages). |
| `notification` | `notification` | Events from outside the agent. This sends the signal without an inbox record. Use [`sendNotificationSignal()`](/docs/harness/notifications) when you want one. |
| `reactive` | `system-reminder` | Context generated by your code or a processor: reminders, policy, background results. |
| `state` | `state` | Current state. Use [`sendStateSignal()`](#state-signals). |

Set `tagName` to change the tag the model sees. Tag and attribute names must start with a letter or underscore and contain only letters, numbers, periods, hyphens, and the `_` character.

### Choose what happens on arrival

By default a signal wakes an idle thread and joins an active run, like a message. Set `ifIdle.behavior` and `ifActive.behavior` to change that:

```typescript title="src/mastra/reminders.ts"
const result = agent.sendSignal(
  { type: 'reactive', contents: 'The staging deploy finished.' },
  {
    resourceId: 'user_123',
    threadId: 'thread_456',
    ifIdle: { behavior: 'persist' },
  },
)

await result.persisted
```

- `wake` (idle only): Start a run with the signal.
- `deliver` (active only): Add the signal to the running loop.
- `persist`: Save the signal to the thread's history without running the agent. The model sees it on the next run.
- `discard`: Drop the signal.

`result.accepted` resolves to the action Mastra took. When the behavior is `persist`, await `result.persisted` to know the write finished. Pass `ifIdle.streamOptions` when a woken run needs options such as request context or a different model.

### Send transient context

Set `transient: true` for context that's only true right now, such as the current time. The model sees a transient signal on the next model call, but Mastra doesn't save it, so it never builds up in history. Send it again each time it should appear.

A transient signal can't also be persisted: combining `transient` with a `persist` behavior discards the signal. State signals can't be transient.

## Send signals from a processor

Processors receive `sendSignal` in `processInputStep()`. Use it to add context based on what's happening in the run. This processor adds the current time before every model call:

```typescript title="src/mastra/processors/clock-reminder.ts"
import type { Processor } from '@mastra/core/processors'

export const clockReminder = {
  id: 'clock-reminder',
  async processInputStep({ sendSignal }) {
    await sendSignal?.({
      type: 'reactive',
      transient: true,
      contents: `Current time: ${new Date().toISOString()}`,
      attributes: { type: 'clock' },
    })
  },
} satisfies Processor
```

Register it with `inputProcessors: [clockReminder]` on the agent. The model sees:

```xml
<system-reminder type="clock">Current time: 2026-10-14T09:00:00.000Z</system-reminder>
```

Await `sendSignal()` so the signal reaches subscribers in order with the run's other output.

When a processor reacts to something in the history, such as a tool reading an `AGENTS.md` file, check the history for a reminder it already sent before sending another. Mastra doesn't deduplicate non-transient reactive signals.

## State signals

State signals keep the model's view of something that changes, such as a browser, an editor, or a cart, current without repeating it on every turn. Each state lane has an `id`. Each update has a `cacheKey` that identifies the value, and a `mode`: a full `snapshot` or a `delta` describing what changed.

Mastra stores the latest state on the thread and skips an update when its `cacheKey` and `mode` match the current state, so you can send the same state as often as you like.

### Send state from outside the agent

Use `sendStateSignal()` when a separate process notices the change:

```typescript title="src/mastra/browser-watcher.ts"
const result = await agent.sendStateSignal(
  {
    id: 'browser',
    mode: 'snapshot',
    cacheKey: 'browser:https://example.com',
    contents: 'Active tab: https://example.com',
    value: { url: 'https://example.com' },
  },
  { resourceId: 'user_123', threadId: 'thread_456' },
)

if (result.skipped) console.log('State unchanged')
```

`sendStateSignal()` needs the agent to have memory, and the thread must already exist. It throws when either is missing.

### Compute state in a processor

When the agent's own code owns the state, implement `computeStateSignal()` on a processor and set `stateId`. Mastra calls it before each model call and applies the same `cacheKey` check:

```typescript title="src/mastra/processors/cart-state.ts"
import type { Processor } from '@mastra/core/processors'
import { getCart } from '../cart'

export const cartState = {
  id: 'cart-state',
  stateId: 'cart',
  computeStateSignal() {
    const cart = getCart()
    return {
      mode: 'snapshot',
      cacheKey: `cart:${cart.version}`,
      contents: `Cart has ${cart.items.length} item(s).`,
      value: cart,
    }
  },
} satisfies Processor
```

The model sees `<state>Cart has 2 item(s).</state>` once per change.

To send deltas, read `lastSnapshot` and `deltasSinceSnapshot` from the arguments, compare them with the current value, and return `mode: 'delta'` with a `delta`. The processor owns the diff. When `contextWindow.hasSnapshot` is `false`, older state messages have been trimmed from the context window, so return a fresh `snapshot`.

The built-in browser context processor uses the `browser` state lane with snapshots and deltas.

## Legacy signal types

Mastra still accepts the older `type: 'user-message'` and `type: 'system-reminder'` payloads, and reads stored signals that use them. They're converted to `type: 'user'` and `type: 'reactive'` with `tagName: 'system-reminder'`.
