# Signals

**Added in:** `@mastra/core@1.39.0`

Signals let you talk to an agent through a thread instead of through one `agent.stream()` call per turn. You subscribe to the thread once, then send it input at any time. If the agent is idle, the input wakes it. If the agent is running, the input joins the active run at the next safe point. The model sees it before it answers.

Use signals when input can arrive while the agent works. For example, a user corrects the agent mid-answer, a CI system reports a failure, or a processor adds context the model needs.

:::tip[📹 Watch]

Watch [Mastra signals overview](https://www.youtube.com/watch?v=7It2y89TVP4) to see how signals wake and steer long-running agents.

:::

## Choose an input

Every input is addressed to a thread with `resourceId` and `threadId`. Pick the method by who the input comes from.

| Input | Use it for | Method | Guide |
| - | - | - | - |
| Message | Text a person wrote | `sendMessage()`, `queueMessage()` | [Messages and steering](/docs/harness/signals-messages) |
| Notification | An event from an external system that should be stored in an inbox | `sendNotificationSignal()` | [Notifications](/docs/harness/notifications) |
| Signal | System context such as reminders, policy, or processor output | `sendSignal()` | [Custom signals](/docs/harness/custom-signals) |
| State | A value that changes over time, such as browser or editor state | `sendStateSignal()`, `computeStateSignal()` | [Custom signals](/docs/harness/custom-signals#state-signals) |

To connect an external system once and route its events to every thread that cares, build a [signal provider](/docs/harness/signal-providers).

## Quickstart

Register an agent with memory on a `Mastra` instance that has storage, subscribe to a thread, and send a message. A second message sent while the agent is answering joins the same run.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user compare options.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory(),
})

export const mastra = new Mastra({
  agents: { supportAgent },
  storage: new LibSQLStore({ id: 'mastra-storage', url: 'file:./mastra.db' }),
})
```

```typescript title="src/chat.ts"
import { mastra } from './mastra'

const agent = mastra.getAgent('supportAgent')
const thread = { resourceId: 'user_123', threadId: 'thread_456' }

const subscription = await agent.subscribeToThread(thread)

agent.sendMessage('Compare plan A and plan B.', thread)

setTimeout(() => {
  agent.sendMessage('Only consider the monthly price.', thread)
}, 200)

for await (const chunk of subscription.stream) {
  if (chunk.type === 'text-delta') process.stdout.write(chunk.payload.text)
  if (chunk.type === 'finish') break
}

subscription.unsubscribe()
```

The first message wakes the idle agent. The second arrives while the model is still answering, so Mastra holds it until that response ends, then calls the model again with both messages in the same run. The subscription sees one run and one `finish` chunk.

`subscription.stream` doesn't end on its own. It stays open across runs so it can show the next one, which is what a chat UI wants. Break out of the loop when you're done and call `unsubscribe()`.

Memory isn't required to send a message, but without it each run starts with no history. The agent doesn't remember earlier messages on the thread.

## Active and idle threads

What happens to an input depends on whether the thread has a run in progress.

| Thread state | Default | Other options |
| - | - | - |
| Idle | `wake`: start a run with the input | `persist`: save it for the next run, `discard`: drop it |
| Active | `deliver`: add the input to the running loop | `persist`, `discard` |

Set `ifIdle.behavior` and `ifActive.behavior` on [`sendSignal()`](/docs/harness/custom-signals#choose-what-happens-on-arrival) to change this. Every send returns an `accepted` promise. It resolves to the action Mastra took (`wake`, `deliver`, `persist`, `discard`, or `blocked` when the thread is busy with a different agent's run or with a run suspended for tool approval).

`queueMessage()` is the exception: on an active thread it waits for the current run to finish and then starts a new one. See [Messages and steering](/docs/harness/signals-messages#queue-a-message-for-the-next-turn).

## Use the client SDK

From a browser or another service, use the same flow through [`@mastra/client-js`](/reference/client-js/agents#subscribetothread). Subscribe before sending so the client receives the run the message starts.

```typescript title="src/app/chat.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const agent = client.getAgent('supportAgent')
const thread = { resourceId: 'user_123', threadId: 'thread_456' }

const subscription = await agent.subscribeToThread(thread)

await agent.sendMessage({ message: 'Show the shorter version.', ...thread })

await subscription.processDataStream({
  onChunk: chunk => {
    console.log(chunk)
  },
  reconnect: true,
})
```

Pass `reconnect: true` for long-lived subscriptions so the client reconnects when the network drops the stream. Pass `withInitialHistory: true` to `subscribeToThread()` to receive the stored messages as the first chunk, so a page load can render history and live output from one subscription.

## Run on more than one instance

Signals coordinate through the `Mastra` instance's pub/sub. The default in-memory pub/sub only reaches one process. On serverless platforms or behind a load balancer, a follow-up message can reach a different instance from the one running the agent. That instance can't reach the run, so it starts a second run on the same thread.

Configure a shared pub/sub that also provides leases, such as Redis Streams, so exactly one instance owns a thread at a time:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  agents: { supportAgent },
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL,
    keyPrefix: 'mastra:my-app',
  }),
})
```

See the [PubSub guide](/docs/server/pubsub) and [`RedisStreamsPubSub` reference](/reference/pubsub/redis-streams).
