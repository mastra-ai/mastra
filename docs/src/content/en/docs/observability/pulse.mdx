# Pulse (experimental)

:::warning

DRAFT — experimental research preview; API subject to spec review. Interfaces, table shapes, and semantics may change without notice.

:::

Pulse is an event-first observability model. Instead of storing spans with durations and parent pointers, Pulse appends instant facts (`pulses`) and link rows (`relationships`), and derives everything else at read time.

Nothing derived is ever stored. Flows, span trees, durations, and status are reconstructed from the raw rows by the storage adapter when you query. Because facts land as they happen, in-flight runs are visible mid-execution, for example a pending tool approval. Span-based views can't show this until a run ends.

## When to use Pulse

- Inspect runs while they're still executing, not only after they finish.
- Keep session-layer facts (tool approvals, the true abort outcome) next to span facts.
- Experiment with the event-first storage direction on top of ClickHouse.

Pulse runs alongside the existing exporters. Adding the [ClickHouseHttpPulseExporter](/reference/observability/pulse-exporter) doesn't change what [MastraStorageExporter](/reference/observability/tracing/exporters/mastra-storage-exporter) or any other exporter records.

## Install

```bash npm2yarn
npm install @mastra/pulse
```

## Configure

The whole pipeline lives in `@mastra/core` behind one config key, fully independent of the observability system (hard split — pulse never reads spans). Configuring `pulse` on Mastra constructs a dedicated PulseBus, native AgentController session forwarding, and a batching writer into the `pulse` storage domain:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraCompositeStore } from '@mastra/core/storage'
import { PulseStorageClickhouse } from '@mastra/clickhouse'
import { LibSQLStore } from '@mastra/libsql'

const pulseStore = new PulseStorageClickhouse({
  url: 'http://localhost:8123',
  username: 'default',
  password: process.env.CLICKHOUSE_PASSWORD!,
})

export const mastra = new Mastra({
  storage: new MastraCompositeStore({
    id: 'composite-storage',
    default: new LibSQLStore({
      id: 'mastra-storage',
      url: 'file:./mastra.db',
    }),
    domains: {
      pulse: pulseStore,
    },
  }),
  // One switch: emitter sink + session forwarding + writer over the pulse domain.
  pulse: {},
})
```

Without `pulse` configured, nothing is constructed — stock behavior. The read model (derived flows, trees, timelines) is available today through the pulse storage domain's reader methods (`listFlows`, `getFlow`, `getFlowTimeline`); HTTP endpoints and a client SDK surface are deliberately not part of this prototype and will be designed after the data model is settled.

Token usage is recorded first-hand on model end facts (`total_input_tokens`, `total_output_tokens`); cost is never stored — readers derive it at read time from the versioned `model_prices` table, so price corrections apply retroactively.

### Standalone ClickHouse writer (no composite store)

Users without a composite store can register the standalone HTTP writer from `@mastra/pulse` as a pulse exporter (create the tables once with `ensurePulseTables`):

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { ClickHouseHttpPulseExporter, ensurePulseTables } from '@mastra/pulse'

await ensurePulseTables({ url: 'http://localhost:8123', database: 'pulse' })

export const mastra = new Mastra({
  pulse: {
    exporters: [
      new ClickHouseHttpPulseExporter({
        url: 'http://localhost:8123',
        database: 'pulse',
      }),
    ],
  },
})
```

:::note
Visit the [ClickHouseHttpPulseExporter reference](/reference/observability/pulse-exporter) for all configuration options and the storage domain methods.
:::

## Flow status

A flow is everything grouped under one trace. Its status is derived from the raw rows at read time and has five states:

| Status | Meaning |
| - | - |
| `running` | Root started, no terminal pulse yet, recent activity |
| `completed` | Root received its `*_completed` pulse without error |
| `failed` | Root received a `*_failed` pulse |
| `aborted` | The session layer recorded an abort for a run in this flow |
| `stale` | No terminal pulse and no activity for 30 seconds |

Two rules matter here:

- Session abort overrides the span outcome. The span layer records aborted runs as completed; the session-layer abort fact is authoritative, so the derived status is `aborted`. Abort facts carry the aborted run's id, so attribution is an exact join — the abort flips only the flow that contains that run. An abort without a run id attributes to nothing; attribution is never guessed.
- Staleness is time-based. A flow with no terminal pulse goes `stale` after 30 seconds of silence. This is how crashed processes surface, since their unflushed tail is lost by design.

## What gets captured

Every fact is recorded FIRST-HAND at the source call sites (run, model,
steps, tools, memory, processors, signals, approvals, content). Pulse
never ingests spans: it works identically with observability enabled or
disabled — the two systems are independent recorders.

| Event family | What Pulse records |
| - | - |
| Agent lifecycle | Run/model/step/tool/memory/processor starts and ends, with computed ids and parentage; abort and suspend are honest terminals. |
| Semantics | Signal routing/drain, exact model-input membership (`included_in_model_input` with position), request freeze/execution, approval decisions, content changes. |
| Metrics | Not a lane: a metric is just an item in the `data` field of a pulse. Model facts carry token usage first-hand; cost is derived at read time from the versioned `model_prices` table. |
| Logs | Not yet in the prototype ("a log is a pulse" is planned as a native hook; the old span-bridge translation was removed with the hard split). |
| Scores / Feedback | Skipped for the prototype (maintainer direction). |
| Workflow / durable engines | Out of prototype scope (agent-only, maintainer direction). |

Session-layer facts (tool approvals, the true abort outcome with its run id, follow-up queueing, mode and model switches) aren't spans. They are forwarded natively: when `pulse` is configured on `Mastra`, every AgentController session gets an internal subscriber — no wiring required.

## Limitations

Pulse is a research preview. Known gaps:

- Facts are bounded per run (record count and byte caps); when a cap trips, the flow is stamped `native_capture_incomplete` — never a silent drop.
- No span ingestion and no historic backfill: pulse records only what happens after it is enabled (deliberate hard split; migration tooling is future work).
- The emitter sink is process-global: multiple Mastra instances in one process are not yet supported (instance-owned runtime is a pending design decision).
- Write buffers are in-memory. A hard crash loses the unflushed tail, and the affected flows surface as `stale`. `mastra.pulseBus.flush()` drains the writers; one poison record does not discard its batch — failed batches fall back to per-record writes, and dropped rows surface as `events_dropped` pulses once storage recovers.
