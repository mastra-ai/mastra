# State signals

A state signal holds named current context on a thread, separate from chat messages. Each state ID is a labeled slot the model can consult: the page a user is looking at, a result a background job produced, or the state of a long-running task. A producer sends a snapshot or delta for that slot, and Mastra stores the value durably and gives it to the model as context.

The producer owns merge and diff logic. Mastra doesn't merge values for you.

Use state signals when the model needs a current view of something that changes across turns and isn't a user message. [Sending signals](/docs/signals/sending-signals) covers the durable input paths.

## How state signals work

A state ID names a slot of current context, sometimes called a state lane. A **snapshot** is the full state of that slot. A **delta** describes only what changed since the last snapshot.

Send a snapshot when the producer first establishes the slot, when the model's context no longer contains one, or when a delta would be ambiguous. Send a delta when the model already has a snapshot and only part of it changed. If you can't tell, send a snapshot.

When Mastra accepts a state signal, it stores compact tracking metadata. If a producer sends the same `cacheKey` and mode while that state is current, Mastra skips the duplicate and `sendStateSignal()` reports `{ skipped: true, reason: 'unchanged' }`.

State signals are durable, so they survive later turns and, with shared storage, process restarts. Because every accepted update becomes context, batch or summarize frequent changes before sending.

## Send a state signal

Use [`sendStateSignal()`](/reference/agents/agent#sendstatesignalstate-options) when an external producer detects a change. `id` names the state lane, `mode` selects a snapshot or delta, `cacheKey` identifies the version for deduplication, `contents` is the text the model reads, and `value` carries structured data for processors and application code. The [Agent reference](/reference/agents/agent#sendstatesignalstate-options) covers every field and return value.

```typescript title="src/mastra/browser-watcher.ts"
await agent.sendStateSignal(
  {
    id: 'browser',
    mode: 'snapshot',
    cacheKey: 'browser:https://example.com:3-tabs',
    contents: 'Browser is open. Active tab URL: https://example.com. 3 open tabs.',
    value: {
      activeUrl: 'https://example.com',
      tabCount: 3,
      open: true,
    },
  },
  {
    resourceId: 'user_123',
    threadId: 'thread_456',
  },
)
```

## Compute state in a processor

Use [`computeStateSignal()`](/reference/processors/processor-interface#computestatesignal) when a processor owns a state lane. Mastra calls it once per model input step after [`processInputStep()`](/reference/processors/processor-interface#processinputstep) and before the model request is finalized. The processor reads `activeStateSignals`, the last snapshot, and `deltasSinceSnapshot`, and returns `undefined` when nothing changed. The [Processors guide](/docs/agents/processors) covers its place in the execution order.

```typescript title="src/mastra/processors/browser-state.ts"
import type { ComputeStateSignalArgs, Processor } from '@mastra/core/processors'

export const browserStateProcessor: Processor = {
  id: 'browser-state',
  stateId: 'browser',
  computeStateSignal(args: ComputeStateSignalArgs) {
    const browser = readCurrentBrowserState()
    const previous = readMostRecentBrowserState(args.activeStateSignals)
    const changed = previous ? diffBrowserState(previous, browser) : browser
    const shouldRefreshSnapshot = Boolean(args.lastSnapshot && !args.contextWindow.hasSnapshot)

    if (previous && Object.keys(changed).length === 0 && !shouldRefreshSnapshot) {
      return
    }

    const isDelta = Boolean(previous && !shouldRefreshSnapshot)

    return {
      mode: isDelta ? 'delta' : 'snapshot',
      cacheKey: stableBrowserStateCacheKey(browser),
      contents: isDelta ? describeBrowserDelta(changed) : describeBrowserSnapshot(browser),
      value: browser,
      ...(isDelta ? { delta: changed } : {}),
    }
  },
}
```

Mastra resolves `lastSnapshot` and `deltasSinceSnapshot` from message history when the current message list lacks the latest snapshot. The processor still owns merge and diff logic.

## Built-in uses

Mastra uses state signals for long-lived context, and the same patterns apply to your application:

- The [browser](/docs/browser) context processor keeps the active page and tabs under `browser`.
- [Goals](/docs/harness/goals) keep the current objective under the `goal` id.
- [Task tracking](/docs/agents/tools#task-tracking) stores task state through [`TaskStateProcessor`](/reference/signals/task-signal-provider).
- [Working memory](/docs/memory/working-memory#opt-in-to-state-signals-experimental) can move out of the system prompt and into a `working-memory` state signal with `useStateSignals: true`.

## Choose another input path

- **User input:** use [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options).
- **Prompt-only context:** use a transient reactive signal.
- **Discrete external events:** use a notification with a durable inbox record and delivery policy.
- **Named current context:** use a state signal.

## Persistence and truncation

State signals can't be transient. Mastra rebuilds tracking metadata from persisted history, so a delivery-only signal would break deduplication. With shared storage, persisted state and its tracking survive a restart; without it, a new process starts without the lane.

`contextWindow.hasSnapshot` tells the processor whether the active window already contains a snapshot for the lane. If it's `false`, return a fresh `snapshot` so the model sees current state after older state messages are trimmed.
