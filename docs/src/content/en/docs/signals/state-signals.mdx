# State signals

State signals expose named, thread-scoped context lanes. Use them for durable context that changes over time, such as browser state, editor state, or a background watcher result. They aren't chat messages. The model sees them as context alongside the conversation. State signals are one of the durable input paths covered in [Sending signals](/docs/signals/sending-signals).

## When to use state signals

Use a state signal when the model needs a current view of something that changes across turns and isn't a user message:

- **Live application state:** the active browser page, open editor file, selected record, or another value your app already tracks.
- **Background results:** a watcher, sync job, or integration updates context that should stay available on the thread.
- **Long-running work:** the agent needs the latest snapshot after older context is truncated, without replaying every intermediate update.

State signals are durable, so they survive later turns and, with shared storage, process restarts.

### When not to use state signals

Use a different input path when the data has a different lifecycle:

- **User input:** use [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options), not a state lane.
- **Prompt-only context for one call:** use a transient reactive signal with `transient: true`.
- **Discrete external events:** use notifications so they get a durable inbox record and delivery policy.
- When updates arrive frequently, batch or summarize changes before sending. Every accepted state signal becomes context, and snapshots are reinserted after older state messages leave the context window.

## Snapshots and deltas

A **snapshot** is the full state of a lane. A **delta** describes only what changed since the last snapshot. The producer owns the merge and diff logic: Mastra stores and tracks state signals, but it doesn't merge values on your behalf.

Send a snapshot when the producer first establishes a lane, when the model's context no longer contains a snapshot, or when a delta would be ambiguous without the earlier state. Send a delta when the model already has a current snapshot and only a small part changed. If you can't tell whether the model still has the snapshot, send a snapshot.

## Built-in uses

Mastra uses state signals for its own long-lived context, and the same patterns apply to your application:

- The [browser](/docs/browser) context processor keeps the active page and tabs under the `browser` id.
- [Goals](/docs/harness/goals) keep the current objective under the `goal` id so the model always knows what it's working toward.
- [Task tracking](/docs/agents/tools#task-tracking) stores task state through [`TaskStateProcessor`](/reference/signals/task-signal-provider).
- [Working memory](/docs/memory/working-memory#opt-in-to-state-signals-experimental) can move out of the system prompt and into a `working-memory` state signal with `useStateSignals: true`.

## Send a state signal

Use [`sendStateSignal()`](/reference/agents/agent#sendstatesignalstate-options) when an external producer detects a state change. Each state signal identifies a state lane with `id`, a producer-owned `cacheKey`, and whether the update is a snapshot or delta. The [Agent reference](/reference/agents/agent#sendstatesignalstate-options) covers every field and return value.

```typescript title="src/mastra/browser-watcher.ts"
await agent.sendStateSignal(
  {
    id: 'browser',
    mode: 'snapshot',
    cacheKey: 'browser:https://example.com:3-tabs',
    contents: 'Browser is open. Active tab URL: https://example.com. 3 open tabs.',
    value: {
      activeUrl: 'https://example.com',
      tabCount: 3,
      open: true,
    },
  },
  {
    resourceId: 'user_123',
    threadId: 'thread_456',
  },
)
```

## Compute state in a processor

Use [`computeStateSignal()`](/reference/processors/processor-interface#computestatesignal) when a processor owns a state lane. Mastra calls it once per model input step after [`processInputStep()`](/reference/processors/processor-interface#processinputstep) and before the model request is finalized. The processor reads the active state through `activeStateSignals`, the last snapshot, and `deltasSinceSnapshot`. Return `undefined` when nothing changed. The [Processors guide](/docs/agents/processors) covers where this hook sits in the execution order.

```typescript title="src/mastra/processors/browser-state.ts"
import type { ComputeStateSignalArgs, Processor } from '@mastra/core/processors'

export const browserStateProcessor: Processor = {
  id: 'browser-state',
  stateId: 'browser',
  computeStateSignal(args: ComputeStateSignalArgs) {
    const browser = readCurrentBrowserState()
    const previous = readMostRecentBrowserState(args.activeStateSignals)
    const changed = previous ? diffBrowserState(previous, browser) : browser
    const shouldRefreshSnapshot = Boolean(args.lastSnapshot && !args.contextWindow.hasSnapshot)

    if (previous && Object.keys(changed).length === 0 && !shouldRefreshSnapshot) {
      return
    }

    const isDelta = Boolean(previous && !shouldRefreshSnapshot)

    return {
      mode: isDelta ? 'delta' : 'snapshot',
      cacheKey: stableBrowserStateCacheKey(browser),
      contents: isDelta ? describeBrowserDelta(changed) : describeBrowserSnapshot(browser),
      value: browser,
      ...(isDelta ? { delta: changed } : {}),
    }
  },
}
```

Mastra passes `lastSnapshot` and `deltasSinceSnapshot` into `computeStateSignal()`. It resolves them from message history when the current message list doesn't contain the latest snapshot. The processor still owns merge and diff logic.

## Deduplication and tracking

When Mastra accepts a state signal, it stores compact tracking metadata on the thread. If a producer sends the same `cacheKey` and mode again while that state is still current, Mastra skips the duplicate. Direct `sendStateSignal()` calls report that as `{ skipped: true, reason: 'unchanged' }` rather than creating another stored signal.

## State after context truncation

`contextWindow.hasSnapshot` tells the processor whether the active message window already contains a snapshot for this state lane. If it's `false`, return a fresh `snapshot` so the model sees the current state even after older state messages are trimmed from the context window.

## Persistence rules

State signals can't be transient. Mastra rebuilds the lane's tracking metadata from persisted history, so a delivery-only state signal would break deduplication. Persisted state signals and their tracking survive a process restart when the agent's storage is shared; without shared storage, a new process starts without the lane.
