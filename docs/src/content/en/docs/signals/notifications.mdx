# Notifications

A notification is an external event that should reach an agent but shouldn't disappear if the agent is busy. Use [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) to store the event as a durable inbox record, apply a delivery policy, and deliver it now or later. The agent can read pending records with [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool).

Unlike a chat message, a notification has its own lifecycle: it can be coalesced, summarized, deferred, retried, read, dismissed, or archived. The [Notifications reference](/reference/signals/notifications) documents the record and policy types.

## When to use notifications

Use notifications for external events that need to survive until the agent acts on them:

- **CI failures and review activity:** a failed build, a new pull request comment, or a requested review.
- **Messages and mentions:** email, Slack mentions, or direct messages that arrive outside the current conversation.
- **Operational events:** incidents, alerts, or recordings that should enter the thread with a priority.
- **Background work:** a long-running job or integration finishes and reports back after the original request.

The durable record is the reason to use this path. It lets the agent triage events later, avoids losing an event while a run is active, and supports deduplication and retries.

### When not to use notifications

- **User input:** use [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) so the message becomes part of the conversation.
- **Live application context:** use a [state signal](/docs/signals/state-signals) for values that change across turns, such as browser or editor state.
- **Context for one model call:** use a transient reactive signal. See [Send context from a system](/docs/signals/sending-signals#send-context-from-a-system).
- **Notification-shaped context without an inbox:** use [`sendSignal({ type: 'notification' })`](/reference/agents/agent#sendsignalsignal-options). It skips record storage, delivery policy, retries, and later reading.

## Quickstart

Notification records need a storage adapter with the `notifications` domain. This example uses libSQL, subscribes to the thread first, then sends a high-priority CI failure:

```typescript title="src/mastra/notifications.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({
  id: 'mastra',
  url: 'file:./mastra.db',
})

const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
})

const mastra = new Mastra({
  agents: { ciAgent },
  storage,
})

const agent = mastra.getAgent('ciAgent')
const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed in the API suite.',
    payload: {
      repository: 'acme/app',
      branch: 'main',
      runId: '123456',
    },
    dedupeKey: 'github:acme/app:main:ci',
  },
  thread,
)

console.log(record.status, decision.action)

for await (const chunk of subscription.stream) {
  console.log(chunk)

  if (chunk.type === 'finish') break
}
```

On an idle thread, a high-priority notification delivers immediately and starts a run. On an active thread, Mastra summarizes it first, then delivers the full notification when the thread is idle. The subscription receives both the summary and the full notification as [thread stream](/docs/signals/thread-streams) chunks.

## Notification records

Ingress and dispatch are separate phases. During ingress, `sendNotificationSignal()` creates or coalesces a record and resolves the agent's delivery policy. During dispatch, Mastra consumes due records and emits full notifications or summaries.

The record and the signal are different objects. The record stores routing, priority, status, delivery attempts, and the original payload. The signal is what the model sees: an XML element built from the record's `summary` and attributes. The record's `payload` is not included in the model context.

Records move through these statuses:

- `pending`: eligible for dispatch or for the inbox tool to read.
- `delivered`: a full notification signal was emitted.
- `seen`: the record was read in the inbox or its full content was already injected.
- `dismissed` and `archived`: inbox states managed by the agent or application.
- `discarded`: the delivery policy rejected the record.
- `failed`: delivery reached the attempt cap.

A summarized record stays `pending`, because a summary tells the model that records exist without marking them delivered. The reference lists every [record field](/reference/signals/notifications#notification-records) and [status](/reference/signals/notifications#priorities-and-statuses).

## Create and coalesce records

`sendNotificationSignal()` accepts one notification or an array. Each item is created independently, then the storage layer decides whether it can merge into an existing pending record.

Two keys control merging: `dedupeKey` identifies the same event, while `coalesceKey` groups related events. They use the same matching rules; the difference is intent, so a dedupe key represents one event that may arrive twice, and a coalesce key represents a set of related events.

Merging only considers records on the same thread, source, kind, agent, and resource that are still pending. The [Notifications reference](/reference/signals/notifications#coalescing-pending-records) documents the fields that merge and their precedence.

## Storage and dispatcher setup

Notification records require a storage adapter that implements the `notifications` domain. The supported adapters are [libSQL](/integrations/databases/libsql), [PostgreSQL](/integrations/databases/postgresql), and [MongoDB](/integrations/databases/mongodb). Without the domain, `sendNotificationSignal()` throws instead of silently dropping the record.

Scheduled dispatch is enabled by default and runs through the workflow scheduler. Configure it on the `Mastra` instance:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { ciAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

The defaults are `enabled: true`, `cron: '*/1 * * * *'` (once per minute), and `batchSize: 100`. The dispatch schedule is created lazily on the first deferred or summarized notification, and the workflow scheduler activates with it. Apps that never defer a notification don't run the dispatcher. Set `enabled: false` to opt out.

## Delivery policy

Every record gets a decision when it is received, and possibly again when it is dispatched. The built-in policy uses priority and whether the thread is active or idle:

| Priority | Idle thread | Active thread |
| - | - | - |
| `urgent` | Deliver immediately | Deliver immediately |
| `high` | Deliver immediately | Summarize now, then deliver when idle |
| `medium` | Deliver immediately | Batch into a summary |
| `low` | Batch into a summary | Batch into a summary |

Configure a policy on the agent when the defaults don't fit. Source rules run before priority rules, so a noisy source can be summarized while everything else delivers:

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Memory } from '@mastra/memory'

// storage from the Quickstart
export const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
  notifications: {
    deliveryPolicy: {
      sources: {
        github: 'summarize',
      },
      priorities: {
        urgent: 'deliver',
        low: 'discard',
      },
    },
  },
})
```

Mastra evaluates the policy in this order:

1. A custom `decide()` function.
1. `sources`, matched against `record.source`.
1. `priorities`, matched against `record.priority`.
1. `default`.
1. The built-in priority policy.

A custom `decide()` function runs at receipt time and again at delivery time for records whose first decision deferred them or scheduled a summary. At delivery time, the record's stored schedule already fixes when and how it delivers, so only `streamOptions` and `hold` from the new decision are honored. Keep `decide()` side-effect free.

## Dispatch

The dispatcher reads due records from storage, groups summaries by `agentId`, `resourceId`, and `threadId`, and emits signals through the thread runtime.

`deliver` emits a full notification immediately. `summarize` emits a summary now or at `summaryAt`. `defer` leaves the record pending until `deliverAt`. `persist` stores the record without a signal, and `discard` marks it discarded. A decision can also use `hold` at delivery time to leave the record for another process's dispatcher without counting an attempt.

### Summaries

Summaries keep a busy thread from receiving a burst of individual notifications. The model sees a compact digest:

```xml
<notification-summary pending="10">github: 3, email: 5, slack: 2</notification-summary>
```

A full notification delivers the record's summary as its contents:

```xml
<notification source="github" kind="ci-status" priority="high" status="delivered">CI failed on main: 3 tests failed in the API suite.</notification>
```

When Mastra emits a summary, it clears `summaryAt` and sets `summarySignalId` on each summarized record. The records stay `pending` and readable. When a full notification is emitted, Mastra sets `deliveredSignalId` and marks the record `delivered`.

Summaries do not mark records delivered. If the agent needs the full content behind a summary, it reads those records through the inbox. Reading can inject the full notification signal and mark the record `seen`, which prevents a duplicate delivery later.

### Retries and failures

A failed delivery attempt increments `deliveryAttempts` and records `lastDeliveryAttemptAt` and `lastDeliveryError`. The record stays pending and becomes due again on the next dispatch pass.

After five failed attempts, the record moves to `failed` and stops being due. The cap is exported as `MAX_NOTIFICATION_DELIVERY_ATTEMPTS`. A `hold` decision leaves the record pending without counting an attempt, so another dispatcher can pick it up.

If a custom policy throws during ingress, the record is left pending with an immediate `deliverAt` and a failed attempt, so the dispatcher can retry it instead of leaving it unscheduled.

## Work with the inbox

Give the agent the inbox tool so it can inspect records without exposing storage APIs:

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'

const notificationsStorage = await storage.getStore('notifications')

export const ciAgent = new Agent({
  // ...
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notificationsStorage }),
  },
})
```

The tool supports `list`, `read`, `search`, `markSeen`, `dismiss`, and `archive`. Listing, reading, and searching mark the returned unread records as `seen`, including `failed` records so the agent can learn that delivery gave up. `list` defaults to pending, delivered, and failed records; `search` spans all statuses.

`read` is the important action after a summary. It loads the selected records and delivers their full contents as notification signals, not as ordinary tool output. The agent therefore sees the notification context on the thread even though the tool call produced only a short status message.

## Agent and client surfaces

[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) is the canonical way to create durable notification records. It returns the record and the policy decision, and includes `accepted`, `signal`, and `persisted` when a signal was emitted, matching the other signal methods described in [Sending signals](/docs/signals/sending-signals).

The JavaScript client SDK can send notification-shaped context through [`client.getAgent().sendSignal()`](/reference/client-js/agents#sendsignal). That path bypasses inbox storage, so use it only when the event doesn't need a record, retries, or later reading. Durable notification records over HTTP go through the AgentController Session notification route, which forwards to the same `sendNotificationSignal()` behavior. See the [Session reference](/reference/agent-controller/session) for its method signature and [Agent Controller](/docs/harness/agent-controller) for how a Session manages threads and subscriptions.
