# Notifications

A notification is an external event that should reach an agent but shouldn't disappear if the agent is busy. A build doesn't stop failing because the agent was halfway through an answer, and a review comment doesn't wait politely for the next turn. Use [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) to store the event as a durable inbox record, apply a delivery policy, and deliver it now or later. The agent can read pending records with [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool).

Unlike a chat message, a notification has its own lifecycle: it can be coalesced, summarized, deferred, retried, read, dismissed, or archived. The [Notifications reference](/reference/signals/notifications) documents the record and policy types.

Use a notification when an external event must survive until the agent acts on it, such as a failed build, a review comment, an email or Slack mention, an incident, or a background job finishing. A durable record lets the agent triage the event later, keeps an active run from losing it, and gives Mastra a place to deduplicate and retry.

For other lifecycles, use a different path. User input belongs in [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) so it becomes part of the conversation. Changing application context belongs in a [state signal](/docs/signals/state-signals), and context for one model call belongs in a transient reactive signal. Notification-shaped context that needs no inbox, policy, or retries can use [`sendSignal({ type: 'notification' })`](/reference/agents/agent#sendsignalsignal-options) directly.

## Quickstart

Notification records need a storage adapter with the `notifications` domain. This example uses libSQL, subscribes to the thread first, then sends a high-priority CI failure:

```typescript title="src/mastra/notifications.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({
  id: 'mastra',
  url: 'file:./mastra.db',
})

const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
})

const mastra = new Mastra({
  agents: { ciAgent },
  storage,
})

const agent = mastra.getAgent('ciAgent')
const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed in the API suite.',
    payload: {
      repository: 'acme/app',
      branch: 'main',
      runId: '123456',
    },
    dedupeKey: 'github:acme/app:main:ci',
  },
  thread,
)

console.log(record.status, decision.action)

for await (const chunk of subscription.stream) {
  console.log(chunk)

  if (chunk.type === 'finish') break
}
```

On an idle thread, a high-priority notification delivers immediately and starts a run. On an active thread, Mastra summarizes it first, then delivers the full notification when the thread is idle. The subscription receives both the summary and the full notification as [thread stream](/docs/signals/thread-streams) chunks.

## Notification records

Ingress and dispatch are separate phases. `sendNotificationSignal()` creates or coalesces a record and resolves the delivery policy. Dispatch consumes due records and emits full notifications or summaries.

The record and signal differ. The record stores routing, priority, status, delivery attempts, and the original payload. The model sees an XML element built from `summary` and attributes. `payload` stays out of model context.

Records move through `pending`, `delivered`, `seen`, `dismissed`, `archived`, `discarded`, and `failed`. A summarized record stays `pending`, because a summary tells the model that records exist without marking them delivered. The reference lists every [record field](/reference/signals/notifications#notification-records) and [status](/reference/signals/notifications#priorities-and-statuses).

## Create and coalesce records

`sendNotificationSignal()` accepts one notification or an array. Each item is created independently, then storage decides whether it can merge into an existing pending record.

The `dedupeKey` identifies the same event, while `coalesceKey` groups related events. Both use the same matching rules. A dedupe key represents one event that may arrive twice, and a coalesce key represents a set of related events.

Merging only considers records on the same thread, source, kind, agent, and resource that are still pending. The [Notifications reference](/reference/signals/notifications#coalescing-pending-records) documents the fields that merge and their precedence.

## Storage and dispatcher setup

Notification records require a storage adapter with the `notifications` domain: [libSQL](/integrations/databases/libsql), [PostgreSQL](/integrations/databases/postgresql), or [MongoDB](/integrations/databases/mongodb). Without it, `sendNotificationSignal()` throws instead of silently dropping the record.

Scheduled dispatch is enabled by default and runs through the workflow scheduler. Configure it on the `Mastra` instance:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { ciAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

The defaults are `enabled: true`, `cron: '*/1 * * * *'` (once per minute), and `batchSize: 100`. Only apps that defer or summarize a notification create the lazy dispatch schedule and activate the workflow scheduler with it. Set `enabled: false` to opt out.

## Delivery policy

Every record gets a decision when received, and possibly again when dispatched. The built-in policy uses priority and thread state:

| Priority | Idle thread | Active thread |
| - | - | - |
| `urgent` | Deliver immediately | Deliver immediately |
| `high` | Deliver immediately | Summarize now, then deliver when idle |
| `medium` | Deliver immediately | Batch into a summary |
| `low` | Batch into a summary | Batch into a summary |

Configure a policy on the agent when the defaults don't fit. Source rules run before priority rules, so a noisy source can be summarized while everything else delivers:

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Memory } from '@mastra/memory'

// storage from the Quickstart
export const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
  notifications: {
    deliveryPolicy: {
      sources: {
        github: 'summarize',
      },
      priorities: {
        urgent: 'deliver',
        low: 'discard',
      },
    },
  },
})
```

Mastra evaluates the policy in this order:

1. A custom `decide()` function.
1. `sources`, matched against `record.source`.
1. `priorities`, matched against `record.priority`.
1. `default`.
1. The built-in priority policy.

`decide()` runs at receipt and again at delivery for records whose first decision deferred them or scheduled a summary. The stored schedule fixes when and how they deliver. Delivery honors only `streamOptions` and `hold` from the new decision. Keep `decide()` side-effect free.

## Dispatch

The dispatcher reads due records, groups summaries by `agentId`, `resourceId`, and `threadId`, and emits signals through the thread runtime.

`deliver` emits a full notification immediately. `summarize` emits a summary now or at `summaryAt`. `defer` leaves the record pending until `deliverAt`. `persist` stores it without a signal, and `discard` marks it discarded. `hold` leaves the record for another process's dispatcher without counting an attempt.

### Summaries

Summaries keep a busy thread from receiving a burst of individual notifications. The model sees a compact digest:

```xml
<notification-summary pending="10">github: 3, email: 5, slack: 2</notification-summary>
```

A full notification delivers the record's summary as its contents:

```xml
<notification source="github" kind="ci-status" priority="high" status="delivered">CI failed on main: 3 tests failed in the API suite.</notification>
```

A summary clears `summaryAt` and sets `summarySignalId`. The records stay `pending` and readable. A full notification sets `deliveredSignalId` and marks the record `delivered`.

Summaries don't mark records delivered. When the agent needs the full content, it reads the records through the inbox; reading can inject the full signal and mark the record `seen`, preventing duplicate delivery later.

### Retries and failures

A failed attempt increments `deliveryAttempts` and records `lastDeliveryAttemptAt` and `lastDeliveryError`. The record stays pending and is due again on the next dispatch pass.

After five failed attempts, the record moves to `failed` and stops being due. The cap is exported as `MAX_NOTIFICATION_DELIVERY_ATTEMPTS`. A `hold` leaves it pending without counting an attempt, so another dispatcher can pick it up.

If a custom policy throws during ingress, the record stays pending with an immediate `deliverAt` and a failed attempt, so the dispatcher can retry it.

## Work with the inbox

Give the agent the inbox tool so it can inspect records without exposing storage APIs:

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'

const notificationsStorage = await storage.getStore('notifications')

export const ciAgent = new Agent({
  // ...
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notificationsStorage }),
  },
})
```

The tool supports `list`, `read`, `search`, `markSeen`, `dismiss`, and `archive`. Listing, reading, and searching mark returned unread records `seen`, including `failed` records so the agent learns delivery gave up. `list` defaults to pending, delivered, and failed records. `search` spans all statuses.

`read` matters after a summary. It delivers the selected records' full contents as notification signals rather than ordinary tool output. The agent sees the context on the thread even though the call returned a short status message.

## Agent and client surfaces

[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) is the canonical way to create durable notification records. It returns the record and the policy decision, and includes `accepted`, `signal`, and `persisted` when a signal was emitted, matching the other signal methods described in [Sending signals](/docs/signals/sending-signals).

The JavaScript client SDK can send notification-shaped context through [`client.getAgent().sendSignal()`](/reference/client-js/agents#sendsignal). That path bypasses inbox storage, so use it only when the event needs no record, retries, or later reading. Durable records over HTTP go through the AgentController Session notification route, which forwards to `sendNotificationSignal()`. See the [Session reference](/reference/agent-controller/session) and [Agent Controller](/docs/harness/agent-controller).
