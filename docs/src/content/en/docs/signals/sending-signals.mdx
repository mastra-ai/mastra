# Sending signals

Signals are how input reaches a thread outside the original `agent.stream()` call. This page starts with `sendMessage()`, the method most applications need, then covers queued follow-ups, input from your system, and the durable notification and state paths. The examples call methods on an `Agent`; if your app talks to a running Mastra server, use the same methods through the [client SDK](/reference/client-js/agents) or the [server routes](/reference/server/routes#agent-message-routes). The [Agent reference](/reference/agents/agent#thread-signals) is canonical for signatures.

## Send a message

Use [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) for user-authored input. Pass the thread identifiers so Mastra knows where the input belongs:

```typescript title="src/mastra/signals.ts"
await agent.sendMessage('Compare that with the previous option.', {
  resourceId: 'user_123',
  threadId: 'thread_456',
})
```

Mastra checks the thread first. If it is idle, the message starts a new run. If a run is already active, the message joins it and the model sees it on the next request. When the agent has memory, the message is stored on the thread, so later runs and your UI see it too. [When the agent sees your input](#when-the-agent-sees-your-input) covers the interrupt and wait rules.

When several people share a thread, add `attributes` so the model can tell their messages apart. Mastra renders them as XML attributes on the user message:

```typescript
await agent.sendMessage(
  {
    contents: 'Use the latest customer note too.',
    attributes: { name: 'Jane', sentFrom: 'slack' },
  },
  { resourceId: 'user_123', threadId: 'thread_456' },
)
```

The model receives `<user name="Jane" sentFrom="slack">Use the latest customer note too.</user>`. Messages without attributes arrive as plain user input.

## Queue a follow-up

Use [`queueMessage()`](/reference/agents/agent#queuemessagemessage-options) when the current answer should finish before the agent sees the next message:

```typescript title="src/mastra/signals.ts"
await agent.queueMessage('Also check whether the tests need updates.', {
  resourceId: 'user_123',
  threadId: 'thread_456',
})
```

Queued input always waits for the active run to finish, then starts a new run on the same thread. On an idle thread, it starts immediately. If you change your mind before the queued input runs, [`cancelQueuedMessages()`](/reference/agents/agent#cancelqueuedmessagesoptions) removes it without stopping the active run. Cancellation is best-effort across processes and doesn't revoke an input that has already been accepted for execution.

If the input is system context rather than a user message, use [`queueSignal()`](/reference/agents/agent#queuesignalsignal-options). It takes the same queue and cancellation behavior, but keeps the signal's own `type`, `tagName`, and attributes.

## Send context from a system

Use [`sendSignal()`](/reference/agents/agent#sendsignalsignal-options) when the input isn't a user message. A background job, a webhook handler, or another part of your application can attach context to the thread, and the model sees it as an XML element instead of a user message:

```typescript title="src/mastra/signals.ts"
await agent.sendSignal(
  {
    type: 'reactive',
    tagName: 'ci-result',
    contents: 'CI failed on main: 3 tests failed.',
  },
  { resourceId: 'user_123', threadId: 'thread_456' },
)
```

The `type` describes where the input came from. `reactive` is for context generated by your system or a processor, and `notification` is for an external event. The `tagName` controls the XML tag the model sees, so the example appears as `<ci-result>CI failed on main: 3 tests failed.</ci-result>`. If you omit `tagName`, Mastra uses the type name, except `reactive` defaults to `system-reminder`.

By default, `sendSignal()` uses the same delivery rules as `sendMessage()`: deliver to an active run, wake an idle thread. If the context should apply only to the current request, set `transient: true` so Mastra doesn't store it. Transient signals can't be state signals. The [Agent reference](/reference/agents/agent#sendsignalsignal-options) covers `attributes`, `metadata`, and `providerOptions`.

## Control when input arrives

The defaults are what most applications want: an active thread receives the input, and an idle thread wakes. Override them only when you need a different result.

| Thread state | Default | Other options |
| - | - | - |
| Active | Deliver to the active run | Persist without delivering, or discard |
| Idle | Wake a new run | Persist without running, or discard |

Set the behavior with `ifActive.behavior` or `ifIdle.behavior`. For example, an event that should be available next time but shouldn't start a run on its own can be persisted:

```typescript title="src/mastra/signals.ts"
const result = agent.sendSignal(
  {
    type: 'notification',
    contents: 'A new pull request is ready for review.',
  },
  {
    ...thread,
    ifIdle: { behavior: 'persist' },
  },
)

await result.persisted
```

Every send returns an `accepted` promise. It resolves once Mastra has decided what to do, not when a run finishes: `wake` means this process started a run, `deliver` means the input joined an existing run or another process acknowledged an idle wake and now owns it, `persist` and `discard` mean nothing ran, and `blocked` means a suspended thread couldn't accept a new idle wake. When the action is `wake`, the result also carries the run's `output` stream. A routing failure rejects `accepted`; a run that fails after starting reports the error on that output. Use [`persisted`](/reference/agents/agent#sendsignalsignal-options) to wait for a storage write.

## When the agent sees your input

The delivery decision above resolves when Mastra accepts the input. How soon the model sees it depends on what the active run has already produced.

While a model request has produced only reasoning or metadata, including while waiting for the first token, Mastra can cancel it, discard its response from history, and retry in the same run and step with the new input. Interrupted requests don't count toward `maxSteps` or advance `stepNumber`, so a single-step budget can still produce a replacement response. Mastra doesn't set a separate interruption limit, so repeated input can keep restarting reasoning until a request completes, the run is cancelled, or its timeout expires.

The interrupt window closes as soon as the request produces text, a tool call, or other response content. From then on, input waits for the next loop boundary. Running tools are neither cancelled nor repeated, and queued input never jumps ahead of the active run. If the run reaches `maxSteps` before that boundary, Mastra may save queued input without producing a response.

Reasoning that already streamed may remain visible until the client reloads history. Per-step input processors finish before Mastra cancels the request they prepared. Output processors settle before the next request, and their side effects aren't undone. Usage totals exclude interrupted requests, though providers may still bill for them.

Signals reach the model as XML elements: user messages as `<user>`, reactive context as `<system-reminder>` by default, and external events as `<notification>`. Accepted signals are written into thread history, so later requests see them alongside the messages they followed. [State signals](/docs/signals/state-signals) and [Notifications](/docs/signals/notifications) have their own context shapes.

## Stop a run or clear queued input

Aborting a run preserves queued input by default. Pass `clearPendingSignals: true` to drop the queue as well:

```typescript
subscription.abort({ clearPendingSignals: true })
```

Without a subscription, call [`agent.abortThreadStream()`](/reference/agents/agent#abortthreadstreamoptions) with the same option. Listeners stay subscribed, and a later message can start a new run. With shared PubSub, the clear request is forwarded to the process that owns the run, but it only clears that process's local queue. Neither abort nor cancellation revokes an acceptance that already resolved. Continuation runs started with `continueWithMessages()` are separate from the run that was aborted, so aborting the original run doesn't cancel them.

## Input that outlives the conversation

Some input shouldn't disappear when the current run ends. Mastra has two durable paths for that.

### Notifications

Use [`sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) when an external event should become a tracked notification rather than a one-off piece of context:

```typescript title="src/mastra/signals.ts"
await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed.',
    dedupeKey: 'github:acme/app:main:ci',
  },
  { resourceId: 'user_123', threadId: 'thread_456' },
)
```

Mastra creates or coalesces a durable inbox record and applies the agent's delivery policy. `priority` controls how quickly it is delivered, and `dedupeKey` prevents duplicate pending records for the same event. Unlike `sendSignal({ type: 'notification' })`, this path stores the record for later reading. The [Notifications guide](/docs/signals/notifications) covers delivery and the inbox tool, and the [Notifications reference](/reference/signals/notifications) covers records, priorities, and policies.

### State signals

Use [`sendStateSignal()`](/reference/agents/agent#sendstatesignalstate-options) when the thread needs a named, durable lane of structured context, such as browser state or a background watcher result. State signals are not chat messages; they are snapshots or deltas that the model sees as context. The [State signals guide](/docs/signals/state-signals) covers when to send a snapshot versus a delta and how to compute state in a processor.

If you are building on AgentController, its `Session` wraps these methods and manages the thread subscription for you. The mapping is:

| Task | `Agent` | AgentController `Session` |
| - | - | - |
| Send a user message | `agent.sendMessage()` | `session.sendMessage()` |
| Queue a user follow-up | `agent.queueMessage()` | `session.queueMessage()` |
| Send a typed signal | `agent.sendSignal()` | `session.sendSignal()` |
| Queue a typed signal | `agent.queueSignal()` | `session.queueSignal()` |
| Send a notification | `agent.sendNotificationSignal()` | `session.sendNotificationSignal()` |
| Write a state signal | `agent.sendStateSignal()` | Not exposed on `Session` |
| Subscribe to a thread | `agent.subscribeToThread()` | Managed by `Session` |

See [Agent Controller](/docs/harness/agent-controller) for how `Session` manages threads and subscriptions.
