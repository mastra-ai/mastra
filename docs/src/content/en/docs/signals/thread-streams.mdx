# Thread streams

A thread stream is the ordered output for a [thread](/docs/memory/message-history#threads-and-resources): model text, tool calls, approvals, errors, and run events, delivered as [chunks](/reference/streaming/ChunkType). You read it through a subscription, which can start with stored history as a [`thread-history` chunk](/reference/streaming/ChunkType#thread-history) before live output. Use [`Agent.subscribeToThread()`](/reference/agents/agent#subscribetothreadoptions) when your code owns the [Agent](/reference/agents/agent), or the [client SDK](/reference/client-js/agents#subscribetothread) when it calls a running server.

## Quickstart

Subscribe before you send input. A run starts in response to a signal, so a subscription created afterward misses the beginning of the stream. If an existing subscription's connection drops, reconnect can resume output that's still retained. See [Reconnect](#reconnect). This example uses the JavaScript client SDK against a running Mastra server, so the [Memory](/docs/memory/overview) that stores thread history belongs to the server's agent. If your code owns the `Agent` instance, see the [Agent example](/docs/signals/overview#use-an-agent), which configures Memory alongside the agent.

```typescript title="src/app/chat.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const agent = client.getAgent('support-agent')

const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await agent.sendMessage({
  message: 'Show the shorter version.',
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await subscription.processDataStream({
  onChunk: chunk => {
    console.log(chunk)
  },
  reconnect: true,
})
```

The example creates a client with [`client.getAgent()`](/reference/client-js/mastra-client#methods), subscribes to the thread, sends a message, and reads the chunks with [`processDataStream()`](/reference/client-js/agents#subscribetothread). [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) returns when Mastra accepts the input. The output arrives through `onChunk`.

## Read the stream

### Stored history and live parts

Pass `withInitialHistory: true` to begin with a `thread-history` chunk, which carries the newest page of stored messages in oldest-first order. `perPage` defaults to 40. Subscribers then receive retained parts newer than that history, followed by live parts. History requires memory. Without it, or before the thread has messages, the chunk still arrives first with an empty `messages` array.

### Chunks and runs

Subscribers receive model output, tool calls and results, approvals, aborts, errors, and `thread-history` chunks. [ChunkType](/reference/streaming/ChunkType) lists their shapes. Each chunk carries the `runId` of the run that produced it, so group output per run. The subscription's `activeRunId()` returns the active run or `null`.

### Approve tool calls

When a subscribed run pauses for tool approval, approve or decline the tool call with the subscription-native methods. The resumed chunks arrive through the existing thread subscription. Visit [`client.getAgent().sendToolApproval()` reference](/reference/client-js/agents#sendtoolapproval) and [server agent routes](/reference/server/routes#subscription-tool-approval-routes) for request and response shapes.

A suspended run holds the thread. Until it resumes or is aborted, a new idle wake resolves `accepted` to `blocked`. Pending approvals and suspensions are replayed when you subscribe again. Completed runs aren't. [When the agent sees your input](/docs/signals/sending-signals#when-the-agent-sees-your-input) covers the interrupt and wait rules for input that arrives during a run.

### Filter signals in a subscription

`hideSignals` filters signal chunks for one subscriber. Pass `true` to hide every recognized signal, `false` to show them, or an array of signal types. It doesn't change model context, stored messages, shared broadcasts, or other subscribers, and it isn't a security boundary. The option exists on the in-process core subscription. HTTP and `client-js` subscription requests don't support it.

## Stop a run or close a subscription

[`abort()`](/reference/client-js/agents#subscribetothread) requests cancellation of the active run. `unsubscribe()` closes the subscription without aborting, so the run continues and you can subscribe again later. Pending signals survive an abort unless you pass `clearPendingSignals: true`.

## Reconnect

Use `reconnect: true` for long-lived subscriptions. `processDataStream()` then resubscribes when the transport closes or a reconnect request fails, retrying indefinitely with a one-second delay by default. A 4xx other than `408` or `429`, or a `501`, stops reconnecting and rejects. See the [`subscribeToThread()` reference](/reference/client-js/agents#subscribetothread) for retry options.

A reconnect continues from retained stream data when the shared PubSub backend still holds it. Events held only in another process's in-memory cache can't be recovered. Stored thread history remains the durable record, and `withInitialHistory` reloads its newest page.

### SSE heartbeats for custom endpoints

If you expose your own Server-Sent Events (SSE) endpoint for thread subscriptions, send periodic heartbeat frames while the stream is idle. This keeps browsers, proxies, and load balancers from closing the connection before the next signal or model chunk arrives.

The following example sends an SSE comment every 25 seconds:

```typescript title="src/api/subscribe.ts"
const heartbeat = setInterval(() => {
  controller.enqueue(encoder.encode(': keep-alive\n\n'))
}, 25_000)

request.signal.addEventListener('abort', () => {
  clearInterval(heartbeat)
})
```

Use heartbeats together with client-side reconnect logic. Heartbeats reduce idle disconnects, while reconnects recover when the network or runtime still closes the stream.

## What's replayed and what isn't

Completed runs aren't replayed, even when stored history is loaded. Pending tool approvals and suspensions are emitted when you subscribe again. History is stored messages, not model deltas, so reconnecting doesn't reconstruct text that was never retained.

## Public chunks and internal events

The public stream is typed as `AgentChunkType`, and `thread-history` is a `ThreadHistoryChunk`. The [ChunkType reference](/reference/streaming/ChunkType) documents both. `subscribeThreadEvents()` has its own [Thread events reference](/reference/signals/thread-events). The internal runtime event union isn't public and isn't documented.
