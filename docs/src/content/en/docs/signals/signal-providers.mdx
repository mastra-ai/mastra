# Signal providers

A signal provider connects an external system to your agents. It tracks which threads care about which external resources, watches those resources, and sends matching events into each thread as [notifications](/docs/signals/notifications).

Use a provider when more than one thread can watch the same source and you don't want to wire that bookkeeping by hand. The [`SignalProvider`](/reference/signals/signal-provider) base class owns the subscription registry, polling loop, and notification delivery.

## When to use a provider

Build or configure a provider when:

- An external source produces events tied to resources that threads follow, such as a pull request, Slack channel, or build pipeline.
- Several threads can watch the same resource, and your app needs one place to track those subscriptions.
- You want one integration that supports polling, webhooks, or both.
- The integration also needs to contribute processors or tools to the agent.

### When a provider is overkill

A provider adds a subscription registry and a long-running watcher. Skip it when:

- **You have a single event:** call [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) from your existing server code instead.
- **The data is thread state, not an event:** use a [state signal](/docs/signals/state-signals) so the agent sees the latest value.
- **The content is only needed for one model call:** use a transient reactive signal instead of a durable notification record.

## How a provider works

A provider combines three responsibilities:

- **Subscription tracking:** the base class maps each `resourceId` and `threadId` pair to the external resources it watches.
- **Ingestion:** you implement [`poll()`](/reference/signals/signal-provider#polling) for pull-based sources or [`handleWebhook()`](/reference/signals/signal-provider#webhooks) for push-based sources.
- **Delivery:** when an event matches a subscription, call the protected [`notify()`](/reference/signals/signal-provider#notifications) helper. It forwards the event to [`Agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options). The record gets the same delivery policy, retries, and inbox behavior as any other notification.

Pass the provider to an agent's `signals` array. The agent connects it, starts polling when `pollInterval` is set, and merges any processors or tools the provider returns.

## Map external identities to threads

A notification target has two ids:

- `resourceId` identifies the owner of the thread, such as a user, team, or tenant.
- `threadId` identifies the conversation that should receive the event.

The provider adds a third id, `externalResourceId`, for the thing being watched in the source system. Use a stable, provider-specific format:

- A pull request: `github:acme/app#123`
- A Slack channel: `slack:C0B01RW7A4T`
- A CI pipeline: `acme-app-main`

A subscription is keyed by all three values. The same thread can watch several resources, and several threads can watch the same resource. Store extra provider data in the subscription's `metadata` argument rather than encoding it into the external resource id.

For webhooks, match the incoming payload to `externalResourceId`, then use each subscription's `resourceId` and `threadId` as the notification target. That keeps source identity and Mastra thread identity separate.

## Quickstart

This provider polls a CI system and notifies every thread subscribed to a failing pipeline.

Notification storage must be configured on the `Mastra` instance, as described in [Notifications storage setup](/docs/signals/notifications#storage-and-dispatcher-setup). Without it, `notify()` can't create records.

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderTarget, SignalSubscription } from '@mastra/core/signals'

type BuildStatus = {
  id: string
  status: 'passed' | 'failed'
}

const builds = new Map<string, BuildStatus>([
  ['acme-app-main', { id: 'build_123', status: 'failed' }],
])

async function fetchBuildStatus(pipeline: string): Promise<BuildStatus> {
  return builds.get(pipeline) ?? { id: 'build_unknown', status: 'passed' }
}

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const
  readonly pollInterval = 30_000

  watch(target: SignalProviderTarget, pipeline: string) {
    return this.subscribe(target, pipeline)
  }

  unwatch(target: SignalProviderTarget, pipeline: string) {
    return this.unsubscribe(target, pipeline)
  }

  async poll(subscriptions: SignalSubscription[]) {
    for (const sub of subscriptions) {
      const build = await fetchBuildStatus(sub.externalResourceId)

      if (build.status !== 'failed') continue

      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build failed for ${sub.externalResourceId}`,
          payload: build,
          dedupeKey: `${this.id}:${sub.externalResourceId}:${build.id}`,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }
  }
}
```

Register the provider with an agent, then subscribe a thread to the pipeline it should watch:

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { CiSignals } from '../signals/ci-signals'

export const ciSignals = new CiSignals()

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage CI updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [ciSignals],
})

ciSignals.watch({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme-app-main')
```

The agent calls `connect()`, starts polling, and sends a notification when the pipeline fails.

## Build a provider

### Connect and subscriptions

Override [`connect()`](/reference/signals/signal-provider#connection) only when you need setup that depends on the connected agent. Always call `super.connect(agent)` first.

Subscriptions live behind protected methods:

- `subscribe(target, externalResourceId, metadata?)` adds a subscription or merges metadata into an existing one.
- `unsubscribe(target, externalResourceId)` removes one subscription.
- `unsubscribeAll(target)` removes every subscription for a thread.
- `getSubscriptions()`, `getSubscriptionsForResource()`, and `getSubscriptionsForThread()` read the registry.
- `hasSubscription()` and `subscriptionCount` support guards and diagnostics.

Expose only the operations your application needs. The CI example wraps `subscribe()` and `unsubscribe()` in public `watch()` and `unwatch()` methods so application code doesn't reach into the provider's protected API.

### Polling

Set `pollInterval` in milliseconds and implement `poll(subscriptions)` when the source doesn't push events to your app.

The base class handles the timer:

- It skips a cycle when there are no subscriptions.
- It doesn't overlap cycles, so a slow `poll()` doesn't run concurrently with itself.
- It catches errors from `poll()`, logs them, and waits for the next cycle.
- It calls `unref()` on the timer so polling alone doesn't keep the process alive.

The base class doesn't retry a failed poll immediately. If a source is temporarily unavailable, let the next interval retry, or add your own backoff inside `poll()`.

### Webhooks

Use webhooks when the source can call your app. Override `handleWebhook(request)` to parse the payload, look up subscriptions, and call `notify()` for each match:

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderWebhookRequest } from '@mastra/core/signals'

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const

  async handleWebhook(request: SignalProviderWebhookRequest) {
    const payload = request.body as { pipeline: string; status: string }
    const subscriptions = this.getSubscriptionsForResource(payload.pipeline)

    for (const sub of subscriptions) {
      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build ${payload.status} for ${payload.pipeline}`,
          payload,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }

    return { status: 200, body: { matched: subscriptions.length } }
  }
}
```

`handleWebhook()` is a provider method, not an auto-mounted HTTP route. Call it from your own endpoint with the request body, headers, and route params. Verify the source's signature against the raw request body before parsing or notifying where the source requires it.

### Durable subscriptions

The base registry is in-memory and belongs to one provider instance in one process. It doesn't survive a restart and isn't shared across instances.

If subscriptions must survive a restart, persist them in your own storage and rehydrate them in [`start()`](/reference/signals/signal-provider#start). Call `subscribe()` for each persisted subscription before polling needs it. A second process has an empty registry until it rehydrates its own copy.

### Lifecycle hooks

The agent calls `connect()` when it's constructed and starts polling immediately after. It also invokes `start()` without awaiting it, so keep `start()` independent of the first poll cycle and handle its errors.

[`stop()`](/reference/signals/signal-provider#stop) is synchronous. The default implementation stops polling and clears every subscription index. Override it for cleanup, but call `super.stop()` so the registry is released:

```typescript oxfmt:false
override stop() {
  this.closeClient()
  super.stop()
}
```

Call `stop()` from your application's shutdown path. The agent doesn't call it for you. If closing an external client is asynchronous, expose a separate async shutdown method and await it before calling `stop()`.

### Processors and tools

Providers can contribute behavior to the connected agent:

- Return input processors from `getInputProcessors()` and output processors from `getOutputProcessors()`.
- Return agent-callable tools from `getTools()`.

The agent resolves these once, after `connect()`, and registers the processors with the Mastra instance. This is how the built-in task provider wires its state processor and task tools together.

### Send notifications

[`notify()`](/reference/signals/signal-provider#notifications) is a thin wrapper around the connected agent's `sendNotificationSignal()`. Accepts the same notification fields: `source`, `kind`, `summary`, optional `priority`, `payload`, `dedupeKey`, `coalesceKey`, and `attributes`.

Use `dedupeKey` for one event that may arrive more than once, such as the same failing build detected on consecutive polls. Use `coalesceKey` when several related events should merge into one pending record. The [Notifications guide](/docs/signals/notifications#create-and-coalesce-records) covers the merge rules.

`notify()` throws when the provider isn't connected to an agent. It also propagates storage errors from `sendNotificationSignal()`, so let those reach your poll or webhook error handling instead of swallowing them.

### Shut down cleanly

During shutdown:

1. Stop accepting new webhook work.
1. Stop polling with `stopPolling()` or `stop()`.
1. Clear the subscription registry.
1. Close or release external clients and connections.
1. Let in-flight `notify()` calls finish where your runtime allows it.

The base class clears the registry in `stop()`. It can't drain an in-flight webhook handler or close an async client for you, so coordinate those in your application's shutdown path.

## Built-in providers

### Task signal provider

[`TaskSignalProvider`](/reference/signals/task-signal-provider) bundles the task tools and the `TaskStateProcessor` behind one registration. Add it when you want the agent to maintain a task list across turns:

```typescript
import { Agent } from '@mastra/core/agent'
import { TaskSignalProvider } from '@mastra/core/signals'

const agent = new Agent({
  // ...
  signals: [new TaskSignalProvider()],
})
```

The provider contributes `task_write`, `task_update`, `task_complete`, and `task_check`, plus the processor that projects the task list onto a state-signal lane. Task tracking requires a memory-backed thread and a Mastra `storage` instance; without memory, the tools report that tracking needs agent memory.

### Webhook signal provider

For generic webhook sources, use [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider) instead of writing a subclass. Configure a function that extracts the resource id from the payload and an optional function that builds the notification:

```typescript title="src/mastra/index.ts"
import { Agent } from '@mastra/core/agent'
import { WebhookSignalProvider } from '@mastra/core/signals'

const webhooks = new WebhookSignalProvider({
  extractResourceId: payload => (payload as { repository: string }).repository,
  buildNotification: (payload, sub) => ({
    source: 'ci',
    kind: 'build-status',
    priority: 'medium',
    summary: `Build ${(payload as { status: string }).status} for ${sub.externalResourceId}`,
  }),
})

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [webhooks],
})

webhooks.subscribeThread({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme/app')
```

When a webhook arrives, call `webhooks.handleWebhook({ body, headers })` from your route. The provider matches the extracted resource id, which can be a string or an array of strings, against its subscriptions and notifies each matching thread.

Without `extractResourceId`, the provider reads `resource` or `externalResourceId` from the payload. Without `buildNotification`, it sends a `webhook-event` notification at `medium` priority.

## Production checklist

Before you deploy a provider:

- **Deduplicate retries:** give every event a stable `dedupeKey` or `coalesceKey`. Webhook deliveries and poll cycles can repeat, and the provider doesn't deduplicate before calling `notify()`.
- **Verify webhooks:** check signatures against the raw request body before parsing. Reject invalid requests at your HTTP endpoint, not inside `notify()`.
- **Handle source outages:** Polling retries on the next interval. Add backoff inside `poll()` if the source needs it. Webhook sources usually retry from their side, so return a non-2xx status when you couldn't accept the event.
- **Persist subscriptions if they matter:** the registry is in-memory. Rehydrate it in `start()` when a restart must preserve watches.
- **Use shared storage:** notification records and delivery policy depend on the Mastra storage configured for the agent.
- **Plan shutdown:** stop accepting webhooks, stop polling, close clients, and let in-flight notifications settle.
- **Watch the notification queue:** summaries and deferred deliveries rely on the [notification dispatcher](/docs/signals/notifications#dispatch), especially when several processes share the same storage.
