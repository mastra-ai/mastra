# Signals

**Added in:** `@mastra/core@1.39.0`

Signals are typed asynchronous input to a thread. A thread is the durable, addressable conversation an agent works on. [Memory](/docs/memory/message-history#threads-and-resources) owns that concept and its storage. You subscribe to the thread's stream to receive output, then send input whenever you have it. Mastra decides whether the input joins an active run or starts a run on an idle thread, so you don't manage active or idle state.

For a thread-based agent, signals are the default input path. Send a message when a user replies, a signal when a background job adds context, and a notification when an external event should reach the agent later. [`agent.stream()`](/reference/streaming/agents/stream) is the exception: use it for a one-off request that doesn't need an addressable thread.

## Quickstart

Create an agent, subscribe to a thread, then send input to that thread. Subscribing first means the subscription is already open when the input starts a run.

### Use an Agent

This example uses a new thread ID and no memory, so it demonstrates input routing but doesn't persist history between runs or process restarts. Configure [Memory](/docs/memory/overview) if you want stored thread history.

```typescript title="src/mastra/signals.ts"
import { Agent } from '@mastra/core/agent'

const agent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user compare options.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

await agent.sendMessage('Compare that with the previous option.', thread)

for await (const chunk of subscription.stream) {
  console.log(chunk)
}
```

When the thread has a running agent stream, [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) becomes new input inside that agent loop. When the thread is idle, Mastra starts a stream with the message as the first input. [Sending signals](/docs/signals/sending-signals) covers the other input paths and their delivery behavior.

### Use the client SDK

The same order applies through [`client.getAgent()`](/reference/client-js/mastra-client#methods): call `subscribeToThread()` first, then send a message to the same thread. The client returns the subscription stream and leaves run ownership on the server. [Thread streams](/docs/signals/thread-streams) shows the full client example.

## How signals reach a thread

You send input to the thread, not to a specific request. If a run is active, Mastra delivers the input into that run when the loop can accept it. Otherwise the input waits or starts a new run on the idle thread. A queued follow-up waits for the active run to finish. Delivery policy can also persist input without running it or discard it. Only one process owns a thread at a time, so input sent elsewhere routes to that owner. [Sending signals](/docs/signals/sending-signals#when-the-agent-sees-your-input) covers delivery choices and accepted results, and [Running across processes](/docs/signals/running-across-processes) covers leases.

## Choose an API surface

| Surface | Use it for | Canonical reference |
| - | - | - |
| Direct `Agent` methods | Server-side code that owns the agent instance | [Agent reference](/reference/agents/agent#thread-signals) |
| HTTP or the JavaScript client SDK | Applications that call a running Mastra server | [Server agent routes](/reference/server/routes#agent-message-routes), [`client.getAgent()`](/reference/client-js/agents) |
| AgentController `Session` | Long-running assistants and coding agents built on AgentController | [Agent Controller](/docs/harness/agent-controller) |

The `Agent` methods are the canonical Signals API. `Session` is a higher-level convenience surface that manages a thread and subscription for you. It's not the recommended starting point for most applications. See [Agent Controller](/docs/harness/agent-controller) for how it manages threads.
