# Signals

**Added in:** `@mastra/core@1.39.0`

Signals are typed input you send into an existing agent thread instead of passing everything into a single `agent.stream()` call. A signal can be a message, extra context, or a state update, and Mastra decides how it joins the thread based on what the agent is doing.

For long-running agents, that removes the need to restart a request whenever something changes. The thread keeps its history, the active run keeps its context, and your UI keeps one stream open instead of reconnecting for every update.

Watch [Mastra signals overview](https://www.youtube.com/watch?v=7It2y89TVP4) to see how signals wake and steer long-running agents.

:::

## When to use signals

Reach for signals when input arrives after the original `agent.stream()` call:

- A user replies while the agent is still working.
- A background job adds context to an active thread.
- An external system needs to wake, update, or notify the agent.
- An agent needs a durable lane of structured context across turns.

Use [`sendMessage()` and `queueMessage()`](/docs/signals/sending-signals#send-a-message) for user-authored input, [`sendSignal()`](/docs/signals/sending-signals#send-context-from-a-system) for system context, [`sendStateSignal()`](/docs/signals/state-signals) for durable state lanes, and [`sendNotificationSignal()`](/docs/signals/notifications) when an external event should create a durable notification inbox record.

The same mechanism connects to the rest of Mastra. [Memory](/docs/memory/overview) stores signal messages on the thread, while state signals and notifications keep their own durable lanes and records. [Processors](/docs/agents/processors) can send signals and compute state during a run. [Workflows](/docs/workflows/overview) can send signals as part of a larger process, and [schedules](/docs/harness/schedules) use signals to deliver input on a timer. A shared [PubSub](/docs/server/pubsub) backend coordinates signals across processes. AgentController's [`Session`](/docs/harness/agent-controller) wraps thread signals for long-running assistants that manage their own thread and subscription.

## Quickstart

Create an agent, subscribe to a thread, then send a message to that thread. The subscription receives the active stream when the message wakes the agent or enters a running loop.

### Use an Agent

```typescript title="src/mastra/signals.ts"
import { Agent } from '@mastra/core/agent'

const agent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user compare options.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

await agent.sendMessage('Compare that with the previous option.', thread)

for await (const chunk of subscription.stream) {
  console.log(chunk)
}
```

When the thread has a running agent stream, `sendMessage()` becomes new input inside that agent loop. When the thread is idle, Mastra starts a stream with the message as the first input.

## Signals and thread streams

:::note[Outline]

- **Durable thread:** the stored conversation that outlives a single request.
- **Run:** one execution of the agent loop. One run owns a thread at a time.
- **Signal:** typed input attached to a thread.
- **Thread stream:** the ordered output and lifecycle events for a thread.

State the spine: signals are input; thread streams are output.

:::

## Choose an API surface

| Surface | Use it for | Canonical reference |
| - | - | - |
| Direct `Agent` methods | Server-side code that owns the agent instance | [Agent reference](/reference/agents/agent#thread-signals) |
| HTTP or the JavaScript client SDK | Applications that call a running Mastra server | [Server agent routes](/reference/server/routes#agent-message-routes), [`client.getAgent()`](/reference/client-js/agents) |
| AgentController `Session` | Long-running assistants and coding agents built on AgentController | [Agent Controller](/docs/harness/agent-controller) |

The `Agent` methods are the canonical Signals API. `Session` is a higher-level convenience surface built on AgentController that manages a thread and subscription for you. It is not the recommended starting point for most applications; see [Agent Controller](/docs/harness/agent-controller) for how it manages threads.
