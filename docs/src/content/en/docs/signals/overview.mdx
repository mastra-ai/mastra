# Signals

**Added in:** `@mastra/core@1.39.0`

Signals are typed input you send into an existing agent thread instead of passing everything into a single [`agent.stream()`](/reference/streaming/agents/stream) call. A signal can be a message, extra context, or a state update, and Mastra decides how it joins the thread based on what the agent is doing.

For long-running agents, that removes the need to restart a request whenever something changes. The thread keeps its history, the active run keeps its context, and your UI keeps one stream open instead of reconnecting for every update.

Watch [Mastra signals overview](https://www.youtube.com/watch?v=7It2y89TVP4) to see how signals wake and steer long-running agents.

:::

## When to use signals

Use signals when input arrives after the original `agent.stream()` call:

- A user replies while the agent is still working.
- A background job adds context to an active thread.
- An external system needs to wake, update, or notify the agent.
- An agent needs context that stays available across turns, such as browser state.

The same mechanism connects to the rest of Mastra. [Memory](/docs/memory/overview) stores signal messages on the thread, [processors](/docs/agents/processors) can send signals during a run, [workflows](/docs/workflows/overview) and [schedules](/docs/harness/schedules) can send them as part of a larger process, and a shared [PubSub](/docs/server/pubsub) backend coordinates them across processes. AgentController's [`Session`](/docs/harness/agent-controller) wraps thread signals for long-running assistants that manage their own thread and subscription.

## Signals and thread streams

A **thread** is the conversation a request works on. With memory, Mastra stores that conversation so it outlives a single request.

A **run** is one execution of the agent loop. A thread has at most one active run at a time.

A **signal** is typed input attached to a thread: a user message, system context, a state update, or a notification.

A **thread stream** is the ordered output and lifecycle events for that thread: model text, tool calls, approvals, errors, and run events.

Signals are input. Thread streams are output. Sending a signal changes what the agent knows. Subscribing to the thread stream shows what the agent does about it.

### How input joins a thread

By default, an idle thread wakes a new run. [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options), [`queueMessage()`](/reference/agents/agent#queuemessagemessage-options), [`sendSignal()`](/reference/agents/agent#sendsignalsignal-options), and [`queueSignal()`](/reference/agents/agent#queuesignalsignal-options) start that run when this process owns the thread. Otherwise, the input routes to the process that owns it.

By default, an active run receives the input. Before the request produces text or a tool call, Mastra can replace the request with one that includes the input. After content starts, the input waits for the next loop boundary.

A queued follow-up waits for the active run to finish. [`queueMessage()`](/reference/agents/agent#queuemessagemessage-options) and [`queueSignal()`](/reference/agents/agent#queuesignalsignal-options) share the same queue. On an idle thread, they start a run immediately.

Only one process owns a thread at a time. Delivery policy can also persist input without running it, or discard it. [Sending signals](/docs/signals/sending-signals#when-the-agent-sees-your-input) covers the interrupt rules and accepted result, and [Running across processes](/docs/signals/running-across-processes) covers leases.

To send input, use [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) and [`queueMessage()`](/reference/agents/agent#queuemessagemessage-options) for user-authored input, [`sendSignal()`](/reference/agents/agent#sendsignalsignal-options) for system context, [`sendStateSignal()`](/reference/agents/agent#sendstatesignalstate-options) for durable state lanes, and [`sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) when an external event should create a durable notification inbox record. The [Sending signals guide](/docs/signals/sending-signals) walks through each path.

## Quickstart

Create an agent, call [`Agent.subscribeToThread()`](/reference/agents/agent#subscribetothreadoptions), then send a message to that thread. The subscription receives the active stream when the message wakes the agent or enters a running loop.

### Use an Agent

This example uses a new thread ID and no memory, so nothing is persisted between runs or process restarts. Configure [memory](/docs/memory/overview) if you want stored thread history.

```typescript title="src/mastra/signals.ts"
import { Agent } from '@mastra/core/agent'

const agent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user compare options.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

await agent.sendMessage('Compare that with the previous option.', thread)

for await (const chunk of subscription.stream) {
  console.log(chunk)
}
```

When the thread has a running agent stream, `sendMessage()` becomes new input inside that agent loop. When the thread is idle, Mastra starts a stream with the message as the first input.

## Choose an API surface

| Surface | Use it for | Canonical reference |
| - | - | - |
| Direct `Agent` methods | Server-side code that owns the agent instance | [Agent reference](/reference/agents/agent#thread-signals) |
| HTTP or the JavaScript client SDK | Applications that call a running Mastra server | [Server agent routes](/reference/server/routes#agent-message-routes), [`client.getAgent()`](/reference/client-js/agents) |
| AgentController `Session` | Long-running assistants and coding agents built on AgentController | [Agent Controller](/docs/harness/agent-controller) |

The `Agent` methods are the canonical Signals API. `Session` is a higher-level convenience surface built on AgentController that manages a thread and subscription for you. It's not the recommended starting point for most applications. See [Agent Controller](/docs/harness/agent-controller) for how it manages threads.
