# Signals

**Added in:** `@mastra/core@1.39.0`

Signals are typed input you send into an agent thread instead of packing everything into a single `agent.stream()` call. A signal can be a user follow-up, an event from another system, a policy reminder, or state that a processor computed. Because the thread stores the conversation, Mastra can wake an idle agent with the signal, deliver it into a run that is already active, or hold it for the next turn. A thread subscription streams the output and lifecycle back to your app, so the UI stays current while the agent keeps working.

The value is one durable thread that accepts input from many sources. Users can steer a run, background jobs can attach context, and external systems can wake or notify the agent without restarting the conversation. Subscribers see a single ordered stream regardless of where that input came from. For the method-by-method choice, see [Choose a method](/docs/signals/sending-signals#choose-a-method).

## What signals and thread streams are

### Threads, runs, signals, and streams

:::note[Outline]

- **Durable thread:** the stored conversation that outlives a single request.
- **Run:** one execution of the agent loop. One run owns a thread at a time.
- **Signal:** typed input attached to a thread.
- **Thread stream:** the ordered output and lifecycle events for a thread.

State the spine: signals are input; thread streams are output.

:::

### How input joins a thread

:::

## When to use signals

Use signals when an agent thread needs new input or context outside the original `stream()` call. Signals are useful when users send follow-up messages while a run is active, when background systems need to add context to a thread, or when external events should wake, update, or notify the agent.

Use `sendMessage()` and `queueMessage()` for user-authored input. Use `sendSignal()` for lower-level system context. Use `sendStateSignal()` for durable state lanes, and use `sendNotificationSignal()` when an external event should create a durable notification inbox record.

## Quickstart

Create an agent, subscribe to a thread, then send a message to that thread. The subscription receives the active stream when the message wakes the agent or enters a running loop.

### Use an Agent

```typescript title="src/mastra/signals.ts"
import { Agent } from '@mastra/core/agent'

const agent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user compare options.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

await agent.sendMessage('Compare that with the previous option.', thread)

for await (const chunk of subscription.stream) {
  console.log(chunk)
}
```

When the thread has a running agent stream, `sendMessage()` becomes new input inside that agent loop. When the thread is idle, Mastra starts a stream with the message as the first input.

## Choose an API surface

| Surface | Use it for | Canonical reference |
| - | - | - |
| Direct `Agent` methods | Server-side code that owns the agent instance | [Agent reference](/reference/agents/agent#thread-signals) |
| HTTP or the JavaScript client SDK | Applications that call a running Mastra server | [Server agent routes](/reference/server/routes#agent-message-routes), [`client.getAgent()`](/reference/client-js/agents) |
| AgentController `Session` | Long-running assistants and coding agents built on AgentController | [Agent Controller](/docs/harness/agent-controller) |

The `Agent` methods are the canonical Signals API. `Session` is a higher-level convenience surface built on AgentController that manages a thread and subscription for you. It is not the recommended starting point for most applications; see [Agent and AgentController surfaces](/docs/signals/sending-signals#agent-and-agentcontroller-surfaces) for the method mapping.

## How signals relate to other features

- [Memory](/docs/memory/overview): signal input is stored as messages on a memory-backed thread; state signals and notifications keep their own durable lanes and records.
- [Processors](/docs/agents/processors): processors can send signals and compute state during a run.
- [Workflows](/docs/workflows/overview): workflows can send signals into a thread as part of a larger process.
- [PubSub](/docs/server/pubsub): a shared PubSub backend coordinates signals across processes.
- [Harness](/docs/harness/overview): harness features such as goals and schedules deliver input through signals.
- [Agent Controller](/docs/harness/agent-controller): `Session` wraps thread signals for long-running assistants.
