# Classifier

**Added in:** `@mastra/core@1.69.0`

A language model writes text for people to read. When your application needs the judgment inside that text, you ask for prose and then parse a decision back out of it. A classifier avoids the parsing entirely. You send a decision model your state, which can be any JSON-compatible data, together with a fixed set of typed questions, and it returns one typed answer per question. The model generates no text.

An answer is a named choice from a list, a position on an ordered scale, or the probability that a statement is true. Choice and score answers can also carry a probability for every option, so your code can set a threshold, compare options, or weigh one answer against another. The model supplies the judgment and your code supplies the policy. An answer changes nothing until your application acts on it.

Classifiers run on a decision model: a model built to answer this kind of question. Create it with a provider's `decisionModel()` factory, such as the [TypeSafe AI provider](https://ai-sdk.dev/providers/ai-sdk-providers/typesafe-ai). It isn't the agent's language model, and the constructor doesn't accept a `'provider/model'` string. See [Choosing a decision model](#choosing-a-decision-model).

## When to use a classifier

Use a classifier when the decision has a small, known set of outcomes:

- Route a request to the right team, handler, or workflow branch.
- Gate an action on a threshold, such as whether a tool call needs human review.
- Score one dimension of an output, such as tone or quality.
- Answer a yes-or-no question about an input, such as whether a message is unsafe.

A classifier fits when you can describe the decision as a question with a fixed answer shape. If the model needs to produce a data object with many interdependent fields, use [structured output](/docs/agents/structured-output) on an agent instead.

[Evals](/docs/evals/overview) answer a different question: they measure whether outputs are good over time, while a classifier makes one decision at runtime that your application acts on. Use [`createClassifierScorer()`](/reference/evals/create-classifier-scorer) to project a classifier answer into a score for the eval pipeline.

## How classifiers work

A classifier holds a set of named questions and a decision model. Each [`decide()`](/reference/classifier/classifier#decideoptions) call sends the state once, with every question attached, and returns one answer per question, keyed by question name. Because the questions travel in the same request, adding another one doesn't add a round trip.

Questions come in three types:

| Type | Asks | Returns |
| - | - | - |
| `choice` | Which key of the `criteria` record applies? | `choice`, plus a probability for every option when the provider reports them |
| `score` | Where on the ordered `criteria` list does the state fall? | `score`, plus a probability for every level when the provider reports them |
| `boolean` | Is this statement true? | `probability` |

For `score`, the indexes of the `criteria` list define the range of answers, and scores can be fractional.

A `boolean` answer is the probability that the statement is true. A value of `0.9` means the decision model estimates a 90% chance the answer is `true`. It doesn't mean the model is 90% confident of whichever outcome is more likely.

Each question should ask for one judgment. A question that weighs several factors produces an answer you can't route on, because a shift in any factor moves it. Ask for the factors separately and combine the answers in code, where you can retune a threshold without rewriting a prompt. See [Designing questions](/reference/classifier/classifier#designing-questions).

This example uses the TypeSafe AI provider. Install `@ai-sdk/typesafe-ai` and set `TYPESAFE_AI_API_KEY` before running it. It asks one boolean question and acts on the answer:

```typescript title="src/mastra/safety.ts"
import { Classifier } from '@mastra/core/classifier'
import { typeSafeAi } from '@ai-sdk/typesafe-ai'

const safety = new Classifier({
  id: 'safety',
  model: typeSafeAi.decisionModel('__AI_SDK_TYPESAFE_DECISION_MODEL__'),
  questions: {
    unsafe: {
      type: 'boolean',
      instructions: 'Does this message contain unsafe content?',
    },
  },
})

const { answers } = await safety.decide({
  state: { message: userInput },
})

if (answers.unsafe.type === 'refusal') {
  // The model declined to answer. Apply your fallback policy.
} else if (answers.unsafe.probability > 0.8) {
  // Block the message.
}
```

A decision model can refuse a question, for example when a safety policy prevents it from answering. A refused question returns `{ type: 'refusal' }` with no `choice`, `score`, or `probability`, while the other questions in the same call keep their answers. Check `type` before reading an answer field.

## Where classifiers run

Call `decide()` directly when your application controls the decision point. Mastra also runs classifiers in several places:

- **Workflow routing.** A [`.classifier()`](/docs/workflows/control-flow#route-with-a-classifier) step classifies the workflow input before `.branch()` routes on the answer.
- **Guardrails and moderation.** [`ClassifierProcessor`](/reference/processors/classifier-processor) runs a classifier over agent input, output, or stream chunks and passes the answers to `onResult`, where you can abort or filter the content. See [Guardrails](/docs/agents/guardrails).
- **Model selection.** [`ModelSelectionProcessor`](/reference/processors/model-selection-processor) classifies the incoming request and downgrades the agent to a cheaper model when a decision model is confident the cheaper model can handle it.
- **Scorers.** `createClassifierScorer()` turns one classifier question into a scorer for the eval pipeline.

You can also register classifiers on the `Mastra` instance, which shares them across your application and lets workflows reference them by ID. See [Registering classifiers](/reference/classifier/classifier#registering-classifiers).

## Choosing a decision model

The examples on this page use the TypeSafe AI provider. Other AI SDK providers, including OpenAI, Anthropic, and Google, expose `decisionModel()` factories as well. Each provider declares which question types its models support. For the full list of providers and model IDs, see [Decision models](/reference/classifier/classifier#decision-models).

If provider output needs normalization before the classifier validates it, wrap the decision model in [`MastraDecisionModel`](/reference/classifier/classifier#customize-provider-responses). The classifier wraps a raw AI SDK decision model in `MastraDecisionModel` automatically.

The classifier forwards the state you pass to the provider along with each question's `instructions`. Send only the data the decision needs. If the state contains sensitive fields, redact them before the call or use a provider that meets your data-handling requirements.

## Reliability

`decide()` makes two retry attempts after retryable AI SDK `APICallError` failures by default. Set `maxRetries` to change the count. Other errors reject immediately, and an `abortSignal` cancels the active request and any wait between retries.

Before returning, the classifier validates provider output. It requires exactly one answer per question, checks that each answer matches its question type, and rejects incomplete probability distributions, out-of-range scores, non-finite token counts, and invalid response timestamps. Invalid output rejects instead of returning partial answers. See [Validation and errors](/reference/classifier/classifier#validation-and-errors) for the full list.

## Observability

Inside an active Mastra trace, each `decide()` call creates a `CLASSIFIER_EVALUATION` child span. The span records the state, questions, and answers, along with the classifier and model identifiers, provider, attempts, duration, and token usage. Token usage also feeds [automatic token metrics](/reference/observability/metrics/automatic-metrics#token-usage-metrics). Registered classifiers start a root span when evaluated outside a trace.

Classifier traces appear under the classifier entity in [Studio](/docs/studio/overview), where you can filter and group them like agents and workflows. Workflow classifier steps render as classifier nodes in the flow graph. To keep state and answers out of exported traces, set `hideInput` and `hideOutput` on the run that calls the classifier. See [hiding sensitive input/output](/docs/observability/tracing/overview#hiding-sensitive-inputoutput).
