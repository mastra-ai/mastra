# Mastra server

Mastra compiles your application into a standalone Node.js server that can run on any platform supporting Node.js, Bun, or Deno.

:::tip

This guide covers deploying the standalone server generated by `mastra build`. If you need to integrate Mastra into an existing Express or Hono application, see [Server Adapters](/docs/server/server-adapters) instead.

:::

## Building your application

Run the build command from your project root:

```bash
mastra build
```

This creates a `.mastra` directory containing your production-ready server. Read the [`mastra build`](/reference/cli/mastra#mastra-build) reference for all available flags.

## Build output

After building, Mastra creates the following structure:

```
.mastra/
├── .build/                # Intermediate build artifacts (module maps, analysis)
└── output/
    ├── index.mjs          # Server entry point
    ├── mastra.mjs         # Your bundled Mastra configuration
    ├── tools.mjs          # Aggregated tool exports
    ├── tools/             # Individual tool bundles
    ├── package.json       # Production dependencies
    ├── node_modules/      # Installed dependencies
    ├── .npmrc             # Copied from your project (if present)
    ├── public/            # Static assets (if src/mastra/public exists)
    └── playground/        # Studio UI (if --studio flag used)
```

The `output` directory is self-contained. You can copy it to any server and run it directly.

## Running the server

Start the server using the Mastra CLI:

```bash
mastra start
```

Or run directly with Node.js:

```bash
node .mastra/output/index.mjs
```

The `mastra start` command provides additional features:

- Loads environment variables from `.env.production` and `.env`
- Provides helpful error messages for missing modules
- Handles process signals for graceful shutdown

Read the [`mastra start`](/reference/cli/mastra#mastra-start) reference for all available flags.

## Graceful shutdown and rolling deploys

A deploy replaces the running server process. Any agent turn served by a plain `agent.stream()` call is owned by that process, so no other replica can pick up the stream. If the process is killed mid-turn, the client sees the connection close without a terminal event, and observability spans for the run stay unfinished.

This section covers what the generated server does when it's asked to stop, how to give long turns time to finish, and when to reach for [durable agents](/docs/harness/durable-agents) instead.

### What happens on `SIGINT` or `SIGTERM`

By default the generated server installs its own signal handlers. On the first `SIGINT` or `SIGTERM` it:

1. Stops accepting new connections. Idle keep-alive connections are closed immediately so they don't consume the drain window.
1. Waits for in-flight requests, including active streams, to finish, bounded by [`server.drainTimeout`](/reference/configuration#serverdraintimeout) (default 5 seconds). When the window passes, remaining HTTP connections are force-closed.
1. Runs `mastra.shutdown()` to release storage and other resources, bounded by a separate 5 second limit.
1. Exits the process.

A second shutdown signal skips the drain and terminates immediately. Set [`server.handleShutdownSignals`](/reference/configuration#serverhandleshutdownsignals) to `false` to manage signals yourself, with the caveats described in the reference.

### Let long turns finish with `server.drainTimeout`

The 5 second default is too short for agent turns that run for minutes. Set `drainTimeout` above your longest expected turn:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'

export const mastra = new Mastra({
  server: {
    // Allow in-flight turns up to 4 minutes to finish during shutdown
    drainTimeout: 240_000,
  },
})
```

The drain only helps if your hosting platform waits that long between sending `SIGTERM` and hard-killing the process. Check your platform's termination grace period (for example `terminationGracePeriodSeconds` on Kubernetes) and keep `drainTimeout` below it, leaving room for the 5 second `mastra.shutdown()` bound.

### When draining isn't enough

A drained stream finishes normally, but a stream cut off by the drain timeout or a hard kill can't be recovered: the run state only existed in the terminated process. If turns must survive a process replacement, wrap the agent with [durable agents](/docs/harness/durable-agents). Durable runs persist their state to storage, clients can [reconnect to the stream](/docs/harness/durable-agents#resumable-streams) after a disconnect, and [crash recovery](/docs/harness/durable-agents#crash-recovery) can re-drive interrupted runs on the next server start.

Durability isn't free. Recovery re-issues model calls and re-executes tool calls, so your tools must be idempotent. Run state also needs a shared persistent database, and multi-replica recovery has no distributed lease yet. Reserve durability for turns where losing progress is worse than that added complexity.

### Handling interrupted streams in the client

No configuration can guarantee a final application event when the process is hard-killed. Treat a connection that closes before your protocol's terminal event (for example a `finish` chunk over SSE) as an interrupted turn: surface it to the user and offer a retry, or reconcile against persisted state. With durable agents, reconnect to the run's stream instead of retrying the whole turn.

### Choosing a strategy

| Situation | Approach |
| - | - |
| Turns are short or bounded interruption is acceptable | Default drain; optionally raise `server.drainTimeout` |
| Turns run for minutes and the platform's grace period allows it | Raise `server.drainTimeout` above the longest turn |
| Turns must survive process replacement or client disconnects | [Durable agents](/docs/harness/durable-agents) with reconnect and recovery |
| Interruption is rare and cheap to redo | Detect premature stream close in the client and retry |

## Build configuration

### Build-time configuration

Mastra reads the `bundler`, `deployer`, and `server` options while it builds your application. Keep those options as direct properties of the object passed to `new Mastra()` so the build can extract them.

The following entry-file shape works:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'

export const mastra = new Mastra({
  bundler: {
    externals: ['sharp'],
  },
  server: {
    port: 4111,
  },
})
```

The value of each option can come from a variable, import, or function call. The option itself must remain a direct property. Don't hide build-time options behind a factory call or an object spread:

```typescript title="src/mastra/index.ts"
const options = {
  bundler: {
    externals: ['sharp'],
  },
}

// These patterns prevent Mastra from extracting `bundler` during the build.
export const mastra = new Mastra(createMastraOptions())
export const otherMastra = new Mastra({ ...options })
```

When Mastra can't extract an option, it uses the default build behavior for that option. See the [configuration reference](/reference/configuration) for the available `bundler`, `deployer`, and `server` settings.

### Public folder

If a `public` folder exists in your Mastra directory (`src/mastra/public`), its contents are copied to the output directory during build. These files are served as static assets by the server.

### Mastra configuration

The build process respects configuration in your Mastra instance. For server behavior like CORS, timeouts, and middleware, see [server overview](/docs/server/overview). For all available options, see the [configuration reference](/reference/configuration).

## Build process

The build follows these steps:

1. **Locates entry file**: Finds `index.ts` or `index.js` in your Mastra directory.
1. **Discovers tools**: Scans for tool files matching `{mastraDir}/tools/**/*.{js,ts}`, excluding test files.
1. **Analyzes dependencies**: Determines which packages to bundle vs. install externally.
1. **Bundles code**: Uses Rollup with tree-shaking and optional source maps.
1. **Generates server**: Creates a Hono-based HTTP server as `index.mjs`.
1. **Installs dependencies**: Runs `npm install` in the output directory.
1. **Copies assets**: Copies `public` folder and `.npmrc` if present.

## Environment variables

| Variable | Description |
| - | - |
| `PORT` | Server port (default: `4111`) |
| `MASTRA_STUDIO_PATH` | Path to Studio build directory (default: `./playground`) |
| `MASTRA_SKIP_DOTENV` | Skip loading `.env` files when set |
| `NODE_OPTIONS` | Node.js options (e.g., `--max-old-space-size=4096` for build memory issues) |

## Server endpoints

The built server exposes endpoints for health checks, agents, workflows, and more:

| Endpoint | Description |
| - | - |
| `GET /health` | Health check endpoint, returns `200 OK` |
| `GET /api/openapi.json` | OpenAPI specification (if `server.build.openAPIDocs` is enabled). |
| `GET /swagger-ui` | Interactive API documentation (if `server.build.swaggerUI` is enabled) |

This list isn't exhaustive. To view all endpoints, run `mastra dev` and visit `http://localhost:4111/swagger-ui`.

To add your own endpoints, see [Custom API Routes](/docs/server/custom-api-routes).

## Troubleshooting

### Memory errors during build

If you encounter `JavaScript heap out of memory` errors:

```bash
NODE_OPTIONS="--max-old-space-size=4096" mastra build
```
