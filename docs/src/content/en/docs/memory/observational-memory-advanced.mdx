# Observational Memory: advanced configuration

This page covers the settings to change after [Observational Memory](/docs/memory/observational-memory) (OM) is running: activating early for prompt caching, failure handling, extracting structured values, hooks, and running the engine yourself. You can read the sections in any order. For every option and its default, see the [Observational Memory reference](/reference/memory/observational-memory).

## Early activation

By default, buffered observations activate when message history reaches `observation.messageTokens`. OM can activate them sooner, which helps when a prompt cache is about to expire or when the agent switches model providers. In both cases the next request can't reuse the cached prompt anyway, so sending a smaller, compressed context costs nothing extra.

- `activateAfterIdle`: activate after the thread has been idle for this long. Accepts milliseconds (`300_000`), a duration string (`'5m'`, `'1hr'`), `'auto'` for a provider-aware prompt cache TTL, or a per-provider object (see [per-provider idle TTLs](#per-provider-idle-ttls)).
- `activateOnProviderChange`: activate when the next step uses a different `provider/model` than the one that produced the latest assistant step. Default `false`.

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: 'auto',
      activateOnProviderChange: true,
    },
  },
})
```

Top-level settings apply to observations only. Reflections opt in on their own, through the nested `reflection` settings:

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: '5m',
      observation: {
        activateAfterIdle: false,
      },
      reflection: {
        activateAfterIdle: '10m',
        activateOnProviderChange: true,
      },
    },
  },
})
```

Here observations ignore the top-level idle setting, while reflections opt into idle and provider-change activation.

### Automatic idle TTLs

With `activateAfterIdle: 'auto'`, Mastra picks the idle TTL from the active model provider:

| Provider | Auto TTL |
| - | - |
| Anthropic, OpenRouter, unknown providers, xAI | 5 minutes |
| DeepSeek | 1 hour |
| Google Gemini | 24 hours |
| Groq | 2 hours |
| OpenAI with `providerOptions.openai.promptCacheRetention: "24h"` | 1 hour |
| OpenAI with `providerOptions.openai.promptCacheRetention: "in_memory"` | 5 minutes |
| OpenAI `gpt-4*`, `gpt-5`, `gpt-5-*`, and `gpt-5.1` through `gpt-5.4` (including `-` suffixed variants) | 5 minutes |
| Other OpenAI models | 1 hour |

For a fixed TTL instead, use `'5m'` or `300_000`.

### Per-provider idle TTLs

`'auto'` can't see a cache TTL that you set on individual messages, such as Anthropic's `cacheControl: { type: 'ephemeral', ttl: '1h' }`. It keeps using the provider's 5-minute default, so buffered observations activate while the 1-hour cache is still warm. Pass an object to set the TTL per provider:

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: { default: 'auto', anthropic: '1h' },
    },
  },
})
```

Set the `anthropic` entry to the same TTL as your `cacheControl.ttl`. Mastra doesn't read the per-message cache setting, so keep the two in sync by hand.

How the object resolves:

- Keys are provider names. Mastra compares them case-insensitively with the part of the model's provider before the first `.`, so `anthropic` matches both `anthropic` and `anthropic.messages`. Claude served through another provider uses that provider's key, for example `amazon-bedrock`. Keys must not contain `.` or `/`.
- Each value accepts the same forms as a single TTL: milliseconds, a duration string, `'auto'`, or `false` to turn off idle activation for that provider.
- `default` applies to every provider without its own key. Without `default`, those providers don't idle-activate.
- `observation.activateAfterIdle` and `reflection.activateAfterIdle` accept the same object. An `observation.activateAfterIdle` object replaces the top-level value and isn't merged with it.

## Buffer on idle

Set `observation.bufferOnIdle: true` to run background observation buffering when an agent turn ends and the agent becomes idle. Short turns then get observed without waiting for the next turn or the `messageTokens` threshold.

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        bufferOnIdle: true,
      },
    },
  },
})
```

`bufferOnIdle` is off by default. It's separate from `bufferTokens`: `bufferTokens` controls buffering during steps, `bufferOnIdle` controls buffering at the end of an idle turn.

## When buffering falls behind

When messages arrive faster than the Observer can buffer them, history can pass `messageTokens` before a buffered chunk is ready. Between `messageTokens` and `observation.blockAfter` (default `1.2`, so 36,000 tokens with the default threshold), Mastra keeps buffering in the background and activates the chunk on a later step, so the agent doesn't wait.

If pending tokens still reach `blockAfter` after buffered activation, for example when a large tool result leaves an uncovered tail, a synchronous observation runs. At `blockAfter`, activation first waits a bounded time for a buffered observation that's still being produced. If that takes longer, Mastra observes the remaining messages synchronously and drops the late observation if its messages are already observed. Activations triggered by the idle TTL or a provider change don't wait.

Above `blockAfter`, activation may overshoot the retention target instead of using fewer chunks. Buffered activation usually keeps a minimum remaining context (the smaller of about 1,000 tokens or the configured retention floor), but a single chunk that covers the whole pending window still activates and can leave less.

Async buffered Observer calls don't produce continuation hints, because a delayed hint can be stale by the time it activates. When buffered chunks activate, any stored suggested response and current task are cleared.

Reflection buffers the same way. It starts in the background when observations reach `reflection.bufferActivation` (default `0.5`) of `reflection.observationTokens`, and runs synchronously above `reflection.blockAfter` (default `1.2`) when no buffered reflection is ready.

## Retries and failure policy

Observer and Reflector model calls are retried on transient provider errors. Each stage has two settings:

- `maxRetries`: retries after the first model call. Default `8`. This is the only retry setting for the stage: the underlying model call runs with no provider-level retries.
- `failurePolicy`: what happens once retries run out. `'abort'` (default) fails the turn, and `'continue'` lets it go on.

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        maxRetries: 8,
        failurePolicy: 'continue',
      },
      reflection: {
        maxRetries: 8,
        failurePolicy: 'continue',
      },
    },
  },
})
```

A provider outage usually takes out both stages, so set the policy on both if you want the turn to survive one.

With `'continue'`, Mastra reports the failure through OM diagnostics, keeps the failed input pending for a later cycle, and lets the turn continue. It doesn't advance observation boundaries or discard unobserved messages. A Reflector failure leaves already-persisted observations committed and retries reflection at the next threshold crossing.

The policy covers only Observer and Reflector model and provider failures in synchronous runs: at `blockAfter`, when async buffering is off, and in resource-scoped observation. Persistence, indexing, transform, locking, invariant and explicit abort failures stay fatal.

Background buffering failures never stop the turn, whatever the policy. They're reported as `om_buffering_failed`, and the failed input stays pending. If it keeps growing, it reaches `blockAfter`, where synchronous observation applies `failurePolicy`.

:::warning

`'continue'` has no backstop for a long outage. Unobserved messages stay pending and keep growing in the main agent's context until they reach the model's context limit.

:::

## Temporal gap markers

Temporal gap markers insert a short reminder before a new user message when at least 10 minutes have passed since the previous message in the thread. They're off by default.

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      temporalMarkers: true,
    },
  },
})
```

The marker is stored in memory and also emitted as a transient reminder event, so clients can render it as a timeline hint. The Observer sees the markers too, so observations can say when something happened, for example "User asked about deployment after a 2-day gap".

## Token estimates

OM decides when to observe from local token estimates, not from the provider's usage report. Text is estimated with `tokenx`; images use provider-aware heuristics, which also apply to image-like `file` parts. Provider counts can run higher than the estimate, which is why [context-overflow recovery](/docs/memory/observational-memory#context-overflow-recovery) exists.

### Token-count cache

OM caches estimates in message metadata so threshold checks don't recount the same content:

- Per-part estimates are stored on `part.providerMetadata.mastra` and reused while the cache version and tokenizer source match.
- Messages with string-only content (no parts) use a message-level cache.
- Message and conversation overhead is recalculated every pass. Only payload estimates are cached.
- `data-*` and `reasoning` parts are skipped and not cached.

### Supplying your own estimate for a file

You can attach a token estimate to an `image` or `file` part with `providerMetadata.mastra.tokenEstimate`. The token counter uses it as is:

```typescript
const filePart = {
  type: 'file',
  data: 'storage://bucket/large-report.pdf',
  mimeType: 'application/pdf',
  filename: 'large-report.pdf',
  providerMetadata: {
    mastra: {
      tokenEstimate: {
        v: 0,
        source: 'client',
        key: 'client',
        tokens: 100_000,
      },
    },
  },
}
```

- `v`: cache schema version. Set it to `0`. OM doesn't read it for caller entries.
- `source`: must be `'client'`. This marks the entry as authoritative so it isn't recomputed or overwritten.
- `key`: set to `'client'`. Framework entries put a content hash here. `'client'` keeps your estimate stable across writes.
- `tokens`: the count to use. Must be a finite, non-negative number.

The estimate is honored only on `image` and `file` parts. `text` and `tool-invocation` parts are always counted.

## Limiting what the Observer re-reads

By default the Observer receives the full observation log as context with every batch of new messages, plus the previous `current-task` and `suggested-response` values. When the log grows large, set `observation.previousObserverTokens` to cap it:

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        previousObserverTokens: 10_000,
      },
    },
  },
})
```

- `false` (default): send the full log.
- A number such as `2000`: keep about that many tokens of the most recent observations.
- `0`: send no previous observations.

When a buffered reflection is pending, the lines it already covers are replaced with the reflection before truncation.

## Extractors

Extractors persist specific values alongside observations. The built-in current task, suggested response and thread title use the same pipeline. This example extracts a small user profile:

```typescript title="src/mastra/agents/assistant.ts"
import { Agent } from '@mastra/core/agent'
import { Extractor, Memory } from '@mastra/memory'
import { z } from 'zod'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        extract: [
          new Extractor({
            name: 'User profile',
            instructions: 'Extract stable user profile facts that should be remembered.',
            schema: z.object({
              preferredName: z.string().optional(),
              timezone: z.string().optional(),
              tools: z.array(z.string()).optional(),
            }),
          }),
        ],
      },
    },
  },
})

export const assistant = new Agent({
  id: 'assistant',
  name: 'Assistant',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  memory,
})
```

An extractor with a `schema` runs as a follow-up structured-output request. Without a schema it's an inline string extractor, emitted directly in the Observer or Reflector response:

```typescript
new Extractor({
  name: 'Mood',
  instructions: 'Extract the user mood as a short phrase.',
})
```

By default the extractor sees its last value on later runs. Set `includePreviousExtraction: false` to hide it:

```typescript
new Extractor({
  name: 'Latest blocker',
  instructions: 'Extract any blockers the agent is running into.',
  includePreviousExtraction: false,
})
```

`instructions` and `schema` can be functions when they depend on runtime context, such as the memory instance or request context:

```typescript
new Extractor({
  name: 'Workspace summary',
  instructions: ({ memory }) =>
    memory ? 'Extract workspace facts for this memory instance.' : 'Extract workspace facts.',
})
```

Use `onExtracted` to normalize a value before it's persisted:

```typescript
new Extractor({
  name: 'Project status',
  instructions: 'Extract the current project status.',
  schema: z.string(),
  onExtracted: ({ current }) => current.trim().toLowerCase(),
})
```

`onExtracted` also receives `previous` and `sendSignal`, so it can tell the agent when a value changes. The hook runs on every extraction, so compare `previous` with `current` before sending a signal; otherwise each observation sends another one.

A failed extractor is reported in OM markers and doesn't drop values from extractors that succeeded. See the [Extractor API](/reference/memory/observational-memory#extractor-api) for the full shape.

### Read extracted values from a stream

Extractor results arrive when OM completes an observation or reflection. Read both completion data parts from the stream:

```typescript title="src/run.ts"
const stream = await agent.stream('Remember that I prefer dark mode.', {
  memory: { resource: 'user-123', thread: 'conversation-123' },
})

for await (const chunk of stream.fullStream) {
  if (chunk.type === 'data-om-observation-end' || chunk.type === 'data-om-buffering-end') {
    const { operationType, extractedValues = {}, extractionFailures = [] } = chunk.data

    for (const [slug, value] of Object.entries(extractedValues)) {
      console.log(`${operationType} extractor ${slug}:`, value)
    }

    for (const failure of extractionFailures) {
      console.error(`Extractor ${failure.slug} failed:`, failure.error)
    }
  }
}
```

`extractedValues` is keyed by each extractor's slug. Both fields are optional.

`data-om-observation-end` reports a synchronous completion. `data-om-buffering-end` reports finished background work: its extractor values are persisted at once, but the buffered observations stay inactive until activation. `operationType` says whether the work was an observation or a reflection. See [`data-om-observation-end`](/reference/memory/observational-memory#data-om-observation-end) and [`data-om-buffering-end`](/reference/memory/observational-memory#data-om-buffering-end) for the payloads.

## Let the Observer manage working memory

Set `observation.manageWorkingMemory: true` to have the Observer keep [working memory](/docs/memory/working-memory) up to date, instead of relying on the main agent to call the working memory tool.

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    workingMemory: {
      enabled: true,
    },
    observationalMemory: {
      observation: {
        manageWorkingMemory: true,
      },
    },
  },
})
```

This adds a `WorkingMemoryExtractor` and changes two working memory defaults:

- `workingMemory.agentManaged` defaults to `false`, so the main agent no longer gets the working memory tool and instructions. Set it to `true` to keep them.
- `workingMemory.useStateSignals` defaults to `true`, which moves working memory out of the system prompt into state signals so updates don't invalidate the prompt cache.

## Hooks

`observationalMemory.hooks` takes two kinds of hooks:

- **Lifecycle hooks** (`onObservationStart`, `onObservationEnd`, `onReflectionStart`, `onReflectionEnd`) are for telemetry. They receive `threadId`, `resourceId` and `trigger`; the end hooks also receive the model call's `usage`, `providerMetadata` and any `error`. They never change what OM stores.
- **Transform hooks** (`beforeObservation`, `afterObservation`, `beforeReflection`, `afterReflection`) change the data flowing through a cycle. Return nothing to pass the input through, or return a replacement.

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      hooks: {
        // Drop or redact messages before the Observer sees them.
        beforeObservation: ({ messages }) => ({
          messages: messages.filter(m => !isSensitive(m)),
        }),
        // Rewrite observations before they are persisted.
        afterObservation: ({ observations }) => ({
          observations: redact(observations),
        }),
        // Rewrite the text the Reflector condenses.
        beforeReflection: ({ observations }) => ({
          observations: stripInternalNotes(observations),
        }),
        afterReflection: async ({ observations, resourceId }) => {
          await syncToExternalStore(resourceId, observations)
        },
      },
    },
  },
})
```

Transform hooks are always awaited, on every path: manual `observe()` and `reflect()`, synchronous observation during a turn, and async buffering. If `beforeObservation` returns an empty `messages` array, the Observer call is skipped and those messages are still marked as observed. If a transform hook throws, the cycle fails before committing the transformed text. Extractor callbacks and other side effects that already ran aren't rolled back.

`afterObservation` and `afterReflection` replace only the observation or reflection text. They don't touch the structured extractor values stored in thread metadata, and reflection extraction runs before `afterReflection`. Don't treat an after hook as a redaction boundary for everything in the cycle.

Hooks receive `threadId` and `resourceId`, so they can also update working memory with `memory.updateWorkingMemory()`. Those updates aren't atomic with the OM commit.

### Redact skill results

[Skills](/docs/skills) reach the agent as tools (`skill`, `skill_search`, `skill_read`) whose results hold the skill's full instructions or files. Without redaction, the Observer re-reads that text every time a skill is used. `skillResultRedactor()` is a ready-made `beforeObservation` hook that replaces those results with a placeholder. The tool call stays, so the Observer still records which skill was used.

```typescript
import { Memory } from '@mastra/memory'
import { skillResultRedactor } from '@mastra/memory/hooks'

const memory = new Memory({
  options: {
    observationalMemory: {
      hooks: {
        beforeObservation: skillResultRedactor(),
      },
    },
  },
})
```

Pass `toolNames` to redact a different set of tools. To combine it with your own transform, chain the outputs and await each hook:

```typescript oxfmt:false
const dropSkillResults = skillResultRedactor()

hooks: {
  beforeObservation: async input => {
    const messages = (await dropSkillResults(input))?.messages ?? input.messages
    return { messages: messages.filter(m => m.role !== 'signal') }
  },
}
```

## Run the engine yourself

Most apps should use the `Memory` class. Use the `ObservationalMemory` engine directly for benchmarking, experiments, or when OM must run in a specific order with other processors such as [guardrails](/docs/agents/guardrails).

Wrap the engine in an `ObservationalMemoryProcessor`, which needs a `Memory` instance to load and persist messages. `stores.memory` is typed as optional on storage adapters, so assert or check it:

```typescript title="src/mastra/agents/agent.ts"
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'
import { ObservationalMemory, ObservationalMemoryProcessor } from '@mastra/memory/processors'

const storage = new LibSQLStore({
  id: 'my-storage',
  url: 'file:./memory.db',
})

const memory = new Memory({ storage })

const om = new ObservationalMemory({
  storage: storage.stores.memory!,
  memory,
  model: '__GATEWAY_GOOGLE_MODEL_FLASH__',
  observation: {
    messageTokens: 20_000,
  },
  reflection: {
    observationTokens: 60_000,
  },
})

const omProcessor = new ObservationalMemoryProcessor(om, memory)

export const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  inputProcessors: [omProcessor],
  outputProcessors: [omProcessor],
})
```

The engine takes the same options as the `observationalMemory` config, plus `storage`, `onDebugEvent` and `obscureThreadIds`. See [standalone config](/reference/memory/observational-memory#standalone-config).

`om.observe()` only observes once pending tokens reach the threshold. Pass `force: true` to observe pending messages now. The bypass applies to that call only.

```typescript
const result = await om.observe({ threadId, resourceId, force: true })
// result.observed is true when pending messages were observed
```

Agents don't need this to recover from context-window errors. [Context-overflow recovery](/docs/memory/observational-memory#context-overflow-recovery) handles that.

## Migrating existing threads

No migration is needed. OM reads existing messages and observes them when a thread first exceeds `observation.messageTokens`, processing the backlog then. Under the deprecated resource scope, all unobserved messages across a resource's threads are processed together, which can take a long time for users with many threads.
