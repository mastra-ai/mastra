# Sandbox

**Added in:** `@mastra/core@1.1.0`

Agents work with files and run shell commands. Because their actions aren't always predictable, they should operate within deliberate boundaries that protect the host system. A sandbox provides that execution environment.

In Mastra, a sandbox operates through a `Workspace`. `Workspace` is the API you configure and attach to `Mastra` or an agent. Its `sandbox` provider defines where commands run, while the workspace gives the agent tools for using that environment.

You control how long the environment lasts and who shares it. A workspace can belong to the application or a specific agent. Resolver functions can scope a sandbox or filesystem to request context such as a user, tenant, or thread.

Workspace filesystems can persist independently from the sandbox. Supported providers can mount them through FUSE, which lets an ephemeral sandbox start with seeded files and save results to storage that survives the run. You can also configure a workspace with only a filesystem. The agent then receives file and search tools without a shell command tool.

A sandbox provider can control:

- **Command execution**: Run shell commands with arguments
- **Background processes**: Spawn long-running processes like dev servers and watchers
- **Working directory**: Commands run from a specific directory
- **Environment variables**: Control what variables are available
- **Timeouts**: Prevent long-running commands from hanging
- **Isolation**: Optional OS-level sandboxing for security

:::warning[Isolation depends on the provider]

Provider choice determines the isolation boundary. `LocalSandbox` runs commands directly on the host unless you enable native isolation with macOS Seatbelt or Linux Bubblewrap. Container and remote providers such as Daytona run commands within their own isolation boundaries.

Choose the provider and controls that meet your requirements for network access, credentials, retention, and deletion.

:::

## Runtime boundary

The sandbox controls where shell commands run. Application code, including agent tools, workflow steps, and model callbacks, still runs in your application process unless it explicitly calls workspace or sandbox APIs.

Giving an agent a sandbox doesn't move its authored tools or your application runtime into that sandbox. It adds sandbox-backed command tools to the agent.

## Sandbox and filesystem

The workspace `sandbox` and `filesystem` options are separate capabilities:

- The sandbox provides command execution and may have its own filesystem.
- The workspace filesystem provides file tools such as read, write, list, and grep.

They share files only when you configure them to use the same storage. For local development, point `LocalFilesystem.basePath` and `LocalSandbox.workingDirectory` at the same directory. For supported remote sandboxes, use [`mounts`](/docs/workspace/filesystem#mounts-and-compositefilesystem) to make workspace storage available to commands.

Mastra doesn't define one working directory that applies to every sandbox provider. Relative paths, absolute paths, persistence, and the default command directory depend on the provider. Pass `cwd` when a command must run from a specific directory.

## Supported providers

- [`LocalSandbox`](/reference/workspace/local-sandbox): Executes commands on the local machine
- [`AgentCoreRuntimeSandbox`](/reference/workspace/agentcore-runtime-sandbox): Executes commands in AWS Bedrock AgentCore Runtime sessions
- [`AppleContainerSandbox`](/reference/workspace/apple-container-sandbox): Executes commands in local OCI Linux containers using Apple's `container` CLI
- [`BlaxelSandbox`](/reference/workspace/blaxel-sandbox): Executes commands in isolated Blaxel cloud sandboxes
- [`DaytonaSandbox`](/reference/workspace/daytona-sandbox): Executes commands in isolated Daytona cloud sandboxes
- [`DockerSandbox`](/reference/workspace/docker-sandbox): Executes commands in long-lived Docker containers on the local machine
- [`E2BSandbox`](/reference/workspace/e2b-sandbox): Executes commands in isolated E2B cloud sandboxes
- [`ModalSandbox`](/reference/workspace/modal-sandbox): Executes commands in isolated Modal cloud sandboxes
- [`PlatformSandbox`](/reference/workspace/platform-sandbox): Executes commands in a sandbox tied to a Mastra Platform environment
- [`RailwaySandbox`](/reference/workspace/railway-sandbox): Executes commands in ephemeral, isolated Railway cloud sandboxes
- [`VercelSandbox`](/reference/workspace/vercel-sandbox): Executes commands in an ephemeral Vercel Sandbox Firecracker MicroVM
- [`VercelServerlessSandbox`](/reference/workspace/vercel-serverless): Executes commands as stateless Vercel serverless functions

## Quickstart

Create a workspace with a sandbox and register it with `Mastra`. For local development, point `LocalFilesystem` and `LocalSandbox` at the same directory so file tools and commands use the same files:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

const workspace = new Workspace({
  filesystem: new LocalFilesystem({
    basePath: './workspace',
  }),
  sandbox: new LocalSandbox({
    workingDirectory: './workspace',
  }),
})

export const mastra = new Mastra({
  workspace,
})
```

All agents registered with this `Mastra` instance inherit the workspace and receive tools for its configured capabilities. Set `workspace` on an individual agent when it needs a different environment.

See [`LocalSandbox` reference](/reference/workspace/local-sandbox) for configuration options including environment isolation and native OS sandboxing.

## Configuration patterns

Choose capabilities based on what the agent needs:

| Need | Configuration | Learn more |
| - | - | - |
| Run commands | `sandbox` | [Agent tools](#agent-tools) |
| Read and write files | `filesystem` | [Filesystem](/docs/workspace/filesystem) |
| Work with local files and commands | `filesystem` and `sandbox` pointed at the same directory | [Sandbox and filesystem](#sandbox-and-filesystem) |
| Access cloud storage from a sandbox | `mounts` and `sandbox` | [Mounts](/docs/workspace/filesystem#mounts-and-compositefilesystem) |
| Inspect code with language servers | `lsp` with a compatible filesystem or sandbox | [LSP inspection](/docs/workspace/lsp) |
| Search files or load reusable instructions | Search options or `skills` | [Search](/docs/workspace/search) and [Skills](/docs/workspace/skills) |

## Sandbox without a filesystem

Configure only `sandbox` when an agent needs command execution without filesystem tools:

```typescript
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
})
```

## Use a sandbox from application code

Mastra passes the agent's workspace to authored tools through the tool execution context. The tool function runs in your application process. A command runs in the sandbox only when the tool calls the sandbox API:

```typescript title="src/mastra/tools/run-analysis.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const runAnalysisTool = createTool({
  id: 'run-analysis',
  description: 'Runs a JavaScript analysis in the agent sandbox',
  inputSchema: z.object({
    script: z.string(),
  }),
  execute: async ({ script }, { workspace }) => {
    // This tool function runs in the application process.
    const sandbox = workspace?.sandbox
    if (!sandbox?.executeCommand) {
      throw new Error('This tool requires a workspace with command execution')
    }

    // The Node.js command runs inside the configured sandbox.
    const result = await sandbox.executeCommand('node', ['-e', script])
    return { stdout: result.stdout, stderr: result.stderr }
  },
})
```

Here, `workspace` is the workspace assigned to the agent that called the tool. The `workspace.sandbox` property contains the provider instance when `Workspace` was configured with `sandbox: new LocalSandbox(...)` or another provider object.

Outside a tool call, use the same `Workspace` object that your application passes to `Mastra` or an agent. Use the process manager when a command must continue running while your application does other work:

```typescript
const sandbox = workspace.sandbox
if (!sandbox?.processes) {
  throw new Error('This sandbox does not support background processes')
}

const server = await sandbox.processes.spawn('python -m http.server 8000')

// Do other work while the server runs.

await server.kill()
```

Process handles support output streams, `wait()`, `kill()`, and, when the provider supports it, `sendStdin()`. See the [`SandboxProcessManager` reference](/reference/workspace/process-manager) for the full API.

## Lifecycle and persistence

Sandbox provider objects passed directly to a workspace are owned by that workspace. Most providers initialize on first use, so calling `workspace.init()` is optional. Call it when you use a workspace outside Mastra or need to provision resources before the first agent request.

Calling `workspace.destroy()` destroys its owned sandbox. Calling `mastra.shutdown()` destroys registered workspaces and closes their resources, including sandboxes, filesystem handles, language servers, and browsers.

The meaning of `stop()` is provider-specific. It may pause existing compute or tear it down, and some providers preserve a snapshot as part of that operation. Files and processes aren't guaranteed to survive a stop. Application restarts and idle timeouts also have provider-specific persistence.

Every sandbox has an `id`, but the ID isn't a cross-provider persistence guarantee. Some providers use it to reconnect to existing compute, while others require a separate provider ID or create a new sandbox after a stop. Read the selected provider's reference before relying on reconnection or persisted state.

Resolver-returned sandboxes remain application-owned. A workspace cache key keeps later requests pointed at the same resolved object, but doesn't change the provider's persistence or cleanup behavior.

## Network and credential safety

Mastra doesn't define one network policy that applies to every sandbox provider. Network isolation, allowlists, private networking, and public port exposure are provider capabilities.

The optional `sandbox.networking.getPortUrl()` API returns a public URL when the provider supports exposing ports:

```typescript
const url = await sandbox.networking?.getPortUrl(8000)
```

This API exposes a port. It doesn't configure egress policy. Configure network access through the selected provider. `LocalSandbox` with native isolation blocks network access by default unless `allowNetwork` is enabled. Without native isolation, local commands use the host network.

Environment variables passed to a sandbox or command are available to code running there. Mastra doesn't provide a provider-neutral credential broker that keeps a secret outside the sandbox while injecting it into outbound requests. Pass only the credentials the command needs and follow the selected provider's secret-management guidance.

## Agent tools

When you configure a sandbox on a workspace, agents receive the `mastra_workspace_execute_command` tool for running shell commands.

If your sandbox provider supports running processes in the background, `mastra_workspace_execute_command` also accepts `background: true` for starting long-running processes, and two additional tools are registered:

| Tool | Description |
| - | - |
| `mastra_workspace_execute_command` | Run a shell command. Returns stdout, stderr, and exit code. Supports `background: true` to spawn a long-running process and return a PID. |
| `mastra_workspace_get_process_output` | Get stdout, stderr, and status of a background process by PID. Supports `tail` to limit output lines and `wait: true` to block until exit. |
| `mastra_workspace_kill_process` | Stop a background process by PID. Returns recent output. |

These tools are registered automatically. See [Workspace class reference](/reference/workspace/workspace-class#sandbox-tools) for the full tool name list.

### Configure sandbox tools

Use `WORKSPACE_TOOLS.SANDBOX` constants to configure command and process tools. The following configuration requires approval before command execution and limits command output to 5,000 tokens:

```typescript title="src/mastra/workspaces.ts"
import { LocalSandbox, Workspace, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      requireApproval: true,
      maxOutputTokens: 5000,
    },
  },
})
```

Set `enabled: false` on a tool to remove it from the agent's toolset. See [`WorkspaceToolsConfig`](/reference/workspace/workspace-class#tool-configuration) for shared settings, dynamic policies, tool naming, and hooks.

### Output limits

Command output is limited to the last 200 lines by default. Set the command's `tail` argument to change the line limit, or set it to `0` to disable line-based truncation.

After applying the line limit, Mastra limits the output to 2,000 tokens by default. Set `maxOutputTokens` on the corresponding `WORKSPACE_TOOLS.SANDBOX` entry to change the token limit for that tool.

ANSI escape codes are removed before output reaches the model. Raw output keeps its formatting in streams and terminal interfaces.

## Background process callbacks

When agents start background processes through `mastra_workspace_execute_command`, you can receive lifecycle callbacks for stdout, stderr, and process exit. Configure these through the `backgroundProcesses` option on its `WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND` entry:

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalSandbox, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      backgroundProcesses: {
        onStdout: (data, { pid }) => console.log(`[${pid}] ${data}`),
        onStderr: (data, { pid }) => console.error(`[${pid}] ${data}`),
        onExit: ({ pid, exitCode }) => console.log(`Process ${pid} exited: ${exitCode}`),
      },
    },
  },
})
```

These callbacks fire for all background processes started by the agent through `mastra_workspace_execute_command`.

### Abort signal

By default, background processes inherit the agent's abort signal and are killed when the agent disconnects. Control this behavior with the `abortSignal` option:

- **`undefined`** (default): Uses the agent's abort signal
- **`AbortSignal`**: Uses a custom signal
- **`null` or `false`**: Disables abort: processes persist after agent shutdown

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalSandbox, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      backgroundProcesses: {
        abortSignal: null, // Processes survive agent disconnection
      },
    },
  },
})
```

Use `null` or `false` for cloud sandboxes (for example, E2B, Daytona, or Modal) where processes should outlive the agent.

:::note
For the full `SandboxProcessManager` API (spawning processes programmatically and reading output, plus sending stdin), see the [`SandboxProcessManager` reference](/reference/workspace/process-manager).
:::

## Dynamic sandboxes

Most workspaces pass a provider object directly to `sandbox`. Use a resolver function instead when the sandbox must change by request, user, role, or tenant:

```typescript title="src/mastra/workspaces.ts"
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: ({ requestContext }) => {
    const userId = requestContext.get('user-id') as string
    return new LocalSandbox({
      workingDirectory: `/workspaces/${userId}`,
    })
  },
})
```

Workspace tools resolve the sandbox automatically from the request context used for the agent call. Application code can resolve the same sandbox explicitly:

```typescript
const sandbox = await workspace.resolveSandbox({ requestContext })
```

The resolver can be asynchronous when sandbox configuration comes from another service:

```typescript
const workspace = new Workspace({
  sandbox: async ({ requestContext }) => {
    const tenant = await db.getTenant(requestContext.get('tenant-id'))
    return new LocalSandbox({ workingDirectory: tenant.workspacePath })
  },
})
```

### Resolver ownership

The workspace doesn't own sandboxes returned by a resolver. Return a sandbox that's ready to use, and destroy it through your application's lifecycle code when it's no longer needed. `workspace.destroy()` doesn't destroy resolver-returned sandboxes.

Resolvers are incompatible with `mounts` and `lsp: true`, because both require a provider object when the workspace is constructed. Using a resolver with `mounts` throws an `INVALID_CONFIG` error. With `lsp: true`, Mastra disables LSP and logs a warning.

### Tool registration

When `sandbox` contains a provider object, the workspace inspects its capabilities before registering tools. With a resolver, the workspace registers all sandbox tools because the provider isn't known until execution. Calling an unsupported capability throws `SandboxFeatureNotSupportedError`.

### Background process continuity

Background process tools must resolve the same sandbox that started the process. By default, a resolved sandbox is cached for one request. Set `sandboxCacheKey` when later requests or conversation turns must reach the same sandbox:

```typescript
const workspace = new Workspace({
  sandbox: ({ requestContext }) => resolveSandbox(requestContext),
  sandboxCacheKey: ({ requestContext }) => requestContext.get('thread-id') as string,
})
```

Destroy the resolved sandbox in your lifecycle code before calling `workspace.clearSandboxCache(cacheKey)`. Clearing the cache only removes the workspace's reference.

### Workspace instructions

By default, workspace instructions use stable placeholder text for a resolver-backed sandbox. This prevents prompt construction from provisioning a sandbox and keeps the system message consistent across requests.

Set `instructions.dynamicSandbox` to `'resolve'` when the agent needs instructions from the resolved provider:

```typescript
const workspace = new Workspace({
  sandbox: ({ requestContext }) => resolveSandbox(requestContext),
  instructions: { dynamicSandbox: 'resolve' },
})
```

This calls the resolver while building instructions. To describe the request-specific environment without provisioning it, pass a function that returns instruction text from `requestContext`.

## Custom sandbox providers

Implement [`WorkspaceSandbox`](/reference/workspace/sandbox) to connect another execution backend. The interface defines identity and lifecycle, while command execution, background processes, public port URLs, native file upload, cloning, and mounts are separate capabilities.

Extend `MastraSandbox` when you want the base lifecycle state management, mount handling, and command execution built on a `SandboxProcessManager`. A provider that doesn't support a capability can omit it, and Mastra won't register the corresponding tools when that provider object is passed directly to a workspace.
