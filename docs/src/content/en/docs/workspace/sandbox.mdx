# Sandbox

Agents can generate code and run shell commands against filesystems. Because you can't predict every action an agent might take, its execution environment should be isolated from the host and its sensitive data. Sandboxes provide this boundary.

In Mastra, sandboxes are backends that define the environment where an agent operates. You can attach one sandbox to an application or agent, or resolve separate environments for each user, tenant, or thread.

Supported backends can FUSE-mount a filesystem into the sandbox. This lets you seed an ephemeral environment with files and persist its output between runs.

## When to use sandboxes?

Sandboxes are useful for:

- **Coding agents and software factories**: Clone repositories and run shell, Git, build, or test workflows without giving autonomous agents access to the host system.
- **Deep research and analysis**: Prepare source material and perform analysis with the required libraries in an isolated environment.
- **Long-running tasks**: Offload work such as research jobs, browser sessions, servers, or data processing without tying it to one agent request.
- **Parallel work**: Give concurrent tasks separate environments so they can run without interfering with each other's files or processes.

## Quickstart

In Mastra, a sandbox operates through a `Workspace`. `Workspace` is the API you configure and attach to `Mastra` or an agent. Its `sandbox` provider defines where commands run, while the workspace gives the agent tools for using that environment.

Create a workspace with a sandbox and register it with `Mastra`:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({
    workingDirectory: './workspace',
  }),
})

export const mastra = new Mastra({
  workspace,
})
```

:::warning

`LocalSandbox` runs commands on the host by default and is best suited to trusted local development. Enable [native isolation](#localsandbox) before using it for untrusted commands, or choose a remote or container backend with an isolation boundary that fits your workload.

:::

All agents registered with this `Mastra` instance inherit the workspace. Set `workspace` on an individual agent when it needs a different environment.

## Using the sandbox

Agents receive tools for the capabilities supported by the sandbox provider:

| Tool | Does |
| - | - |
| `execute_command` | Runs a shell command and returns stdout, stderr, and the exit code. Supports `background: true` when the backend can spawn long-running processes. |
| `get_process_output` | Gets stdout, stderr, and status for a background process. Supports `tail` to limit output and `wait: true` to wait for the process to exit. |
| `kill_process` | Stops a background process and returns its recent output. |

The process tools are only added when the backend supports them. You can disable or rename each tool individually. Approval requirements and output limits can also reduce risk and context-window usage. See the [workspace tool configuration reference](/reference/workspace/workspace-class#tool-configuration).

Authored runtime functions, including tools and workflow steps, can get the live sandbox from their execution context. Start a server, watcher, notebook kernel, browser, or worker and interact with it across agent turns.

```typescript title="src/mastra/tools/start-server.ts"
import type { ProcessHandle } from '@mastra/core/sandbox'
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const startServerTool = createTool({
  id: 'start-server',
  description: 'Starts a server in the sandbox',
  inputSchema: z.object({
    command: z.string(),
  }),
  execute: async ({ command }, ctx) => {
    const sandbox = await ctx.getSandbox()
    const server: ProcessHandle = await sandbox.spawn({ command })
    return { pid: server.pid }
  },
})
```

The authored function itself runs in your application process. Only operations called through the sandbox handle run inside the sandbox.

## Supported backends

### `LocalSandbox`

[`LocalSandbox`](/reference/workspace/local-sandbox) executes commands on the same machine as your Mastra application. By default, commands run directly on the host with the permissions of the application process.

Enable native isolation to restrict filesystem and network access at the operating-system level:

- **macOS**: Seatbelt (`sandbox-exec`)
- **Linux**: Bubblewrap (`bwrap`)

```typescript
const sandbox = new LocalSandbox({
  workingDirectory: './workspace',
  isolation: 'seatbelt', // Use 'bwrap' on Linux
  nativeSandbox: {
    allowNetwork: false,
    readOnlyPaths: ['./reference-data'],
  },
})
```

Use `LocalSandbox.detectIsolation()` to detect the recommended backend before constructing the sandbox. The `nativeSandbox` options control network access, read-only or writable paths, workspace write access, and system binaries. You can also provide a custom Seatbelt profile or Bubblewrap arguments. See [`LocalSandbox`](/reference/workspace/local-sandbox) for the full configuration.

## Persistent storage

Some execution backends can also mount cloud filesystems through FUSE. Mounted files appear as local directories inside the sandbox, so commands can use standard tools to read and write them.

Configure mounts on the workspace alongside the sandbox:

```typescript
import { Workspace } from '@mastra/core/workspace'
import { DaytonaSandbox } from '@mastra/daytona'
import { S3Filesystem } from '@mastra/s3'

const workspace = new Workspace({
  mounts: {
    '/data': new S3Filesystem({
      bucket: 'agent-data',
      region: 'us-east-1',
    }),
  },
  sandbox: new DaytonaSandbox(),
})
```

The agent receives filesystem tools for the mounted storage, and commands in the sandbox can access the same files under `/data`. This lets you seed an ephemeral sandbox with existing files and persist its output after the sandbox stops.

Mount support varies by sandbox provider. See [Filesystem](/docs/workspace/filesystem) for the full list of storage providers and detailed mount configuration.

## Multi-tenant sandboxes

Use a resolver when each user, tenant, or thread needs a separate sandbox. Set `sandboxCacheKey` to the identity that owns the sandbox so later requests reuse the same live environment.

This example creates one Daytona sandbox and one S3 storage prefix per memory thread. The S3 filesystem is also mounted at `/workspace` inside the sandbox:

```typescript title="src/mastra/workspaces.ts"
import { MASTRA_THREAD_ID_KEY, type RequestContext } from '@mastra/core/request-context'
import { Workspace } from '@mastra/core/workspace'
import { DaytonaSandbox } from '@mastra/daytona'
import { S3Filesystem } from '@mastra/s3'

const getThreadId = (requestContext: RequestContext) => {
  const threadId = requestContext.get(MASTRA_THREAD_ID_KEY)
  if (typeof threadId !== 'string' || !threadId) {
    throw new Error('A memory thread is required to use this workspace')
  }

  return threadId
}

const createThreadFilesystem = (threadId: string) =>
  new S3Filesystem({
    bucket: process.env.S3_BUCKET!,
    region: process.env.S3_REGION!,
    prefix: `threads/${threadId}`,
  })

const workspace = new Workspace({
  filesystem: ({ requestContext }) => createThreadFilesystem(getThreadId(requestContext)),
  sandbox: async ({ requestContext }) => {
    const threadId = getThreadId(requestContext)
    const sandbox = new DaytonaSandbox({
      id: `thread-${threadId}`,
      language: 'typescript',
    })

    await sandbox.start()
    await sandbox.mount(createThreadFilesystem(threadId), '/workspace')
    return sandbox
  },
  sandboxCacheKey: ({ requestContext }) => getThreadId(requestContext),
})
```

The first request in a thread runs the resolver and starts the sandbox. Later requests with the same thread ID reuse the cached sandbox. A different thread ID creates a different sandbox and storage prefix.

Workspace-level `mounts` can't be combined with a sandbox resolver, so the example mounts the filesystem inside the resolver. Workspace tools resolve the filesystem and sandbox automatically from the request context.

### Resolver ownership

The workspace doesn't own sandboxes returned by a resolver. Return a sandbox that's ready to use, and destroy it through your application's lifecycle code when it's no longer needed. `workspace.destroy()` doesn't destroy resolver-returned sandboxes.

Resolvers are incompatible with `mounts` and `lsp: true`, because both require a provider object when the workspace is constructed. Using a resolver with `mounts` throws an `INVALID_CONFIG` error. With `lsp: true`, Mastra disables LSP and logs a warning.

### Tool registration

When `sandbox` contains a provider object, the workspace inspects its capabilities before registering tools. With a resolver, the workspace registers all sandbox tools because the provider isn't known until execution. Calling an unsupported capability throws `SandboxFeatureNotSupportedError`.

## Background processes

When agents start background processes through `execute_command`, you can receive lifecycle callbacks for stdout, stderr, and process exit. Configure these through the `backgroundProcesses` option on its `WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND` entry:

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalSandbox, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      backgroundProcesses: {
        onStdout: (data, { pid }) => console.log(`[${pid}] ${data}`),
        onStderr: (data, { pid }) => console.error(`[${pid}] ${data}`),
        onExit: ({ pid, exitCode }) => console.log(`Process ${pid} exited: ${exitCode}`),
      },
    },
  },
})
```

These callbacks fire for all background processes started by the agent through `execute_command`.

By default, background processes inherit the agent's abort signal and stop when the agent disconnects. Set `abortSignal` to a custom signal, or use `null` or `false` when the process should continue after the request ends.

For the full `SandboxProcessManager` API (spawning processes programmatically and reading output, plus sending stdin), see the [`SandboxProcessManager` reference](/reference/workspace/process-manager).

## Lifecycle and persistence

Sandbox lifetime depends on how you configure the workspace:

| Configuration | Sandbox scope |
| - | - |
| `sandbox: new DaytonaSandbox()` | One sandbox shared by every agent, user, and thread that uses the workspace. |
| Resolver without `sandboxCacheKey` | One resolved sandbox per `RequestContext` instance. |
| Resolver keyed by user ID | One sandbox per user. |
| Resolver keyed by thread ID | One sandbox per thread. The first request in a new thread resolves a new sandbox. |

Passing `new DaytonaSandbox()` creates the provider object when your server starts. Daytona provisions or reconnects to the remote sandbox when the workspace starts or first uses it. A request from user A starts that shared sandbox if needed. A new thread from user A and a request from user B use the same sandbox because the workspace still uses that provider object. Creating a thread by itself doesn't provision a sandbox.

To isolate users or threads, use the resolver and `sandboxCacheKey` described in [Multi-tenant sandboxes](#multi-tenant-sandboxes).

### Start

Sandbox provider objects are created with your application, but their execution environment usually starts lazily on the first command. Call `workspace.init()` when you want to provision it during application startup instead.

Resolver-backed sandboxes aren't started by `workspace.init()` because no provider exists until the resolver runs. Return a sandbox that's already started or can start itself on first use.

### Hooks

Use `onStart`, `onStop`, and `onDestroy` to run application code during lifecycle transitions. Hooks receive the live sandbox instance:

```typescript
const sandbox = new DaytonaSandbox({
  onStart: ({ sandbox }) => console.log(`Started ${sandbox.id}`),
  onStop: ({ sandbox }) => console.log(`Stopping ${sandbox.id}`),
  onDestroy: ({ sandbox }) => console.log(`Destroying ${sandbox.id}`),
})
```

`onStart` runs after the sandbox starts. `onStop` and `onDestroy` run before their corresponding operation.

### Cleanup

Sandboxes passed directly to a workspace are owned by that workspace. Call `mastra.shutdown()` when your server shuts down. Mastra destroys its registered workspaces, and each workspace destroys its owned sandbox. You can also call `workspace.destroy()` directly.

For `DaytonaSandbox`, destroying the workspace deletes the remote sandbox. Provider settings such as idle stop, archive, or automatic deletion can also control remote resource lifetime. Stopping a sandbox isn't necessarily the same as deleting it.

Sandboxes returned by a resolver are owned by your application. `workspace.destroy()` and `mastra.shutdown()` clear workspace references but don't destroy those resolved sandboxes. Your resolver or application lifecycle must keep track of them, call `destroy()` when their user, thread, or session ends, and then call `workspace.clearSandboxCache(cacheKey)` for keyed entries.

### Persistence

Persistence is backend-specific. Files and processes aren't guaranteed to survive when a sandbox stops or the application restarts. An idle timeout may also discard them. Some backends reconnect by sandbox ID or preserve snapshots and volumes. Others create a fresh environment.

Every sandbox has an `id`, but the ID isn't a cross-backend persistence guarantee. Read the selected backend's reference before relying on reconnection or persisted state.

## Network and credential safety

Mastra doesn't define one network policy that applies to every sandbox provider. Network isolation, allowlists, private networking, and public port exposure are provider capabilities.

The optional `sandbox.networking.getPortUrl()` API returns a public URL when the provider supports exposing ports:

```typescript
const url = await sandbox.networking?.getPortUrl(8000)
```

This API exposes a port. It doesn't configure egress policy. Configure network access through the selected provider. `LocalSandbox` with native isolation blocks network access by default unless `allowNetwork` is enabled. Without native isolation, local commands use the host network.

Environment variables passed to a sandbox or command are available to code running there. Mastra doesn't provide a provider-neutral credential broker that keeps a secret outside the sandbox while injecting it into outbound requests. Pass only the credentials the command needs and follow the selected provider's secret-management guidance.
