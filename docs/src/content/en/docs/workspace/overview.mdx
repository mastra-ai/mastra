# Workspaces

**Added in:** `@mastra/core@1.1.0`

A workspace gives agents an environment for working with files and running commands. Add code inspection, search, or reusable skills based on what the agent needs.

Workspaces support:

- **[Filesystem](/docs/workspace/filesystem)**: Store, read, and manage files
- **[Sandbox](/docs/workspace/sandbox)**: Run commands and background processes locally or in an isolated environment
- **[LSP inspection](/docs/workspace/lsp)**: Inspect symbols and navigate code through language servers
- **[Search](/docs/workspace/search)**: Find indexed content with keyword or semantic search
- **[Skills](/docs/workspace/skills)**: Load reusable instructions from the filesystem

## When to use workspaces

Use a workspace when an agent needs files or code execution. A workspace can also make resources outside the conversation context available to the agent. Configure only the capabilities it needs.

## How it works

Create a `Workspace` with one or more providers, then assign it globally through `Mastra` or directly to an agent. Mastra adds tools for each configured capability to the agent's toolset.

## Get started

For local development, point `LocalFilesystem` and `LocalSandbox` at the same directory. Files written through filesystem tools are immediately available to commands in the sandbox:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { LocalFilesystem, LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  filesystem: new LocalFilesystem({ basePath: './workspace' }),
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
})

export const mastra = new Mastra({
  workspace,
})
```

All agents registered with this `Mastra` instance inherit the workspace. Set `workspace` on an individual agent when it needs different providers or capabilities.

[File-based agents](/reference/file-based-agents/workspace) receive a default local workspace when discovered through `mastra dev` or `mastra build`. Their `workspace/` directory can also seed the runtime workspace with files.

## Configuration patterns

Choose providers based on what the agent needs to do:

| Need | Configuration | Learn more |
| - | - | - |
| Read and write files | `filesystem` | [Filesystem](/docs/workspace/filesystem) |
| Run commands | `sandbox` | [Sandbox](/docs/workspace/sandbox) |
| Work with local files and commands | `filesystem` and `sandbox` pointed at the same directory | [Filesystem](/docs/workspace/filesystem) and [Sandbox](/docs/workspace/sandbox) |
| Access cloud storage from a sandbox | `mounts` and `sandbox` | [Mounts](/docs/workspace/filesystem#mounts-and-compositefilesystem) |
| Inspect code with language servers | `lsp` with a compatible filesystem or sandbox | [LSP inspection](/docs/workspace/lsp) |
| Search files or load reusable instructions | Search options or `skills` | [Search](/docs/workspace/search) and [Skills](/docs/workspace/skills) |

Use resolver functions when each request needs its own filesystem or sandbox. See [dynamic filesystems](/docs/workspace/filesystem#dynamic-filesystem) and [dynamic sandboxes](/docs/workspace/sandbox#dynamic-sandbox) for request-scoped configuration.

## Tool configuration

Each capability registers its corresponding tools. Configure capability-specific tools on the [Filesystem](/docs/workspace/filesystem#agent-tools), [Sandbox](/docs/workspace/sandbox#agent-tools), [LSP inspection](/docs/workspace/lsp#tool-name-remapping), and [Search](/docs/workspace/search#agent-tools) pages.

Use `WorkspaceToolsConfig` for shared behavior such as global defaults, dynamic policies, name remapping, and hooks. See the [`Workspace` tool configuration reference](/reference/workspace/workspace-class#tool-configuration) for the complete API.

## Lifecycle and cleanup

Most providers initialize on first use, so calling `workspace.init()` is optional. Call it when you use a workspace outside of Mastra or need to provision resources before the first agent request.

Mastra registers global and agent-level workspaces. Calling `mastra.shutdown()` destroys registered workspaces that Mastra owns and closes resources such as filesystem handles, language servers, browsers, and sandbox processes.

Static providers are owned by their workspace. Your application owns providers returned by resolver functions and decides when to destroy them. See [sandbox lifecycle ownership](/docs/workspace/sandbox#lifecycle-ownership) for resolver cleanup patterns.

Use [`mastra.removeWorkspace()`](/reference/core/removeWorkspace) to remove a workspace from the registry. Pass `{ destroy: true }` to destroy it before removal.
