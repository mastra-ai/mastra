# Knowledge

Studio's Knowledge page shows what your agents know: every scope and page, how they link, and who wrote what. Use it to check content you loaded and to watch agents' edits as they happen. It's read-only.

:::alpha

Knowledge is in alpha. Its API may change between releases.

:::

## Enable the routes

The Knowledge routes are **off by default**. Until you enable them, Studio's Knowledge page says browsing isn't enabled. Register the Knowledge instance on `Mastra` and add the routes:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES } from '@mastra/server/server-adapter'
import { knowledge } from './knowledge'
import { supportAgent } from './agents/support-agent'

export const mastra = new Mastra({
  agents: { supportAgent },
  knowledge: { company: knowledge },
  server: { apiRoutes: [...KNOWLEDGE_ROUTES] },
})
```

They mount under your configured API prefix (`/api/knowledge` by default) and are gated by the `knowledge:read` permission. They need `@mastra/core` 1.81.0 or later. With an older version, they return `501`. The `link-counts` and `links` routes need 1.82.0 or later and return `501` before it. Studio then counts links among the pages it has loaded.

| Route | Returns |
| - | - |
| `GET /knowledge` | The Knowledge instances you can read |
| `GET /knowledge/:knowledgeKey/tree` | The root scopes, or the child scopes and pages under `parentId` |
| `GET /knowledge/:knowledgeKey/pages/:pageId` | One page with its ancestors, notes, pin and referenced pages |
| `GET /knowledge/:knowledgeKey/link-counts` | How many links go into and out of each page |
| `GET /knowledge/:knowledgeKey/pages/:pageId/links` | The links into and out of one page |
| `GET /knowledge/:knowledgeKey/graph` | A bounded graph of pages with parent and mention edges, and the access grants between scopes |
| `GET /knowledge/:knowledgeKey/search` | Pages and notes matching a query |
| `GET /knowledge/:knowledgeKey/activity` | Recent changes, optionally for one scope or page |
| `GET /knowledge/:knowledgeKey/events` | A Server-Sent Events stream of the writes the caller can read, which Studio follows to show changes as they happen |

## What you see

- **Tree**: every scope and the pages inside it, nested the way your agents organized them.
- **Graph**: the same pages and how they connect. Lines show each page's parent, the pages its notes mention, the links written in its body, and which scopes grant access to which. A legend names each kind of line. Select a page in either view to open it.
- **Page**: the body, version and who last updated it, its notes with their authors, its child pages, the notes on other pages that mention it, and who it's pinned for.
- **Activity**: each page's history of creates, edits, moves, merges, notes and pins, with the author and time of each.
- **Search**: over page names, descriptions, bodies and note text.

On narrow screens the tree and graph share one panel, with a toggle between them that keeps the selected page.

When an agent writes, the tree, graph and open page update as it happens, without a reload. Studio follows writes made through the Knowledge instance registered with Mastra. Writes from another process or another instance on the same storage show up after a reload.

## Control who sees what

What the routes return depends on whether your app configures auth (`server.auth` or `studio.auth`):

- **No auth:** the routes read as the instance owner and return every scope, page and note to anyone who can reach the server. Use this only for a local or test project, and add auth before you deploy.
- **Auth:** the routes return only what the signed-in user can read. In `authorize`, set the request context key `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` to the user's Knowledge scopes. Knowledge applies the same access rules agents use. A user with no scopes set gets `403`.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES, MASTRA_KNOWLEDGE_PRINCIPALS_KEY } from '@mastra/server/server-adapter'
import { appAuthorize } from './auth' // your existing authorization

export const mastra = new Mastra({
  server: {
    apiRoutes: [...KNOWLEDGE_ROUTES],
    auth: {
      // authenticateToken, ...
      authorize: async (path, method, user, context) => {
        if (path.startsWith('/api/knowledge')) {
          context
            .get('requestContext')
            .set(
              MASTRA_KNOWLEDGE_PRINCIPALS_KEY,
              user.isAdmin ? 'all' : [`org:${user.orgId}`, `team:${user.orgId}:${user.teamId}`],
            )
          return true
        }
        return appAuthorize(path, method, user, context)
      },
    },
  },
})
```

An `authorize` function replaces the server's rules and role checks for every route, so keep your app's existing decision for the other paths, as above. Returning `true` for everything would let any signed-in user call any route.

Set the value to an array of scopes, or `'all'` for someone who should see the whole instance. An empty array reads nothing. Any other value, or a scope that matches no declared scope type, is a configuration error and returns `500`. If you configure `studio.auth`, Studio requests use it instead of `server.auth`, so set the key in that `authorize`.

### Deployment notes

- **No RBAC provider:** the `knowledge:read` check is skipped, so any authenticated user with a principal mapping can read the pages those principals cover, in every instance.
- **With an FGA provider:** each Knowledge instance is checked as resource type `knowledge`, by its registered key (`main` in `knowledge: { main }`), with `knowledge:read`. `GET /knowledge` lists only the instances the user can read. The other routes return `403` for any other instance. With `requireForProtectedRoutes`, `GET /knowledge` is refused, because like the other list routes it has no FGA metadata.
- **NestJS:** the NestJS adapter doesn't serve the Knowledge routes yet.

## Build your own view

To show Knowledge changes in your own app, subscribe with [`knowledge.onChange()`](/reference/knowledge/knowledge-class#onchange). Events carry IDs, not content. Read the page again under the user's scopes before you show it to them.
