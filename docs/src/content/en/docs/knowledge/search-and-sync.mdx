# Search and sync

:::alpha

Knowledge is in alpha. Its API may change between releases.

:::

Agents find pages with `knowledge_search`, which matches words out of the box. This page shows how to add search by meaning, how to sync content from your own systems into Knowledge, and how search ranks what it returns.

## Add search by meaning

Pass a `vector` store and an `embedder` to match pages and notes by meaning as well as by keyword. A search for "reimbursement" then finds a page about getting money back, with no shared word:

```typescript title="src/mastra/knowledge.ts"
import { Knowledge, knowledgeMemoryScopes } from '@mastra/core/knowledge'
import { ModelRouterEmbeddingModel } from '@mastra/core/llm'
import { LibSQLStore, LibSQLVector } from '@mastra/libsql'

export const knowledge = new Knowledge({
  id: 'company',
  storage: new LibSQLStore({ id: 'knowledge', url: 'file:./knowledge.db' }),
  vector: new LibSQLVector({ id: 'knowledge-vector', url: 'file:./knowledge.db' }),
  embedder: new ModelRouterEmbeddingModel('openai/text-embedding-3-small'),
  scopes: { ...knowledgeMemoryScopes() },
  tools: true,
})
```

Pass both or neither. Passing only one throws ``Knowledge semantic search needs both `vector` and `embedder`; pass both or neither.`` `embedderOptions` (`maxRetries`, `headers`, `providerOptions`, `telemetry`) applies to every embedding call, the same way it does in Memory. `maxRetries` retries transient provider errors.

`knowledge_search` then merges keyword and meaning results by rank, so a close meaning match can come before a name match. Every semantic hit is read again with the run's access before it can take a place in the results. A run never sees content it can't read, and that content never takes a slot from content it can.

Pages and notes written through the tools are embedded as they're written. Scope pages aren't embedded, but notes on them are.

A page too long for one embedding is embedded as overlapping chunks of about 2,000 tokens, cut between paragraphs and before headings. Each chunk starts with the page's name and description. Search still returns the page once, ranked by its best chunk. A page gets at most 100 chunks, about 200,000 tokens of body. Search finds the rest of a longer body by keyword only. Rewriting a page replaces its chunks, and deleting it removes them.

Run `reindex()` to re-embed every page and note. It returns how many it indexed. Run it after:

- Content written straight to the store, outside the tools.
- An upgrade from a release that didn't chunk long pages. Pages that were too long to embed then become searchable by meaning.
- A write that logged `Knowledge semantic index update failed; run knowledge.reindex() to repair`. The write itself succeeded. Only search by meaning misses it until you reindex.

To reindex:

```typescript
const indexed = await knowledge.reindex()
```

If the embedder or vector store fails during a search, the search returns keyword results and logs a warning.

## Sync your content

Use `knowledge.upsertPage()` to write pages from your own server code, for example to keep your product docs in Knowledge so agents can search and read them. A page is identified by its scope and its key path, so running the sync again updates the same pages. A page whose content hasn't changed comes back `unchanged` and isn't written again. These methods are a way in until built-in importers are available.

Declare a scope for the synced content and say who can read it:

```typescript title="src/mastra/knowledge.ts"
import { Knowledge, knowledgeMemoryScopes } from '@mastra/core/knowledge'
import { LibSQLStore } from '@mastra/libsql'

export const knowledge = new Knowledge({
  id: 'company',
  storage: new LibSQLStore({ id: 'knowledge', url: 'file:./knowledge.db' }),
  scopes: {
    ...knowledgeMemoryScopes(),
    'docs:$orgId': {
      description: 'Product docs, synced from the docs site',
      belongsTo: 'org:$orgId',
      access: [{ principal: 'org:$orgId', role: 'viewer' }],
    },
  },
  tools: true,
})
```

Then write each doc to a path in that scope. Keys in a path can't contain `#` or `%`, and missing pages along the path are created with their key as name:

```typescript title="src/sync-docs.ts"
import { knowledge } from './mastra/knowledge'

type Doc = { slug: string; title: string; markdown: string }

export async function syncDocs(orgId: string, docs: Doc[]) {
  for (const doc of docs) {
    // slug "guides/install" becomes the page docs:acme#guides/install
    const { status } = await knowledge.upsertPage({
      scope: `docs:${orgId}`,
      path: doc.slug,
      name: doc.title,
      body: doc.markdown,
      author: 'sync:docs',
    })
    console.log(doc.slug, status) // 'created', 'updated' or 'unchanged'
  }
}

export async function removeDocs(orgId: string, slugs: string[]) {
  // Remove child pages before their parents.
  const deepestFirst = [...slugs].sort((a, b) => b.split('/').length - a.split('/').length)
  for (const slug of deepestFirst) {
    await knowledge.removePage({ scope: `docs:${orgId}`, path: slug })
  }
}
```

Agents whose run scopes include `org:acme` can now find these pages with `knowledge_search` and open them with `knowledge_read`, for example `docs:acme#guides/install`.

To sync notes too, such as comments or dated changes, add them to a page with `knowledge.addNote()`. Notes have no path, so store the ID it returns next to your source's ID:

```typescript title="src/sync-docs.ts"
const note = await knowledge.addNote({
  scope: 'docs:acme',
  path: 'guides/install',
  text: 'Node 18 support ends on [[docs:acme#releases/2026-12]].',
  when: new Date('2026-11-01'),
  author: 'sync:docs',
})

// Notes are immutable: updateNote replaces the note and returns one with a new ID.
const updated = await knowledge.updateNote({ id: note.id, text: 'Node 18 support ended.' })

await knowledge.removeNote({ id: updated.id }) // null if it was already removed
```

By default a note is visible to readers of the page's scope. Pass `stamps` (scope addresses) to choose whose readers see it instead: a reader needs the page and one of the stamps. A `[[scope#path]]` mention links the note to that page and hides the note from readers who can't read that page's scope. Other `[[...]]` text stays as written.

Keep in mind:

- These methods are for trusted server code. They check no run scopes or access rules, so don't call them from an agent tool or from a route without admin-level auth. The scope's `access` rules decide who can read the pages. `explainAccess()` explains what runs can reach and doesn't cover these writes.
- A scope first created by `upsertPage()` gets its `belongsTo` parent (here `org:acme`) the first time a run holding that parent uses Knowledge.
- Notes, yours or agents', stay on a page when the sync updates its body. A note is at most 250 tokens.
- Fields you leave out stay as they are. A `description` is at most 100 tokens.
- With a `vector` store and `embedder`, written pages and notes are embedded. If embedding fails, the write still succeeds and Mastra logs a warning. Run `knowledge.reindex()` to repair.
- `removePage()` returns `null` when no page is at that path. It refuses a page that still has child pages and a page declared in the scope's `pages`. If another write changes the page while it's being removed, the call throws, so run removals from one worker or retry them.
- Track which paths you synced last time in your app, so you know which ones to remove. That includes pages created along a path, such as `releases` for `releases/2026-12`, which stay until you remove them.

## How search ranks results

`knowledge_search` splits the query into words and matches each one case-insensitively as part of any word, so `refund` matches `refunds`. A page matches when its name, description or body contains at least one of the words, and a note when its own text does. Quotes and operators have no special meaning.

Pages come before notes, in this order:

1. A page whose name contains the whole query.
1. Pages that contain more of the query's words, so a long question still finds the page that holds most of it.
1. Among pages with as many words, a word in the name counts for more than one in the description, and one in the description for more than one in the body.
1. Then the most recently updated page.

Notes follow, ranked by how many of the words they contain, then newest first. A one-word query therefore favors pages with that word in their name. `limit` defaults to 10 (at most 50), and results are ranked before the limit is applied. The limit keeps the best matches. A search only returns what the run can read.

With `MongoDBStore`, reads that span many scopes, such as a search without `scope`, slow down as the number of scopes a run can read grows, because the store first collects every readable scope. Reads within one scope stay fast.
