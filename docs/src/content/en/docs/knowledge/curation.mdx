# Knowledge curation

Curation turns committed session observations into durable Knowledge. The Subconscious `curate` observation agent is the only Subconscious writer. It runs after each successful observation commit on a durable thread keyed to the parent session, and it writes through ordinary, authorized Knowledge tools.

```typescript title="src/mastra/memory.ts"
import { Knowledge } from '@mastra/core/knowledge'
import { LibSQLStore } from '@mastra/libsql'
import { Memory, Subconscious } from '@mastra/memory'

const storage = new LibSQLStore({ id: 'memory-storage', url: 'file:./mastra.db' })
const knowledge = new Knowledge({ id: 'mastra', storage })

export const memory = new Memory({
  storage,
  knowledge,
  options: {
    observationalMemory: {
      model: 'openai/gpt-5-mini',
      experimental_subconscious: new Subconscious({ observation: ['remind', 'curate'] }),
    },
  },
})
```

Use the installed package types for the complete configuration shape.

## Lifecycle

- Dispatch happens only after an observation commits. Blank, failed, or uncommitted observations don't dispatch.
- Dispatch is detached. Curation never blocks the parent agent's turn, and curator model or routing failures stay isolated from the parent.
- Observations are framed as untrusted evidence. Their text can't change the curator's instructions, scopes, or tool permissions.

Curation is a best-effort background safety net. Agents that need a fact stored should still file it deliberately.

## Authority

The curator acts with the parent session's host-vouched authority. It gets no separate grants. Every read and write uses the same capability checks as any other caller:

- It reads relevant accessible Knowledge before writing.
- It writes directly only where the parent holds the needed capability, and uses numeric versions for compare-and-swap.
- Suggest capability doesn't permit direct writes. Where the parent can only suggest, the write is denied.
- Denied writes, conflicts, and deleted records are never bypassed, forced, or restored.

Revoking the parent's access revokes the curator's access on the next operation.

## Placement

The curator writes into the session's authorized resource and thread scopes, or into host-configured structural scopes inside that frontier. Scope descriptions guide placement but don't grant authority.

Provisional scopes are optional. A host can configure a provisional scope with a mirror from its public parent for staging. That scope has exactly the parent's effective capabilities, so it isn't private. Names and suffixes such as `:internal` never establish privacy. See [access and scopes](/docs/knowledge/access) for explicit private placement.
