# Knowledge concepts

:::warning

Knowledge is experimental and can change without notice.

:::

## Nodes and records

A **node** is a named, described place in Knowledge, such as `pricing` or `onboarding`. A **record** is one short, dated fact stored under a node. Agents search records, read a node to see everything in it, and add new records.

Records and node descriptions have size limits, counted in tokens. See [limits](/docs/knowledge/limits).

## Scopes and tags

A **scope** decides who sees a record. A scope is identified by a **tag** in the form `<type>:<value>`, for example `org:acme` or `team:acme:director`. The value can contain `:`. The type is lowercase letters, digits, `_` and `-`, starting with a letter. No part of the value may start with `$`. A scope holds at most 8 tags, and their order doesn't matter.

A run gets its tags from the agent: the `scopes` set on the agent, the `scopes` passed to a call, or the request context. Knowledge also adds `resource:<id>` and `thread:<id>` when the run has a resource or thread ID. A run reads records at every tag it holds.

Tags are authority. Only the host application should set them, and a model can't add to them.

## The structure

The `scopes` option on `Knowledge` declares scope types with patterns that use `$param` placeholders. Declaring a type is optional: a run can use any tag, and the holder owns records at its own tag. Declare a type to add a description, child templates, or to say which scope owns it.

```typescript
import { Knowledge } from '@mastra/core/knowledge'

const knowledge = new Knowledge({
  id: 'company',
  storage,
  scopes: {
    'org:$orgId': { description: 'The company' },
    'team:$orgId:$teamId': {
      access: [{ principal: 'org:$orgId', role: 'owner' }],
    },
  },
})
```

Here a run that holds `org:acme` writable can read and write `team:acme:director`, but not `team:other:director`, because `$orgId` is bound from the team's own address. The model reaches `team:acme:support` by passing `scope: ['team:acme:support']` to a Knowledge tool. The role in `access` sets what an owner can do:

| Role | Can |
| - | - |
| `readonly` | Search and read |
| `append` | Read, plus add records (`knowledge_record` op `add`) and create long-form nodes (`knowledge_node` op `write`) |
| `edit` | All of the above, plus remove and rescope records, and update and merge nodes |
| `owner` | Same as `edit` |

A tool that needs a stronger role fails with `This run reaches "team:acme:support" with role append; this needs edit.` Owned scopes are only reached when the model names them in `scope`. A scope the run holds directly isn't limited by role.

Ownership is checked each time a tool runs. A type you don't declare can be held but not owned, and a read-only tag never owns anything. Holding an owner tag gives a run everything that tag owns, so set it only on runs meant to have that reach.

## Read and write access

Scopes are read-only unless you mark them writable. Give a tag as a string to allow reading only, or as `{ scope, access: 'write' }` to allow writing too:

```typescript
await agent.generate('What did the team decide?', {
  scopes: ['org:acme', { scope: 'team:acme:director', access: 'write' }],
})
```

This run reads both scopes and writes only to `team:acme:director`. The same entries work in the agent's `scopes`. The `resource:` and `thread:` tags are the run's Memory identity and are always writable.

Read-only tags are searched by reads and left out of default writes. A write that names one fails with `"org:acme" is read-only for this run.` (or `are read-only` when it names several). The `scope` argument the model passes to a tool is a plain list of tags.

If the agent, the call, or the request context name the same tag with different access, read-only wins, and a model never widens its access. A read-only tag never grants ownership of other scopes.

## Pins

A **pin** is a short note that stays in the model's context on every step. Pins are stored in Knowledge and shown to the agent as a state signal, so they work without Memory. Pins follow the user across threads, so by default they use every run tag except `thread`. The pin set is limited to `maxPins` entries and `maxTokens` tokens in total.
