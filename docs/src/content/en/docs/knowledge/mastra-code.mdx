# Knowledge in Mastra Code

:::warning

Knowledge is experimental and can change without notice.

:::

Knowledge is off in Mastra Code until you turn it on.

## Turn it on in the TUI

Open `/settings`, turn on **Experimental Knowledge**, and restart Mastra Code. The code agent then gets the Knowledge tools (search, read, write, and pin) and pinned context every turn.

This built-in Knowledge is stored with Mastra Code's own storage and declares Memory's scopes with [`knowledgeMemoryScopes()`](/docs/knowledge/scope-types). Every local session runs as `org:local`, so the agent can write pages at `org:local` that every session on the same storage reads.

## Attach your own Knowledge

When you embed Mastra Code, attach Knowledge the way you would on an agent, with `knowledge` and `scopes`:

```typescript
const code = await createMastraCode({
  knowledge: companyKnowledge,
  scopes: ['org:acme', 'team:acme:support'],
})
```

`scopes` say who every run in the session is. What the run may read or write comes from `companyKnowledge`'s [scope declarations](/docs/knowledge/scope-types), so declare each type you pass here. The instance's own `tools` and `pinnedContext` options decide which tools the agent gets.

The instance is registered on the mounted Mastra runtime under its `id`. To register it under another key, pass `knowledge: { key: 'company', instance: companyKnowledge }`.

The `knowledge` option also accepts:

- `true`: the built-in Knowledge, the same one the TUI setting turns on. With no `scopes`, its runs are `org:local`.
- `false`: Knowledge stays off, even when the TUI setting is on.

## Factory sessions

In Factory, the TUI setting has no effect: Knowledge stays off unless the Factory host passes its own `knowledge: { key, instance }`.

Factory sessions add `org:<orgId>` and `project:<projectId>` to the session's scopes, so the instance must declare both types. Otherwise every Knowledge tool call fails with `Knowledge run scope "project:p1" does not match a declared scope type.`

```typescript
import { Knowledge, knowledgeMemoryScopes } from '@mastra/core/knowledge'

const companyKnowledge = new Knowledge({
  id: 'company',
  scopes: {
    ...knowledgeMemoryScopes(),
    'project:$projectId': { access: [{ principal: 'self', role: 'editor' }] },
  },
  tools: true,
})
```

With this setup, a page written at `project:p1` is read by every session in that project, and sessions in other projects don't see it. The agent picks where each page goes with the tools' `scope` argument. Pages it writes at its `resource:` or `thread:` scope stay private to that user or conversation.

If a Factory session has no organization, or a host scope has type `org:` or `project:` with a different value than the session's, the agent runs with only its `resource:` and `thread:` scopes. Nothing it writes is shared, and the `/knowledge` inspector reports Knowledge as unavailable.

## Scopes per message

A long-lived session can change what a run is allowed to see for each task. Pass `scopes` to `session.sendMessage`, in the same plain-string form as above:

```typescript
await session.sendMessage({
  content: 'Fix the login bug',
  scopes: ['request:r25'],
})
```

The run holds `request:r25` on top of the session's scopes. Declare the `request:` type on the Knowledge instance like any other.

A run's scopes are fixed when it starts:

- A message with the same scopes, or none, joins the running run.
- A message with different scopes waits for the running run to end, then starts its own run in the same conversation.
- Several scoped messages sent in the meantime start in the order they were sent.

A scoped message to a thread whose run is owned by another process doesn't wait. It rejects with "scopes don't cross processes". Messages without scopes are unaffected.

`queueMessage`, `queueSignal`, `sendNotificationSignal`, and `steer` take `scopes` the same way. A queued message, steering message, or notification whose scopes differ from the running run's starts its own run after that one instead of joining it.

### Remote callers

Scopes are set in process only. Remote callers, through the agent controller HTTP routes or `@mastra/client-js`, can't send them, and the server drops `scopes` from a request body. To derive scopes from a request, give the agent a `scopes` function that reads trusted request context.

## Upgrading

Mastra Code no longer includes the experimental Subconscious. The Subconscious activity view and the `ask_memory` tool are removed. `experimental_subconscious` and the Memory `knowledge` option are removed too, and setting either throws. Attach Knowledge to the agent instead. The `MASTRACODE_EXPERIMENTAL_KNOWLEDGE` and `MASTRACODE_EXPERIMENTAL_SUBCONSCIOUS` environment variables do nothing.

Scopes are plain strings that say who the run is. The `{ scope, access }` and `{ tag, access }` forms are gone. Roles come from the Knowledge instance's scope declarations.
