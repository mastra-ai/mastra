# createCodingAgent()

**Added in:** `@mastra/core@1.48.0`

`createCodingAgent()` builds a coding [`Agent`](/reference/agents/agent) with portable defaults for the pieces a coding agent always needs: a local workspace, the task-list signal provider when `memory` is configured, network-retry error processors, and the goal judge prompt. Supply only `model` and `instructions` to get a working agent, or override any default.

The returned value is a standard `Agent`, so it works anywhere an `Agent` does: including as the agent passed to an [`AgentController`](/reference/agent-controller/agent-controller-class).

For an introduction to coding agents and each default in context, see [Coding agents](/docs/agents/coding-agent).

## Usage example

Pass a model and instructions. `createCodingAgent()` fills in the workspace and error processors, adds the task signal provider when `memory` is configured, and supplies the goal prompt when a `goal` is configured:

```typescript title="src/mastra/coding-agent.ts"
import { createCodingAgent } from '@mastra/core/coding-agent'

const agent = createCodingAgent({
  id: 'my-coding-agent',
  name: 'My Coding Agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: 'You are a helpful coding assistant.',
})
```

The agent receives the [workspace tools](/reference/workspace/workspace-class#filesystem-tools) for its resolved workspace, so `tools` is only needed for capabilities beyond the workspace.

## Defaults

A default is only filled in when you don't provide the corresponding field. `signals` is the exception: the task signal provider is appended to the providers you pass.

| Field | Default when omitted |
| - | - |
| `workspace` | A [`Workspace`](/reference/workspace/workspace-class) backed by `LocalFilesystem` and `LocalSandbox` rooted at the base path. |
| `signals` | A [`TaskSignalProvider`](/reference/signals/task-signal-provider), added only when `memory` is configured. |
| `errorProcessors` | Unknown stream-error retries with specialized ECONNRESET and bad-request policies, plus `PrefillErrorHandler` and `ProviderHistoryCompat`. |
| `goal.prompt` | `DEFAULT_GOAL_JUDGE_PROMPT` (only when a `goal` is configured). |

### Workspace

When the `workspace` key is omitted, a local workspace rooted at `basePath` (default `process.cwd()`) is built:

```typescript
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

new Workspace({
  filesystem: new LocalFilesystem({ basePath }),
  sandbox: new LocalSandbox({ workingDirectory: basePath }),
})
```

To opt out (for example, when the workspace is injected at the [`AgentController`](/reference/agent-controller/agent-controller-class) level), pass `workspace: undefined` explicitly:

```typescript
const agent = createCodingAgent({
  id: 'my-coding-agent',
  name: 'My Coding Agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: 'You are a helpful coding assistant.',
  workspace: undefined, // opt out of the default workspace
})
```

### Signals

`TaskSignalProvider` needs a memory-backed thread, so it's only added when `memory` is configured. With memory configured, the provider is merged into any `signals` you pass, which keeps task tracking from being dropped by custom providers. Passing `signals: []` alongside `memory` still yields the task provider. To run a memory-backed agent with no task tracking, configure the agent with [`new Agent()`](/reference/agents/agent) instead. Before `@mastra/core@1.49.0`, the provider was always added, which failed in memoryless contexts.

### Error processors

The default [`StreamErrorRetryProcessor`](/reference/processors/stream-error-retry-processor) applies these retry policies:

- Unknown errors left unmatched by provider metadata or a specific matcher retry up to twice with a `3000ms` delay. Known authorization failures surface immediately.
- Network resets (`ECONNRESET` / `socket hang up`) retry up to twice with exponential backoff (`1000ms * 2^retryCount`, capped at `30000ms`).
- Bad-request errors retry once after `2000ms`.

Specific network-reset and bad-request policies take precedence over the unknown-error policy. Passing `errorProcessors` replaces the default processor stack. `PrefillErrorHandler` and `ProviderHistoryCompat` are also included for provider compatibility.
