# defineMastraCodePlugin()

:::experimental

The Mastra Code plugin API is experimental and subject to breaking changes in minor versions.

:::

The `defineMastraCodePlugin()` function defines a Mastra Code plugin. It returns the plugin object unchanged and exists for type inference, so the fields you write are checked against the plugin contract.

A plugin is a directory with an entry file that default-exports a plugin object. Install one with the `/plugins` command in the Mastra Code TUI, from a local path or a GitHub repository. Plugins contribute tools, system instructions, [skills](/reference/workspace/skills) and commands (from `skills/` and `commands/` directories), [processors](/reference/processors/processor-interface), and [signal providers](/reference/signals/signal-provider).

## Usage example

```typescript title="src/index.ts"
import { defineMastraCodePlugin, createTool, z } from 'mastracode/plugin'

export default defineMastraCodePlugin({
  id: 'acme.reviewer',
  name: 'Acme Reviewer',
  description: 'Review helpers for Acme services',
  tools: {
    acme_lookup: {
      tool: createTool({
        id: 'acme_lookup',
        description: 'Look up an Acme service by name',
        inputSchema: z.object({ name: z.string() }),
        execute: async ({ context }) => lookup(context.name),
      }),
    },
  },
})
```

Every contribution field also accepts a function, which receives the [plugin context](#plugin-context) and may be async:

```typescript title="src/index.ts"
export default defineMastraCodePlugin({
  id: 'acme.reviewer',
  processors: async context => ({
    input: [createReviewProcessor(context.config)],
  }),
})
```

`getController` and `getActiveSession` are experimental and currently expose the whole controller and session, which includes session state, model selection, and workspace access. They may narrow to a smaller facade in a future release. Plugins also execute code inside Mastra Code, and their instructions are appended to the agent prompt. Install plugins only from sources you trust.

:::

## Processors

Plugin processors run in the same lanes as Mastra Code's built-in processors, in a fixed slot that isn't configurable: last among the processors Mastra Code configures, after the layers they customize, and before the channel and memory layers the agent appends. Plugins can't request a position, a priority, or an index.

Both lanes are resolved before every LLM call, so enabling, disabling, or updating a plugin takes effect on the next request without restarting Mastra Code.

```typescript title="src/index.ts"
import { defineMastraCodePlugin } from 'mastracode/plugin'
import type { InputProcessor } from 'mastracode/plugin'

const auditLog: InputProcessor = {
  id: 'acme-audit-log',
  async processInputStep({ messages }) {
    await recordTurn(messages)
  },
}

export default defineMastraCodePlugin({
  id: 'acme.audit',
  processors: [auditLog],
})
```

State-signal processors track history under a state id that defaults to the processor id. Derive that id from your plugin id and keep it constant, because a processor rebuilt with a new id orphans its tracking record and re-injects a full snapshot.

## Signal providers

A [signal provider](/reference/signals/signal-provider) monitors an external source and pushes notification signals into a thread. Providers are long-lived objects, so Mastra Code owns their lifecycle rather than handing them to the agent:

1. Registers the running Mastra instance on the provider.
1. Connects it to the coding agent.
1. Starts it polling and calls its `start()` hook. That hook isn't awaited, because it runs during startup and on every plugin reload.
1. Stops it when the plugin is updated, disabled, or uninstalled.

Stopping a provider calls its `stop()` method and drops every reference to it. Anything the provider started itself is its own to clear: override `stop()` to cancel timers, requests, and listeners you own, or a replaced provider keeps running against the thread its successor is now watching. A provider replaced while it's still warming up is stopped a second time once its `start()` settles, so expect `stop()` to be callable before `start()` returns and to run twice.

A provider's `getInputProcessors()` and `getOutputProcessors()` feed the same lanes as the `processors` field. Its `getTools()` is ignored, because only the agent constructor reads that method and plugin providers never reach it. To expose a tool from a provider, inject the tool from inside one of its processors.

```typescript title="src/index.ts"
import { defineMastraCodePlugin, SignalProvider } from 'mastracode/plugin'
import type { SignalSubscription } from 'mastracode/plugin'

class AcmeSignals extends SignalProvider<'acme-signals'> {
  readonly id = 'acme-signals'
  readonly pollInterval = 60_000

  async poll(subscriptions: SignalSubscription[]) {
    // check Acme for changes, notify the subscribed threads
  }
}

export default defineMastraCodePlugin({
  id: 'acme.signals',
  signalProviders: [new AcmeSignals()],
})
```

Only one provider per id may be live at a time. Mastra Code refuses to start a second instance and logs a warning. That covers a plugin providing `GithubSignals` while the built-in `experimentalGithubSignals` setting is on, so turn that setting off when a plugin provides the same provider.

Failures are isolated by layer. A provider that throws while starting, or whose `start()` hook rejects, is stopped and dropped, and the rest of the plugin keeps working. To treat a provider as required, throw from the `signalProviders` resolver instead, which fails the whole plugin record. A dropped provider is retried on the next reload, so fixing the cause and reinstalling or reconfiguring the plugin brings it back.

## Reloading

Mastra Code reloads plugins when one is installed, enabled, disabled, reconfigured, or updated. Processors are rebuilt on the next request. Providers are cycled only when the owning plugin's version stamp changed, so an unrelated reload leaves a polling provider alone.

A plugin counts as changed when:

- Its config values or enabled flag changed.
- For a GitHub-installed plugin: the checkout's git `HEAD` moved, which covers every file in the repository.
- For a local plugin: the entry file's modification time or size changed.

These changes should cycle a provider but don't move the stamp. Each one resolves when Mastra Code restarts:

- Edits to a local plugin's files other than its entry file.
- Changes to a local plugin's dependencies under its own `node_modules`.
- Environment variables the provider reads at construction time.
