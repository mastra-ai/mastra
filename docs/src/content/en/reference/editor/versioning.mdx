# Versioning

Editor versions stored agents and prompt blocks. Database-backed resources use draft and publish operations. Code-backed agent overrides use deterministic files and Git history.

See [Editor versioning](/docs/studio/editor#versioning) for release and experimentation patterns.

## Database lifecycle

The resource record stores an `activeVersionId`, while individual snapshots don't store a lifecycle status.

| Term | Meaning |
| - | - |
| Latest | The most recently created configuration snapshot |
| Published | The snapshot selected by `activeVersionId` |
| Draft | The latest snapshot when it differs from `activeVersionId`, or when no active version exists |
| Historical | Any other retained snapshot |

Saving changed snapshot fields creates a new latest version. Saving identical snapshot fields or changing metadata alone doesn't create a version.

If an active version exists, creating a draft doesn't change the version handling published requests. Publishing updates `activeVersionId`. Restoring a historical version copies its configuration into a new inactive draft.

The direct namespace methods and the REST APIs agree on this. `editor.prompt.update()` and `editor.agent.update()` both create an inactive draft. Neither assigns the new version to `activeVersionId`. To publish a version from the SDK, pass it explicitly: `editor.agent.update({ id, status: 'published', activeVersionId: version.id })`. The stored-agent REST `PATCH` route also creates an inactive draft unless `autoPublish` is enabled, and `POST /stored/agents/:id/versions/:versionId/activate` publishes it.

When a generic stored resource has no active version, published resolution can fall back to the latest snapshot. For a code-defined agent override, requesting `status: 'published'` without an active override returns the original code agent.

## Code source

With `source: 'code'`, active agent overrides are serialized as deterministic JSON under `<codePath>/agents/<encodedAgentId>.json`. The default `codePath` is `./mastra/editor`.

The initial agent is published to create the file. Later server updates create a draft by default and write the file when that version becomes active. Git versions are read-only in Studio and use the commit message as their change message. The default history scan reads up to 50 recent commits and skips consecutive commits whose parsed JSON snapshot is unchanged.

See [`MastraEditor`](/reference/editor/mastra-editor#source) for source options.

## Select an agent version

Calling [`mastra.getAgentById()`](/reference/core/getAgentById) without a selector returns the registered code-defined agent. Pass `status` or `versionId` to apply a stored override. See [Select a version](/docs/studio/editor#select-a-version) for a TypeScript example.

With the default server prefix, pass selectors as query parameters under `/api`:

```bash title="Version selection through the API"
# Published version
curl http://localhost:4111/api/agents/support-agent

# Latest draft
curl http://localhost:4111/api/agents/support-agent?status=draft

# Exact version
curl http://localhost:4111/api/agents/support-agent?versionId=abc-123
```

See the [Client SDK agents reference](/reference/client-js/agents#version-management) for Client SDK and React SDK selectors.

## Version tags

A version tag is a name, such as `production` or `staging`, that points at one version of a stored agent or prompt block. Callers select the tag instead of a version ID, so moving the tag changes which version they get without changing their code.

The agent or prompt block record stores tags in `metadata.versionTags`, a map of tag name to version ID, so setting a tag doesn't create a version or change the published version.

### Set a tag

Send the tag map in a stored-agent update. The map replaces the agent's existing tags, so include every tag to keep. Other `metadata` keys aren't affected.

```bash title="Tag a version"
curl -X PATCH http://localhost:4111/api/stored/agents/support-agent \
  -H "Content-Type: application/json" \
  -d '{
    "metadata": {
      "versionTags": {
        "production": "abc-123",
        "staging": "def-456"
      }
    }
  }'
```

To move a tag, send the map with the new version ID. To remove a tag, send the map without it. In Studio, the version history panel of the agent editor lists the tags and has a field to tag the selected version.

The update is rejected with a `400` response when:

- A tag name isn't 1 to 63 letters, digits, `.`, `_`, or `-`, or doesn't start with a letter or digit
- A tag is named `published` or `draft`. These names are reserved because they select the matching `status`
- A tag points at a version that doesn't exist or belongs to another agent
- The agent would have more than 20 tags

Tags can't be set in the request that creates an agent, because the agent has no versions yet.

Prompt blocks take the same tag map, with the same rules, through `PATCH /api/stored/prompt-blocks/:storedPromptBlockId`. In Studio, the prompt block editor has the same version history panel for tagging a version.

### Select a version by tag

Pass `tag` as a query parameter to read the tagged version:

```bash title="Read a tagged version"
curl http://localhost:4111/api/agents/support-agent?tag=production
```

To run the tagged version, pass `agentVersionTag` in the request context of a `generate` or `stream` call:

```bash title="Run a tagged version"
curl -X POST http://localhost:4111/api/agents/support-agent/generate \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [{ "role": "user", "content": "Where is my order?" }],
    "requestContext": { "agentVersionTag": "production" }
  }'
```

When several selectors are sent, `versionId` wins over `tag`, and `tag` wins over `status`. A tag the agent doesn't have returns a `404` response.

The tag applies to the whole run:

- **Sub-agents:** Each sub-agent that has the tag runs its tagged version. A sub-agent without the tag runs its published version. A version the request sets under [sub-agent versions](#sub-agent-versioning) wins over the tag.
- **Prompt blocks:** Each prompt block the agent or a sub-agent references that has the tag renders its tagged version. A prompt block without the tag renders its published version. Send `promptVersionTag` to select prompt blocks with a different tag.

### Select a prompt block version by tag

Pass `tag` as a query parameter to read the tagged version of a prompt block. A tag the prompt block doesn't have returns a `404` response.

```bash title="Read a tagged prompt block"
curl http://localhost:4111/api/stored/prompt-blocks/tone-of-voice?tag=production
```

To run an agent with tagged prompt blocks, pass `promptVersionTag` in the request context. Every prompt block the agent references that has the tag renders its tagged version. A referenced prompt block without the tag renders its published version. When none of the prompt blocks the agent and its sub-agents reference has the tag, the request returns a `404` response, so a mistyped tag doesn't run on published prompts.

```bash title="Run an agent with tagged prompt blocks"
curl -X POST http://localhost:4111/api/agents/support-agent/generate \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [{ "role": "user", "content": "Where is my order?" }],
    "requestContext": { "promptVersionTag": "production" }
  }'
```

A request can send both `agentVersionTag` and `promptVersionTag`. The agent tag selects the agent and sub-agent versions, and the prompt tag selects the versions of the prompt blocks they reference. Without `promptVersionTag`, the agent tag selects the prompt blocks too. The reserved names `published` and `draft` are ignored in `promptVersionTag`, so a run can't use it to load draft prompt blocks.

### See which versions ran

With [tracing](/docs/observability/tracing/overview) enabled, the agent run span of each agent in the run reports the versions it used in its metadata:

- `entityVersionId`: The agent version that ran
- `versionTag`: The tag that selected that agent version
- `promptVersionTag`: The tag applied to the agent's prompt blocks
- `promptBlockVersions`: A map of prompt block ID to the version ID that was rendered
- `promptBlocksWithoutTag`: The IDs of rendered prompt blocks that don't have the tag and used their published version

`promptBlockVersions` is reported for untagged runs too. The other tag fields are only present when a tag was used.

### Retention

A tagged version is kept like the published version. It can't be deleted until the tag is removed or moved, and it's skipped when old versions are pruned from the version history.

## Sub-agent versioning

Version overrides propagate through [supervisor-agent delegation](/docs/subagents) in request context. Define selectors at three levels:

1. `Mastra` instance `versions`: Defaults for every invocation
1. Server request-body `versions`: Per-request values added to request context
1. Direct `generate()` or `stream()` `versions`: Per-invocation values

Entries merge by agent ID. For the same ID, precedence is **direct invocation > request body or existing request context > Mastra instance default**.

Set defaults on the Mastra instance:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraEditor } from '@mastra/editor'

export const mastra = new Mastra({
  agents: { supervisor, researchAgent, writerAgent },
  editor: new MastraEditor(),
  versions: {
    agents: {
      'research-agent': { status: 'published' },
      'writer-agent': { versionId: 'abc-123' },
    },
  },
})
```

Override one sub-agent for a direct invocation:

```typescript title="src/routes/experiment.ts"
const result = await supervisor.generate('Research and write about AI safety', {
  versions: {
    agents: {
      'research-agent': { status: 'draft' },
    },
  },
})
```

Or pass selectors in the server request body:

```bash title="Per-request sub-agent versions"
curl -X POST http://localhost:4111/api/agents/supervisor/generate \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [{ "role": "user", "content": "Research AI safety" }],
    "versions": {
      "agents": {
        "research-agent": { "status": "draft" }
      }
    }
  }'
```

If Editor isn't configured or a version can't be resolved, Mastra logs a warning and uses the code-defined sub-agent.

## Stored-agent REST API

The default Mastra server prefix is `/api`. A custom server prefix changes the paths below.

| Method | Path | Description |
| - | - | - |
| `GET` | `/api/stored/agents` | List stored agents |
| `POST` | `/api/stored/agents` | Create a stored agent |
| `GET` | `/api/stored/agents/:storedAgentId` | Get a stored agent |
| `PATCH` | `/api/stored/agents/:storedAgentId` | Update a stored agent |
| `DELETE` | `/api/stored/agents/:storedAgentId` | Delete a stored agent |
| `GET` | `/api/stored/agents/:storedAgentId/dependents` | List readable dependents and count hidden cross-workspace references |
| `POST` | `/api/stored/agents/:storedAgentId/export` | Export the allowed override fields as deterministic JSON |

The dependents response lists caller-readable agents by `id` and `name`. Its `hiddenCount` field counts cross-workspace references that the caller can't read, but only when the target agent is public.

Version-management routes are nested under `/api/stored/agents/:storedAgentId/versions`. See [version management](/reference/client-js/agents#version-management) for operations and Client SDK methods.

The Client SDK exposes `listStoredAgents()`, `createStoredAgent()`, and `getStoredAgent()`. The resource returned by `getStoredAgent(id)` includes methods for updates, deletion, dependents, export, and version management.
