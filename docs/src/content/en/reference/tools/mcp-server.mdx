# MCPServer

The `MCPServer` class exposes your existing Mastra tools, agents and workflows as a Model Context Protocol (MCP) server. Any MCP client that speaks the `2026-07-28` revision can connect to these capabilities and make them available to an agent.

If you only need to use your tools or agents inside your Mastra application you don't need an MCP server. This API exists to expose Mastra capabilities to _external_ MCP clients.

`MCPServer` serves the MCP **2026-07-28** revision only, over [stdio and Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports). Every request is self-contained and carries everything the server needs. The server never opens a session or initiates a request of its own. Tools, resources and prompts that need input from the caller return an `input_required` continuation, and the client repeats the call with its answers. Clients on older revisions are rejected with an explicit protocol error; to keep serving them, stay on `@mastra/mcp` 1.x. See the [v2 migration guide](/reference/migrations/mcp-v2) for the full list of changes.

## Constructor

To create a new `MCPServer`, provide basic information about the server, the tools it offers and, optionally, agents and workflows to expose as tools.

```typescript
import { Agent } from '@mastra/core/agent'
import { createTool } from '@mastra/core/tools'
import { MCPServer } from '@mastra/mcp'
import { z } from 'zod'
import { dataProcessingWorkflow } from '../workflows/dataProcessingWorkflow'

const myAgent = new Agent({
  id: 'my-example-agent',
  name: 'MyExampleAgent',
  description: 'A generalist to help with basic questions.',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const weatherTool = createTool({
  id: 'getWeather',
  description: 'Gets the current weather for a location.',
  inputSchema: z.object({ location: z.string() }),
  execute: async inputData => `Weather in ${inputData.location} is sunny.`,
})

const server = new MCPServer({
  id: 'my-custom-server',
  name: 'My Custom Server',
  version: '1.0.0',
  description: 'A server that provides weather data and agent capabilities',
  instructions:
    'Use the available tools to help users with weather information and data processing tasks.',
  tools: { weatherTool },
  agents: { myAgent }, // this agent will become tool "ask_myAgent"
  workflows: {
    dataProcessingWorkflow, // this workflow will become tool "run_dataProcessingWorkflow"
  },
})
```

## Tool schemas and structured results

Tool input and output schemas are advertised as JSON Schema 2020-12, the dialect the `2026-07-28` revision assumes, with the dialect declared in `$schema`. Supported references, composition keywords and tuple (`prefixItems`) shapes are preserved. A tool input schema must describe an object.

A tool with an `outputSchema` can return any JSON value, including an object, array, string, number, boolean or `null`. The value is sent as `structuredContent` without wrapping it in an object, alongside a JSON text fallback in `content`. The server validates structured output against the output schema before returning it. A violation reaches the client as a tool error.

## Exposing agents and workflows as tools

When you provide `agents`, each agent becomes a tool named `ask_<agentKey>`:

- **Description**: "Ask agent `<agent.name>` a question. Agent description: `<agent.description>`".
- **Input**: `{ message: string }`.
- **Execution**: calls the agent's `generate()` with the message and returns its text.

When you provide `workflows`, each workflow becomes a tool named `run_<workflowKey>` whose input schema is the workflow's `inputSchema`. The tool creates a run and starts it with the tool input.

An agent or workflow without a non-empty `description` makes the constructor throw. If a derived name collides with an explicit tool in `tools`, the explicit tool takes precedence and a warning is logged.

## Request context in tools

Ordinary tools and protocol-aware tools see the request differently.

### Ordinary tools (`createTool`)

Tools created with `createTool` run on the MCP server exactly as they do in agents and workflows. They receive their normal execution context, which has no `context.mcp` property. Transport authentication is available on the trusted request context:

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const getUserData = createTool({
  id: 'getUserData',
  description: 'Fetches data for the authenticated user',
  inputSchema: z.object({ userId: z.string() }),
  execute: async (inputData, context) => {
    const authInfo = context.requestContext?.get('authInfo') as { token?: string } | undefined
    if (!authInfo?.token) throw new Error('Authentication required')

    const response = await fetch(`https://api.example.com/users/${inputData.userId}`, {
      headers: { Authorization: `Bearer ${authInfo.token}` },
    })
    return response.json()
  },
})
```

The request context carries:

| Key | Value |
| - | - |
| `authInfo` | The `AuthInfo` resolved for the HTTP request (see [Authentication context](#authentication-context)) |
| `user` | The value returned by `mapAuthInfoToUser`, when configured |
| `traceContext` | W3C `traceparent`, `tracestate` and `baggage` sent by the client in `_meta`, as opaque strings for observability. Never use them for authorization. |

Cancellation reaches the tool through `context.abortSignal`.

## Input-required continuation

A tool, resource or prompt that needs information from the caller returns an `input_required` result instead of holding the request open. The client answers by calling again with keyed `inputResponses` and the echoed `requestState`, and the handler runs again from the top for the new round. Responses are per round: the framework never replays earlier rounds, so carry what the next round needs in `requestState`.

```typescript
import { createMCPTool } from '@mastra/core/mcp'
import { createRequestStateCodec, inputRequired } from '@modelcontextprotocol/server'
import { MCPServer } from '@mastra/mcp'
import { z } from 'zod'

type BookingState = {
  phase: 'address' | 'confirm'
  opKey: string
  principal: string
  address?: string
}

const codec = createRequestStateCodec<BookingState>({
  key: process.env.MCP_STATE_KEY!,
  ttlSeconds: 600,
})

const bookDelivery = createMCPTool({
  id: 'bookDelivery',
  description: 'Books a delivery after collecting an address and a confirmation',
  inputSchema: z.object({ opKey: z.string() }),
  outputSchema: z.object({ status: z.string() }),
  execute: async ({ opKey }, { request, requestContext }) => {
    const principal =
      (requestContext.get('authInfo') as { clientId?: string } | undefined)?.clientId ?? 'anonymous'
    const state = request.requestState as BookingState | undefined
    const responses = request.inputResponses ?? {}

    if (!state) {
      return {
        kind: 'input_required',
        result: inputRequired({
          inputRequests: {
            address: inputRequired.elicit({
              message: 'Delivery address?',
              requestedSchema: {
                type: 'object',
                properties: { address: { type: 'string' } },
                required: ['address'],
              },
            }),
          },
          requestState: await codec.mint({ phase: 'address', opKey, principal }),
        }),
      }
    }
    if (state.principal !== principal)
      throw new Error('Continuation belongs to a different principal')

    if (state.phase === 'address') {
      const address = responses.address
      if (!address) throw new Error('Missing response for "address"')
      if (address.action !== 'accept') return { kind: 'completed', value: { status: 'declined' } }
      return {
        kind: 'input_required',
        result: inputRequired({
          inputRequests: {
            confirm: inputRequired.elicit({
              message: 'Confirm booking?',
              requestedSchema: {
                type: 'object',
                properties: { ok: { type: 'boolean' } },
                required: ['ok'],
              },
            }),
          },
          requestState: await codec.mint({
            ...state,
            phase: 'confirm',
            address: (address.content as { address: string }).address,
          }),
        }),
      }
    }

    const confirm = responses.confirm
    if (confirm?.action !== 'accept' || !(confirm.content as { ok: boolean }).ok) {
      return { kind: 'completed', value: { status: 'cancelled' } }
    }
    await bookOnce(state.opKey, state.address!) // idempotent on the domain operation key
    return { kind: 'completed', value: { status: 'booked' } }
  },
})

const server = new MCPServer({
  name: 'Booking',
  version: '1.0.0',
  tools: { bookDelivery },
  requestState: { verify: codec.verify },
})
```

Rules the framework enforces:

- The `input_required` result is validated before it's serialized. Only elicitation requests (`form` or `url` mode) are accepted as embedded requests. The server never embeds `roots/list` or `sampling/createMessage`.
- A `completed` value is validated against `outputSchema`. A continuation isn't, and an ordinary tool can't return a continuation by shaping its output like one.
- `requestState` is client-controlled. With `requestState: { verify }` configured, tampered or expired state is rejected with `-32602` before your handler runs and `request.requestState` holds the decoded payload. Without it, treat the raw string as untrusted.
- Authorization is re-derived from the transport on every round. Nothing is carried between rounds except what you put in `requestState`. Signing state isn't authorization and isn't idempotency: bind the principal into the state and key side effects on a domain operation key, as above.
- Clients that don't advertise the `elicitation` capability can't answer an embedded request. The call fails with an explicit error instead of fabricating an answer.

Resource and prompt callbacks can return the same `{ kind: 'input_required', result }` shape (typed as `MCPInputRequired`) from `getResourceContent` and `getPromptMessages`.

## Methods

### `startStdio()`

Serves the current process's stdio. Use this when the server runs as a command-line program launched by the client.

```typescript oxfmt:false
async startStdio(): Promise<void>
```

```typescript
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: {/* ... */},
})
await server.startStdio()
```

A client that opens the connection with a pre-2026 exchange is rejected.

### `startHTTP()`

Handles one Streamable HTTP request from an existing Node web server. Call it for every request that arrives at your MCP path.

```typescript oxfmt:false
async startHTTP({
  url,
  httpPath,
  req,
  res,
  options,
}: {
  url: URL;
  httpPath: string;
  req: http.IncomingMessage;
  res: http.ServerResponse<http.IncomingMessage>;
  options?: MCPServerHTTPRequestOptions;
}): Promise<void>
```

Every request is self-contained: there is no session to create or resume, so `options` only carries request guards.

| Option | Behavior |
| - | - |
| `enableDnsRebindingProtection` | When `true`, the `Host` and `Origin` headers are checked against `allowedHosts` and `allowedOrigins` before the request is handled. |
| `allowedHosts` | Hosts (`host[:port]`) accepted when DNS rebinding protection is on. |
| `allowedOrigins` | Origins accepted when DNS rebinding protection is on. |

```typescript
import http from 'node:http'

const httpServer = http.createServer(async (req, res) => {
  await server.startHTTP({
    url: new URL(req.url || '', `http://localhost:1234`),
    httpPath: '/mcp',
    req,
    res,
    options: { enableDnsRebindingProtection: true, allowedHosts: ['localhost:1234'] },
  })
})

httpServer.listen(1234)
```

Requests to any other path answer `404`. If body-parsing middleware (`express.json()`, Fastify) has already consumed the stream, the parsed `req.body` is used. Responses are streamed as Server-Sent Events when the request produces notifications; requests without a `2026-07-28` envelope, `initialize`, `ping` and the standalone `/sse` transport are rejected. Streaming works the same way whether the process is long-lived or serverless.

When the server is registered on a Mastra instance, the Mastra server serves it at `/api/mcp/:serverId/mcp` and calls `startHTTP` for you.

Executes an ordinary tool outside a protocol request (for example from Studio or a REST route) and returns its business result. Native tools created with `createMCPTool` can't run this way and throw, because they need a protocol request.

```typescript oxfmt:false

  toolId: string,
  input: unknown,
```

Runs any catalogue tool with a full protocol context and returns its outcome (`{ kind: 'completed', value }` or `{ kind: 'input_required', result }`). This is the path `tools/call` uses, and FGA is enforced for native and ordinary tools alike.

```typescript oxfmt:false

  toolId: string,
  input: unknown,
  context: MCPToolExecutionContextV2,

```

Returns the current tool catalogue, keyed by MCP tool name.



## Resource handling

### What are MCP Resources?

MCP resources expose server data that clients can read and use as context for LLM interactions: file contents, database records, API responses, live system data, screenshots or log files. Resources are identified by unique URIs (e.g., `file:///home/user/documents/report.pdf`) and contain either text (UTF-8) or binary data (base64).

Clients discover resources through `resources/list` (concrete resources) and `resources/templates/list` (RFC 6570 URI templates for runtime-defined resources), read them with `resources/read`, and receive `notifications/resources/list_changed` and `notifications/resources/updated` through a `subscriptions/listen` stream. See the [MCP resources documentation](https://modelcontextprotocol.io/docs/concepts/resources).

### `MCPServerResources` Type

Every callback receives the request-scoped `MCPServerRequest` (`{ request, requestContext }`) described in [Request context in tools](#protocol-aware-tools-createmcptool), so resource access can be authorized per request and cancelled through `request.signal`.

```typescript
export type MCPServerResources = {
  listResources: (params: MCPServerRequest) => Promise<Resource[]>

  getResourceContent: (
    params: { uri: string } & MCPServerRequest,
  ) => Promise<MCPServerResourceContent | MCPServerResourceContent[] | MCPInputRequired>

  resourceTemplates?: (params: MCPServerRequest) => Promise<ResourceTemplate[]>
}

export type MCPServerResourceContent = { text?: string } | { blob?: string }
```

Example:

```typescript
import { MCPServer } from '@mastra/mcp'
import type {
  MCPServerResourceContent,
  MCPServerResources,
  Resource,
  ResourceTemplate,
} from '@mastra/mcp'

const myResources: Resource[] = [
  { uri: 'file://data/123.txt', name: 'Data File', mimeType: 'text/plain' },
]

const myResourceContents: Record<string, MCPServerResourceContent> = {
  'file://data/123.txt': { text: 'This is the content of the data file.' },
}

const myResourceTemplates: ResourceTemplate[] = [
  {
    uriTemplate: 'file://data/{id}',
    name: 'Data File',
    description: 'A file containing data.',
    mimeType: 'text/plain',
  },
]

const myResourceHandlers: MCPServerResources = {
  listResources: async ({ requestContext }) => {
    if (!requestContext.get('authInfo')) return []
    return myResources
  },
  getResourceContent: async ({ uri, request }) => {
    request.signal.throwIfAborted()
    const content = myResourceContents[uri]
    if (!content) throw new Error(`Resource content not found for ${uri}`)
    return content
  },
  resourceTemplates: async () => myResourceTemplates,
}

const serverWithResources = new MCPServer({
  id: 'resourceful-server',
  name: 'Resourceful Server',
  version: '1.0.0',
  tools: {/* ... your tools ... */},
  resources: myResourceHandlers,
})
```

### Notifying Clients of Resource Changes

#### `server.resources.notifyUpdated({ uri: string })`

Call this when the content of a resource has changed. Clients listening for that URI receive `notifications/resources/updated`.

```typescript oxfmt:false

```

```typescript
await serverWithResources.resources.notifyUpdated({ uri: 'file://data/123.txt' })
```

#### `server.resources.notifyListChanged()`

Call this when the list of resources has changed. Listening clients receive `notifications/resources/list_changed`.

```typescript oxfmt:false
async server.resources.notifyListChanged(): Promise<void>
```

## Prompt handling

### What are MCP Prompts?

Prompts are reusable templates or workflows that MCP servers expose to clients. They can accept arguments and include resource context, and they standardize LLM interactions. Prompts are identified by a unique name.

### `MCPServerPrompts` Type

```typescript
export type MCPServerPrompts = {
  listPrompts: (params: MCPServerRequest) => Promise<Prompt[]>

  getPromptMessages?: (
    params: { name: string; args?: Record<string, unknown> } & MCPServerRequest,
  ) => Promise<PromptMessage[] | MCPInputRequired>
}
```

The server validates required prompt arguments against the `arguments` declared on the listed prompt before calling `getPromptMessages`, and returns the listed prompt's `description` with the messages.

Example:

```typescript
import { MCPServer } from '@mastra/mcp'
import type { Prompt, MCPServerPrompts } from '@mastra/mcp'

const prompts: Prompt[] = [
  {
    name: 'analyze-code',
    description: 'Analyze code for improvements',
    arguments: [{ name: 'code', description: 'The code to analyze', required: true }],
  },
]

const myPromptHandlers: MCPServerPrompts = {
  listPrompts: async () => prompts,
  getPromptMessages: async ({ name, args }) => {
    if (name !== 'analyze-code') throw new Error('Prompt not found')
    return [
      {
        role: 'user',
        content: { type: 'text', text: `Analyze this code: ${args?.code}` },
      },
    ]
  },
}

const serverWithPrompts = new MCPServer({
  id: 'promptful-server',
  name: 'Promptful Server',
  version: '1.0.0',
  tools: {/* ... */},
  prompts: myPromptHandlers,
})
```

### Notifying Clients of Prompt Changes

#### `server.prompts.notifyListChanged()`

Call this when the list of prompts has changed. Listening clients receive `notifications/prompts/list_changed`.

```typescript oxfmt:false
async server.prompts.notifyListChanged(): Promise<void>
```

### Best practices for Prompt Handling

- Use clear, descriptive prompt names and descriptions.
- Declare `arguments` on each prompt so required arguments are validated before your callback runs.
- Notify clients when prompt lists change.
- Handle errors with informative messages.

## Dynamic tool management

Tools are usually provided when constructing the `MCPServer`, but you can also add or remove tools while the server is running through the `toolActions` property. When the tool list changes, listening clients receive `notifications/tools/list_changed`.

The property is `toolActions` because `tools()` is the method that returns the registered catalogue.

### `toolActions.add(tools)`

Registers new tools and notifies clients. Tools are keyed by their record key, the same as tools passed to the constructor. Adding a tool under an existing key replaces it.

```typescript oxfmt:false
async server.toolActions.add(tools: MCPServerToolsV2): Promise<void>
```

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

const searchTool = createTool({
  id: 'search',
  description: 'Searches the knowledge base.',
  inputSchema: z.object({ query: z.string() }),
  execute: async ({ query }) => ({ results: [] }),
})

await server.toolActions.add({ searchTool })
```

### `toolActions.remove(toolIds)`

Removes tools by key and notifies clients. Unknown keys are ignored, and a notification is sent only when at least one tool is removed.

```typescript oxfmt:false
async server.toolActions.remove(toolIds: string[]): Promise<void>
```

### `toolActions.notifyListChanged()`

Sends `notifications/tools/list_changed` without modifying the catalogue. Call this when tool availability changes through other means (for example, authorization changes).

```typescript oxfmt:false
async server.toolActions.notifyListChanged(): Promise<void>
```

### Mastra registry synchronization

When the server is registered with a Mastra instance, `toolActions.add()` and `toolActions.remove()` also update the Mastra tool registry, matching the registration that happens at startup. Ordinary tools become available through `mastra.listTools()` (keyed by the tool's `id` when present). Native tools created with `createMCPTool` are never added to it.

## Logging and progress

The server advertises the `logging` capability but doesn't accept `logging/setLevel`, because without connection state there is no per-connection log level to set. Instead, a client opts in per request by sending the `io.modelcontextprotocol/logLevel` key in `_meta`. `request.log(level, data)` inside a native tool, resource or prompt callback then delivers `notifications/message` to that request's caller, filtered to the requested minimum severity (RFC 5424 ordering). Requests without the opt-in receive nothing, and one request's level never affects a concurrent request or a later continuation round.

```typescript
const auditedTool = createMCPTool({
  id: 'audited',
  description: 'Logs to the caller',
  inputSchema: z.object({}),
  outputSchema: z.object({ ok: z.boolean() }),
  execute: async (_input, { request }) => {
    await request.log('info', { message: 'starting' })
    await request.progress(1, 2, 'half way')
    await request.log('warning', { message: 'slow upstream' })
    await request.progress(2, 2, 'done')
    return { kind: 'completed', value: { ok: true } }
  },
})
```

`request.progress()` sends `notifications/progress` when the client supplied a `progressToken` in `_meta`, and is a no-op otherwise.

Ordinary tools keep using the Mastra logger and observability, which are unaffected by per-request log delivery. Mastra's `MCPClient` opts in at `'info'` by default (`enableServerLogs` / `serverLogLevel`).

## Notification delivery

`resources.notifyListChanged()`, `prompts.notifyListChanged()` and `toolActions.notifyListChanged()` reach every client that holds a `subscriptions/listen` stream with the matching list-changed interest, and `resources.notifyUpdated()` reaches clients listening for that resource URI. Notifications travel on the listen stream. A notification sent before any transport is serving is dropped.

## OAuth protection

To protect the server with OAuth per the [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), use `createOAuthMiddleware`:

```typescript
import http from 'node:http'
import { MCPServer, createOAuthMiddleware, createStaticTokenValidator } from '@mastra/mcp'

const mcpServer = new MCPServer({
  id: 'protected-server',
  name: 'Protected MCP Server',
  version: '1.0.0',
  tools: {/* your tools */},
})

const oauthMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    scopesSupported: ['mcp:read', 'mcp:write'],
    resourceName: 'My Protected MCP Server',
    validateToken: createStaticTokenValidator(['allowed-token-1']),
  },
  mcpPath: '/mcp',
})

const httpServer = http.createServer(async (req, res) => {
  const url = new URL(req.url || '', 'https://mcp.example.com')

  const result = await oauthMiddleware(req, res, url)
  if (!result.proceed) return // Middleware handled the response (401, metadata, ...)

  await mcpServer.startHTTP({ url, httpPath: '/mcp', req, res })
})

httpServer.listen(3000)
```

The middleware:

- Serves **Protected Resource Metadata** at `/.well-known/oauth-protected-resource` (RFC 9728)
- Returns `401 Unauthorized` with a `WWW-Authenticate` header when authentication is required
- Validates bearer tokens with your validator and sets `req.auth` for the MCP handler

### Token Validation

```typescript
import { createOAuthMiddleware, createIntrospectionValidator } from '@mastra/mcp'

// Option 1: Token introspection (RFC 7662)
const middleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: createIntrospectionValidator('https://auth.example.com/oauth/introspect', {
      clientId: 'mcp-server',
      clientSecret: 'secret',
    }),
  },
})

// Option 2: Custom validation (JWT, database lookup, etc.)
const customMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: async (token, resource) => {
      const decoded = await verifyJWT(token)
      if (!decoded) {
        return { valid: false, error: 'invalid_token' }
      }
      return {
        valid: true,
        scopes: decoded.scope?.split(' ') || [],
        subject: decoded.sub,
      }
    },
  },
})
```

## Authentication context

Whatever your HTTP middleware sets on `req.auth` before `startHTTP()` becomes the `authInfo` entry of the request context for that request, for ordinary and native tools alike. Stdio requests carry no `authInfo`.

```
req.auth = { token, clientId, scopes, extra }  →  requestContext.get('authInfo')
```

### Where `authInfo` comes from on a Mastra server

When the MCP server is served by a Mastra server, `req.auth` is populated from the principal resolved by `server.auth`:

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    auth: new MastraJwtAuth({ secret: process.env.JWT_SECRET! }),
  },
})
```

| `authInfo` field | Value |
| - | - |
| `token` | The bearer token or session cookie value used for the request |
| `clientId` | The first present of `user.id`, `user.sub`, `user.userId`, `user.email` |
| `scopes` | `user.scopes`, `user.scope`, or `user.permissions`, normalized to an array |
| `extra.user` | The full user object returned by the auth provider |

If your own middleware performs the verification, set `server.mcpOptions.setRequestAuth` to build `authInfo` yourself. The hook replaces the default mapping:

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    middleware: [verifyBearerToken], // stores the payload on the request context
    mcpOptions: {
      setRequestAuth: (req, requestContext) => {
        const payload = requestContext.get('bearerPayload')
        req.auth = {
          token: payload.token,
          clientId: payload.sub,
          scopes: payload.scope.split(' '),
        }
      },
    },
  },
})
```

Leaving `req.auth` unset inside the hook opts the request out of auth info entirely.

### Map auth data for FGA

When the server is registered on a Mastra instance with a fine-grained authorization (FGA) provider, Mastra checks `requestContext.get('user')` before listing or calling tools. Use `mapAuthInfoToUser` to derive the user shape your FGA provider expects. It runs on every request and every continuation round.

```typescript
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const extra = authInfo.extra as
      | { userId?: string; organizationMembershipId?: string }
      | undefined
    if (!extra?.userId) return null
    return { id: extra.userId, organizationMembershipId: extra.organizationMembershipId }
  },
})
```

### Scope MCP tool FGA separately

Use `fga.resourceMapping` and `fga.permissionMapping` when MCP clients need a different authorization scope than internal agent or workflow tool execution. The override applies only to this server's `tools/list` and `tools/call` checks.

```typescript
import { MastraFGAPermissions } from '@mastra/core/auth/ee'

const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const extra = authInfo.extra as { userId?: string } | undefined
    return extra?.userId ? { id: extra.userId } : null
  },
  fga: {
    resourceMapping: {
      tool: {
        fgaResourceType: 'user',
        deriveId: ({ user }) => (user as { id: string }).id,
      },
    },
    permissionMapping: {
      [MastraFGAPermissions.TOOLS_EXECUTE]: 'read',
    },
  },
})
```

### Setting up authentication middleware on your own server

Populate `req.auth` before calling `server.startHTTP()`:

```typescript
import express from 'express'

type MCPAuthenticatedRequest = express.Request & {
  auth?: {
    token: string
    clientId: string
    scopes: string[]
    expiresAt?: number
    extra?: Record<string, unknown>
  }
}

const app = express()

app.use('/mcp', async (req, res, next) => {
  const authorization = req.headers.authorization
  if (!authorization?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Missing bearer token' })
  }
  const token = authorization.slice('Bearer '.length)
  const user = await verifyToken(token)
  if (!user) {
    return res.status(401).json({ error: 'Invalid token' })
  }
  ;(req as MCPAuthenticatedRequest).auth = {
    token,
    clientId: user.id,
    scopes: user.scopes,
    extra: { userId: user.id, email: user.email },
  }
  next()
})

app.all('/mcp', async (req, res) => {
  await server.startHTTP({
    url: new URL(req.url, `http://${req.headers.host}`),
    httpPath: '/mcp',
    req,
    res,
  })
})
```

### Passing the request context through to an agent

The request context an ordinary tool receives can be forwarded to an agent so the agent's own tools see the same principal:

```typescript
execute: async (inputData, context) => {
  const authInfo = context.requestContext?.get('authInfo') as
    | { extra?: { userId?: string } }
    | undefined
  if (!authInfo?.extra?.userId) throw new Error('Authentication required')

  const agent = context.mastra?.getAgentById('some-agent-id')
  if (!agent) throw new Error("Agent 'some-agent-id' not found")

  const response = await agent.generate(inputData.prompt, {
    requestContext: context.requestContext,
  })
  return response.text
}
```

```typescript
const calculatorTool = createTool({
  id: 'calculatorWithUI',
  description: 'An interactive calculator',
  inputSchema: z.object({
    num1: z.number(),
    num2: z.number(),
    operation: z.enum(['add', 'subtract']),
  }),
  outputSchema: z.object({ result: z.number() }),
  mcp: {
    _meta: { ui: { resourceUri: 'ui://calculator/main' } },
  },
  execute: async ({ num1, num2, operation }) => ({
    result: operation === 'add' ? num1 + num2 : num1 - num2,
  }),
})

const server = new MCPServer({
  id: 'app-server',
  name: 'App Server',
  version: '1.0.0',
  tools: { calculatorTool },
  appResources: {
    'ui://calculator/main': {
      name: 'Interactive Calculator',
      html: '<html><body><h2>Calculator</h2>...</body></html>',
    },
  },
})
```
