# ModelRouterProcessor

`ModelRouterProcessor` classifies the incoming request once, then overrides the model for the agent's first step. It is intended for cost routing: keep a capable model as the agent's configured default and let the router downgrade to a cheaper model when a [Classifier](/reference/classifier/classifier) is confident the request is simple.

The router only ever replaces the model for step 0. Later steps in the same run use the agent's configured model, so a run that turns out to be harder than the first turn suggested is not locked to the cheap model for its whole life.

```typescript
import { Classifier } from '@mastra/core/classifier'
import { Agent } from '@mastra/core/agent'
import { ModelRouterProcessor } from '@mastra/core/processors'

const triage = new Classifier({
  id: 'triage',
  model,
  questions: {
    complexity: {
      type: 'choice',
      criteria: {
        trivial:
          'Answerable in one or two sentences from general knowledge, with no reasoning steps',
        complex:
          'Requires multi-step reasoning, planning, weighing trade-offs, or careful judgment',
      },
    },
  },
})

export const agent = new Agent({
  name: 'support-agent',
  instructions: 'Answer the user concisely.',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [
    new ModelRouterProcessor({
      classifier: triage,
      question: 'complexity',
      models: {
        trivial: '__GATEWAY_OPENAI_MODEL_MINI__',
        complex: '__GATEWAY_OPENAI_MODEL__',
      },
    }),
  ],
})
```

## Routing on more than one dimension

Choice criteria are mutually exclusive, which is the wrong shape when routing depends on independent dimensions. Use `select` instead and combine the answers yourself. It receives the fully typed answers, so the policy stays yours:

```typescript
const triage = new Classifier({
  id: 'triage',
  model,
  questions: {
    complexity: {
      type: 'choice',
      criteria: {
        trivial: 'Answerable in one or two sentences with no reasoning steps',
        complex: 'Requires multi-step reasoning or careful judgment',
      },
    },
    sensitive: {
      type: 'boolean',
      criteria: {
        true: 'Involves money, credentials, legal, medical, or safety consequences',
        false: 'Routine request with no sensitive consequences',
      },
    },
  },
})

new ModelRouterProcessor({
  classifier: triage,
  select: ({ complexity, sensitive }) => {
    // Never downgrade a sensitive request, however simple it looks.
    if (sensitive.probability >= 0.3) return undefined
    return complexity.choice === 'trivial' ? '__GATEWAY_OPENAI_MODEL_MINI__' : undefined
  },
})
```

Returning `undefined` abstains, and the agent's configured model is used.

## Probabilities and `minProbability`

Not every evaluation model returns a probability distribution for choice questions. Boolean questions report `P(true)`, but a choice answer may carry only the selected criterion.

This is why `minProbability` has no default. The two modes are explicit:

- **Omitted**: route on the selected choice. The classifier's answer is the decision.
- **Set**: require a probability at or above the threshold. If the model returns no probability at all, the router **abstains**, because a threshold that cannot be evaluated must not quietly pass.

Verify that your evaluation model returns choice probabilities before setting `minProbability`, otherwise the router will abstain on every request and the option will look broken. If you want calibrated abstention and your model only reports probabilities for booleans, express the decision as a boolean question and use `select`.

## Failure behavior

Routing fails open. If the classifier errors, the classifier ID is not registered, or the request has no user text to classify, the processor logs a warning and the agent's configured model is used. This is the safe direction for a cost optimization: the worst case is that you pay for the model you already configured.

This is the opposite of the fail-closed stance appropriate for [tool approval](/docs/agents/human-in-the-loop), where uncertainty should escalate rather than pass through.

## Measured behavior

Routing was evaluated on a tool-using support agent over 26 requests, weighted toward underspecified phrasing rather than obviously easy or obviously hard questions. Each request was answered by both models so the two could be compared directly, and the downgraded subset was graded by a stronger model in both A/B orders, discarding any verdict that flipped when the order was swapped.

| Measure | Result |
| - | - |
| Downgraded | 13 of 26 requests |
| Clearly complex requests downgraded | 0 of 6 |
| Cost saving on agent calls | \~39% |
| Downgraded answers judged worse | 3 of 13 |

Two results matter more than the headline saving.

**The classifier call is not free relative to what it saves.** It used around 424 tokens per request, against roughly 436 input tokens for the agent call it was optimizing. The saving was about $0.0008 per request at the list prices above. Whether routing is net positive depends on your evaluation model's price and on the gap between your two agent models being wide enough to clear that cost. A narrow gap can make routing cost more than it saves.

**Downgrading is not quality-neutral.** Three of thirteen downgraded answers were judged worse by a stronger model, consistently in both orders. The failures were omitted policy conditions and less precise details rather than outright wrong answers, and one occurred on a request that looked entirely routine. Treat some quality cost on downgraded traffic as expected, not as a bug to tune away.

With 13 downgraded samples, one provider, one taxonomy, and one judge, the regression rate is directionally useful and not a precise figure. Run the comparison on your own traffic before enabling this broadly: answer the same requests with both models, compare the downgraded subset, and confirm the saving clears your classifier cost.

## Cost and behavior notes

- The classifier runs **once per request**, in `processInput`, not once per step. The decision is stashed in per-request state and read at step 0.
- Only downgrade. Keep the capable model as the agent's configured default and use the router to move down, so an incorrect routing decision costs quality on one step rather than removing the capable model from the run entirely.
- The router adds a classifier round-trip to the critical path of every request, including those it ends up abstaining on. As the measurements above show, this round-trip can be comparable in size to the agent call it is optimizing, so confirm the saving is real for your model pair rather than assuming it.
