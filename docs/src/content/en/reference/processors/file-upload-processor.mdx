# FileUploadProcessor

The `FileUploadProcessor` uploads files attached to user messages to a [workspace sandbox](/reference/workspace/sandbox) and replaces each file with a text reference to its path. The model receives the path and never the file content. The agent works on the file with its sandbox tools.

A file that the filter accepts never reaches the model. When the processor can't upload it, the processor stops the turn instead of letting the file through.

To upload a file, the processor requires an agent with [memory](/docs/memory/overview) and a thread that isn't read-only. The replaced message is what gets stored, which is why the same file isn't uploaded again on the next turn. A turn without a file needs neither.

## Usage example

Pass the same workspace to the agent and to the processor:

```typescript
import { Agent } from '@mastra/core/agent'
import { FileUploadProcessor } from '@mastra/core/processors'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'
import { Memory } from '@mastra/memory'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
})

export const agent = new Agent({
  id: 'file-agent',
  name: 'file-agent',
  instructions: 'Work on the files the user uploads to the sandbox.',
  model: '__GATEWAY_OPENAI_MODEL_NANO__',
  memory: new Memory(),
  workspace,
  inputProcessors: [
    new FileUploadProcessor({
      workspace,
      filter: ({ extension }) => extension === 'xlsx' || extension === 'docx',
    }),
  ],
})
```

Set a size limit per file with `maxFileSize`. The function returns a number of bytes:

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const megabyte = 1024 * 1024

const fileUpload = new FileUploadProcessor({
  workspace,
  maxFileSize: ({ mimeType }) => (mimeType.startsWith('image/') ? 5 * megabyte : 25 * megabyte),
})
```

Read the reason when the processor stops a turn. The tripwire metadata is typed as `unknown`, so cast it to `FileUploadTripwireMetadata`:

```typescript
import { FILE_UPLOAD_ERROR_CODES } from '@mastra/core/processors'
import type { FileUploadTripwireMetadata } from '@mastra/core/processors'

const result = await agent.generate(messages, {
  memory: { thread: 'thread-1', resource: 'user-1' },
})

if (result.tripwire?.processorId === 'file-upload') {
  const { code, fileName } = result.tripwire.metadata as FileUploadTripwireMetadata

  if (code === FILE_UPLOAD_ERROR_CODES.FILE_TOO_LARGE) {
    console.error(`${fileName} is too large`)
  }
}
```

## File selection

The `filter` function receives each file of the new messages and returns `true` to upload it. A file it rejects is left untouched and reaches the model as usual. Without `filter`, every file is uploaded.

This filter uploads every file except the types the model reads itself:

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const readByModel = ['image/', 'audio/', 'video/', 'text/']

const fileUpload = new FileUploadProcessor({
  workspace,
  filter: ({ mimeType }) =>
    mimeType !== 'application/pdf' && !readByModel.some(prefix => mimeType.startsWith(prefix)),
})
```

`filter` and `maxFileSize` receive the same `FileUploadFileInfo` object:

The size isn't part of it, because it's only known once the data is decoded.

`filter` can be async. It runs again before each model call for the files of the new messages, so it must give the same answer for the same file.

The processor only looks at messages added during the current request, with the `user` or `signal` role. It never checks or changes messages recalled from memory, and it ignores files produced by the assistant. A file already stored in a thread reaches the model as it did before you added the processor.

Only files sent inline, as binary, base64, or a data URL, are uploaded. A file sent as a URL or a provider file ID stays in the message and reaches the model as usual, and `filter` isn't called for it. The processor never downloads a URL, so a request made by the server can't be pointed at an internal address.

## Upload location

Files are written to `uploads/<thread>/<uuid>.<extension>`, relative to the sandbox working directory. Each thread has its own directory, so threads that share a sandbox don't mix their files.

The path keeps nothing of the original name but its extension. A path that looks like the name invites the model to retype one from the other, and to ask the sandbox for a file that doesn't exist. The name stays available in the note and in the message metadata.

| Name sent | Path written |
| - | - |
| `report Q3 (final).pdf` | `uploads/<thread>/<uuid>.pdf` |
| `résumé.PDF` | `uploads/<thread>/<uuid>.pdf` |
| `../../etc/passwd` | `uploads/<thread>/<uuid>` |
| No name, `image/png` | `uploads/<thread>/<uuid>.png` |

A file sent without a name takes its extension from its MIME type when the type is a common one.

The thread ID is rewritten so the directory is safe in a shell command. Accents are removed, and every character outside `A-Z`, `a-z`, `0-9`, `.`, `_`, and `-` becomes `_`. Path separators and `..` are replaced too, so a file always stays inside `uploads/`.

The processor writes with the sandbox `writeFiles` method when the sandbox has one, in a single call for all the files of a turn. Otherwise it writes with `executeCommand`, sending each file as base64 in chunks. This path needs `sh`, `base64`, `printf`, and `mkdir` in the sandbox.

## Message content after upload

The file part is replaced, at the same position in the message, by a text part:

```text
[File uploaded to the sandbox]
path: uploads/thread-1/3f6c1d2e-8a4b-4c0d-9e21-5b7a6c9d0e1f.pdf
name: report.pdf
type: application/pdf
size: 1258291 bytes
```

The processor also records each upload in the message metadata. The metadata is stored with the message and isn't sent to the model, so a client can render the attachment without parsing the text:

```typescript
message.content.metadata.fileUploads
// [{ name: 'report.pdf', path: 'uploads/thread-1/<uuid>.pdf', mimeType: 'application/pdf', size: 1258291 }]
```

`name` is omitted for a file sent without a name.

## Error behavior

The constructor throws a `MastraError` with the ID `FILE_UPLOAD_PROCESSOR_NO_SANDBOX` when `workspace` is missing or has no sandbox configured. `error.details.code` is `NO_SANDBOX`.

Every other failure stops the turn by calling `abort()` with `retry: false`. The model isn't called. `agent.generate()` resolves with `result.tripwire` set instead of rejecting, and `agent.stream()` emits a `tripwire` chunk.

`FILE_UPLOAD_ERROR_CODES` lists every code:

| Code | When it happens |
| - | - |
| `MEMORY_REQUIRED` | A file is sent, and the agent has no memory, the call has no thread, or memory is read-only |
| `NO_SANDBOX` | The workspace resolved no sandbox for the request, or resolving it failed |
| `NO_WRITE_CAPABILITY` | The sandbox has neither `writeFiles` nor `executeCommand` |
| `INVALID_MAX_FILE_SIZE` | `maxFileSize` threw, or returned something other than a non-negative number |
| `INVALID_FILTER` | `filter` threw, or returned something other than `true` or `false` |
| `INVALID_FILE_DATA` | The inline data of a file to upload can't be decoded |
| `FILE_TOO_LARGE` | A file to upload is larger than its limit |
| `UPLOAD_FAILED` | Writing to the sandbox failed |
| `FILE_NOT_UPLOADED` | A file of a new message that the filter accepts is still there right before the model call |

The processor checks nothing on a turn without a file to upload, and the turn runs as if the processor weren't there. Scorers, agent networks, and calls without a thread run input processors too, and keep working. A workspace without any sandbox is still caught when the processor is created. A sandbox resolver that fails shows on the first upload.

All the files of a turn are checked before the first write. One file that fails stops the whole turn, and nothing is uploaded.

When a write fails, the processor removes the files it wrote during the turn with `rm -f` before it stops the turn. If the removal fails, or the sandbox can't run commands, `orphanPaths` lists the paths that may remain.

Before it stops a turn, the processor replaces every file of that turn that the filter accepts with a `[File not uploaded]` note. When the filter itself fails, every file of the turn is replaced. A stopped turn can still be stored, for example on a durable agent, and this keeps raw files out of the thread.

## Files sent with signals

The processor handles files sent with `agent.sendMessage()` and `agent.sendSignal()`:

- A signal that wakes an idle agent is processed like the input of `agent.stream()`.
- A signal delivered to an active run is processed before the next model call of that run.

## Limitations

- **Stored messages with a raw file.** A message stored without going through the processor keeps its file, and the model receives it on later turns. This happens with threads created before you added the processor, and with a signal sent with the `persist` behavior, which is stored without running input processors.
- **Text files sent from Studio.** Studio inserts a text file, such as a CSV, JSON, Markdown, or source file, into the message as text instead of attaching it as a file. The processor never sees it, so it isn't uploaded and its whole content goes into the prompt. A file sent through the API as a file part is uploaded as usual.
- **Durable agents and early signals.** On a durable agent, a signal that arrives before the first model call of a run isn't uploaded. The turn stops with `FILE_NOT_UPLOADED`.
- **Relative paths with `writeFiles`.** Each sandbox provider resolves the relative `uploads/` path itself. Check that your provider resolves it against the directory where commands run.
- **Processor workflows.** The check before each model call doesn't run when the processor is nested in a processor workflow.
