# Mastra.getMCPServer()

The `.getMCPServer()` method retrieves an MCP server instance by its registry key (the key used when registering the server in the `mcpServers` configuration). For retrieving by the server's intrinsic `id` property, use `.getMCPServerById()` instead.

## Usage example

```typescript
// Register an MCP server with a registry key
const myServer = new MCPServer({
  id: 'my-mcp-server',
  name: 'My Server',
  version: '1.0.0',
  tools: {/* ... */},
})

export const mastra = new Mastra({
  mcpServers: {
    customKey: myServer, // 'customKey' is the registry key
  },
})

// Retrieve by registry key
const server = mastra.getMCPServer('customKey')

// Alternatively, retrieve by intrinsic ID
const serverById = mastra.getMCPServerById('my-mcp-server')
```

## MCP v1 and v2 servers

`MCPServerRegistryEntry` is the union of `MCPServerBase` and `MCPServerBaseV2`, exported from `@mastra/core/mcp`. Existing MCP 1.x servers don't need new properties or methods. Use `isMCPServerV2(server)` after checking that the lookup returned a server to narrow the union.

`MCPServerBaseV2` is a copy of `MCPServerBase` with the same `MCPServerConfig`, id handling, `convertTools`, `tools()` and Mastra registration of tools, agents and workflows. The differences are limited to what the 2026-07-28 protocol changed, which means the base has no `startSSE` or `startHonoSSE` methods, its `executeTool` reports a suspended tool rather than a bare result, and it carries `mcpVersion` set to `2`. None of this changes the behavior of an installed `@mastra/mcp` 1.x server.

### Tools that ask for input

A 2026-07-28 server runs ordinary `createTool` definitions. A tool that needs something from the user before it can finish declares `suspendSchema` and `resumeSchema` and calls `suspend()`, exactly as it would for an agent or a workflow. The server turns that suspension into an `input_required` round, and resumes the tool with the answer in `resumeData`.

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

const confirm = createTool({
  id: 'confirm',
  description: 'Ask for confirmation before charging',
  inputSchema: z.object({ amount: z.number() }),
  outputSchema: z.boolean(),
  suspendSchema: z.object({ phase: z.literal('confirm'), amount: z.number() }),
  resumeSchema: z.object({ confirmed: z.boolean() }),
  execute: async ({ amount }, context) => {
    const round = context.mcpv2
    if (!round?.resumeData) {
      await round?.suspend({ phase: 'confirm', amount })
      return
    }
    return round.resumeData.confirmed
  },
})
```

The same tool keeps working from agents and workflows, which surface the suspension through their own resume paths. `resumeSchema` must be a flat object of primitive fields so it can be presented as an input form.

### The `mcpv2` context

When an `@mastra/mcp` 2.x server executes a tool, `context.mcpv2` is an `MCPToolExecutionContextV2`. The legacy `context.mcp` shape provided by `@mastra/mcp` 1.x is unchanged and is never present on a 2.x server. The `v2` suffix is temporary: the next major release of `@mastra/core` renames it to `context.mcp`.

`mcpv2` contains `protocolVersion: '2026-07-28'`, `requestId`, `signal`, optional request `metadata`, request-scoped `log(level, data, logger?)` and `progress(progress, total?, message?)`, and the suspend/resume trio: `suspend(payload)`, `resumeData` (the current round's answer, validated against `resumeSchema`), and `suspendPayload` (what the tool last suspended with). Because the framework never replays earlier rounds, handlers branch on explicit named phases, every round is re-authorized, and writes rely on domain-owned idempotency.

`suspendPayload` is also handed back to tools resumed by agents and workflows.

### Registration and execution

Tools are registered on the Mastra instance exactly as a 1.x server registers them. `executeTool(toolId, args, context?)` returns `{ status: 'completed', output }` or, when the tool suspended, `{ status: 'suspended', suspendPayload, resumeSchema }` with `resumeSchema` as JSON Schema. Shared REST execution endpoints return the suspended shape instead of pretending the tool finished. Legacy SSE routes remain available only to v1 server instances.

Registering another server under an occupied registry key keeps the existing instance. Registry keys and intrinsic server IDs remain distinct.
