# Span filtering

Span filtering controls which spans are exported from an observability config. Use it to reduce noise or lower per-span costs. It can also keep only the spans that matter for a specific exporter or environment.

For a shorter overview of tracing configuration, see [Tracing](/docs/observability/tracing/overview).

## Usage example

The following example demonstrates how to combine `excludeSpanTypes` and `spanFilter` in one observability config:

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { SpanType } from '@mastra/core/observability'
import { Observability, MastraStorageExporter } from '@mastra/observability'
import { LangfuseExporter } from '@mastra/langfuse'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-app',
        exporters: [new MastraStorageExporter(), new LangfuseExporter()],
        excludeSpanTypes: [SpanType.MODEL_CHUNK, SpanType.MODEL_STEP],
        spanFilter: span => {
          if (span.type === SpanType.MODEL_INFERENCE && span.entityName === 'judge') {
            return false
          }

          return true
        },
      },
    },
  }),
})
```

### `excludeSpanTypes`

Use `excludeSpanTypes` when you want to suppress whole categories of spans with minimal configuration.

For the current set of supported values, see the [`SpanType` enum](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/observability/types/tracing.ts).

```ts title="src/mastra/index.ts"
import { SpanType } from '@mastra/core/observability'

excludeSpanTypes: [SpanType.MODEL_CHUNK, SpanType.MODEL_STEP, SpanType.WORKFLOW_SLEEP]
```

### `spanFilter`

When filtering depends on the exported span contents, use `spanFilter`.

```ts title="src/mastra/index.ts"
import { SpanType } from '@mastra/core/observability'

spanFilter: span => {
  if (span.type === SpanType.MODEL_CHUNK) return false
  if (span.type === SpanType.MODEL_INFERENCE && span.entityName === 'judge') return false

  return true
}
```

Additional examples:

```ts title="src/mastra/index.ts"
// Only export spans from production
spanFilter: span => span.metadata?.environment === 'production'

// Exclude spans from a specific entity
spanFilter: span => span.entityId !== 'noisy-agent'
```

## Processing order

Span filtering happens at export time in this order:

1. Internal spans are dropped unless `includeInternalSpans` is `true`.
1. `excludeSpanTypes` removes matching span types.
1. `spanOutputProcessors` transform the remaining spans.
1. `spanFilter` decides whether to keep the final exported span.

If `spanFilter` throws an error, Mastra keeps the span and logs the error to avoid silent data loss.

## Start and end events

Mastra calls `spanFilter` for each event of a span: when the span starts, on each update, and when it ends. Each call receives the span data at that moment. Data set when the span ends, such as `output`, an error, or `attributes.success`, isn't available when the span starts.

### Drop a span from its start

A filter that only reads data the span has when it starts returns the same answer for every event. That data is the type, name, entity, input, and the attributes and metadata set at creation. No exporter receives the span. Its children attach to the nearest ancestor that was exported, which keeps the trace tree connected.

### Drop a span at its end

A filter that reads end-time data keeps the start event and drops the end event. The result depends on when the exporter writes a span:

- Exporters that write a span when it ends never write this span. Langfuse, the OpenTelemetry exporters, and `MastraStorageExporter` with the `insert-only` strategy work this way. Children of the span were already exported with the span as their parent. In that tool they have no parent.
- Exporters that write a span when it starts keep the span and close it at its end time, without its end-time data. `MastraStorageExporter` with the `realtime` or `batch-with-updates` strategy, Braintrust, LangSmith, and Sentry work this way.

To drop a span and keep a connected tree in every exporter, filter on data the span has when it starts.

A custom exporter that opens a span on its start event can implement [`onSpanFilteredEvent`](/reference/observability/tracing/interfaces#observabilityexporter) to close a span whose end was dropped.
