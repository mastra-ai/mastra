# Feedback

**Added in:** `@mastra/core@1.18.0`

Feedback APIs store and query human-in-the-loop observability signals such as ratings, thumbs, comments, and corrections. Use the [feedback guide](/docs/observability/feedback) for usage patterns.

## Usage example

The following example records a rating for a persisted trace through the observability entrypoint. `addFeedback()` is optional on the entrypoint, so check that the active observability implementation supports it before calling it.

```typescript
if (!mastra.observability.addFeedback) {
  throw new Error('Feedback is not supported by the active observability implementation')
}

await mastra.observability.addFeedback({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

## Create feedback

### `addFeedback(args)`

Sends feedback about a trace or span to configured exporters.

```typescript
await mastra.observability.addFeedback?.({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

<PropertiesTable
  content={[
  { name: 'traceId', type: 'string', description: 'Trace that anchors the feedback target.', isOptional: true },
  { name: 'spanId', type: 'string', description: 'Span that anchors the feedback target.', isOptional: true },
  {
    name: 'correlationContext',
    type: 'CorrelationContext',
    description: 'Live span or trace context to emit from without rehydrating the target from storage.',
    isOptional: true,
  },
  { name: 'feedback', type: 'FeedbackInput', description: 'Feedback payload to add.' },
]}
/>

Without `correlationContext`, each exporter handles the target trace or span at its own destination. `MastraStorageExporter` resolves it from local storage. A failed local lookup doesn't block other exporters. `MastraPlatformExporter` doesn't require local storage. Use `flush()` or `shutdown()` to drain pending deliveries.

Local lookup requires the target span's parent chain through its root so feedback inherits the correct root tags. If any ancestor remains missing after retries, the storage exporter logs a warning and skips the local write. Other exporters still receive the feedback.

### `createFeedback(args)`

Creates one feedback record through the observability storage domain. Storage-level calls write directly to the store, so include `timestamp`.

```typescript
await observability.createFeedback({
  feedback: {
    feedbackId: 'feedback-1',
    timestamp: new Date(),
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

The HTTP and client SDK create route accepts `CreateFeedbackBody`, which requires a nonblank `feedback.traceId` and allows an optional `spanId`. The client supplies a missing `feedbackId` and ISO `timestamp` before retries. Direct OSS HTTP calls can omit them for server defaults. An optional top-level `contextMode` selects supplied context or stored-span resolution. OSS defaults to `"provided"`. Platform defaults to `"resolve"`. See [signal write options](/reference/client-js/observability#signal-write-options):

```typescript
await mastraClient.createFeedback({
  feedback: {
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
  },
})
```

For OSS HTTP requests, the authenticated user's ID takes precedence as `feedbackUserId`. Without an authenticated user, supply `feedbackUserId` explicitly or leave it null for anonymous feedback. `userId` describes the span user and isn't used as the HTTP feedback author. Direct storage calls retain the deprecated `userId` author alias when `feedbackUserId` is omitted. An explicit null author stays null.

### `batchCreateFeedback(args)`

Creates multiple feedback records through the observability storage domain. This method isn't exposed by the HTTP routes or `@mastra/client-js`.

```typescript
await observability.batchCreateFeedback({
  feedbacks: [
    {
      feedbackId: 'feedback-1',
      timestamp: new Date(),
      traceId: 'trace-123',
      feedbackSource: 'user',
      feedbackType: 'rating',
      value: 1,
    },
    {
      feedbackId: 'feedback-2',
      timestamp: new Date(),
      traceId: 'trace-123',
      feedbackSource: 'qa',
      feedbackType: 'comment',
      value: 'Needs a citation before shipping.',
    },
  ],
})
```

## Delete feedback

### `deleteFeedback(args)`

Deletes up to 1,000 feedback records by id. The operation is idempotent: ids that don't exist are ignored, and an empty `feedbackIds` array is a no-op. When `organizationId` or `resourceId` is provided, only records matching that scope are deleted.

```typescript
await mastraClient.deleteFeedback({
  feedbackIds: ['feedback-1', 'feedback-2'],
})
```

<PropertiesTable
  content={[
  {
    name: 'feedbackIds',
    type: 'string[]',
    description: 'Ids of the feedback records to delete. Accepts at most 1,000 ids.',
  },
  {
    name: 'organizationId',
    type: 'string',
    description: 'Restricts the delete to records with this organization id.',
    isOptional: true,
  },
  {
    name: 'resourceId',
    type: 'string',
    description: 'Restricts the delete to records with this resource id.',
    isOptional: true,
  },
]}
/>

The OSS HTTP route returns `{ success: boolean }`. `mastraClient.deleteFeedback()` returns `Promise<{ success: boolean } | { accepted: true }>` to also support Platform backends with queued batch deletion. An accepted response means cleanup is queued, and records can remain readable until cleanup runs. See [client deletion response handling](/reference/client-js/observability#deleting-traces). The storage domain method returns `Promise<void>`. Requests with more than 1,000 ids return `400`, and a server running `@mastra/core` older than `1.66.0` returns `501`. ClickHouse vNext, PostgreSQL vNext, DuckDB, and the in-memory store implement deletion. Every other adapter, including LibSQL and MongoDB, throws `OBSERVABILITY_STORAGE_DELETE_FEEDBACK_NOT_IMPLEMENTED`.

On ClickHouse, deletion uses lightweight deletes on the main feedback events table to remove rows from reads, including OLAP queries, without guaranteeing immediate physical removal, so open-source deployments must configure an [observability retention period](/reference/storage/retention) to physically purge them. Each request is marked applied once its delete succeeds; if the delete fails, the request stays unapplied, doesn't block `updateFeedbackReviewStatus()` on the still-visible feedback, and you retry by calling `deleteFeedback()` again. `updateFeedbackReviewStatus()` also retries the delete and throws a not-found error if the retry succeeds, or saves the new status and throws the delete's error if it fails again. Open-source deployments have no background reconciler. ClickHouse applies a TTL to deletion requests only when all five signals have finite retention. See [ClickHouse native TTL](/reference/storage/retention#clickhouse-native-ttl). Delete APIs leave the separate delta cursor table untouched. Its rows contain identifiers rather than feedback payloads and expire within two days.

### `deleteScores(args)`

Deletes up to 1,000 score records by id. It behaves like `deleteFeedback()` with `scoreIds` in place of `feedbackIds`, and Oracle Database also implements it. Unsupported adapters throw `OBSERVABILITY_STORAGE_DELETE_SCORES_NOT_IMPLEMENTED`.

```typescript
await mastraClient.deleteScores({
  scoreIds: ['score-1', 'score-2'],
})
```

## Replace feedback

`PUT /api/observability/feedback/:feedbackId` accepts a full `{ feedback: { ... } }` replacement. Keep the original `feedbackId`, `traceId`, and `timestamp`, and include every field you want to retain. Omitted optional fields are cleared. The URL and body IDs must match. See [the client example](/reference/client-js/observability#replacing-feedback).

OSS writes to its configured storage before returning success and notifies supporting exporters independently. `contextMode` has the same meaning as on create. In `"resolve"` mode, the local trace or span must exist. A missing feedback record is created from the full replacement. Changing an existing record's trace or timestamp returns `409`.

In-memory, PostgreSQL vNext, DuckDB, and ClickHouse vNext storage support replacement. Check `capabilities.feedbackReplacement` on the server. Unsupported versions return `501`. Sequential retries of the original HTTP create don't undo a replacement. Direct storage `createFeedback()` calls retain upsert behavior. Pass `onConflict: 'ignore'` to keep an existing record.

ClickHouse support uses the existing schema without a migration. Concurrent writes from separate processes can race, so it doesn't guarantee ordering between overlapping creates and replacements. Serialize edits to the same feedback record when using this adapter.

To send a replacement to configured exporters without depending on local storage, use the observability entrypoint:

```typescript
await mastra.observability.replaceFeedback?.({
  traceId: 'trace-123',
  feedback: {
    feedbackId: 'feedback-1',
    timestamp: new Date('2026-11-11T12:00:00.123Z'),
    feedbackType: 'thumbs',
    value: -1,
  },
})
```

Each exporter handles its destination independently. `MastraStorageExporter` resolves local span context when needed, and `MastraPlatformExporter` sends a PUT to Platform. Exporters without a replacement handler skip the event. `flush()` and `shutdown()` wait for pending deliveries.

## Updating review status

To change review status at configured exporter destinations, pass the feedback ID and either `"reviewed"` or `"needs-review"`:

```typescript
await observability.updateFeedbackReviewStatus({
  feedbackId: 'feedback-123',
  reviewStatus: 'reviewed',
})
await observability.flush()
```

Each supporting exporter updates its own destination. Missing local feedback doesn't prevent remote delivery. Exporters without review-status support skip the update. `flush()` and `shutdown()` wait for pending deliveries; delivery failures are logged.

HTTP callers use `PATCH /api/observability/feedback/:feedbackId/review-status` with `{ "reviewStatus": "reviewed" }`. The OSS server updates local storage before returning the updated feedback record, then notifies remote exporters independently. Missing feedback returns `404`. No timestamp is required, and the update preserves the feedback's other fields.

### List query parameters

`GET /api/observability/feedback` takes its arguments as URL query parameters. The [Mastra Platform Feedback API](/docs/mastra-platform/api#feedback-api) accepts the same parameters on its `GET /feedback` endpoint.

```bash
curl -sS "http://localhost:4111/api/observability/feedback?traceId=trace-123&environment=production&feedbackType=rating&page=0&perPage=20"
```

Every field of [`FeedbackFilter`](#feedbackfilter) is accepted as a top-level query parameter with the same name, for example `traceId`, `spanId`, `feedbackType`, `feedbackSource`, `feedbackUserId`, `reviewStatus`, `entityName`, `environment`, `experimentId`, or `tags`. Repeat a parameter to pass multiple values where the filter accepts an array, such as `feedbackType=rating&feedbackType=thumbs`. Pass object-valued filters such as `timestamp` as JSON, for example `timestamp={"start":"2026-01-01T00:00:00Z"}` URL-encoded.

    type: 'string',
    description: 'Opaque delta cursor returned by the previous delta response. Delta mode only.',
    isOptional: true,
  },
  {
    name: 'limit',
    type: 'number',
    description: 'Maximum number of updates to return, from 1 to 100. Delta mode only.',
    isOptional: true,
  },
]}
/>

Requests that mix modes return `400`, for example `page` or `perPage` with `mode=delta`, or `after` or `limit` without it. The analytics routes take the same JSON bodies as [`getFeedbackAggregate()`](#getfeedbackaggregateargs), [`getFeedbackBreakdown()`](#getfeedbackbreakdownargs), [`getFeedbackTimeSeries()`](#getfeedbacktimeseriesargs), and [`getFeedbackPercentiles()`](#getfeedbackpercentilesargs).
