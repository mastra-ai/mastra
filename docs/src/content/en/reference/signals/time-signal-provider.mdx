# TimeSignalProvider

**Added in:** `@mastra/core@1.86.0`

Keeps the agent aware of the current time through a `<current-time>` [state signal](/docs/signals/state-signals). The provider reads the clock each time the agent takes a model step and adds a new snapshot only when the configured interval has moved on, so the model always sees the time to that precision without calling a tool.

Extends [`SignalProvider`](/reference/signals/signal-provider). It runs no timers and never wakes an idle thread: a thread that sits idle for a day gets one new snapshot when its next run starts. To make an agent act on a clock, use [schedules](/docs/harness/schedules) instead.

## Usage example

Register the provider on an agent that has `Memory`:

```typescript title="src/mastra/index.ts"
import { Agent } from '@mastra/core/agent'
import { TimeSignalProvider } from '@mastra/core/signals'

const agent = new Agent({
  id: 'assistant',
  name: 'assistant',
  instructions: '...',
  model,
  memory,
  signals: [new TimeSignalProvider({ timeZone: 'America/New_York' })],
})
```

The model then sees a state signal like this, refreshed every 15 minutes at :00, :15, :30 and :45 by default:

```xml
<current-time timeZone="America/New_York">Tuesday, November 24, 2026 at 3:15 AM EST</current-time>
```

One provider instance can be listed on several agents and serves every thread.

## Requirements and cost

- **Memory is required.** Like every state signal, the time lane is tracked on a memory-backed thread. Listing the provider on an agent without memory makes every run fail with `computeStateSignal requires Mastra memory with an active resourceId and threadId`.
- **Each snapshot stays in the context.** State signals are appended, not replaced: each new snapshot is a persisted message that remains in the prompt until memory trims it. A two-hour run carries about 8 `<current-time>` messages at the default 15-minute interval, and about 120 at `interval: 'minute'` if it takes a step every minute. Choose the coarsest interval the agent needs.
- **The time shown can be up to one interval old.** The snapshot carries the time it was taken and isn't refreshed until the next interval begins, so at the default 15 minutes the time the model sees can be up to 15 minutes stale. Use a shorter interval if the agent needs the exact minute.
- **One provider per time zone on an agent.** Each time zone has its own state lane, so one agent can carry providers for several zones (for example UTC and the user's zone). Adding a second provider for a zone the agent already has makes the agent constructor throw, because the two would overwrite each other's snapshot.
- If an earlier snapshot is trimmed from the context window, the provider adds a fresh one on the next step.
- An interval that spans a daylight saving change can add one extra snapshot that day, carrying the new UTC offset.

## State signal

| Field | Value |
| - | - |
| `id` | `current-time:<timeZone>`, for example `current-time:America/New_York` |
| `tagName` | `current-time` |
| `mode` | `snapshot` |
| `attributes` | `{ timeZone }` |
| `value` | `{ iso, timeZone, interval }`: the time read, as ISO 8601 |

## Methods

### `getInputProcessors()`

Returns the provider's time-lane processor. The Agent registers it on the input-processor chain when the provider is passed to `signals`, so you normally don't call it directly.

Returns: `InputProcessorOrWorkflow[]`
