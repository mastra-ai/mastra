# Memory.branchThread()

The `.branchThread()` method creates a child thread that reads an immutable prefix of its parent's message history and stores only new messages added to the child. Use it for non-destructive edit and regenerate flows where the original conversation must remain available.

Unlike [`cloneThread()`](/reference/memory/cloneThread) and [`copyThread()`](/reference/memory/copyThread), branch creation doesn't copy inherited message rows or their semantic-recall embeddings. Inherited messages keep their original IDs and physical `threadId` values.

## Usage

```typescript
const { thread, branch } = await memory.branchThread({
  threadId: 'conversation-1',
  branchPointMessageId: 'message-3',
  title: 'Alternative answer',
  metadata: { reason: 'regenerate' },
})
```

The new thread ID is generated by Mastra. The child always uses the source thread's `resourceId`.

`branchPointMessageId` must be reachable from the selected source thread. For a nested branch, it may identify a message inherited from any ancestor on that branch's path.

## Returns

```typescript
interface BranchThreadOutput {
  thread: StorageThreadType
  branch: {
    parentThreadId: string
    branchPointMessageId: string
    branchPointCreatedAt: Date
    branchCreatedAt: Date
  }
}
```

The `thread` object doesn't expose Mastra's reserved lineage metadata or internal Observational Memory locator.

## Fork boundary and message identity

Mastra orders messages by `createdAt` and then `id`. The child inherits every message whose `(createdAt, id)` tuple is less than or equal to the branch-point tuple. The ID tie-breaker keeps the boundary exact when several messages have the same timestamp.

Messages created after the fork are visible only on their own path:

- The child doesn't see later messages added to its parent or messages from sibling branches.
- The parent doesn't see messages added to the child.
- New child messages use new IDs and the child thread's `threadId`.
- Direct, included, recent, semantic, and model-input reads use the same reachable path.

## Derived memory

Branch creation snapshots the current active derived state rather than reconstructing state as it existed at the fork:

- **Thread-scoped Observational Memory**: The active record is copied into child-owned storage. Reachable message references keep their IDs; unreachable references are removed.
- **Resource-scoped Observational Memory**: The active record is copied into child-owned storage keyed by the child thread while retaining the real resource identity. Later source and child updates are isolated.
- **Thread-scoped Working Memory**: The current value is copied to the child.
- **Resource-scoped Working Memory**: The value remains shared by the source and child because both use the same resource.

Only the active Observational Memory generation is copied. Historical generations aren't copied, and transient observation or reflection flags are reset.

:::warning
Free-form Observational Memory text or thread-scoped Working Memory may already contain knowledge learned from source messages after the selected fork. Mastra filters message references but doesn't rewrite aggregate text to reconstruct historical state.

Concurrent branch creation synchronizes Observational Memory and Working Memory independently. Each copied value is complete from either before or after a concurrent update, but the values don't form one cross-component snapshot.
:::

## Mutation and visibility rules

A branch is published only after its lineage and derived state are ready. Incomplete `pending` children stay hidden from public reads and lists. A process crash can leave a hidden pending row; automatic cleanup isn't part of this version.

Inherited messages are immutable through the child. A thread with ready descendants can't be changed in a way that invalidates their lineage. Branch mutation locks coordinate one `Memory` instance and process; storage adapters may provide stronger atomicity for shared deployments.

## Errors

Branch methods throw a `MastraError` with one of these IDs:

- `BRANCHING_UNSUPPORTED`: The configured Memory implementation doesn't support shared-history branches or the required adapter operations.
- `BRANCH_INVALID_REQUEST`: Input, pagination, or an operation's branch scope is invalid.
- `BRANCH_NOT_FOUND`: The source, branch point, or authorized lineage isn't available.
- `BRANCH_LINEAGE_CORRUPT`: Persisted lineage is malformed, cyclic, or inconsistent.
- `BRANCH_MUTATION_CONFLICT`: Concurrent state changed, a generated destination collided repeatedly, or a mutation would invalidate lineage.

The authenticated server evaluates access to the selected thread and every ancestor at read time. An inaccessible ancestor is reported as `BRANCH_NOT_FOUND` so lineage isn't disclosed.
