# MastraAuthOidc class

The `MastraAuthOidc` class authenticates Mastra against any OpenID Connect (OIDC) provider. Endpoints are read from the issuer's discovery document at `{issuer}/.well-known/openid-configuration`, so only the issuer and client credentials are required. The protocol is handled by [openid-client](https://github.com/panva/openid-client), the OpenID Foundation certified relying party library. Register it with the Mastra server using the `auth` option.

Use a dedicated package such as [MastraAuthAuth0](/reference/auth/auth0), [MastraAuthOkta](/reference/auth/okta), or [MastraAuthGoogle](/reference/auth/google) when one exists for your provider. Those packages add provider-specific features that the generic implementation can't offer.

## Usage example

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraAuthOidc } from '@mastra/auth-oidc'

export const mastra = new Mastra({
  server: {
    auth: new MastraAuthOidc({
      issuer: process.env.OIDC_ISSUER,
      clientId: process.env.OIDC_CLIENT_ID,
      clientSecret: process.env.OIDC_CLIENT_SECRET,
      redirectUri: process.env.OIDC_REDIRECT_URI,
    }),
  },
})
```

:::note

You can omit the constructor parameters if the matching environment variables are set. In that case, use `new MastraAuthOidc()` without any arguments.

:::

### Authentication flow

`MastraAuthOidc` authenticates requests in the following order:

1. **Session cookie**: when SSO is enabled, the encrypted session cookie is decrypted. A valid, unexpired session authenticates the request.
1. **Bearer token**: otherwise the `Authorization` header token is verified against the issuer's JWKS, checking the `iss` claim against `issuer` and the `aud` claim against `audience`.

After authentication, `authorizeUser` accepts any user that has an `id`. Pass your own `authorizeUser` to apply stricter rules.

The login flow runs the authorization code grant through `openid-client`, with an OIDC `nonce` and Proof Key for Code Exchange (PKCE) when the provider advertises `code_challenge_methods_supported`. The `state` parameter is an encrypted token carrying the nonce, redirect URI, and PKCE verifier, so no login state is held in server memory and the flow survives restarts and multiple instances.

### Methods

#### `getConfig()`

Resolves the underlying `openid-client` configuration, running discovery on first use and caching the result for the lifetime of the instance. A failed attempt isn't cached, so the next call retries. Use `config.serverMetadata()` to read the provider's resolved endpoints.

Returns: `Promise<Configuration>`

#### `getUser(userId)`

Always resolves to `null`. OpenID Connect defines no standard user lookup API, so users are only available from the incoming request.

#### `isSSOEnabled()`

Returns `true` when a client secret is configured. The SSO and session methods are only present on the instance in that case, so Studio doesn't offer a login button the provider can't complete.

### `mapOidcClaimsToUser(payload)`

Default claim mapper, exported for reuse inside a custom `mapClaims` function.

```typescript title="src/mastra/index.ts"
import { mapOidcClaimsToUser, MastraAuthOidc } from '@mastra/auth-oidc'

new MastraAuthOidc({
  mapClaims: payload => ({
    ...mapOidcClaimsToUser(payload),
    groups: payload.roles as string[],
  }),
})
```

Returns: `OidcUser`
