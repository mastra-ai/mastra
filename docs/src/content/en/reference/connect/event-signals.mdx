# ConnectEventSignals

A [signal provider](/docs/signals/signal-providers) that sends provider events from a project's connections to an agent as notification signals, such as a GitHub pull request opening or a Linear issue changing. Pass it to `Agent({ signals: [...] })`. It subscribes with [`ConnectEvents`](/reference/connect/events) when the agent is created.

## Usage example

```typescript title="src/mastra/agents/ops-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ConnectEventSignals } from '@mastra/connect'

const signals = new ConnectEventSignals({
  events: {
    github: ['pull_request.opened', 'pull_request.closed'],
    linear: true,
  },
  target: event => ({
    threadId: `${event.provider}:${event.connectionId}`,
    resourceId: 'team-ops',
  }),
  notification: event =>
    event.provider === 'github'
      ? {
          summary: `PR ${event.payload.action}: ${event.payload.pull_request.title}`,
          priority: 'high',
        }
      : undefined,
  rateLimit: { limit: 5, windowMs: 60_000 },
})

export const opsAgent = new Agent({
  id: 'ops-agent',
  name: 'Ops Agent',
  instructions: 'Triage pull requests and issues as they change.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [signals],
})
```

The agent needs a `Mastra` instance with `storage`, where notifications are stored. A thread that's idle wakes to handle the notification unless the target sets `ifIdle`.

### Typed events

The `target` and `notification` functions receive the events `events` selects. For a provider with [typed payloads](/reference/connect/events#typed-payloads), every event it sends has a typed payload, so checking `event.provider` and `event.eventType` narrows `event.payload`. With `includeUnverified`, check `event.unverified` first: unverified payloads aren't typed.

An event type that the provider doesn't send is a compile error.

### Default notification

| Field | Value |
| - | - |
| `source` | `connect` |
| `kind` | The provider and event type, such as `github:pull_request.opened` |
| `summary` | The provider and event type, such as `github pull_request.opened` |
| `payload` | The provider's payload |
| `dedupeKey` | The provider and its delivery id, so a redelivered webhook doesn't notify twice |
| `metadata` | `connectionId`, `eventId`, `provider`, `eventType`, plus `resourceId`, `unverified` and `rateLimited` when set |

## Methods

### `start()`

Subscribes to the project's events. The agent calls it when it's created. When the subscription can't start, for example without platform credentials, it logs the error and the agent runs without events.

The subscription also ends, with the error logged, when the events service refuses the token, rejects the cursor and there is no time to fall back to, or when `onGap` or the `cursorStore` throws, or `cursorStore.load` returns an invalid cursor. See [`ConnectEvents` errors](/reference/connect/events#errors). The agent then runs without events until you call `start()` again.

### `stop()`

Ends the subscription. Call it when your app stops, because the agent doesn't call it on shutdown.

## Delivery

Events reach the agent in order. Each event's notification follows the agent's [delivery policy](/docs/signals/notifications), so by default one can wake an idle agent and start a run. Set `rateLimit` so a burst of webhooks from one connection can't start a run per event. An event whose target or notification function throws, or whose notification can't be stored, is logged and skipped, and later events are still delivered. Errors that end the subscription are described under [`start()`](#start). Without a `cursorStore`, the subscription starts at the newest event each time it starts.
