# ConnectEventWorker

A [worker](/docs/deployment/workers) that starts workflows from provider events on a project's connections, such as a GitHub pull request opening or a Linear issue being created. Pass it to `Mastra({ workers: [...] })`. It subscribes with [`ConnectEvents`](/reference/connect/events) when Mastra starts its workers.

## Usage example

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { ConnectEventWorker, onConnectEvent } from '@mastra/connect'
import { reviewPullRequest } from './workflows/review-pull-request'
import { triageIssue } from './workflows/triage-issue'

const connectEvents = new ConnectEventWorker({
  triggers: [
    onConnectEvent({
      events: { github: ['pull_request.opened', 'pull_request.reopened'] },
      workflow: reviewPullRequest,
      inputData: event => ({
        repo: event.payload.repository.full_name,
        number: event.payload.number,
      }),
    }),
    onConnectEvent({
      events: { linear: ['Issue.create'] },
      workflow: triageIssue,
      inputData: event => ({ issueId: event.payload.data.id }),
    }),
  ],
})

export const mastra = new Mastra({
  workflows: { reviewPullRequest, triageIssue },
  workers: [connectEvents],
})
```

Each workflow must be registered on the same `Mastra` instance, which needs `storage` so a redelivered webhook doesn't start a workflow twice.

### Typed events

`inputData` receives the events `events` selects. For a provider with [typed payloads](/reference/connect/events#typed-payloads), every event it sends has a typed payload, so checking `event.provider` and `event.eventType` narrows `event.payload`. With `includeUnverified`, check `event.unverified` first: unverified payloads aren't typed.

An event type that the provider doesn't send is a compile error, and so is an input that doesn't match the workflow's input.

### Filter in `inputData`

Return `undefined` to skip events the event types alone don't rule out:

```typescript title="src/mastra/index.ts"
onConnectEvent({
  events: { github: ['pull_request.opened'] },
  workflow: reviewPullRequest,
  inputData: event =>
    event.payload.pull_request.base.ref === 'main'
      ? { repo: event.payload.repository.full_name, number: event.payload.number }
      : undefined,
})
```

## Runs

The run id comes from the workflow id, the provider and the provider's delivery id, such as `connect:review-pull-request:github:<delivery id>`. When the platform delivers a webhook again, the worker finds the run it already started and skips the event, including after a restart. A workflow that doesn't persist snapshots can't be found again, so it can start twice.

When the event's connection belongs to an end user, the run gets the event's `resourceId`.

The worker starts each run and moves on to the next event without waiting for the run to finish.

## Properties

### `isRunning`

`true` while the worker is subscribed to the project's events.

## Methods

### `start()`

Subscribes to the project's events. Mastra calls it when it starts its workers, so you only call it after `stop()`. A trigger whose workflow isn't registered is logged and never runs. When the subscription can't start, for example without platform credentials, the worker logs the error and Mastra starts its other workers.

### `stop(options?)`

Ends the subscription and waits for the event being handled, up to `options.drainTimeout` milliseconds. Runs already started keep running. Mastra calls it when it stops its workers.

## Delivery

Events are handled in order. An event whose `inputData` throws, or whose workflow can't start, is logged and skipped, and later events are still handled. Without a `cursorStore`, the subscription starts at the newest event each time it starts, so events that arrive while the worker is stopped aren't handled.

Run the worker in one process. Every process that runs it receives every event, so two processes can both start the run for one event. Use [`MASTRA_WORKERS`](/docs/deployment/workers#select-workers) to pick the process.
