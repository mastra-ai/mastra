# Workflow DevKit

The [Workflow DevKit](https://useworkflow.dev/) is Vercel's durable execution framework for JavaScript and TypeScript, published as the `workflow` package. The `@mastra/workflow` package lets you author workflows with the standard Mastra API and run them as durable DevKit runs inside your existing app, with no separate workflow server or worker process.

:::warning
`@mastra/workflow` is experimental and not ready for production use. The API may change between releases. See the [package README](https://github.com/mastra-ai/mastra/tree/main/workflows/workflow) for the current state.
:::

## How the Workflow DevKit works with Mastra

Mastra workflows authored with `createWorkflow()` and `createStep()` run as Workflow DevKit runs. Instead of compiling each workflow into DevKit code, `@mastra/workflow` ships a single generic runner marked `"use workflow"`. The runner walks your workflow's serialized step graph inside the DevKit's deterministic sandbox and delegates all real work to `"use step"` functions:

- Each step `execute`, branch condition, and loop predicate runs in a step function with full Node.js access, automatic retries, and journal-based memoization. Completed steps are skipped when a run is retried or resumed.
- Suspend and resume map to DevKit [hooks](https://useworkflow.dev/docs/foundations/hooks). A suspended step creates a hook token that external code resumes with `resumeHook()`.
- `sleep()` and `sleepUntil()` map to the DevKit's durable [`sleep()`](https://useworkflow.dev/docs/api-reference/workflow/sleep), which holds no compute while the run waits.
- Watching a run and streaming step output map to the run's namespaced [streams](https://useworkflow.dev/docs/foundations/streaming).
- Cancelling a Mastra run cancels the underlying DevKit run.

Because the runner is shipped by the library, you don't write DevKit code yourself. You author standard Mastra workflows, and the DevKit provides durability.

## Setup

Install the required packages:

```bash npm2yarn
npm install @mastra/workflow@latest workflow
```

:::note
Requires `workflow` v5 or later.
:::

### Configuring your framework

The DevKit compiler processes the `"use workflow"` and `"use step"` directives at build time, so it needs to be wired into your bundler. This guide uses Next.js. Wrap your Next.js config with `withWorkflow()`:

```ts title="next.config.ts"
import { withWorkflow } from 'workflow/next'
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  // rest of your Next.js config
}

export default withWorkflow(nextConfig)
```

Other frameworks work the same way, including Nitro, Hono, Express, Fastify, SvelteKit, Nuxt, and Astro. See the [Workflow DevKit getting started guides](https://useworkflow.dev/docs/getting-started) for the integration that matches your app.

## Building a DevKit-backed workflow

This guide walks through creating a workflow with the Workflow DevKit and Mastra, demonstrating a counter application that increments a value.

### Workflow DevKit initialization

Initialize the integration to obtain Mastra-compatible workflow helpers. The `createWorkflow()` and `createStep()` functions are bound to `mastraRunner`, the library-provided runner that executes the workflow inside the DevKit.

```ts title="src/mastra/workflows/index.ts"
import { z } from 'zod'
import { init } from '@mastra/workflow'
import { mastraRunner } from '@mastra/workflow/workflows'

const { createWorkflow, createStep } = init({ runner: mastraRunner })
```

### Creating steps

Define the individual steps that will compose your workflow. Each step's `execute` function runs as a DevKit step with its own retry policy.

```ts title="src/mastra/workflows/index.ts"
const incrementStep = createStep({
  id: 'increment',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
  execute: async ({ inputData }) => {
    return { value: inputData.value + 1 }
  },
})
```

### Creating the workflow

Compose the steps into a workflow and commit it.

```ts title="src/mastra/workflows/index.ts"
const workflow = createWorkflow({
  id: 'increment-workflow',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
}).then(incrementStep)

workflow.commit()

export { workflow as incrementWorkflow }
```

### Configuring the Mastra instance

Register the workflow with Mastra as you would for any other workflow.

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { PinoLogger } from '@mastra/loggers'
import { incrementWorkflow } from './workflows'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

### Registering the runner

Add a `workflows/mastra.ts` file at the root of your project. This file is required.

```ts title="workflows/mastra.ts"
export * from '@mastra/workflow/workflows'
import '../src/mastra'
```

It does two things:

- The `export *` re-exports the library's `"use workflow"` runner from a stable path in your own source tree. The DevKit compiler [generates workflow ids from file paths and function names](https://useworkflow.dev/docs/how-it-works/code-transform), so exporting the runner from a fixed path in your project keeps those ids stable across builds instead of tying them to the package's resolved location in `node_modules`.
- The side-effect `import '../src/mastra'` loads your Mastra instance in the process that handles workflow execution, so the runner can look up your workflow definitions by id at run time.

The DevKit compiler discovers any file that contains the directives. A `workflows/` directory at the project root is the convention used in the DevKit's own guides. Adjust the relative import if your Mastra entry file lives elsewhere.

## Running workflows

### Running locally

Local development needs no extra infrastructure. The DevKit's embedded local backend persists runs to disk in your project, under `.next/workflow-data` for Next.js apps and `.workflow-data` elsewhere.

1. Start your dev server:

   ```bash
   npm run dev
   ```

1. Trigger a run from a route handler, a server action, or a script:

   ```ts title="scripts/run.ts"
   import { mastra } from '../src/mastra'

   const run = await mastra.getWorkflow('incrementWorkflow').createRun()
   const result = await run.start({ inputData: { value: 5 } })

   console.log(result)
   ```

1. Inspect runs in the DevKit web UI, which shows each run's steps, inputs, outputs, and retries:

   ```bash
   npx workflow web
   ```

   For a terminal interface, use the CLI instead:

   ```bash
   npx workflow inspect runs
   ```

### Running in production

The runner executes inside your app's own compute, so there's no separate worker process to deploy or scale. What changes between environments is the backend that stores run state and drives the queue.

#### Vercel

Deploying to Vercel switches the DevKit to its managed, queue-backed backend with no code or configuration changes. Runs appear in the Vercel dashboard alongside your deployment.

```bash
vercel deploy
```

:::warning
Enable [Fluid compute](https://vercel.com/docs/functions/fluid-compute) on the project before deploying. The DevKit relies on it for efficient suspension and resumption. Without it, every resume pays a separate function cold start, which raises cost.
:::

#### Self-hosting

To run on your own infrastructure, point the DevKit at a different backend with the `WORKFLOW_TARGET_WORLD` environment variable. The Postgres backend keeps run state in a database you control:

```bash title=".env"
WORKFLOW_TARGET_WORLD=@workflow/world-postgres
DATABASE_URL=postgres://user:password@host:5432/database
```

See the [Workflow DevKit deploying guide](https://useworkflow.dev/docs/deploying) for the full list of backends and their configuration.

## Constraints and notes

- `workflow` v5 or later is required.
- The `workflows/mastra.ts` file is required for stable workflow ids and for runtime registration. See [Registering the runner](#registering-the-runner).
- Nested workflows, `.map()` data mapping, and time travel aren't supported yet.
- Flow control options available on Inngest workflows, such as `concurrency`, `rateLimit`, `throttle`, and `debounce`, aren't available. Use your platform's concurrency controls instead.
