# Neon

[Neon](https://neon.com) is a managed PostgreSQL platform. Use it with Mastra in four ways:

- **Agent tools** let an agent manage Neon projects and branches, run SQL, and apply schema migrations through [Mastra Connect](/docs/mastra-platform/connect/overview).
- **[Postgres storage](#postgres-storage)** stores Mastra data, such as memory and workflow state, in a Neon database.
- **[Neon Functions](#deploy-to-neon-functions)** run your Mastra server on your Neon branch.
- **[Object storage](#object-storage)** keeps an agent's workspace files in a Neon bucket that branches with your database.

## Connect

Before you start, complete the [Connect setup](/docs/mastra-platform/connect/overview#get-started) to install `@mastra/connect` and configure your platform project.

## Postgres storage

Mastra connects to Neon through [`PostgresStore`](/integrations/databases/postgresql), which uses the Node.js `pg` driver. Neon doesn't require a separate Mastra storage package.

### Quickstart

Create a Neon project, then copy its [pooled connection string](https://neon.com/docs/connect/connect-from-any-app) into `DATABASE_URL`.

Install the PostgreSQL storage package:

```bash npm2yarn
npm install @mastra/pg@latest
```

Pass the pooled connection string to `PostgresStore`:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { PostgresStore } from '@mastra/pg'

export const mastra = new Mastra({
  storage: new PostgresStore({
    id: 'neon-storage',
    connectionString: process.env.DATABASE_URL!,
  }),
})
```

On startup, Mastra calls `storage.init()` and creates its tables and indexes in Neon.

### Set up Neon with the CLI

The Neon CLI requires Node.js 20.19 or newer.

Install the [Neon CLI](https://neon.com/docs/cli/install):

```bash npm2yarn
npm install -g neon
```

From your project directory, link an existing Neon project or create one:

```bash
neon link
```

`neon link` signs you in and writes project context to `.neon`. It also pulls the current branch's environment variables. Run `neon env pull` again whenever you need to refresh them:

```bash
neon env pull
```

The command writes `DATABASE_URL` and `DATABASE_URL_UNPOOLED` to `.env.local` or to `.env` when that file already exists.

#### Add `neon.ts`

To manage branch settings in the repository, create a [`neon.ts`](https://neon.com/docs/reference/neon-ts) file:

```bash
neon config init
```

This installs `@neon/config` and `@neon/env` and creates a starter config. For example, the following policy expires new non-default branches after seven days:

```typescript title="neon.ts"
import { defineConfig } from '@neon/config/v1'

export default defineConfig({
  branch: branch => {
    if (branch.isDefault) {
      return {}
    }

    if (!branch.exists) {
      return { ttl: '7d' }
    }

    return {}
  },
})
```

Apply the config:

```bash
neon deploy
```

### Install Neon agent skills

Install the [`neon` and `neon-postgres` agent skills](https://neon.com/docs/ai/agent-skills) from your project directory:

```bash npm2yarn
npx skills add neondatabase/agent-skills --skill neon --skill neon-postgres -y
```

The skills give compatible coding agents Neon setup instructions and Postgres-specific guidance.

### Production connections

Neon provides direct and pooled connection strings:

- `DATABASE_URL` uses Neon's pooled endpoint. Use it for normal application traffic.
- `DATABASE_URL_UNPOOLED` connects directly to Postgres. Use it for administrative tasks or schema changes that run outside the application.

For most applications, use the pooled `DATABASE_URL` shown in the quickstart and let Mastra initialize the schema at startup. `PostgresStore` supports initialization through a transaction-pooled connection.

#### Separate schema initialization

If the runtime database role shouldn't create tables or indexes, initialize the schema during deployment with the direct connection:

```typescript title="scripts/init-storage.ts"
import { PostgresStore } from '@mastra/pg'

const storage = new PostgresStore({
  id: 'neon-storage-init',
  connectionString: process.env.DATABASE_URL_UNPOOLED!,
})

try {
  await storage.init()
} finally {
  await storage.close()
}
```

After the schema exists, use the pooled connection at runtime and disable automatic initialization:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { PostgresStore } from '@mastra/pg'

export const mastra = new Mastra({
  storage: new PostgresStore({
    id: 'neon-storage',
    connectionString: process.env.DATABASE_URL!,
    disableInit: true,
  }),
})
```

See [Neon connection pooling](https://neon.com/docs/connect/connection-pooling) for details.

### Vector search

Neon supports the [`pgvector` extension](https://neon.com/docs/extensions/pgvector). Use the direct `DATABASE_URL_UNPOOLED` connection while creating the extension and indexes. After setup, configure [`PgVector`](/integrations/vectors/pg) with the pooled connection for runtime queries:

```typescript
import { PgVector } from '@mastra/pg'

const vector = new PgVector({
  id: 'neon-vector',
  connectionString: process.env.DATABASE_URL!,
  disableInit: true,
})
```

Setting `disableInit: true` prevents the runtime process from creating or changing the extension, tables and indexes.

## Deploy to Neon Functions

Deploy your Mastra server as a [Neon Function](https://neon.com/docs/compute/functions/overview) (a long-running Node.js process) on your Neon branch. The function gets a public HTTPS URL and `DATABASE_URL` is injected from the branch's Postgres database.

Neon Functions are a `fetch` handler. This guide uses the [Hono server adapter](/docs/server/server-adapters) rather than `mastra build` / `mastra start`. If you're using a [web framework](/docs/deployment/web-framework), deploy the way you normally would for that framework.

Neon Functions are in beta and available only in AWS US East (Ohio) (`aws-us-east-2`). You'll need to create your project in that region.

### Function prerequisites

You'll need:

- A [Mastra application](/docs)
- A [Neon](https://neon.com) account
- A Neon project in `aws-us-east-2`
- Node.js `v22.13.0` or later

Neon Functions can evict an idle isolate, so in-memory and local-file storage is lost. Use [PostgresStore with Neon](#postgres-storage) instead of [LibSQLStore](/integrations/databases/libsql) with a file URL. For workspace files, use [Neon Object Storage](#object-storage) instead of [`LocalFilesystem`](/reference/workspace/local-filesystem).

### Install the function dependencies

Install the [Neon CLI](https://neon.com/docs/cli/install):

```bash npm2yarn
npm install -g neon
```

Add the Hono adapter, Hono, and `@neon/config`:

```bash npm2yarn
npm install @mastra/hono@latest hono @neon/config
```

### Configure `neon.ts`

At the root of your project, create a file named `neon.ts`. `neon deploy` and `neon dev` read this file:

```typescript title="neon.ts"
import { defineConfig } from '@neon/config/v1'

export default defineConfig({
  preview: {
    aiGateway: true,
    functions: {
      mastra: {
        name: 'Mastra server',
        source: './src/index.ts',
      },
    },
  },
})
```

The object key (`mastra`) is the function slug. It can't be renamed after the first deploy.

`aiGateway: true` provisions the [Neon AI Gateway](/models/gateways/neon) on the branch. `neon deploy` injects `NEON_AI_GATEWAY_BASE_URL` and `NEON_AI_GATEWAY_TOKEN`. Mastra reads those variables for `neon/` model ids.

For a provider API key instead of the gateway, declare it under the function's `env` field and use that provider's model id, not a `neon/` id. Values are read from `process.env` when `neon deploy` runs:

```typescript title="neon.ts"
import { defineConfig } from '@neon/config/v1'

export default defineConfig({
  preview: {
    functions: {
      mastra: {
        name: 'Mastra server',
        source: './src/index.ts',
        env: {
          OPENAI_API_KEY: process.env.OPENAI_API_KEY!,
        },
      },
    },
  },
})
```

```bash
neon deploy --env .env
```

`--env` loads the file for config evaluation. Only keys listed in `env` are deployed. See [Neon Functions environment variables](https://neon.com/docs/compute/functions/environment-variables).

### Export a Hono fetch handler

Wire the [Hono adapter](/reference/server/hono-adapter) and export the app. Neon Functions invoke the default export's `fetch` method.

```typescript title="src/index.ts"
import { Hono } from 'hono'
import { HonoBindings, HonoVariables, MastraServer } from '@mastra/hono'
import { mastra } from './mastra'

const app = new Hono<{ Bindings: HonoBindings; Variables: HonoVariables }>()
const server = new MastraServer({ app, mastra })

await server.init()

export default app
```

Register agents on the `mastra` instance in `src/mastra/index.ts`.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { Agent } from '@mastra/core/agent'

const assistant = new Agent({
  id: 'assistant',
  name: 'Assistant',
  instructions: 'You are a helpful assistant',
  model: 'neon/claude-fable-5',
})

export const mastra = new Mastra({
  agents: { assistant },
})
```

See the [Neon AI Gateway](/models/gateways/neon) for the model list.

### Deploy

<Steps>
  <StepItem>
    From the project directory, link an existing Neon project (or create one):

    ```bash
    neon link
    ```

    `neon link` writes project context to `.neon` and pulls the current branch's environment variables.
  </StepItem>

  <StepItem>
    Deploy the function:

    ```bash
    neon deploy
    ```

    The CLI bundles the handler with esbuild, uploads it, and waits until the deployment status is `completed`. If you declared function `env` values, pass `--env <file>` so `neon.ts` can read them.
  </StepItem>

  <StepItem>
    Get the public URL:

    ```bash
    neon functions get mastra
    ```

    The `invocation_url` looks like `https://<branch-id>-mastra.compute.<cell>.us-east-2.aws.neon.tech/`.
  </StepItem>

  <StepItem>
    Verify the deployment at `https://<branch-id>-mastra.compute.<cell>.us-east-2.aws.neon.tech/api/agents`, which should return a JSON list of your agents.

    Since the Mastra server prefixes every API endpoint with `/api`, add it to your URLs when making requests.

    `DATABASE_URL` is injected from the branch. Gateway credentials are injected when `aiGateway: true` is set in `neon.ts`.
  </StepItem>

  <StepItem>
    You can now call your Mastra endpoints over HTTP.

    :::warning
    Set up [authentication](/docs/auth/overview) before exposing your endpoints publicly. The function URL is public. See [Neon Functions authentication](https://neon.com/docs/compute/functions/authentication).
    :::
  </StepItem>
</Steps>

### Local development

`neon dev` serves every function declared in `neon.ts` with hot reload, and injects the linked branch's environment variables:

```bash
neon dev
```

The Mastra server is at `http://localhost:8787/api/agents`.

## Object storage

[Neon Object Storage](https://neon.com/docs/storage/overview) is S3-compatible storage built into a Neon project. Buckets belong to a branch, and a child branch starts with a copy-on-write copy of its parent's files. Mastra connects to it through [`S3Filesystem`](/integrations/file-storage/amazon-s3), so agents get workspace files that branch together with the rows in your [Neon Postgres](#postgres-storage) database. For interface details, see [WorkspaceFilesystem Interface](/reference/workspace/filesystem).

### Storage prerequisites

You'll need:

- A [Neon](https://neon.com) project in a region that supports Object Storage: `aws-us-east-1`, `aws-us-east-2`, `aws-eu-central-1`, or `aws-ap-southeast-1`
- The [Neon CLI](https://neon.com/docs/cli/install)

### Install the storage packages

```bash npm2yarn
npm install @mastra/s3 @neon/config
```

### Create a bucket

Declare the bucket in `neon.ts` at the root of your project:

```typescript title="neon.ts"
import { defineConfig } from '@neon/config/v1'

export default defineConfig({
  buckets: {
    'agent-files': {},
  },
})
```

Buckets are private by default. Set `access: 'public_read'` to allow anonymous reads.

Link the directory to your Neon project, then create the bucket on the linked branch:

```bash
neon link
neon deploy
```

`neon deploy` creates the bucket and writes the branch's storage credentials to `.env`, or to `.env.local` when no `.env` exists. `mastra dev` loads either file.

To create a bucket without `neon.ts`, run `neon bucket create agent-files`, then pull the credentials yourself:

```bash
neon env pull --service object-storage
```

### Environment variables

Neon sets four variables for object storage:

| Variable | Value |
| - | - |
| `AWS_ACCESS_KEY_ID` | Access key for a branch credential |
| `AWS_SECRET_ACCESS_KEY` | Secret key for that credential |
| `AWS_ENDPOINT_URL_S3` | S3 endpoint of the branch |
| `AWS_REGION` | Region of the project, such as `us-east-2` |

A credential works on the branch it was issued for and on that branch's children. Inside a [Neon Function](#deploy-to-neon-functions), Neon injects these variables, so you don't need a `.env` file.

### Usage

Pass the variables to `S3Filesystem` and assign the workspace to an agent:

```typescript title="src/mastra/agents/file-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Workspace } from '@mastra/core/workspace'
import { S3Filesystem } from '@mastra/s3'

const workspace = new Workspace({
  filesystem: new S3Filesystem({
    bucket: 'agent-files',
    region: process.env.AWS_REGION!,
    endpoint: process.env.AWS_ENDPOINT_URL_S3,
    accessKeyId: process.env.AWS_ACCESS_KEY_ID,
    secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
  }),
})

export const fileAgent = new Agent({
  id: 'file-agent',
  name: 'file-agent',
  instructions: 'You manage files in the workspace.',
  model: '__GATEWAY_ANTHROPIC_MODEL_OPUS__',
  workspace,
})
```

Always set `endpoint`. Neon only accepts path-style requests, and `S3Filesystem` switches to them only when `endpoint` is set. Without it, the AWS SDK still reads `AWS_ENDPOINT_URL_S3` but sends virtual-hosted requests (`agent-files.<endpoint-host>`), which fail TLS verification.

`S3Filesystem` recognizes Neon endpoints. It sets `icon` to `'neon'` and `displayName` to `Neon Object Storage`, so Studio shows a Neon mount in the file tree.

Use `prefix` to give each agent, user, or thread its own folder in one bucket:

```typescript
const filesystem = new S3Filesystem({
  bucket: 'agent-files',
  prefix: `users/${userId}`,
  region: process.env.AWS_REGION,
  endpoint: process.env.AWS_ENDPOINT_URL_S3,
  accessKeyId: process.env.AWS_ACCESS_KEY_ID,
  secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
})
```

The prefix limits which keys the filesystem addresses. It isn't an authorization boundary.

### Branches

Each branch has its own storage endpoint. When you create a branch, it starts with every bucket and file from its parent at that point in time. Writes and deletes on the child don't change the parent, and later writes on the parent don't appear in the child.

Use this to give a preview deployment, a test run, or an experimental agent a full copy of production files without copying any data:

```bash
neon checkout preview/new-tools --create
```

`neon checkout --create` creates the branch, pins it in `.neon`, and pulls the child branch's variables into `.env`, including its endpoint. The parent's credential also works on the child, but the endpoint must be the child's. Delete the branch to discard its files.

### Skill blob storage

`S3BlobStore` holds the content-addressable skill blobs that [`MastraEditor`](/reference/editor/mastra-editor) produces. It takes the same connection options:

```typescript
import { S3BlobStore } from '@mastra/s3'

const blobStore = new S3BlobStore({
  bucket: 'agent-files',
  region: process.env.AWS_REGION!,
  endpoint: process.env.AWS_ENDPOINT_URL_S3,
  accessKeyId: process.env.AWS_ACCESS_KEY_ID,
  secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
})
```

### FilesSDK adapter

If you use [`FilesSDKFilesystem`](/integrations/file-storage/vercel-files), the `neon` adapter reads the same `AWS_*` variables. Install it with the AWS SDK packages it loads:

```bash npm2yarn
npm install @mastra/files-sdk files-sdk @aws-sdk/client-s3 @aws-sdk/s3-presigned-post @aws-sdk/s3-request-presigner
```

```typescript
import { Workspace } from '@mastra/core/workspace'
import { FilesSDKFilesystem } from '@mastra/files-sdk'
import { Files } from 'files-sdk'
import { neon } from 'files-sdk/neon'

const workspace = new Workspace({
  filesystem: new FilesSDKFilesystem({
    files: new Files({ adapter: neon({ bucket: 'agent-files' }) }),
    icon: 'neon',
    displayName: 'Neon Object Storage',
  }),
})
```
