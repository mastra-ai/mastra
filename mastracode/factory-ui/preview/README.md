# Onboarding design preview

This preview renders the production onboarding components. MSW supplies demo responses only in this separate entrypoint; it is never imported by the Factory application. No real integration is connected and submitted keys are discarded.

Run from `mastracode/factory-ui` after building the package’s dependencies:

- `pnpm exec msw init preview/public --no-save`
- `pnpm exec vite --config preview/vite.config.ts`
- `pnpm exec vite build --config preview/vite.config.ts`

The build is written to `preview-dist`. “Try another setup” on the completion screen clears only this preview’s data and onboarding markers. GitHub and Linear redirects return to the same preview with session-local demo connections. The final screen is a preview completion screen, not a running agent factory.

Each desktop scene illustrates its current setting: repository context for new sessions, tracker issues becoming backlog cards, the selected agent model, and personal credentials alongside the unchanged team default. It follows real selection and connection state, with continuous conveyor, repository-link, and board progression loops, plus a static reduced-motion presentation. The Factory stays visible in every setup choice; account labels distinguish connection scope from the credential used at runtime. Tracker issues are explicitly illustrative; connecting a tracker does not automatically import or run work. The side-by-side layout starts at 900px. The illustration is centered in its own viewport-height region so form changes do not move it. Below 900px, full-width choices stay above an illustration centered in the remaining space. The illustration uses the remaining space and is removed on short screens; long forms scroll internally while progress stays visible. Progress lives at the bottom. Back restores editable choices, including the repository and GitHub/GitLab provider. The final review offers direct Edit actions. The Factory, repository link, intake selection, default model are saved only after Create factory; retries reuse the pending Factory. Non-secret draft choices survive redirects and reloads. Connecting an integration or model account still authorizes that account immediately; these reusable connections are separate from the Factory draft.

The right-hand preview is one persistent custom Hairline drawing. Its rounded panel paths morph through five poses: an isometric factory with a joined sawtooth roof and input/output belts; a prominent code repository linked to a miniature of the same Factory; a source issue or incident follow-up entering To do; company/personal setup with a miniature Factory and agent conversations; and model accounts feeding sessions. Intake shows two named jobs moving through To do, Build and Review, with different examples for Linear, Jira and incident.io. The incoming job keeps its source ID and title; no empty placeholder tickets are added. Examples are illustrative and importing remains a post-setup action.

The unchanged skill kernel (MIT license included) drives geometry interpolation, distance-staggered 700ms tweens, the pointer tour, and the movement of work along belts and connections. Silhouettes retain their rounded corners during interpolation; returning to another step starts from the currently drawn pose. There is no Hairline package or stock figure dependency. The SVG and its surfaces persist across steps and rapid back navigation; only HTML annotations fade after the geometry starts moving. Labels stay sharp, untransformed and tied to the actual selection. The codebase scene shrinks and moves the existing Factory to the right, revealing a larger repository on the left. A traveling marker follows their connection; the repository name and branch reflect the current selection. The same geometry then morphs into the work board. Factory and codebase use the skill’s 2:1 camera, rounded solids, opaque faces and dim internal creases. The app uses softer neutral outlines and white card surfaces from its existing theme; there is no blur, SVG filter or scaled HTML text. The setup illustration removes repeated headings and explanatory footers: shared access feeds a miniature Factory and teammate conversations, personal access separates the conversations by account, and hybrid access splits off your connection. Intake and account poses keep front-facing UI geometry with softer theme borders, larger corner radii, and semantic HTML labels for legibility; motion is concentrated on the traveling card so board lanes stay still while reading. The kernel sleeps offscreen, reduced motion lands immediately, and compact screens unmount the drawing when there is insufficient room. No motion controls or outer preview panel are added.

Model onboarding separates API keys from provider sign-in, with explicit organization and personal scope. Both methods use the existing credential endpoints. Provider sign-in is simulated with the code `DEMO`; API key values are discarded and only connection method/scope are retained. “Company account”, “My account” and “Set up my account too” describe which connections to configure now, not permissions for teammates. The checklist is preview-only: this entrypoint supplies an optional save adapter and its MSW route stores the selection locally on final confirmation. Production onboarding keeps its existing flow. Older `allowPersonal` draft values migrate to `setupPersonal`; neither flag governs credential access.

Confirmation saves a Factory default in both paths. Company setup saves the model chosen through an organization connection. My account saves the personally selected model as both the Factory default and the current user’s default; the UI states both effects. With both accounts, the shared and personal model choices remain separate. Without a shared provider, a non-admin can move into personal setup. Nothing revokes existing connections or changes other members’ personal defaults. API keys and provider sign-in remain available in both scopes. No per-lane models are introduced.

Credential resolution is independent of the default model. For the selected model’s provider, deployed-web sessions use these existing rules:

| Context                                          | First choice            | When absent              |
| ------------------------------------------------ | ----------------------- | ------------------------ |
| Factory work, including continued board sessions | Organization credential | Acting user’s credential |
| Ordinary user session                            | User credential         | Organization credential  |

This is fallback when a credential is absent, not automatic failover from an invalid credential. Automatic wake-ups use the work-item session’s recorded `startedBy` identity. Interactive replies resolve the authenticated actor from request context; the account is not durably bound to a session payer. A user session can therefore use company credentials, and personal-account onboarding does not force Factory work to use a personal account. The setup illustration labels its Factory source “Run account · Shared → personal” instead of promising “Run owner pays”. The Factory model is distinct from a person’s default model; choosing a shared model does not overwrite teammates’ defaults.

These rules come from `factory/src/storage/domains/credentials/base.ts`, `factory/src/routes/tenant-credentials.ts`, `sdk/src/agents/credential-resolver.ts`, and `factory/src/rules/{start-coordinator,dispatcher}.ts`. `factory/src/session/factory-session.ts` applies the Factory model and otherwise retains the SDK mode default, which is why personal setup must also save an explicit Factory model.

The exploration branch `origin/exploration/factory-storyboard` proposes additional policies: allowed subscriptions/personal keys, permission for personal sessions, whether those sessions may spend company keys, and shared-vs-owner funding for board work. These are separate choices in its mock state. [FACT-317](https://linear.app/kepler-crm/issue/FACT-317/clarify-who-pays-for-factory-and-personal-sessions) covers enforcement, and [FACT-314](https://linear.app/kepler-crm/issue/FACT-314/keep-the-model-and-payer-unchanged-when-teammates-reply) covers stable model/payer binding; both were Todo on 2026-10-09. Neither is implemented by this onboarding checklist. Company-only guarantees for an enterprise require those backend policies, not an extra onboarding toggle.

GitLab has an existing demo connection with two projects so provider switching can be exercised. No real GitLab account is connected.

After syncing with main, onboarding leaves Observer and Reflector on Auto and never calls the removed `/web/config/om/provider-defaults` endpoint. Existing pinned memory settings remain untouched.

The preview offers Linear, Jira, and incident.io. Previously its Platform connections mock returned 404, intentionally hiding Jira and incident.io. It now returns the same available/connected response shapes as production. The preview Vite config alone substitutes `demo-platform-auth.ts` for the external Nango SDK: Jira authorization completes locally, and incident.io opens the real API-key form but discards the submitted value. The local demo authorization endpoint receives only the fake session identifier, never credentials. Production keeps the real Nango SDK and server-side availability gating. Connection failures offer Retry; expired connections reauthorize their existing account.
