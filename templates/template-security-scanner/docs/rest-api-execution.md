# REST API discovery execution

The executable first-release application driver is `rest_api` version 1 with `observed_json` and optional `openapi` discovery. The executable authentication driver is `api_key_header` version 1. A scanner target must confirm its origin, GET/HEAD method scope, path prefixes, retention for staging or production, request/byte/time budgets, and exact operator route rules. SPA, GraphQL, browser sessions, login/password, arbitrary checker scripts and other driver kinds remain unsupported at execution.

Register each API key as an `api_key_header` profile with a private `credential.value`. The response excludes the value. After registration, update the target's `authenticationDrivers` with each returned profile ID, its sealed `secretRef`, one credential-bearing origin, the validated header name and an existing account-specific `accessCheckPath`. That GET path must have an operator-confirmed `user + owner` rule; a shared collection cannot serve as the check. No `identityEndpoint` or claimed universal role is required. Two accounts may use the same role label; their profile IDs and sealed keys remain separate. A successful scoped JSON read is access evidence only, not proof of a human role or object ownership.

Confirm route rules at the target's new revision. A rule identifies an exact method and path template, `public`, `user` or `admin` audience, `owner` or `shared` for user routes, and expected unauthorized statuses. OpenAPI contributes advertised collection surfaces but cannot confirm access intent. A target update, key change or policy update invalidates earlier scan bindings; a new scan must use current target, policy, profile and credential revisions. `GET /api/products` is public/shared and is never an owner-only candidate. Owner-only detail references must come from an account's own observed JSON collection and match a confirmed detail route.

During discovery, each profile runs in an inspected, firewalled Docker sandbox. The fixed Katana command reads at most bounded JSON bytes through its dedicated gateway port. The credential exists only in a private gateway configuration file; the client sandbox and command arguments receive no key. Remote API-key origins require HTTPS. HTTP is allowed only for the exact project-owned Docker lab address after the runtime revalidates its live container and internal network; marking a target `lab` does not establish that boundary. The gateway checks origin, canonical path, GET/HEAD method, shared request budget, DNS answers and public or exact owned-lab IP. It binds the request's reservation to a numeric IP and port, verifies the connected peer against that complete endpoint, rechecks the flow's connection identity against the pinned binding, and only then inserts the key before request transmission. A reused connection must retain its verified binding and matching IP and port. Budget, DNS, connection and peer failures remove any key from the flow. Cross-origin and private-address requests fail before upstream contact. Redirect following is disabled for the REST command.

The trusted reader parses private JSONL and accepts a response only with the gateway's upstream provenance marker and JSON content type. It extracts bounded explicit `href` links from the collection, checks each detail path against a confirmed owner-only template and target scope, and reads that detail through the same gateway. One further layer of canonical `*Href` links from a detail may be read only if it matches another confirmed owner-only rule. No object ID is guessed. Exported inventory contains only origin, canonical path, method, profile ID, route template, `linkedFrom` prerequisite, provenance and status. Raw JSON bodies, arbitrary headers and API keys are discarded before storage, logs, model input or API output. A malformed, oversized, secret-bearing or unsupported response is withheld and leaves a partial result.

For a public HTTPS test, use an authorized origin that resolves to public IP addresses and has a valid certificate. The optional ngrok procedure in [the example guide](example-target.md) proves the public transport path using a tunnel to the local Hono example; it does not prove independent hosting. External REST execution does not require owned-example labels, addresses or markers. The local example's private Docker address is accepted only while its owned lab boundary is verified.

For REST BOLA, set the optional `principalJsonPointer` on both API-key drivers to the same JSON pointer into the existing `accessCheckPath` response. Use a stable account ID, never a token, role, order ID, array or collection. The owned Orders API returns this ID at `/principal` in `/api/orders`. Both drivers must use the same origin, check path and pointer. The runtime compares bounded strings from successful upstream JSON reads in the same scan, keeping the extracted comparison values only in private memory. Only `SAME`, `DISTINCT` or `UNKNOWN` is retained with the scan's exact profile and credential revisions. Missing, invalid, incompatible or equal account evidence produces an inconclusive BOLA assessment before model calls or verifier requests; ordinary discovery still works without this field. Different keys or profile names alone never prove different accounts.

The comparison relies on the operator selecting a stable, canonical account identifier returned by the target. It compares the string produced by standard JSON decoding and does not validate the meaning of an arbitrary response field or attest an external identity provider.

The extraction/comparison mechanism adds no principal field, value or digest to persistence, model prompts or logs, only the finite comparison. Authorized inventory still retains normalized paths under its existing contract; those paths can contain identifiers. Principal values are not treated as a new credential category. Historical findings without a principal-comparison receipt remain historical and are not recertified by this change.
