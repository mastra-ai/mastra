# Workflow execution

`securityIncidentWorkflow` is one durable graph for all supported alert families. The incident kind selects evidence requirements and the active runbook; it does not select a different workflow.

## Before the graph starts

External producers call `POST /webhooks/alerts`, while native WorkOS events call `POST /webhooks/workos`. Hono verifies the request signature, timestamp, media type, body size, rate limit, source allowlist, schema, tenant scope, and idempotency key. It then writes the alert, incident, first timeline entry, and transactional outbox event in one database transaction.

The outbox dispatcher publishes `security.alert.received` through the in-process domain transport. The transactional LibSQL outbox remains durable and its reconciler recovers interrupted deliveries after restart. The workflow worker claims the event and starts Mastra with identifiers, not the original provider payload.

Studio accepts the same normalized alert JSON for exploration. The first step sends it through the same normalization and persistence boundary, then continues using the durable identifiers. Studio does not emulate an external signature check; that boundary belongs to Hono.

For a WorkOS role restore, containment arms an exact, short-lived expected-callback record before mutation. Its signed webhook advances provider state and is appended to the original incident instead of opening a false positive.

For a WorkOS session revoke, the adapter accepts either a revoked session readback or the matching durable signed `session.revoked` observation. If WorkOS stops listing the revoked session, the provider ledger remains idempotent and a retry reconciles the webhook instead of sending another revoke.

Before approval, `propose-containment` and `validate-containment` intersect the runbook allowlist with the active provider capabilities. The supplied WorkOS adapter supports `restore_previous_role` and `revoke_session`; local-only actions never enter a staging or production plan.

## Reading the early outcomes

The graph keeps the same step IDs for durable resumes. A `benign`, `manual-review`, or `blocked` result passes through the remaining steps without planning, approval or containment work until `finalize-incident` records the outcome. “Closes early” refers to this business outcome; it does not mean that Mastra skips the remaining nodes in the graph.

`buildTriageStopResult` constructs a typed result; it does not abort the Mastra run. The scope-validation step is deterministic. Native supervisor delegation happens later inside each evidence branch.

## Agents are validators, not authorities

The workflow owns provider reads. The configured supervisor performs bounded native delegation to exactly one matching, tool-free specialist per evidence branch; specialist prompts are server-built from tokenized facts, with no forwarded history. Decision validators remain tool-disabled. Agents cannot select a new provider, invent evidence, add a containment action, approve a plan, or mutate a provider. Every security-relevant output is schema-checked and compared with deterministic policy. The containment Tool's `requireApproval` metadata is not authorization: its gateway revalidates durable approval on every call. See [Safe agency](safe-agency.md).

## Evidence-backed claim rendering

`evidenceFactNarrators` in `src/triage/claims.ts` maps each supported fact type to a fixed sentence renderer. Raw role names, IP addresses, actor IDs, provider text, and other untrusted values are not copied into prose.

For a fact to appear in the summary, it must be required by policy, pass freshness/completeness/provider checks, belong to the current tenant, incident, and run, and carry a valid evidence reference. Code selects the fact tokens and renders the final summary canonically without asking a model to echo the candidate. This boundary reduces prompt injection, accidental sensitive-data disclosure, unsupported inference, citation drift, and model-formatting failures.
