# Research sources

The default `openai-web` provider uses GPT-6 Luna Responses web search with domain filtering. Search, extraction and support verification use low reasoning effort within their existing output-token caps; reasoning tokens consume the same shared allowance. URLs/citations discover possible sources; they do not prove a claim. The workflow retrieves bounded HTTPS source pages, records their actual text, then runs structured extraction and a separate semantic-support check. Accepted candidates must also quote an exact substring of retrieved material. The persisted summary cites the resulting evidence IDs.

Business-model classification may infer either an allowed positive or negative category from the captured classification criteria. A hosted API offering and a separate business-customer passage can jointly support B2B SaaS without that literal phrase. Affirmative physical-goods evidence can support `other`; missing information cannot. Adapt category labels, criteria and accepted labels together for another ICP. Search and both model passes receive those captured definitions; they do not retain a fixed B2B search target.

An inferred candidate keeps the main `evidenceId`/`quote`, a separate model-generated `inference.rationale`, and up to three `inference.additionalPassages`. Each passage must be a distinct, contiguous verbatim quote of at most 2000 characters from its named evidence excerpt. All citations must match exactly, and the independent verifier must find that the cited passages collectively establish the configured criteria. Uncited text and the rationale itself cannot substitute for supporting passages. Accepted inference provenance is persisted in `assessment.inferences`, with candidate IDs, classification, rationale and passage references; fact evidence references include every cited source. The summary identifies inference separately. False citations, unsupported inference and unconfigured labels remain unsupported/reviewable.

Employee estimates use the same exact-passage and independent-verification contract, with `basis: inferred` and an employeeCount inference record. Under the default `estimates: 'accept'`, supported finite employee estimates can support automatic qualification and remain explicitly inferred. Set `estimates: 'review'` to keep them advisory. Source-declared counts/ranges remain observed. Headquarters and intent remain explicit.

Only returned URLs on the company domain or configured additional domains can be retrieved. DNS results must be public, connections use validated addresses, and each redirect repeats URL/DNS validation and consumes another request. Credentials, private addresses and non-HTTPS URLs are rejected. Clearly unsupported file extensions, including PDF, office documents, images, archives and media, are skipped before any GET reservation. The round diagnostic records `unsupported_format` and `unsupported_source_format`, without treating the URL as consulted material or evidence. Redirects to these formats do not reserve another GET; the already requested redirect still consumes its request. Unknown/dynamic URLs retain the authoritative HTTP content-type check: only HTML, XHTML or plain text is parsed. No links are crawled and page JavaScript is not executed. Missing or conflicting material produces visible uncertainty.

Candidate `asOf` is the fact’s effective date explicitly supported by the cited content, or `null` for an undated claim. Page `retrievedAt` and captured `assessmentTime` are separate metadata and must not supply that date. Explicit future or expired fact dates remain stale under the captured source policy.

Prerequisites: inspect `EvidenceProvider`/`ResearchContext` in `src/mastra/providers/evidence.ts`, `Evidence` in `research/contracts.ts`, the provider map, and persistent reservations. Default research needs only `OPENAI_API_KEY`.

## Evidence provider contract

`EvidenceProvider` in `src/mastra/providers/evidence.ts` separates evidence acquisition from qualification policy. The interface supports website research, a local dataset or an external business database. A database-backed adapter can implement all three methods without an LLM or crawler; it must still supply provenance and establish factual support.

| Member                                          | Contract                                                                                                                                                                                                                                      |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                            | Stable provider identifier, registered through `createApplicationRuntime({ evidence: [...] })` and selected in `qualification.sources.providerIds`. Each returned evidence item must use this `providerId`.                                   |
| `search(branch, context)`                       | Returns `{ sourceUrls, evidence }`, with optional `preferredSourceUrls`. For stored records, return normalized `Evidence[]` directly with an empty URL list; no page retrieval is needed for that material.                                   |
| `extract(branch, evidence, context)`            | Returns `companyName`, `identityAmbiguous`, `candidates` and `intentCoverageComplete`. Map stored facts to candidates with exact citations to the supplied evidence. Preserve unknown attributes and distinguish estimates from observations. |
| `verify(branch, candidates, evidence, context)` | Returns `supportedCandidateIds` and `intentCoverageComplete`, with optional verifier diagnostics. Establish support for each candidate's value and passages; do not approve candidates just because their IDs or schema are valid.            |

`branch` distinguishes firmographics from buying signals. `ResearchContext` supplies the company domain, approved domains, immutable configuration and assessment time, run ID, shared deadline and reservation store. Its `round` contains the target attribute, missing attributes, previously supported facts and earlier evidence. Use that context to retrieve relevant records without changing policy or inferring an outcome from the company's identity.

For a local or external database, retain source references, original collection dates, bounded excerpts and content hashes in each `Evidence` record. A candidate names its supporting `evidenceId`, exact `quote`, attribute, value and supported effective date (`asOf`), with explicit inference rationale when applicable. Non-web source references require an exact entry in `sources.trustedReferences`; stored website passages still require an approved domain. Reading an old record does not make its evidence newly collected.

A curated database may verify that a proposed value and citation exactly match a previously reviewed fact for that company. This trusts the upstream curation; it is not a new independent semantic check. For unreviewed material, implement an appropriate verification step, which can delegate to `OpenAIEvidenceProvider`. Missing or conflicting decisive facts remain subject to the common review policy. A partial record does not establish that no buying inquiry exists; set intent coverage only when the source actually supports that conclusion.

Startup-loaded datasets are snapshots and need an explicit refresh. Per-lead database or API lookups must reserve shared allowance before each external attempt, respect deadlines and response limits, and settle only known usage. The existing evidence validation, scoring and output routing remain authoritative. An evidence provider does not write CRM stages or prescribe a qualification outcome.

## Inspect verifier decisions

The semantic verifier's `supportedCandidateIds` remains the sole model support authority. Exact quotes, approved provenance, configured labels and the existing deterministic policy still decide whether a candidate can become a fact. A fact outside the ICP can be fully supported and then disqualified by scoring.

The default verifier also requests nullable `diagnostics`: at most one decision per proposed candidate, with `candidateId`, `decision` (`supported` or `rejected`), a finite `reasonCode`, and unique `passageIndexes` from 0 to 3. Index 0 denotes the main quote, followed by inference additional passages. Supported reason codes are `supported_observation` and `supported_inference`; rejection codes distinguish quote, source, value, date, inference, uncertainty, restatement and insufficient-support categories. This is a concise model self-report. It does not prove the model's hidden internal cause, replace evidence, or authorize a fact.

New saved research rounds and final assessments expose `verifierDiagnostics`. Entries bind normalized candidate ID, branch, round, provider, authoritative support membership and reported decision to known source, excerpt and quote digests. They contain no raw reason, rationale, source URL or quotation. Private-source references are omitted and counted. Invalid shape, duplicate/unknown/missing candidate coverage, inconsistent decisions or nonexistent passage references produce `invalid` with a finite code; metadata cannot grant or revoke core semantic support. Core-invalid verifier responses still fail. Otherwise valid core responses can survive unavailable/malformed diagnostic metadata.

Availability is explicit: `missing` means a legacy/custom provider omitted diagnostics, `not_reported` means it returned null, and `reported` means the bounded metadata passed local validation. Historical persisted records may have no ledger at all; they are neither backfilled nor assigned invented decisions. Adapters may omit or return nullable diagnostics. The built-in strict JSON wire requires the nullable property. Each persisted entry is capped at 4096 characters; existing rejected-evidence public-literal diagnostics retain their separate 128-character, private-overlap and 4096-character protections. Both live inside the existing assessment/round JSON and follow the existing 30-day detail retention policy without a database migration.

## Add an approved domain

1. Establish which attributes the source substantiates. A directory with explicit dated workforce data can supplement a company site that omits headcount. Permission to retrieve is not a reliability guarantee.
2. Add the approved hostname, without scheme/path, to `qualificationConfig.sources.additionalDomains`. For a company directory, verify its actual provenance and access requirements before enabling it. Subdomains are included; lookalike suffixes are excluded.
3. Restart and submit a new event. Existing runs retain their captured source policy.
4. Check quotes, IDs, timestamps and digests in the read route. Conflicting decisive facts require review; source priority never silently resolves them.
5. Add controlled responses under `tests/` and run integration checks for attribution, conflicts, off-policy citations, timeout and shared exhaustion. Keep live checks separate.

## Add an evidence integration

An adapter implements `search`, `extract` and `verify`, then registers by ID in `evidenceProviders`. Search returns `{ sourceUrls, evidence }`: web discovery supplies URLs for shared page retrieval; an API/internal adapter can return normalized material directly. Direct evidence must pass the schema and digest check. Web references must match approved domains; non-web references must exactly match `sources.trustedReferences`. Evidence `providerId` must match its adapter.

Discovery may include `preferredSourceUrls`, an optional subset of `sourceUrls` enforced by the schema. The default provider marks exact URLs cited in the search response as preferred for the current target. Target relevance ranks first; citation preference breaks ties between equally relevant returned pages. Preferred URLs pass the same URL/domain checks and still require retrieved text, exact passages and semantic verification. They are discovery hints, never evidence. Target-specific ranking favors relevant corporate/workforce/contact and legal headquarters pages, including localized corporate paths, over support, customer material, individual vacancies and taxonomy archives. Legal/privacy/terms pages are demoted for employee count while remaining eligible headquarters sources. Headquarters discovery starts from a concise headquarters/registered-office query; incorporation or an arbitrary office alone still does not establish headquarters. Each search receives a natural company-domain and target query, with the captured year as freshness context rather than a required query literal. Provider domain filters enforce the approved search scope; queries do not repeat it with Boolean site restrictions. Captured configurable instructions, gaps, facts and prior sources guide refinement and appropriate language variants. Lower-only headcount can ground a separate heuristic working estimate and may seek complementary corporate workforce evidence. The estimate records assumptions and uncertainty; it does not turn the observed open bound into a factual ceiling or change freshness policy. Search-call and shared retrieval limits remain unchanged.

Each discovery result may contain at most 100 URLs and 20 evidence items; each extraction may contain at most 30 candidates. Up to ten configured providers can contribute to a branch without losing valid facts, conflicts or rejection diagnostics. An invalid or oversized adapter result records an explicit provider-contract failure and preserves successful adapters. The summary cites one representative source per rule and reports additional evidence references; the assessment retains every source and fact reference.

Stored evidence IDs bind the provider, adapter record ID, source identity and content digest. Adapters keep their current material IDs during extraction/verification; accepted main and additional citations are remapped together to stable stored IDs. Identical normalized source/quote pairs are deduplicated while preserving the main quote and distinct additional passages; normalized candidates are schema-validated before acceptance. Prior-round sources are supplied under those stored IDs. Reusing a record ID across adapters or changed content therefore cannot overwrite earlier provenance. Conflicting duplicate IDs within one current material set are rejected explicitly as evidence_id_conflict before candidate acceptance.

1. Select the source and any optional credentials. Do not introduce requirements for users retaining the default provider.
2. Normalize references, retrieval/publication times, bounded passages and failures. Distinguish API passages from retrieved pages. Never generate a quote and label it as source text.
3. Reserve allowance before each external attempt using `context.store.reserve`. A source lookup consumes the shared discovery/search allowance, page GETs consume page allowance, and model output reserves tokens. Respect the absolute deadline and retry helper; preserve unknown reservations and settle only known measurements.
4. Delegate extraction/support verification to `OpenAIEvidenceProvider` when appropriate, or implement the same structured contracts. Extraction agents receive no browse or write tools.
5. Pass adapters through `createApplicationRuntime({ evidence: [...] })`, enable their IDs in `sources.providerIds`, and configure exact trusted references. Workflow and scoring need no provider-specific branches.
6. Test provenance, missing/conflicting/unsupported facts, unauthorized references, timeout, redelivery and shared exhaustion with controlled fixtures. Verify default local use still requires no optional provider key.

This composition uses the shipped interface. `loadApprovedMaterial` is your bounded transport for the selected integration; it returns normalized `Evidence[]` and must enforce its response size/deadline without following arbitrary event URLs.

```ts
const model = new OpenAIEvidenceProvider();
const internal: EvidenceProvider = {
  id: 'internal-records',
  async search(branch, context) {
    const reservation = await context.store.reserve(context.runId, 'search', 128);
    const evidence = await loadApprovedMaterial(branch, context);
    await context.store.settle(reservation, { outputTokens: 0 });
    return { sourceUrls: [], evidence };
  },
  extract: (branch, evidence, context) => model.extract(branch, evidence, context),
  verify: (branch, candidates, evidence, context) => model.verify(branch, candidates, evidence, context),
};
```

The minimum output reservation is 128 tokens. This non-model lookup releases that allowance only after known completion with zero model output; interruption retains it conservatively. Different accounting semantics require an explicit contract extension and functional tests. New transports must not bypass shared budgets or multiply allowance by source count.

For another approved domain, change configuration only. Otherwise add one optional adapter with real bounded passages, source references, retrieval times, digests and normalized failures. Share search, GET, byte, token and absolute-time limits across sources/retries. Preserve DNS/redirect validation, exact attribution, semantic support, conflicts, deterministic scoring and production authentication. Keep fixtures/tests under tests/ and operational scripts under scripts/. Add functional attribution, unauthorized-source, conflict, timeout and exhaustion checks. ## Target missing qualification data

The captured `research.targeted` plan researches model/product evidence, workforce and headquarters, then repeats workforce if unresolved. Edit the ordered targets and query instructions for another ICP. Search receives the actual round target, current facts, unresolved attributes, sanitized consulted URLs and bounded earlier public source context; the year comes from captured assessmentTime. It seeks complementary evidence rather than repeating a generic query. Only actual returned approved URLs can be retrieved, at most one useful page per round. Earlier authorized material is reused for extraction and verification when discovery returns no new usable page.

Completed round checkpoints retain material, proposals, rejections and small diagnostics. Restart reuses them; interrupted unknown calls retain reservations. URL outcomes contain no query, fragment or credentials; gap codes distinguish unresolved/rejected/conflicting/stale evidence, lower-only counts, unavailable material and budget exhaustion. `no_count_observed` means extraction obtained no supported count from the inspected material, not that the company publishes no count anywhere. Logs omit excerpts, quotes and inference rationale.

Rejected candidates retain the deterministic checks and the existing verifier's supported-ID membership. New optional `rejections[].diagnostic` version 1 records at most four public-website passages, their stored evidence IDs, source/content/quote fingerprints, lengths and exact/whitespace/Unicode/typographic match indicators. These indicators explain mismatches; only the unchanged exact-substring check can accept a citation. The verifier supplies no explanatory rejection text, so none is inferred. No additional model call is made.

Each diagnostic is limited to 4096 characters. Public literal quotes and rationales may retain a prefix of at most 128 characters; nonliteral proposals and ungrounded rationales retain only fingerprints and lengths. Unknown, submitted and CRM citations omit this diagnostic entirely. Text overlapping words from private material is omitted conservatively, as is text containing credential markers, emails, URLs, control characters or long opaque strings. Source URLs are fingerprinted rather than copied. Omission codes distinguish nonpublic literals, private overlap and sensitive content. Treat retained public text as untrusted source material. Older assessments/checkpoints without the optional field remain readable; saved diagnostics survive restart without repeating research. These records do not change qualification, policy, source selection or research budgets.

Extraction and verification receive current versus previous evidence IDs, target, missing attributes and supported facts. They inspect current evidence first for the unresolved target, then compare previous material and supported facts. A supported lower-only workforce observation retains its open upper bound. A separate heuristic estimate can refine the scored interval under the accept policy; a new source-declared finite count can refine it without becoming an inference merely through normalization. Useful incidental support and genuine contradictions remain eligible. Accepted intervals crossing an ICP boundary remain eligible for follow-up. Rejected restatements cannot poison independent supported firmographics; disjoint ranges and other contradictory values still require review. Compatible employee ranges are intersected with all provenance retained; inferred narrowing remains labeled inferred. Buying-intent rejection/coverage safeguards remain strict. Lower-only employee observations retain max null.

A finite employee estimate needs actual cited workforce cues and a plausible rationale with explicit assumptions and uncertainty. Approximate numeric counts, lower-only staff statements and published team rosters can support heuristic working intervals. The source need not literally establish both bounds: an assumed maximum stays inferred and is never presented as a declared ceiling. Preserve known observed constraints. Cue-free guesses, customer/user/vacancy totals mistaken for staff and ranges chosen merely to fit the ICP remain unsupported. Submitted inquiry evidence is considered first; the default plan performs no public intent search.

The supplied company domain anchors identity. An extraction using only submitted inquiry material cannot introduce an identity conflict. Ambiguity supported by validated website material or explicitly trusted API/CRM research remains cumulative across providers and rounds, even when a later extraction reports no ambiguity.

Employee observations and estimates share the same sourced-candidate contract. A source-declared lower-only count keeps `max: null` and `inference: null` (or omitted); a finite inferred range requires an inference object and a numeric upper bound. The structured response schema encodes these alternatives before generation. Normalizing a stated count does not make it an inference. Estimating a finite range from a lower-only statement or a possibly incomplete roster does require inference, with assumptions about growth or unlisted staff and explicit uncertainty. The ICP thresholds never supply the estimated bounds. Interval ordering, distinct exact passages, independent support verification and the captured accept or review estimate policy still apply. Acceptance of estimates does not resolve missing, unsupported, conflicting, stale or boundary-crossing decisive facts.

### Factual verification and diagnostic disagreements

Verification receives business-model category definitions, candidates, cited evidence and captured round context. Qualification thresholds, accepted-category lists, score contributions and routing outcomes are omitted from the verification input; extraction retains its existing input. A supported employee count outside the ICP remains a fact, and deterministic scoring applies eligibility afterwards. The verifier prompt makes that boundary explicit. This isolation reduces irrelevant decision context; it does not establish that policy context caused any historical rejection or guarantee model accuracy.

New bounded verifier ledgers include `candidateInferred` and `modelReport` containing only allowlisted `decision` and `reasonCode` enums from a schema-valid, candidate-linked model report. `support_membership_mismatch` distinguishes disagreement with authoritative supported IDs; `inference_kind_mismatch` distinguishes a supported observation/inference reason incompatible with candidate provenance. Invalid metadata keeps null validated decision/reason and no passage linkage, while the bounded model report identifies the discrepancy. Arbitrary text, unknown candidate IDs and malformed/unlinked reports are not retained. Private-passage omission and existing retention remain in force; diagnostics never grant or revoke semantic support. Older ledgers and the legacy `decision_mismatch` code remain readable without migration or backfill.
